# Area Context: harness-package

## Responsibility

- Provide the `ty-context` CLI, Minimal Context/default Workflow assets, validators, migrations, source-sync checks and explicit Single-Goal Long-Task Workflow.
- Preserve durable project intent and repeatable verification at low recovery cost without adding lifecycle documents, duplicate authority or agent/process/Git orchestration.
- Own one-Contract V2 authoring, compiled Source/REQ/CTRL/OBL/NCOMP/AC coverage and the Live Evidence Kernel that prevents false completion for declared authority on one current Git-tree snapshot.

## User / System Contract

- `init` installs portable core/default workflow including explicit-only design-system/resource Skills. `ty-context enable long-task` installs the sole Long-Task Skill, templates, package-owned lifecycle Hooks and, only for a `.codex` harness root, one optional fixed Codex worker profile; disable removes only valid package-owned assets. The retired `source-plan-authoring` pointer is no longer installed, while legacy Source Plan documents remain ordinary Source.
- `delivery-contract.yaml` is the only Contract authoring file and is non-authoritative until formal Compile. Real marked Source is mandatory; compiled inventories and coverage are projections, not editable state.
- Read-only Preflight and Compile share activation safety, including one workspace path classifier also reused by verification. It checks `HEAD`-relative changes before first lock and immutable-baseline changes afterward, so forbidden or unclassified files cannot be silently absorbed by direct Compile. First enable protects only actual current package-asset files for configured managed destinations plus exact config/hook files, not managed directory roots or broad `.codex/**`. Only Compile creates Authority Lock; targeted verify never accepts; Final Gate, Stop and close recompile Source authority and rerun the complete Contract on one snapshot.
- Product Surface/Screen Contract workflow is prompt-level and project-owned through `context_surface_contract` and existing roles; the package must not add a surface-specific Context role. The managed Screen Contract template is optional/on-demand and owns durable per-screen/control semantics only when that depth is reusable.
- Material production UI uses UI Authority Closure plus a conditional Design Authority Check: affected stable surface/control/target keys reconcile screen/surface Context, `DESIGN.md`, one authored token source/generation direction and exact-target/constraint/inspiration references before implementation. Every affected adopted exact target/constraint must be opened through its Context-reachable immutable locator and editable upstream/update record; a registry mention alone is not consumption. An unconfigured starter or implementation-generated screenshot is not production design authority; no required design directory or visual workflow state is added.
- Role ownership is converged: `context_product_plan` owns product goals/scope/rules/flows/acceptance meaning; `context_surface_contract` alone owns durable information/action/feedback and main/drilldown surface responsibility; `context_uiux_design` alone owns Design Authority/tokens/rationale/adoption/UI Authority Closure/selected-design alignment; `context_development_engineer` is a narrow explicit architecture/engineering-design adapter rather than a generic implementation or agent trigger.
- Open Design is default. `design-system-authoring` adopts Design Authority; `design-resource-authoring` commissions resources and reconciles selection once. Its formal selected Web/App rules live in one on-demand reference that exploration never loads. Implementation handoffs freeze a canonical machine-readable entry, exact dependencies and digests. The Skill edits no Context/code/Contract; outputs remain Source.
- Selected implementation handoffs use one fail-closed residual `design-resource-handoff-v1`: typed locators atomically index every supported observable design fact, every resource has complete material/supporting closure, exact targets require per-condition full-target layout and pixel facts, and subject × target × condition × dimension applicability, gaps, semantics, blockers and downstream fact bindings stay explicit. Product Control granularity is not the design-fact ceiling; exploration stays lightweight.
- Selected-design authority is shared while proof level is not: Design Source Projection gives each target one canonical `DESIGN.md` or Screen owner while other layers keep pointers; the default route consumes affected targets and reports checked versus unchecked conditions, whereas Long-Task alone compiles exact Fact/method closure into Final Gate.
- `long-task-workflow` sends every input directly into one Source-bound Contract Draft loop. Inventory/synthesis/refinement/provenance/markers and Contract mapping converge there before Preflight/Compile; `source-plan-authoring` is retired from package management and no Source-authoring intermediate stage exists. Requests that require machine completion authority, recovery or auditability route to `long-task-workflow`; other work remains on the default Workflow Contract.
- Long-Task's Source-bound loop owns exact non-UI semantic completeness at a finer ceiling than a paragraph, Requirement, Product Control or broad state catalogue. It inventories subjects, relations, dynamic populations, applicable conditions and atomic properties across product/business rules and technical/backend/architecture semantics; closes every standard family and Inspector-discovered custom family; and conserves exact fact identities through Source, Contract obligations and current per-Fact proof. The default route instead performs model-led, risk-proportional understanding of every expressed material requirement, key condition and failure boundary, verifies the current candidate through project-native checks and reports unresolved or unverified scope. Exact values stay with authoritative Source/Context in both routes.
- The platform Goal owns mutable implementation sequencing, local planning and tool choice. After the first-lock checkpoint, the parent Goal performs an internal Delegation Suitability judgment and may delegate a bounded, independent slice only when the host can explicitly select the exact `long_task_implementation` custom agent and the benefit exceeds coordination cost; a generic/built-in/unknown/null agent type, task name, prompt imitation or model-only choice is not that profile. If exact selection is unavailable, or a spawned type is exposed and is not exact, the parent executes or redoes the packet itself without retrying another agent. Disjoint exact instances may run in parallel, while high-coupling or shared-owner work stays with the parent. The parent exclusively owns Source, Contract, Authority, architecture, Context writeback, integration, current-candidate checks, formal verification, Final Gate, close and native-Goal completion. Harness never allocates, retries, recovers or records delegation, manages models/AppServer, creates a scheduler/DAG/queue/registry, or performs branch/worktree fan-out, merges, pushes, PRs or deployment; delegated outputs are advisory rather than Progress, Evidence or proof and must converge into the selected verification workspace before verification counts.
- While an active binding exists, the package-owned `PreToolUse` Hook denies `spawn_agent`/`Agent` calls unless the official current-call selector is exactly `long_task_implementation`; inactive work is unrestricted. The Hook never rewrites input, infers identity from prompts/transcripts/models, retries, substitutes a generic child or persists capability/delegation state. Installation is not proof that the user trusted the current Hook: Codex/user owns `/hooks` review, Hook changes can require re-review, and Tiny Context neither bypasses, observes nor persists trust.
- First Authority Lock always creates a strict terminal-turn boundary. The Agent performs no product implementation, file edit, build or test after that Compile result, asks the user to handle any model change in the host, and instructs them to send `【继续】` or `[continue]`; an earlier textual model strategy does not skip the boundary. That continuation token resumes ordinary parent-Goal execution but cannot prove that a model change occurred because Harness cannot observe or verify host model state. Later Compile returns `required: false`; Harness stores no acknowledgement, model route or checkpoint state.
- Authority Revision separates authority change from user decision. Mechanically bounded repairs auto-adopt with evidence invalidation; a true semantic/proof boundary change exposes one self-contained deterministic brief before an exact decision. Exact current-task user instructions may be relayed, while blanket authorization cannot; the brief is a projection, not another authority or state.
- `long-task-workflow` is the only active long-task Skill. No alternate “normal” Long-Task Skill or retired Source Plan pointer is installed; absent explicit selection or a valid binding, work of any complexity stays on the default Workflow Contract. `delivery-set` and historical composite commands remain command tombstones only.
- Runtime floor is Node.js `>=24`; public package behavior is documented in English with aligned Chinese translation.

## Context Loading Contract

- This area root is default because it identifies package responsibility and routing.
- Detailed Context Model, Workflow Contract, package-managed-surface rules and verification paths are `on-demand`, selected by task triggers. Their authority is unchanged; only near-universal read cost is reduced.
- Default/core files, manifest candidates, triggers and bounded search form an expandable minimum read set. They never prohibit reading another Area, shared Context, `DESIGN.md`, selected resource or code when task dependencies require it, and the package does not replace this with a full-graph default.
- A monorepo may place Context only for Context-bearing implementation workspaces under `project_context/workspaces/<workspace-id>/**`. Each represented Context workspace maps exactly one code root using existing `[[areas]].root` and `context`, may contain several workspace-local Areas, and requires no new schema. Cross-workspace/repository Areas stay at top-level `project_context/areas/**`; code workspaces with no durable Context get no empty directory, while single-workspace/non-monorepo projects keep the existing layout. `read_policy`, triggers, directory placement and default selection are retrieval guidance rather than read or edit permissions.
- Prefer a small repository-common top-level default Area in monorepos; workspace-local Context remains on-demand unless genuinely near-universal.
- `ty-context doctor` reports the deterministic default Context footprint, exact duplicate default files and `DESIGN.md` authority status as advisory findings, with no new validation or workflow state. Required recovery facts outrank the byte heuristic; source tests exercise the warning but do not hard-gate an absolute total.

## Shared Engineering Quality Contract

- Package behavior changes keep implementation, managed source, package assets, Context, `PROJECT_SPEC.md`, public README and behavior tests aligned.
- Default UI guidance routes missing/conflicting durable UI meaning to its one Context/`DESIGN.md` owner or `context_uiux_design`, keeps local fixes/prototypes lightweight and, for a selected implementation handoff, opens every affected exact target/constraint, identifies declared conditions and blockers, routes them to real production owners and runs the strongest proportionate project checks. It reports unchecked or externally pending conditions and never claims Long-Task-grade exact design closure.
- External generation stays delegated and adoption routes to `context_uiux_design`. Figma, Penpot and OpenPencil are optional rather than default conversions. The residual adapter validates source closure/addressability/coverage; consumers own conformance.
- Every implementation delivery uses one thin Shared Engineering Quality Obligation. Before implementation, its risk-proportional `Architecture Deliberation` also records triggered quality attributes or a concrete preservation basis; during implementation, Goal-owned work preserves owners, real boundaries, failure semantics and the minimum justified abstraction; after project verification, one `Engineering Quality Conformance` includes the existing `Architecture Conformance`.
- Architecture depth is risk-triggered: material decisions resolve owner, unique source of truth, dependency direction, interface/state lifecycle, failure/recovery/compatibility, alternatives, future-change pressure, forbidden shortcuts and project-owned verification. Small work still names its owner/extension point, shortest verification path, unchanged quality attributes and no new/worsened debt.
- Exact product/technical values and conditions remain owned by authoritative Source/Context or selected design. Long-Task projects them into its existing Semantic Fact or selected-design closure; the default route does not reconstruct that exact account. The shared quality obligation owns design/implementation boundaries, applicable engineering risk and proof methods; it creates no quality matrix, duplicate Fact source, stage, Contract, Gate, state or Authority.
- Post-implementation Conformance has one owner per candidate snapshot: default Contract Conformance or Long-Task Final Gate. The Long-Task Gate proves only declared, falsifiable, project-check-bound invariants, not overall code quality. Candidate, declared check-input or authority changes stale the result; no duplicate closure is created.
- Reliability/resource-lifecycle, concurrency/consistency, performance/capacity/cost, security/privacy/safety, compatibility/migration/rollout and operability/observability/testability expand only when real Source/Context or code risk triggers them. A performance claim needs attributable workload, baseline/budget, environment and measurement; preservation-only work uses the cheapest existing evidence and makes no unsupported claim.
- Long-Task quality invariants use existing obligations/constraints/forbidden shortcuts, path/Binding ownership, executable Checks and independent Assertions when needed; no new aspect, Claim/risk type, quality authority layer or generic dependency engine is added.
- Default monorepo work separates retrieval from mutation: resolve task-local intended workspace(s) from explicit user/product/path/repository facts, clarify only genuinely ambiguous sibling targets, enumerate intentional multi-workspace targets and supporting/shared scope, and run a project-owned exact changed-path scope verifier when the repository exposes one. Without one, current-diff owner/scope review remains part of Contract/Architecture Conformance.
- Default non-UI handling identifies architecture owners and boundaries, API/schema/storage/event/job semantics, transaction/consistency/concurrency/idempotency, configuration/migration/compatibility, failure/degradation/recovery, security/privacy, performance/capacity/reliability and deployment/observability whenever material to the task, with depth proportional to risk and honest reporting where evidence is absent. Long-Task retains exact semantic closure. Equivalent low-level code choices that preserve authoritative meaning remain inside `F`; arbitrary implementation detail is not expanded into acceptance authority.
- A Claim that can pass on a proxy while failing in its target runtime uses a current-execution Check in the earliest owning Outcome. Existing input freshness supports optional coalesced feedback chosen by the Goal, while the one Final Gate reruns the live Check; no implementation gate, platform-impact fields, per-platform state or per-Outcome rebuild mandate is added.
- `F = Implementation Freedom Boundary` and `E = Structural Closure Cost Efficiency Boundary` are protected efficiency invariants adjacent to the causal mechanism, not additional acceptance responsibilities. `F` keeps development sequence, methods, local verification cadence and optional agent choice Goal-owned inside Source/Contract, architecture, security, forbidden-shortcut, irreversible-effect and external-action boundaries. `E` requires the complete fine-grained semantic/proof effect to be attained without cost growth from unrelated axes, mechanical ground expansion or copied shared metadata: equivalent-effect mechanism changes compare persistent bytes, DAG/Compile/Preflight/Final-Gate work, peak memory, default Context bytes and one-Fact revision blast radius before total-cost ROI. Neither creates a delivery Gate/Authority/state. Weakening either requires an explicit project-owner design-purpose decision and replacement proof; an `F` restriction also needs a distinct path a lighter/final check cannot cover, while an `E` regression needs a named workload, comparator/budget and independent necessitating semantic/proof/TCB/adapter benefit.
- Preflight diagnostics may improve repair localization through stable refs, safe repair hints and occurrence counts while remaining read-only.
- Modularity diagnostics are capability-aware: JS/TS retains lexical metrics, Python supports lexical per-function statements/branches and other included formats are line-only. Unsupported metrics are unavailable rather than zero; project-native analyzers remain primary, while thresholds, line risk and waiver/fail policy stay stable.

## Key Constraints

- No second Contract plan, editable Source Inventory/Coverage authority, SFC/Packet/Wave/Campaign runtime, Worker scheduler, worktree manager, model router or confirmation tracker.
- No Context read ACL, mandatory Area dependency closure, required directory for every package-manager workspace, full-Context default, `[[workspaces]]`/`workspace`/`owner_area`/`applies_to`/`requires` schema, automatic package-manager topology scan, forced migration, persisted default-workflow target state or universal monorepo/path/import/runtime scanner. Consumer-specific ownership/applicability and changed-path checks remain project facts and project verification.
- No fixed file-level execution plan or Frontier implementation gate in Contract Technical authority; stable owners, obligations, boundaries, paths, Bindings and proof remain explicit while implementation order and optional targeted-feedback cadence stay internal.
- No Harness-owned agent allocation, fixed count, Outcome-to-Agent mapping, delegation registry, retry policy, scheduler, queue or DAG. The parent Goal's post-checkpoint suitability judgment and optional use of one or more disjoint fixed-profile workers remain ephemeral, non-authoritative and converge into the single selected verification workspace.
- No targeted-verify acceptance, historical proof splicing, prose/exit-code acceptance, silent risk/scope downgrade or executing-Agent approval of protected authority reduction.
- No package operation deletes user-authored historical Source/Contract/Campaign data.
- Local affected-test inference may omit and report untracked `.work_products/**` scratch only; tracked or explicitly supplied paths remain verification inputs, and complete-suite discovery is never capped or pruned by feedback-tier budgets.
- Managed-asset changes require build, source sync, idempotence, `package check-source` and applicable package/consumer verification.

## Open Risks

- A complete declared Contract cannot prove omitted requirements were never omitted.
- A complete standard-plus-custom semantic-family closure reduces known omission paths but cannot prove an unexpressed human intention or the semantic soundness of an arbitrary external Oracle; such uncertainty remains `decision_required`, `unavailable` or External Confirmation rather than a passing default.
- Ordinary same-user state and Hooks are drift protection, not hostile-host security.
- Managed source, package assets, generated copies and public docs can drift without parity and behavior tests.
