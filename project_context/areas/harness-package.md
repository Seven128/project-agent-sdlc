# Area Context: harness-package

## Responsibility

- Provide the `ty-context` CLI, Minimal Context/default Workflow assets, validators, migrations, source sync and the explicitly enabled Single-Goal Long-Task Workflow.
- Preserve durable project intent and repeatable verification at low recovery cost without lifecycle document chains, duplicate authority, model/agent/process/Git orchestration or a third workflow route.
- Keep package behavior, managed sources, generated/installed copies, package assets, public guidance, Context, migrations and tests aligned through their existing owners.

## Core User / System Contract

- `init` installs portable Minimal Context/default Workflow plus explicitly triggered design-system/resource authoring Skills. `ty-context enable long-task` adds the sole Long-Task Skill and its package-owned optional host integration; disabling or upgrading changes only validated package-owned surfaces and preserves user collisions.
- Without an explicit selection or valid binding, work of any complexity follows the default Workflow Contract. Complexity changes engineering depth; machine completion authority, recovery or auditability selects Long-Task; Long-Task-internal risk selects proof strength.
- The default route understands expressed material requirements, conditions, owners and failure/recovery boundaries at risk-proportional depth, implements through the real owner, uses fresh project checks and reports checked/unverified/decision-required scope. It creates no complete Fact/Obligation ledger, exact-set proof, Authority, persistent state or machine result.
- Long-Task retains one Source-bound Contract Draft, one Contract Authority, one selected verification workspace, Goal-owned implementation and one source-recompiled current-snapshot Final Gate. It alone owns exact declared semantic/design Fact and proof closure, Authority freshness and machine acceptance.
- Context owns durable intended facts; task Source owns delivery-specific product/technical meaning; code owns current implementation; project tests/CI/runtime/human acceptance prove behavior.
- External design authoring creates ordinary Source only. The Product Surface/Screen Contract workflow is prompt-level and project-owned: durable surface responsibility remains with Product Surface/Screen Context, durable visual-system/adoption meaning with `DESIGN.md`, and implementation/proof with the selected workflow; it must not add a surface-specific Context role.
- `design-resource-authoring` may conditionally persist one versioned, task-local, ignored and non-authoritative recovery checkpoint when a real cross-interruption risk exists. It stores replay inputs rather than live status or acceptance, never enters Long-Task authority, and the simple preview path creates none. The full Base/Delta/decision-authority/writeback contract is on demand in [Design Resource Authoring](harness-package/contracts/design-resource-authoring.md).

## Context Loading Contract

- This Area is default because it identifies package responsibility, workflow selection and shortest owner routes.
- Detailed Context Model, Workflow Contract, package-managed surfaces, implementation index, verification and rationale remain `on-demand` and retain full authority.
- The core/default set, manifest candidates and one bounded high-signal search form an expandable minimum, never a read ACL or complete graph. Read any additional Area, shared dependency, `DESIGN.md`, Source or code needed to understand the task.
- Read scope does not grant modification scope. Resolve intended workspaces from explicit user/product/path/repository facts; when materially different sibling targets remain ambiguous, clarify before product edits. Intentional cross-workspace targets and supporting/shared scope stay explicit.
- In a monorepo, only Context-bearing code workspaces need a sparse `project_context/workspaces/<workspace-id>/**` mirror through existing Area fields. Cross-workspace facts remain top-level; unrepresented code workspaces need no empty directory.
- `ty-context doctor` reports default file/byte footprint and Design Authority status as advisory maintenance information. Required recovery facts outrank the soft byte heuristic.
- The current admitted static/process exact observer remains Level 3. This repository does not self-promote it through implementation or prose; Level 4 continues to require the unchanged complete total-cost ROI evidence, an independent capability audit with no open critical counterexample and a separate explicit project-owner promotion decision. Real-process collection owns only raw/observed facts; its existing verifier is the sole formal ROI conclusion owner.

## Shared Engineering Quality Contract

- Before the first implementation edit, every delivery surfaces one repository-bound, risk-proportional Architecture Deliberation with affected owners/source of truth, dependency/lifecycle boundaries, alternatives, future-change pressure, debt disposition, forbidden shortcuts, project checks and applicable quality risks.
- Correctness/invariants and maintainability/changeability always receive preservation; reliability, concurrency, performance, security, compatibility and operability/testability expand only when material.
- Implementation remains Goal-owned. Reuse the real service/facade/adapter, keep one source of truth, preserve explicit failure/resource semantics and add abstraction only for a stable evidenced change axis.
- After project verification, default Contract Conformance or Long-Task Final Gate—never both—owns the one current-candidate Engineering Quality Conformance including Architecture Conformance. Neither claims overall code quality.
- Durable mechanism changes update their one owning Context before code. Local repairs remain task-local unless they reveal a missing durable fact.

## Anti-Degradation And Efficiency Boundary

- Minimal Context and default Workflow changes preserve effect and their high-quality design-purpose floor before cost is compared. A current gap is fixed, not frozen as the legal baseline.
- A new default rule, validator, test or benchmark must identify an independent real failure path, prove existing owners do not already close it, prefer the lightest owner-local mechanism and have positive total ROI without adding state, Authority, Gate or fixed cost unrelated to the triggering risk.
- Risk-triggered Build/Reuse/Buy judgment evaluates an allowed solution set, prohibited failure modes and required rationale/evidence. It preserves reasonable standard-library, installed-dependency, external-library, small-self-implementation and intentional-non-abstraction choices while rejecting duplicated owner-held rules, extension-point bypass, unjustified dependencies and second sources of truth.
- Default Context keeps only near-universal responsibility, boundaries and routes. Low-frequency host adapters, exact proof machinery, migrations and history remain in existing on-demand Context/code/tests.
- Static wording/parity tests prove distribution and known structure only. Real Agent recall, target choice and ROI claims require the existing frozen fresh-Agent paired benchmark and normalized traces.
- Long-Task changes preserve coverage, false-negative resistance, must-allow behavior, semantic granularity, proof/TCB strength, non-bypassable Authority, fail-closed current-snapshot proof and implementation freedom before structural or total cost is compared. Only evidenced high-ROI/high-efficiency changes are considered, and the current observer remains Level 3 without self-promotion; Level 4 still requires complete total-cost ROI evidence, independent audit and an explicit project-owner decision. Exact accounting, evidence, version, platform and precollection rules stay on demand in the [Long-Task rationale](harness-package/decision-rationale/long-task-workflow.md) and [Delivery Benchmark](delivery-benchmark.md).
- The current rolling carrier is packet-first positive-default: at least two independently safe, positive-benefit, bounded and parent-integratable packets disjoint by owner/path/source of truth require actual attempts to create multiple exact `long_task_implementation` workers unless explicit user/host policy forbids agents. Profile and capacity outcomes come from those host calls rather than parent inference; the Workflow Contract owns six exact solo reasons and partial delegation, while the Skill owns packet and shared-worktree execution. Count and decomposition remain parent-owned; no allocator, scheduler, queue, DAG, registry, persistent state or delegation proof is added, and no measured host adoption, effective model/tier/capacity or runtime-performance result is claimed.
- Long-Task mechanism development stops and refreshes Architecture Deliberation when unplanned owners/control surfaces, cross-PR scope, proof/test growth larger than the core change, order-of-magnitude diff growth, duplicate truth or ROI-governance cost drift appears. Work is classified `keep | shrink | defer | remove` and returned to the original goal before continuing; existing structural-closure cost, Context-footprint, suite-policy, source-mapping and real-diff owners are reused instead of creating another ROI system. This is not a Gate, artifact or state.
- After purpose validity, relative non-degradation, must-allow behavior, structural-cost limits and the applicable measured total-cost threshold are satisfied, the sufficiency rule stops further construction unless a new real counterexample, repeated material cost hot spot or evidence of significant additional net benefit appears. Machine-recomputed `observed_lifecycle_*` facts may guide that review but never supply governance admission or Level 4 promotion.

Full Context and default-workflow admission logic lives in [Minimal Context rationale](harness-package/decision-rationale/minimal-context.md) and [Workflow Contract](harness-package/contracts/workflow-contract.md). Long-Task admission lives in [Long-Task rationale](harness-package/decision-rationale/long-task-workflow.md).

## Package And Migration Boundary

- Canonical managed sources live in `.codex/ty-context-managed/**`; package assets are generated under `packages/ty-context/assets/**` through `packages/ty-context/source-mappings.yaml`; installed/generated copies are not independent owners.
- Public behavior is English-complete, with Chinese as aligned additive guidance.
- Ordinary `sync` refreshes declared managed assets and does not run semantic migration. `upgrade` owns versioned, deterministic, exact-ownership-aware cleanup and reports modified/user-owned collisions as manual.
- Retired compatibility semantics remain only in isolated migration/tombstone/history/release surfaces and their tests. They do not participate in active triggers, default Context, current Skill routing or recommended usage.
- Managed changes require build, source sync twice with an idempotent second pass, workspace installed/generated sync where applicable, `package check-source` and relevant package/consumer verification.

## Hard Constraints

- No second Contract plan, editable Source inventory authority, workflow stage artifact chain, scheduler, model router, worker registry, worktree manager, confirmation tracker or cached test-result completion authority.
- No Context read ACL, full-graph default, required Context directory for every code workspace, new workspace/applicability schema, automatic topology scanner or universal path/import/runtime analyzer.
- No Harness-prescribed implementation sequence, fixed phase/method permission Gate, per-edit verification mandate or agent allocation state.
- No targeted/historical verification acceptance, silent risk/scope downgrade, user-file deletion or executing-Agent approval of protected Authority reduction.
- No change to Long-Task Schema, Authority, Revision, Evidence Kernel, Final Gate, Stop/close, accepted terminal theorem or native-Goal separation without a separate explicit project-owner decision and replacement proof.
- No broad `input_paths` role scan, quote-stripping or slash-rewriting argv heuristic, shell/URI/generic argv dependency parser, file-extension dependency guess, output-flag allowlist, authored Global-Binding namespace change, second Binding registry, packet self-attestation or machine-authored high-ROI/Level-4 verdict.

## Open Risks

- Bounded search can miss synonyms or indirect dependencies, and prompt guidance cannot force correct Agent application.
- A complete declared Contract cannot discover omitted human intent or prove an arbitrary external Oracle semantically sound.
- Same-user files, Git metadata and installed host integrations are trusted compatibility boundaries, not hostile-host isolation.
- Managed, generated, package, public and Context surfaces can drift without current parity and behavior tests.
