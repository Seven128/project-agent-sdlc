# Long-Task Workflow Design Rationale

## Decision

Single-Goal Long-Task Workflow exists to prevent false completion inside one complete declared delivery authority. It uses one native Goal, one selected verification workspace, one continuously authored Contract, semantic Outcome boundaries, optional repair-only targeted verification and one current-snapshot Final Gate. It does not own agent, process, model or Git orchestration; a fixed optional Codex worker profile and its boundary Hook are host affordances, not a control plane.

Source-quality rules and Contract Draft authoring form one Source-bound authoring loop, followed by Preflight repair, formal Compile, one terminal-turn host checkpoint, rolling implementation, verification and Final Gate in one `long-task-workflow` lifecycle. Pre-existing planning or proposal documents remain ordinary Source; no standalone authoring compatibility route participates in the lifecycle.

The shared Architecture Deliberation and applicable-quality assessment occur during Source/Contract authoring before formal Compile and implementation. Long-Task Final Gate is the sole post-implementation Engineering Quality/Architecture Conformance carrier; no default-workflow closure is nested around it.

## Workflow Selection And Assurance Boundary

Long-Task is an explicitly selected machine-trusted delivery-assurance mode, not the route for a task-size class. The stable selection rule is:

> Complexity determines execution and verification depth; required completion authority and recovery determine the workflow route; Long-Task internal risk determines proof strength.

The default Workflow remains eligible for local changes, cross-module features, large refactors and long-running implementation when model-led execution, project-native checks and an evidence-bounded human-review handoff are sufficient. Conversely, a small calculation, permission or billing rule may justify Long-Task when every declared condition must become a stable, independently failing, independently rerunnable and auditable obligation. Duration, complexity and file count neither activate Long-Task nor make a task ineligible; only explicit selection or a valid existing binding enters it.

The selection benefit is verifier-owned completion authority, cross-compaction/session semantic recovery and auditable requirement-to-proof traceability. “Minimal human intervention” means reducing routine progress supervision and item-by-item checking, not eliminating user or external authority: reserved product choices, conflicting or missing Source, preference-sensitive selection, high-risk irreversible actions and External Confirmations can still require a person. “Higher quality” means stronger implementation-conformance assurance for declared and observable product, technical, architecture and selected-design obligations; it does not prove undeclared requirements, global product excellence, optimal architecture, Oracle truth or model success. “Efficiency” means evidenced high efficiency and high total-cost ROI while this complete machine closure is required; Long-Task is not presumed faster or cheaper than the default route, and no global/local optimum claim is required.

This route correction removes the former L0 eligibility barrier only. Once Long-Task is selected, the existing `risk.requested_level: auto | standard | strict`, computed proof floor, Source/Contract/Authority lifecycle, exact Fact/obligation closure, Evidence Kernel, repair loop and sole Final Gate remain the owners. `standard` is the standard internal proof profile; `strict` remains the compiler-enforced floor for affected high-risk Outcomes. Route orthogonality itself creates no Schema, compiler or runtime change; the complete-delivery closure amendment below is a separately authorized mechanism change.

## Controlling Objective

The irreducible input boundary is that authoritative Source is complete, accurate and fine-grained enough to state every intended requirement and AC; the workflow cannot discover an intention the user never expressed. Source authoring must nevertheless expose and close all material implications already present in requirements, controlling Context, repository contracts and declared inputs rather than treating the user's paragraph structure as the semantic ceiling. For non-UI scope it derives an Expected Semantic Fact Universe across product/business meaning and technical/backend/architecture meaning at `subject or relation × atomic applicability × atomic property`. For a formal selected Web/App handoff, authoring separately derives the complete scoped design Expected Fact Universe before generation from requirements, product semantics, design system and target environments. A frozen Inspector then enumerates the acquired canonical source and proves exact manifest/handoff equality for every `subject × target × condition × variation × property` Fact Cell and required proof. Unsupported or unreadable Facts block, and named Inspectors/Oracles remain explicit TCB. Once expressed or necessarily derived, Source mapping, universe closure, executable Oracle sensitivity, freshness and Final Gate completeness are obligations rather than assumed trust.

The design-purpose guarantee is **complete-delivery accepted-terminal-state safety**, not a termination guarantee. Define `AcceptedDeliveryTerminal(snapshot)` as a fresh Final Gate result of either `machine_accepted` or `delivery_accepted`: `machine_accepted` requires every blocking obligation to be closed by package-admitted machine Actual on the current snapshot; `delivery_accepted` requires the same current machine closure plus a fresh, valid and exact per-obligation external fulfillment set for every blocking externally owned predicate. Given complete and accurate authoritative Source at the declared observable granularity, a meaning-preserving Source-to-Contract-to-observer projection and non-bypassable Authority/freshness:

`AcceptedDeliveryTerminal(current snapshot) => DeclaredObservableDrift = empty`

`machine_accepted_external_pending` is compatibility-read-only and deliberately outside that antecedent. It proves only `MachineVerifiableDeclaredDrift = empty` inside historical `declared_machine_authority`; the unresolved externally observed predicate remains unproved. New Final Gates emit `blocked_external` while blocking fulfillment is pending and use advisory warnings for non-blocking confirmations. Harness still has `native_goal_effect: none`; it clears Active Authority only for `machine_accepted` or `delivery_accepted`, and the host remains responsible for native Goal completion. “Deliver drift-free” therefore means that every artifact which reaches the complete accepted delivery state is drift-free inside the full declared and observable scope. If implementation, machine proof or required external observation never closes, the workflow remains unfinished or explicitly qualified; it does not claim that every Goal must eventually reach acceptance.

## Complete-Delivery Closure Amendment

The project owner explicitly authorizes this amendment to the previously protected terminal theorem and External Confirmation boundary. The old implication admitted only fresh `machine_accepted` with no pending confirmation. The replacement admits two disjoint complete terminals without weakening the machine path: `machine_accepted` still requires an all-machine blocking-obligation universe, while `delivery_accepted` additionally admits only Contract-declared external authority whose exact Fact/Claim obligation rows, Expected authority, applicability, method/capabilities, target/environment, relevant production inputs, candidate and evidence are current and complete. `blocked_external`, `needs_work` and historical `machine_accepted_external_pending` remain non-terminal. No aggregate approval can replace per-obligation equality.

The replacement proof preserves the old machine coverage and granularity and adds previously absent protection before external fulfillment can affect acceptance:

1. The existing marked Source inventory remains the sole Source owner. A deterministic Material Fragment and high-signal Semantic Anchor projection is recorded through the existing Semantic Fact manifest Census, not another inventory. Every paragraph, list item, table row, Given/When/Then step, fenced code block and structured configuration line has exactly one Fact-bearing, supporting-basis, superseded, decision-required or scope-excluded disposition. Supporting basis is a closed non-normative relation, never a lexical-similarity judgment: only one package-known carrier or an explicit typed same-semantic-cell relation may suppress a new Fact, and uncertainty stays fact-bearing/decision-required. Exclusion authority must come from an independent exact same-domain scope decision, never any excluded Source itself; design scope cannot remove product/technical meaning. Delivery-semantic Facts remain distinct from source-integrity Facts, and digest/presence cannot close behavioral meaning.
2. The existing Fact/Claim/proof model owns proof adequacy. Observation scope, required method, evidence capabilities, proof surface, Claim kind and applicability impose minimum causal strength; Control existence, state change and downstream product-result change are independently provable. A custom property is objective-machine-capable only through an explicit profile made entirely from the closed standard method catalog and its resulting capability floors; `standard: false` is never a Judgment profile. Exact Source-owned typed delegation may instead make that same supported custom Fact subjective, while a custom method remains non-Machine and non-Judgment and can only use an admitted external Actual comparator or stay unreachable. The same model formally binds Global Facts and expands Global Claim × Global applicability/target × every exactly compatible Outcome-local applicability × Fact × method rather than borrowing the first Outcome's or merely same-target Fact. Exact compatibility is target, journey role, canonical dimension assignment, Given-key set and ordered When equality; required and covered `(outcome, local applicability)` pairs and each Fact's methods are set-equal. A Check without Claim-bearing Assertions is diagnostic and contributes no semantic completion. Claim-bearing Expected values resolve only from Source/Context/canonical-resource or bound Fact authority.
3. `target_profile.completion_authority` is `machine_only` or `declared_authorities`; omitted legacy input reads as fail-safe `machine_only` and receives an authoring migration diagnostic. Preflight derives all candidates across matching proof surfaces before selecting an authority. Required surfaces stay exact; without one, a unique Machine route owns completion while only semantically equivalent External evidence may remain advisory, a unique External-only route may fulfill, and non-equivalent multi-surface candidates are ambiguous. Equivalence is a canonical projection of the existing compiled observation authority: Claim/local Claim, canonical applicability, target, polarity, Expected owner/value digest, Actual projection, method/capabilities and comparator mode/parameters/tolerance/mask must match while proof surface and route locators remain distinct. An External declaration without a unique exact compiled Expected/projection/comparator is never advisory. Reachability records the resulting effective role per exact External obligation and binds it into the existing compiled/acceptance Authority identity; External prepare/submit/status/evaluation and Final Gate consume that one projection rather than raw `blocks_target`. A declared-only actor remains a legal non-completing advisory when Machine owns completion; malformed Judgment, target/scenario mismatch or unrelated/duplicate/mixed declaration cannot borrow another confirmation's advisory identity. Missing, invalid, stale or fulfilled advisory evidence remains audit-visible with no acceptance effect, while any blocking row in a mixed Confirmation still blocks. A mixed signed record must include all effective blocking results but may omit advisory results; after shared signed-envelope integrity and freshness checks, blocking and advisory comparisons produce separate states so an invalid advisory Actual cannot turn fulfilled blockers into failure. Effective ordinary Claim, Semantic Fact and Design Fact identities remain separate projections of their existing owners. `unreachable` blocks Authority Lock before implementation. External Judgment is reachable only for one full Source-owned Claim with identical applicability and an explicit subjective-preference, expert-assessment or authorization delegation. An objective ordinary Claim may use External Actual only through one exact deterministic same-Claim/applicability/surface Assertion after its package observation channel is unavailable; the compiled expected value, projection and comparator are digest-bound, surfaced by prepare and recomputed by submit/Final Gate. Existing Machine success remains Machine authority. Counterfactual preparation executes only the non-External observation projection while retaining the original External route for Reachability and final evaluation.
4. `long-task-external-confirmation-record-v1` stores external Actual/judgment and evidence under the existing Long-Task runtime state boundary. Source/Contract owns Expected, method, applicability and external owner; the actor owns only Actual or an authorized judgment; Harness validates strict shape, declared identity match, hashes, freshness, exact result-set equality and objective comparison where available; the sole Final Gate owns status. Local records prove declared identity and integrity, not cryptographic or real-world actor authentication. Relevant-input identity permits local preservation only when existing Bindings/input envelopes prove independence; otherwise the whole record invalidates.
5. `long-task-final-receipt-v3` makes obligation closure primary, retains per-Check detail for diagnostics and is non-reusable audit output. Final Gate source-recompiles Authority, reruns every machine Check on one snapshot and revalidates current external records. V2 receipts remain compatibility-readable audit history but cannot regain acceptance or close Active Authority. `external prepare|submit|status|revoke` never decides acceptance independently.
6. Existing Findings gain Source fragment, Fact/proof, Expected/Actual, owner, invalidation and rerun context. A Repair Frontier is a current derived view only; it may recommend the smallest reliable targeted feedback set but never persists scheduling or acceptance and never replaces the complete Final Gate rerun.

This change keeps one Contract, Fact manifest, Authority/Revision chain, workflow state, Evidence Kernel and Final Gate. It deliberately defers a generic Browser/Native/Device observer SDK: the admitted machine Actual set remains exact frozen static JSON and Harness-direct process JSON; unsupported browser/native/layout/pixel/accessibility/motion, protected, tolerance/mask and physical predicates use exact blocking external obligations. A future adapter must pass the existing mechanism-admission theorem and extend only the closed Actual set without gaining Expected, comparison or terminal ownership.

Compatibility is explicit rather than silent. Contract V2 remains the carrier with additive fields; missing completion authority defaults to `machine_only`. Legacy external declarations or manifests that lack exact fragment/proof/fulfillment metadata remain readable for diagnosis but are not reachable for a new complete terminal until authoring repair. Receipt V2 and `machine_accepted_external_pending` remain readable historical forms only. Package upgrade may perform deterministic shape migrations but never invent Source meaning, Fact lineage, external Actual, actor authority or evidence.

Structural cost remains bounded by deterministic linear Source scanning, existing Census/Fact/proof indexes, exact set comparison and compatible Session grouping. No generic NLP, open observer registry, confirmation tracker, cached-acceptance path, second Gate, persistent repair queue or provider-specific core branch is admitted. The must-block/must-allow and cross-domain regression population, current-candidate full verification, complete anti-degradation theorem and applicable total-cost measurement remain the replacement-proof evidence owners; a static implementation alone does not establish Level 4 or positive ROI.

The closing amendment strengthens that construction at its remaining loss/race boundaries. Material meaning now starts from all strict-UTF-8 material manifest inputs and proves exact Fragment disposition, typed non-normative support, independent scope decisions, bidirectional Fragment/Fact provenance, exact semantic-cell supersession and Claim-polarity conservation. Proof strength is derived only from closed typed method/scope/quantifier/Claim/Control/property profiles, including formal Global Fact bindings; prose keywords remain advisory. Reachability retains all cross-surface candidates before one exact authority decision, and Judgment cannot replace an objective Actual. Blocking external fulfillment is authenticated only by detached Ed25519 over a current-challenge, whole-candidate, artifact-snapshot-bound canonical V2 record; V1 and declared-only rows cannot fulfill. Final Gate binds a live protected-input digest into `FinalizationIdentityV1` at every commit point and atomically publishes accepted Receipt plus optional Authority cleanup under the existing Active Authority lock. These changes enforce Material Meaning Conservation, Exact Obligation Authority, Authenticated External Fulfillment and Atomic Terminal Finalization without adding a Source inventory, Fact taxonomy, Contract, Authority, Gate, lifecycle or provider/authentication registry.

The objective-Claim bridge deliberately reuses the compiled Assertion and exact comparison owners instead of removing ordinary Assertions, trusting an externally submitted pass/verdict, or creating a new comparator channel. Likewise, advisory suppression applies only to complete exact equivalent routes rather than to an entire mixed Confirmation; mixed-record evaluation requires all blocking rows, admits an advisory subset and keeps the two result states separate; and Counterfactual execution subtracts External observation authorities instead of teaching the Machine observer to consume external evidence. These choices preserve one Expected owner, one Reachability decision and one final evaluator.

Build/Reuse/Buy is closed to the existing owners and mature Node primitives: reuse strict UTF-8/path/no-follow/canonical-JSON/hash/atomic-write/Active-Authority-lock infrastructure and Node's Ed25519 verification; add only bounded owner modules where the current seams would otherwise mix scanning, authority resolution, attestation/challenge or terminal CAS. Handwritten cryptography, Agent-readable private keys, a generic auth/observer SDK, mutable evidence references, blocking cross-candidate carry-forward and any second completion state are prohibited. Linear scans, indexed exact-set checks and content-addressed deduplication preserve the existing cost boundary; the existing ten-category real-process ROI owner remains authoritative and missing current evidence stays unsupported.

The enabling key logic is that drift can be judged only where authoritative meaning is precise, applicable and observable. Text authoring therefore cannot stop at prose paragraphs, Requirements, Product Controls, broad states or “all cases” labels. For non-UI scope it first enumerates subjects, relations and dynamic populations; closes standard and discovered custom semantic families; expands meaningful atomic condition cells; and preserves typed value semantics, provenance, disposition and proof. This includes product/business rules as well as backend and architecture contracts: APIs/data/schema, state/time, events/jobs, transactions/consistency/concurrency/idempotency, failure/recovery, configuration/migration/compatibility, performance/reliability, security/privacy, integration/deployment and observability. A Product Control is a semantic interaction unit, not either the minimum non-UI fact or the minimum UI/UX observation unit. Selected resources close visual/behavioral meaning at `subject × target × condition × variation × atomic property`, including component instances/Anatomy Parts/relations, dynamic populations, exact condition/variation axes, geometry/style/content/state/interaction properties and all property-required methods. Eight design dimensions and non-UI family names are roll-ups. Acceptance retains both `atomic Fact × required method` and `atomic Claim × applicability × proof surface`; exact expected/current sets prevent subject, relation, condition, property, comparison authority or verdict from collapsing.

The implementation logic has two jointly necessary parts. First, Source/design-resource authoring and Architecture Deliberation preserve enough product/business, technical/backend/architecture, Control/relation, applicability, engineering-quality and prederived selected-design meaning to define drift without current code inventing the reference; exact values remain with their unique authoritative Source/Context or canonical resource. Second, Source/Contract continuity, subject/relation Census and exact universe expansion, Claim-specific observers, per-Fact expected/current evidence, frozen verifier dependencies, Authority Lock/Revision and one-snapshot Final Gate fail closed on every unproved unit and revalidate the candidate; declared Engineering Quality/Architecture Conformance shares that Gate. The first part defines comparison authority but cannot enforce delivery; the second cannot recover omitted intent, a missing custom semantic family or Facts an unsupported Inspector/Oracle cannot observe.

Semantic Granularity, Semantic Fidelity and Delegated-Choice Validity are refinements of the existing enabling logic, boundary and first responsibility. Granularity keeps meaning independently decidable under `K`, exposes coarse/unobservable cases under `B` and constrains `R1` to conserve the relevant units. Fidelity keeps recovered meaning accurate/applicable under `K`, exposes lossy Source/transformation/Oracle limits under `B` and prevents `R1` from substituting summaries or IDs for semantics. Delegated-Choice Validity keeps comparison authority legitimate under `K`, treats absent or insufficient delegation as an unresolved `B` boundary and requires `R1` to separate meaning origin, decision authority and resource evidence. None is a replacement responsibility or new theorem premise. `R2` and `AcceptedDeliveryTerminal(current snapshot) => DeclaredObservableDrift = empty` remain unchanged.

DRA Proposal → resource → revision history is upstream Source-quality work. Long-Task observes only the final Proposal, selected immutable resources, formal handoff and bindings that actually enter its Authority plus current implementation/Evidence; its Final Gate cannot prove Provider history, and DRA checkpoints/audits/reconciliation are never completion evidence.

That last condition is not an informal escape hatch. The Harness must compile a **Semantic Assurance Closure** inside the existing Contract/Authority/Final-Gate carrier:

1. Background may contain only text-free Markdown anchors/separators or fixed-field provenance syntax; text-bearing headings, free-form provenance and arbitrary prose cannot be hidden from Material Source classification.
2. Applicability is represented as atomic dimension/value cells. A profile cannot bundle mutually exclusive values, and every Claim is proved on every target/journey/cell it declares without representative or pairwise substitution. Selected-design conditions are themselves atomic cells rather than arrays of modes, states, content cases or input methods.
3. Every behavioral Claim-bearing Assertion has a Claim-relevant narrow semantic mutation plus a claimless target-liveness witness. Whole-file replacement may prove carrier loss but cannot by itself attest which sibling semantic value the observer reads.
4. Every property-required selected-design method emits method-specific evidence for every target/condition cell. Each cell freezes exact `fact_refs` and `fact_expectations`, record/observation paths, expected located digest, comparator/tolerance/mask, Oracle/environment and sensitivity. Runtime `fact_results` are set-equal and individually attributable; every verdict passes, protected raw values are not persisted, and observation identities remain distinct. Integrity/render evidence or aggregate pass cannot stand in for missing Facts or semantic methods.
5. Required runtime capabilities are explicit on the exact execution target and on every design-acceptance blocker. A blocker may close as a machine Claim only when its exact target declares every Source-required capability and the Claim is proved on that target; otherwise it remains a target-blocking External Confirmation. A browser specimen, simulator or detached route cannot substitute for a required physical device, sensor, haptic, assistive-technology or production-root capability.
6. Authority freezes the runner, declared verification inputs and the supported direct-literal local verifier graph: static imports/re-exports, literal dynamic imports, `require`/`require.resolve`/`module.require`, and literal `new URL(..., import.meta.url)` files recurse under the repository. Files explicitly owned by Check `input_paths`, `expected_output_paths` or `artifact_globs` remain candidate/runtime material rather than Oracle identity and are covered by final-snapshot execution/integrity. Non-literal loaders and `createRequire` fail closed; indirect runtime file/process access must be declared in `verification_inputs` or remain part of the named project Oracle TCB. Bare package/runtime/device dependencies that cannot be byte-frozen are likewise named TCB, never silently treated as Harness proof.
7. Long-Task Authority freezes the complete `project_context/**` graph. Population proof either closes a declared machine-enumerable universe or remains target-blocking external confirmation; a runner-created eligible list cannot prove that it enumerated the real universe.
8. Material Architecture Deliberation conclusions continue to use Source-backed Technical Obligations, Constraints/Forbidden Shortcuts, owners/paths/Bindings and executable Claims in the same Contract. At least one architecture-classified Source obligation and current-snapshot proof is required, without adding an architecture field, second Gate or state.
9. Material non-UI scope has one exact conservation chain: `Expected Semantic Fact Universe = Source Indexed Facts = Contract Fact Obligations`, and `required proof obligations = current attributable Fact results`. A result carries `fact_ref`, actual observation, comparison policy and parameters/tolerance where applicable, pass/fail verdict, Oracle identity and environment. Broad assertions or shared executions may reduce runtime cost but cannot collapse Fact identity or result attribution.
10. Applicability closure is standard-plus-custom and census-driven, not a fixed blind Cartesian product. Every standard family receives a grounded applicable/not-applicable/decision-required/unavailable disposition, every discovered domain-specific family remains first-class, relation and dynamic-population members are enumerated or externally blocked, and aggregate strings cannot impersonate member sets.

Natural-language completeness and physical-world truth are irreducible boundaries: no generic Harness can derive an intention the user omitted or mathematically prove that an arbitrary external sensor/oracle denotes the intended real-world predicate. It can and must, however, inventory the declared subject/relation scope, ask every standard semantic-family applicability question, preserve custom families, derive necessary consequences and expose unresolved choices instead of silently omitting them. The workflow therefore admits a complete no-drift terminal claim only when those facts are represented by authoritative Source plus the frozen observer binding above and no declared External Confirmation remains. An explicit External Confirmation preserves the unresolved fact and blocks or qualifies complete delivery; it never supplies machine proof. Merely declaring an oracle “sound”, emitting a passing Boolean, hashing an artifact, reusing current code as its own expected value or labeling a block “background” never satisfies the closure.

Mechanism changes use the Anti-Degradation Assurance two-stage hard gate. First prove `Coverage_new ⊇ Coverage_old`, `FalseNegative_new ⊆ FalseNegative_old`, and preserve non-bypassable Authority, fail-closed behavior and complete final-snapshot execution. Only then compare Authoring, Runtime, State, Recovery, maintenance and migration cost. Cost reduction never compensates for reduced drift detection; this semantic-assurance repair is admitted because it restores the controlling objective before cost optimization is considered.

For selected design resources, one explicit purpose is full implementation/acceptance/test conformance to every material scoped UI/UX Fact. This neither infers unexpressed meaning nor proves the user supplied every requirement. Open Design is the default generator, but formal Web/App authoring derives the Expected Universe before generation, binds the adopted design system, commissions/retrieves canonical source plus manifest, freezes Inspector Census and requires exact universe equality without sampling/truncation. Canonical source owns exact values; the residual handoff projects located identities, dispositions, proof authority and blockers. Exact targets require full-target layout/pixel Facts per condition; incomplete input remains a constraint or blocks. Long-Task preserves every Fact × required-method obligation through Source/Claims/Assertions, `fact_expectations`, `fact_results` and Final Gate.

Intermediate implementation may drift, fail or require rework. The workflow does not guarantee model success or a drift-free path. After the first-lock boundary, the parent follows the Workflow Contract's packet-first positive default and the Skill's bounded execution protocol; all Authority, shared-owner and proof-bearing work still converges into the selected verification workspace. Worker reports are not Progress, Evidence, proof or completion authority. The workflow constrains acceptance: compare Source Authority, Contract, relevant Context and the current artifact; block unsatisfied items; localize failures through Source Item, Outcome, Claim, Assertion, Check, Proof Surface, Binding and owner boundary; direct repair; and revalidate the complete final snapshot. Summary prose, delegated reports, progress, historical tests, Receipts and command exit alone never substitute for proof.

The efficiency target is **Fine-Grained Semantic Purpose-Fulfillment Efficiency**: attain the complete declared fine-grained semantic/proof effect with evidenced high efficiency and high total-cost ROI. Logical Fact and obligation identity may therefore be finer than physical storage, but no semantic or proof unit may disappear. Under the selected restricted DSL, canonical algorithms and named TCB, no known Authoring, persistent Authority, default Context reading, Compilation, Preflight, Runtime Verification, State/Recovery, maintenance, test, revision-blast-radius or migration cost may remain solely because of unrelated axes, derivable repetition, copied shared metadata or mechanical ground expansion. High means a significant, stable margin after all required costs rather than merely clearing zero; it requires neither exhaustive alternatives nor a global/local optimum proof.

Sufficiency is the anti-degradation construction stop: after declared-purpose validity, relative non-degradation, must-allow behavior, Structural Closure Cost Non-Degradation and applicable measured total-cost thresholds close, stop expanding the mechanism. Reopen only for a new real counterexample, a repeated material cost hot spot or evidence of significant additional net benefit.

The non-UI Long-Task Compact Carrier is the admitted persistence boundary for that separation. It reuses the existing Source/Contract Authority, Authority Lock/Revision, drift/repair, current-snapshot compilation and sole Final Gate; it does not reuse UI symbolic policy or join UI symbolic completion. Source owns one compact manifest made from shared catalogs/selectors, Fact sets, deterministic parameterized structure families, exact shared composite structures, proof templates and explicit exceptions. Contract owns one compact projection catalog and bindings rather than repeated rows. Structure-family templates recursively cover nested content while parameters carry only occurrence-specific scalar leaves such as positional locators; templates cannot reference one another, so the catalog remains acyclic. Package authoring chooses the byte-beneficial canonical representation before persistence, and package parsing revalidates catalog closure, canonical identities and the absence of any remaining known same-boundary lower-cost representation before ephemeral expansion. This catalog is part of the one compact Authority, never a second expanded Authority or a long-lived identity layer. Parsing may materialize only explicitly measured and bounded Fact, obligation and result sets through arrays and `Map` indexes, never the theoretical ground universe. Closure remains two exact sets—Facts independently from obligations—and every current result is keyed by stable `obligation_key`, carries its current `obligation_revision_digest`, projects to stable `fact_key`, and carries its current `fact_revision_digest`. Fact revisions include normalized meaning plus all explicitly linked current input revisions; obligation revisions include normalized proof meaning plus the current Fact revision. Repository-backed text input revisions remain exact raw-byte identities, so the repository freezes Git-classified text to LF across hosts instead of treating CRLF and LF as two accepted representations of one digest. A DAG or content digest authenticates current material but is not long-lived identity. Legacy expanded inputs remain readable for compatibility, while each adopted Authority persists one representation and migration removes the equivalent expansion instead of retaining a shadow copy.

Admission is lexicographic: Safety/Coverage; Semantic Granularity; Proof Strength/TCB plus non-bypassable Authority, fail-closed and complete-current-final-snapshot proof; Structural Closure Cost Non-Degradation; then total-cost ROI. For an equivalent-effect workload, persistent bytes, DAG work, Compile/Preflight/Final-Gate work, peak RSS, default Context bytes and one-Fact revision blast radius cannot grow for an unrelated structural reason. The package-owned structural-cost probe reports `K_fact`, `K_rule`, `M_total`, `N_dag`, Source/Contract/Evidence bytes, actual selected default-Context bytes, phase wall times, the isolated gate process's real peak RSS with its process boundary disclosed, and one-Fact changed files/lines/bytes against a reviewed fixed baseline or invariant formula that cannot rise from the current measurement. It also mutates one Fact and adds one unrelated axis to prove revision locality and zero unrelated growth in `K_fact`, `M_value` and persisted shared metadata. Passing measurements are always emitted as a CI artifact. The round-power-of-two capacity budget remains only a fail-closed capacity fuse and supplies no non-degradation baseline. Every justified increase maps to independent semantic coverage, proof strength, TCB hardening or necessary adaptation. Positive ROI then means incremental purpose-fulfillment benefit exceeds every incremental Authoring, Runtime, State, Recovery, maintenance, test, process, introduction, adoption and migration cost and permits consideration rather than automatic adoption. When the evidence boundary is uncertain, fail safe rather than silently accept. This is package mechanism admission, not `AcceptedDeliveryTerminal`, a deadline, a second Gate or runtime state.

### Level-4 evidence acquisition and promotion closure decision

The Level-4 evidence path uses five narrow existing-or-bounded owners rather than one replaceable collection facade. One package materializer owns every detached-worktree install/build/source-parity/pack operation and its reproducibility record. One module-private-branded acquisition runtime privately owns the runner interaction recorder, the existing Windows Job Object supervisor, one delivery-specific Provider bridge and the State bundle capture. The frozen scenario catalog remains the sole owner of the eleven source/applicability/zero policies; collectors state capabilities only. The immutable run-artifact index remains the only byte/role facade passed to formal evaluation, and `verify_long_task_real_process_roi.mjs` remains the only formal conclusion owner. The independent audit and direct-child governance Promotion consume those identities but never become another verifier or Gate.

The Build / Reuse / Buy judgment selects reuse of Node standard-library filesystem/crypto/HTTP/process primitives, the existing npm and package source-parity commands, the current Job Object native adapter and the immutable artifact index. It adds bounded self-implementation only for the stable missing concepts: the package materialization protocol, the branded acquisition facade, one fixed Provider protocol and isolated worker, one finite owner-local benchmark dependency-closure checker and the delivery-specific State payload/ledger. A generic Provider platform, cross-platform supervisor, callback-injectable transport/worker/request seam in an authoritative entry, new parsing/dependency library, duplicate pack implementation, ordinary-spawn fallback, sampling proxy, account-level usage estimate or second evidence registry is prohibited. This viable set is preferred to a new dependency because the required protocol and allowed dependency syntax are repository-specific, the existing owners already cover process containment and artifact integrity, and a library would not remove the need to bind exact local build, Provider, launch-envelope and State semantics.

The acquisition trust boundary is runner-owned. A child receives only its main-output locator, a fresh State-root locator when applicable and a one-shot loopback Provider capability when applicable; it receives neither Provider credentials nor prompt/Provider artifact paths. The parent captures the exact prompt, creates an invocation-local temporary root and launches the exact candidate-owned Provider worker with `process.execPath`, empty `execArgv`, `shell: false`, bounded pipes and an allowlist-built environment. The worker alone uses `node:https`, a bounded response reader and the fixed parser; prompt/response/diagnostic/deadline/abort/output-token limits have one protocol owner and enter adapter/runtime identity. Worker request files are create-new, no-follow ordinary single-link files, never enter the run-set and must be removed after complete worker shutdown; overflow, timeout, disconnect, abort or cleanup doubt fails closed. Provider-issued request/session correlation is primary and time proximity is only a bounded auxiliary check. The provider event binds the unretained response digest plus parser and worker identities; verifier acceptance trusts that formal acquisition TCB and does not claim an independent reparse of retained response bytes. State is post-close, no-follow, link-free exact content bundled into one payload and a recomputable index; a package tarball or execution-duration proxy is ineligible. Human and process monotonic clocks have distinct identifiers and are never numerically compared. Native wall milliseconds are canonicalized by Node before persistence. ## Anti-Degradation Assurance

Anti-Degradation Assurance preserves two mechanism properties plus two adjacent efficiency boundaries that are independently reviewable:

1. **Current causal-chain truth:** current Context must describe the actual current implementation, the indexed code/runtime must realize both jointly necessary responsibilities above, and those responsibilities plus the enabling precision/observability logic and explicit Source/semantic/TCB boundary must imply the controlling accepted-terminal-state purpose.
2. **Cross-version non-degradation:** an accepted mechanism change must not reduce declared drift coverage, increase known or constructible false negatives, or make Authority, fail-closed handling or complete-current-final-snapshot proof bypassable.
3. **`F = Implementation Freedom Boundary`:** because the guarantee is accepted-terminal-state safety rather than path safety or termination, Harness does not prescribe a fixed implementation sequence, development phase/method permission Gate, mandatory per-edit verification cadence or fixed agent allocation. Within declared authority and architecture/security/forbidden-shortcut/irreversible/external-action boundaries, the parent Goal owns implementation order, concrete decomposition and dynamic worker count. The packet-first positive default is the bounded current exception: the Workflow Contract owns its normative predicates, six reasons and partial-delegation outcome, and the main Skill owns its ephemeral dispatch and integration procedure. No agent count, Outcome mapping, retry, queue, DAG, registry or state is persisted; delegation remains non-authoritative and converges into one verification workspace.
4. **`E = Structural Closure Cost Efficiency Boundary`:** the mechanism-design goal is not merely to keep the fine-grained effect unchanged, but to attain that effect efficiently. When Safety, the complete Long-Task causal chain, complete fine-grained denotation, Proof Strength/TCB and Authority/Final-Gate safety are equivalent on a named workload, mechanism structure must not regain cost from unrelated axes, mechanical Fact/obligation expansion or copied shared metadata. Source/Contract/evidence bytes, canonical DAG work, Compile/Preflight/Final-Gate work, peak memory, default Context reading and one-Fact revision blast radius are the observable structural cost family. A regression needs an independent mapped semantic/proof/TCB/adapter benefit and positive total-cost ROI; efficiency evidence never becomes delivery acceptance.

The project owner admits this current canonical/public carrier because Final Gate cannot close the independent development-cost path in which a host exposes parallel capacity and the exact fixed worker but rolling implementation remains serial. Packet-first actual attempts close the availability-inference escape; zero-start and partial delegation keep real host failures explicit without a runtime allocator. Count and decomposition remain parent-owned, all proof converges before Final Gate, and no allocator, scheduler, queue, DAG, registry, persistent state or delegation proof is introduced. The carrier reuses the existing prompt-level judgment, fixed profile, fail-closed Hook and one-way sync, adds no runtime or test/fixture population, and therefore has bounded structural cost. This is rigorous causal/structural admission with an explicit owner decision, not evidence that a host actually delegated or that effective model, tier, capacity, tokens or wall time improved.

The first property closes the former theory/implementation seam. `PROJECT_SPEC.md` and this rationale own intended purpose, key logic, responsibilities and theorem boundary; `implementation-index.md` names the actual current owners; code is current implementation truth; `verification.md`, tests and runtime evidence prove selected properties. A current-implementation description that no longer matches code is stale Context, while code that no longer realizes the protected logic is implementation drift or missing work. Neither side may be silently relabelled to preserve a prose claim. Concrete modules and proof cases may change, so their owners and indexes change with them; the causal roles and boundary remain stable.

The current implementation realizes the first responsibility through Source-bound authoring, Control/relation/applicability and architecture meaning, Context/Design Authority reachability, `design-resource-fact-policy.ts`, strict per-resource fact inventory/closure and formal Source-to-Contract continuity, and realizes the second through complete Claim/applicability/fact/proof-surface expansion, exact fact-bound and target-qualified evidence, Counterfactual sensitivity, frozen proof inputs, Authority Lock/Revision, repair-localizing Findings and the source-recompiled one-snapshot Final Gate. The non-UI semantic-fact extension adds the equivalent standard-plus-custom family catalogue, subject/relation/applicability census, exact Source/Contract conservation and value-location boundary without copying exact values into Contract authority. Semantic-assurance counterexamples, critical sentinels, live lifecycle tests and the implementation index are the recoverable evidence map; no prose assertion alone establishes conformance.

The construction protecting these properties is deliberately layered but not authoritative: canonical design and Context; discovery triggers; the current implementation/proof index; behavior and counterexample suites; causal-chain, implementation-freedom and selected-design-fact critical-semantic sentinels; fail-safe affected-to-Trust-to-complete routing; managed-source, build and Context parity; and existing CI/release gates. Each layer closes a different accidental-degradation or discoverability path. Selected handoffs pay the additional authoring cost of atomic fact/resource closure and already-required method cells pay compact fact-reference equality; exact values stay in canonical resources, exploration pays no schema cost and execution order remains Goal-owned. The layers add no runtime acceptance result, second Authority/Gate/state, mechanism matrix or test-name registry beyond the existing small sentinel policy.

Admission is lexicographic. First prove Safety/Coverage non-degradation, then Semantic Granularity equality, then `FalseNegative_new ⊆ FalseNegative_old`, no weaker Proof Strength/TCB and non-bypassable Authority/fail-closed/complete-current-final-snapshot proof. Next prove Structural Closure Cost Non-Degradation under `E`: equivalent-effect work cannot grow from unrelated axes, mechanical expansion or shared-metadata replication. Only then require positive net ROI: incremental anti-degradation or purpose-fulfillment benefit must exceed every incremental Authoring, Runtime, State, Recovery, maintenance, test, process, introduction, adoption and migration cost. Cost savings never compensate for weaker interception, unchanged correctness never excuses unrelated structural cost growth, and positive net ROI admits consideration rather than adoption. A proposed safeguard with no independent protected path, duplicative proof or greater total cost than its expected benefit is not retained merely because it sounds safer.

The controlling purpose, enabling key logic, two jointly necessary responsibilities, explicit theorem boundary and adjacent `F`/`E` efficiency boundaries are protected design invariants. Neither `F` nor `E` is folded into the no-drift implication as another implementation responsibility: `F` protects path minimality/adaptability and `E` protects the structural efficiency of attaining the same fine-grained effect. Ordinary requirement and implementation work may strengthen these invariants and may replace concrete schemas/modules/tests. Weakening, reinterpreting or replacing one requires an explicit project-owner design-purpose decision recorded in `PROJECT_SPEC.md` and this owning Context. The decision names the old/new implication and boundary, coverage, granularity, proof/TCB and structural-cost effect, compatibility/migration consequence and replacement proof. A mandatory development-stage constraint additionally names a concrete independently uncovered safety, irreversible-effect, false-completion or total-cost path, explains why the existing Final Gate or a lighter project-owned check cannot cover it, preserves Goal ownership, passes non-degradation and has positive net ROI. A structural-cost regression additionally names its equivalent-effect workload, comparator/budget and independent necessitating semantic/proof/TCB/adapter benefit. Generic requirement change, Agent inference, a cost argument or coordinated edits to prose/code/tests do not silently supply that authority.

This assurance is strong against normal mistakes, omitted updates and known/constructible regressions, not absolute against every future governance failure. A maintainer authorized to change every owner can deliberately weaken the specification, implementation and sentinels together; external branch protection or human review may raise that governance cost but is outside the workflow theorem. Likewise, an omitted requirement or semantically unsound external oracle remains outside machine proof. These limits must stay explicit so “anti-degradation” is not mistaken for cryptographic immutability or universal correctness.

## Why Contract Draft Exists

Before the first successful formal Compile, `delivery-contract.yaml` is a non-authoritative Contract Draft. The Draft lets the author progressively preserve Source meaning, decompose it into atomic Claims and named Assertions, bind repository evidence, and resolve Preflight findings without prematurely creating Authority Lock.

The Draft is the same object that will later become formal Contract Authority. It may be edited across many repository reads and model responses. It needs no Draft Receipt, Authoring State, second plan, draft schema, draft CLI or draft runtime record.

## Why Outcomes Decompose Requirement Coupling

A Draft Outcome groups an independently observable and decidable result whose Claims and acceptance can be target-verified and whose dependencies and ownership boundary can be stated. This separates requirement coupling without splitting completion authority.

Outcome boundaries let one Goal project a smaller acceptance/verification-ready working set, shorten targeted verification, localize failures, restore findings on resume, and mark precisely which local result became stale. They do not constrain which in-scope code the Goal may implement next. An Outcome is not a response-length fragment, file group, frontend/backend layer, Agent-capacity unit or parallel-work allocation.

> Outcome decomposes execution and diagnosis, not completion authority.

## Protected Implementation Freedom Without A Scheduler

`depends_on` expresses acceptance and intermediate-proof readiness. The current Goal uses it with current findings to form a temporary Rolling Frontier while independently choosing implementation order as code reality becomes known. The Frontier is a derived view, not a runtime type and adds no schema field; it is not persisted, does not authorize or prohibit edits and does not prescribe a mandatory implementation schedule.

No Draft Outcome creates a Worker, scheduler item, queue, process tree, model route or durable execution DAG. Outcome decomposition does not guarantee parallelism or fewer model calls. It improves intermediate implementation, verification, diagnosis and recovery while leaving final acceptance to the complete Contract.

Harness never owns, persists, allocates, retries or recovers subagent dispatch, a Worker graph, branch/worktree fan-out or delegation state. The prior availability-first wording left an independent serial escape: a parent could label unobserved profile or capacity as unavailable and never exercise an otherwise eligible host. The current packet-first rule therefore decides independent positive-benefit work before host capability, requires real exact-spawn attempts unless explicit user/host policy forbids agents, and distinguishes a zero-start solo fallback from a later-failure partial delegation. Final Gate cannot recover wall time, parent-context pressure or compaction/wait cost already spent serially, while a runtime allocator would add a second control plane. The Workflow Contract owns the six normative reasons; the main Skill owns packet, host-call and shared-worktree procedure. The choice remains ephemeral Goal behavior, reports stay advisory, and every result converges before any declared Check can count.

This is the concrete `F` boundary. It does not remove Source/Contract scope, Architecture Deliberation/Conformance, security, forbidden shortcuts, irreversible/external-action approval boundaries or Final Gate proof. It prevents those end-state and path-safety boundaries from being silently expanded into a universal fixed development sequence, method Gate, per-edit check cadence or agent scheduler. A new constraint is admissible only through the explicit protected-invariant decision and distinct-path/lighter-alternative/non-degradation/positive-ROI proof above.

## Why One Host Model-Change Checkpoint Exists

The host and user own the parent Goal's model selection, and Harness cannot switch the model of a running conversation or Goal. It therefore creates no dynamic model router, tier scheduler, retry loop, persisted route or acknowledgement state.

The first successful Compile is nevertheless a distinct cost boundary: Source, Contract, relevant Context, risk and acceptance evidence are now under Authority Lock. At that point the user can handle any desired model change in the host while the locked Contract, targeted repair and Final Gate continue to constrain completion.

Compile emits `execution_model_checkpoint.required: true` only for the first Authority Lock. The Agent always ends that turn before product implementation, file edits, builds or tests, even if an earlier message already described a model strategy. It asks an English-speaking user to reply exactly `model checkpoint cleared, continue`; Chinese guidance uses the exact localized reply `模型切换卡点解除，继续`. A generic continuation is deliberately insufficient under the package-managed prompt protocol, but the token still does not attest a change: Harness cannot observe the next host message or verify the active host model and creates no unlock state. Later revisions return `required: false`; no repeated cost-only pause occurs.

This checkpoint is an execution-cost optimization enabled by the workflow's drift protection, not acceptance evidence. Host model handling and the continuation never prove a Claim or weaken Final Gate requirements.

The old implication treated any packaged model-specific worker surface as prohibited because it could become a second routing/control plane. The project owner now explicitly permits one narrower host adapter: `ty-context enable long-task` may install a fixed Codex-native `long_task_implementation` custom agent profile whose current model and reasoning effort exist only in the canonical package-owned TOML, with child-local multi-agent disabled and an exact `SubagentStart` boundary injection. It is usable only for bounded rolling implementation/repair after the parent Goal's checkpoint. The profile is static, stateless, optional and non-authoritative; it never becomes Source, Contract, Authority, Context writeback, Progress, Evidence, Receipt or Final Gate, and its absence, invalidity or a preserved same-path user customization cannot change the formal acceptance path. It cannot select models dynamically, classify tasks into tiers, spawn/retry agents, schedule work, create a branch/worktree or persist delegation/model state. An active-binding `PreToolUse` guard denies generic agent invocation unless the official current-call selector is exactly this profile, then freshly reuses the profile owner's no-follow bootstrap-path inspection to require the installed regular profile to parse and remain byte-identical to the package asset; missing, invalid, outdated, symlinked, non-regular or otherwise conflicting state denies the spawn and returns the packet to the parent. The guard performs no prompt/transcript/model inference, input rewrite, retry, substitution or persistence. Static installation still does not prove that the host selected the profile, and installing/updating the Hook does not prove that Codex/user trusted it; `/hooks` review is host-owned and Tiny Context cannot observe or persist trust.

## Why Context Remains Mutable During Execution

`Context Delta` is not a one-time pre-Compile decision. The current Goal must re-evaluate `Context Delta` whenever implementation or repair discovers a durable fact and update the owning Context rather than freezing a known error until the end.

The verifier distinguishes two classes in referenced snapshot mode:

- **Controlling Context** includes core Context, every explicit `context_ref`, verification and deployment Context, and every other selected file whose semantics can change ownership, architecture, contract, risk, recovery or repeatable verification. A change always requires Authority Revision and invalidates affected proof, but it requires a user decision only when the compiled Claims, targets, proof obligations or another decision boundary change. A raw snapshot update with those locked semantics unchanged is mechanically bounded rather than a reason to interrupt.
- **Supporting Context** is limited to graph-derived, non-explicit `implementation-index` and `archive` files. These files improve navigation or preserve background material but do not define acceptance. Their content may auto-revise through `compile --revise` without user approval, and a supporting-only revision does not invalidate otherwise fresh targeted Progress.

Full snapshot mode treats every Context file as controlling. Explicitly referencing an otherwise supporting role also makes it controlling. This prevents the executing Agent from relabeling a requirement-bearing file as support to bypass Authority Revision. Final Gate still recompiles and binds the complete current Context snapshot, so supporting updates remain visible without becoming an acceptance authority.

## Why Contract Draft Authoring Is Integrated

An early design considered having Web GPT independently emit a complete Contract Draft before repository work. That scenario was abandoned because a complete Draft can exceed Web GPT's reliable single-response length; requiring one response to contain the whole delivery Contract would make completeness depend on output capacity.

Once work enters Codex, the same Draft can be revised continuously in the real repository. Keeping Draft authoring inside `long-task-workflow` also has six architectural advantages:

1. real repository and Context reads are required to bind owners, paths, runners, verification inputs, proof surfaces and Bindings;
2. Preflight findings can directly repair the same Draft;
3. no extra Skill handoff can lose Source meaning, repository evidence or unresolved findings;
4. there is less pressure to create a second plan, Authoring Authority or Authoring Receipt;
5. Draft-to-Compile remains a lifecycle transition of one object rather than a conversion between products; and
6. the Skill can iterate across as many responses as necessary, then continue through Compile, the one-time host checkpoint, rolling execution, verification and Final Gate.

The platform-neutral form of this rationale belongs in `PROJECT_SPEC.md`. The Web GPT-to-Codex history remains source-workspace rationale only and must not enter package-managed Skills or public consumer guidance.

The earlier separate authoring-service boundary existed so an external conversational service could prepare a high-fidelity proposal before Codex. The project owner explicitly includes ordinary model-authored verifier mistakes in the threat model for material machine acceptance. A pre-existing verifier can still be a self-attesting report reader, while a newly authored observer can be trustworthy when it only drives a package-owned admitted adapter; age is therefore a risk signal, never an admission rule. Classification does not split spaces, remove quotes or rewrite backslashes; it examines only one independent token or the value of one explicit `--name=value` form, treats standalone switches as labels and denies unrecognized compound syntax machine closure. ## Why Engineering Quality Reuses The Final Gate

Long-Task shares the same thin engineering-quality obligation as default work: one visible repository-bound Architecture Deliberation before implementation includes triggered quality attributes or concrete preservation, Goal-owned implementation keeps the shared boundary/failure/abstraction discipline, and one current-candidate Engineering Quality Conformance includes Architecture Conformance after project verification. Live Check ownership plus the one Final Gate close the false-acceptance path from a current snapshot containing stale self-reported runtime status. Early targeted cadence closes no additional completion path; it is retained only as an adaptive late-rework cost recommendation and may be deferred or skipped. The bounded runtime-family and entrypoint schema prevents a browser or internal route from silently standing in for a native/root journey. Capability-specific probes remain project-owned and are required only for the Claims that need them. Targeted results remain repair-only; stale or absent Progress may enter Final Gate because that Gate reruns every declared live Check on the final snapshot.

## Mechanism Admission And Cost Boundary

A Long-Task change begins with the controlling design purpose and accounts for total cost by explicitly including the cost of introducing the change in its ROI judgment. A change to mechanism semantics, invariants, authority/proof boundaries or runtime behavior modifies the mechanism and its verification; a change that does not affect a mechanism stays at its owning point instead of being promoted into one.

A mechanism is considered only after proving a declared-purpose validity floor: every frozen critical counterexample is rejected, every independently grounded correct control passes, the sentinel fails at its claimed owner/semantic boundary and no open critical false acceptance remains hidden by prose or green aggregates. A discovered invalid behavior is defect, not valid baseline. The candidate then proves `Coverage_new ⊇ Coverage_valid_baseline`, must-allow correctness, `FalseNegative_new ⊆ FalseNegative_valid_baseline`, Authority/fail-closed non-bypassability and complete-current-final-snapshot proof. It then needs a concrete insufficiently covered false-completion or delivery-drift path, a testable invariant, fail-closed behavior and high total-cost ROI: incremental purpose-fulfillment benefit has a significant, stable margin over all incremental Authoring, Runtime, State, Recovery, maintenance, test, process, introduction, adoption and migration cost. High ROI admits a candidate to consideration and never adopts it automatically; it requires neither exhaustive alternatives nor a global/local optimum proof. Coverage means demonstrably rejected erroneous completion paths, not test/Fact/tag counts. Prefer measured data, benchmarks or operational evidence. When a formally required cost is unverified, keep total ROI unsupported; rigorous causal reasoning plus simple bounded validation may guide an experiment but cannot manufacture that evidence. Fresh-Agent experiments measure guidance adoption and cost, never establish critical false-acceptance safety. Unsupported intuition alone is not sufficient.

With the design purpose fixed, non-degradation proved and high total-cost ROI established, prefer stronger purpose fulfillment when total cost is comparable, or lower implementation and operating cost when purpose fulfillment is comparable. Prefer a cohesive one-time change when partial mechanisms would preserve semantic seams or create more aggregate migration and maintenance cost. Stop after the validity, relative non-degradation, must-allow, structural-cost and applicable measured total-cost thresholds close; reopen only for a new real counterexample, repeated material cost hot spot or evidence of significant additional net benefit.

Review must identify the path, invariant, proof, overlap with existing mechanisms, the risk reopened by deletion, total cost, net benefit, fail-closed behavior and whether the proposal creates a second Authority, second plan or scheduling plane. This review is a design and code-review principle, not a matrix file, Receipt or runtime Registry.

The same review protects `F` against ceremony growth. A proposed fixed implementation phase/order, method Gate, mandatory per-edit/per-Outcome verification cadence or agent-allocation/orchestration rule must first show an independently uncovered safety, irreversible-effect, false-completion or total-cost path and why the existing final proof or a lighter project-owned check cannot cover it. It then needs explicit project-owner design-purpose authority, unchanged acceptance coverage/false-negative strength, preserved Goal ownership/no delegation proof or state, and positive net ROI. Otherwise it remains optional Goal behavior or stays outside the workflow.

The rule has two independent decisions. Route selection is explicit and assurance-driven: absent a binding or selection, any task remains on the artifact-free default Workflow; when machine completion authority, recovery or auditability is required, even a small task may select Long-Task and pay one complete Contract, rolling repair and a current-snapshot Final Gate. Inside Long-Task, `auto | standard | strict` remains risk-proportional and raises proof only on affected high-risk Outcomes. Internal risk may rise automatically or explicitly and cannot be downgraded by the executing Agent, but it never auto-activates Long-Task.

Affected-test selection follows the same rule. It shortens the developer feedback loop by mapping known hot spots to focused tests, widening unmapped Long-Task runtime changes to the canonical Trust Boundary Gate, and widening shared package, dependency or unknown changes to the full suite. One plan executes only its highest aggregate, so complete coverage supersedes a redundant Trust invocation. Inferred local discovery omits and reports only untracked `.work_products/**`; tracked or explicitly supplied paths remain inputs. Reviewed Trust/focused/hotspot budgets, one small critical-semantic registry with fail-closed platform applicability and the current environment-bound Package-CI `github-ubuntu-v3` profile prevent silent semantic/cost growth while complete discovery stays exhaustive. A failed timing Gate first triggers hotspot attribution and safe efficiency work; only measured necessary residual cost may justify a new immutable profile with explicit observation, margin and review. Test deletion, coverage/sentinel/isolation weakening, contention-masking concurrency and retries are not budget repairs. A platform that cannot execute an invariant neither passes nor fails that sentinel, while an applicable platform still requires its direct passing observation; the cross-platform atomic-finalization sentinel is therefore independent from the Windows-only finalization-tree and Job-containment sentinels, which are excluded from Ubuntu coverage and directly executed in the Windows Package-CI job. These mechanisms are fail safe and never replace complete CI/release gates or the workflow Final Gate.

Phase 4 runtime reduction and its anti-degradation closure stay below the acceptance boundary. A deterministic build-input fingerprint prevents stale `dist` from consuming a suite run; an immutable process-scoped fixture seed removes repeated Git initialization while each test still owns a copied repository, and those disposable copies locally disable optional fsync plus automatic maintenance/GC without changing production Git policy. Bulk revision field/semantic permutations execute through the canonical compiler's state-free diagnose mode and decision projector while existing real CLI, pending, protected-failure and adoption cases retain process/persistence coverage; verifier migration reuses one disposable package through actual locator renames and exact-byte restoration while bundle/schema/Hook identity, content-specific Verify and protected Compile remain live. Terminal sentinel coverage and per-file/top-10 timing derive from the same current event stream; concurrency applies only to explicit proven-isolated files while every unknown file fails closed to serial. The opt-in performance probe reuses the canonical schema-sensitive Global fixture, runs small semantic fixtures before the large repository, separates default/Windows catastrophic profiles and counts a shared runner only once. `resume` completes the workspace status/fingerprint, including its index-writing phase, before observing current Git state against the same repository; independent fixture repositories remain eligible for bounded concurrency after a real shared-seed probe. Stable IDs protect only independent critical invariants rather than freezing every test name, and Trust membership derives from the same records. These mechanisms reduce recurring cost and protect the design purpose without a duplicate classifier, persistent worker, cached result, retrying Git locks, weakened current-snapshot proof or a test authority/scheduler/state plane.

Authority Revision and terminal guidance use the same cost rule. The former `reduction_reasons == approval_required` rule paid a human interruption for execution repairs even though exact identity, evidence invalidation and Final Gate already carried the safety cost. The revised derived policy retains those protections but asks only for real user-decision reasons; Rev3-Rev36 read-only replay projects 33 approvals to two decision events (31/33, 93.94% fewer), and Rev12's exact existing instruction removes the duplicate prompt so only Rev3 needs a new question. A verifier-content identity change remains one of those fail-closed decisions and invalidates prior evidence, but the digest delta alone does not prove that acceptance or proof coverage was reduced. Its brief names changed verifier files and explicitly records that preservation is not independently established; only previous-Authority proof or trusted external release provenance could support a future automatic transition. This evidence is a regression corpus, not permission to auto-classify an uncertain change: missing preservation proof remains fail closed.

The implementation adds only derived fields/classification and tests. It adds no command, persistent state, editable review artifact, instruction ledger, native-Goal state, second Gate or positive Agent-judgment proof. Before asking, an Agent may mechanically relay an explicit current task instruction only when it exactly covers every listed decision reason; generic blanket authorization or inference cannot. Candidate diagnosis stays stateless so withdrawn identities do not produce questions. This yields positive ROI: negligible runtime/recovery cost versus removal of repeated high-cost interruptions while the unchanged Final Gate still proves the adopted snapshot.

When a rolling blocker motivates revision, implementation difficulty alone cannot move a machine-verifiable requirement behind an External Confirmation or erase it. A real scope change is marked Source meaning and follows Authority Revision; repo-bound implementation scope alone may auto-adopt, while any Product/Claim/target/acceptance/external boundary change requires the exact user-decision identity. After adoption, affected weak-observability or high-risk Outcomes pay an adversarial evidence review: the Check must reach the furthest independently failing boundary named by the Claim, provide the declared capability records, and use a causal Counterfactual or failure/input-variation record when carrier presence alone can diverge. Risk-proportional review is enforced by the existing activation kernel and Final Gate rather than a universal runtime suite.

## Current Mechanisms And False-Completion Paths

- **Material/background/formal Source ownership closure** prevents any non-empty Source content from being silently ignored, while exact Material inventory prevents a Source item from being omitted, rewritten or disappearing without a mapping.
- **Atomic non-Result Claim Coverage** prevents several specific requirements from collapsing into one broad Outcome Result.
- **Control field and cross-Control relation closure** prevents empty fields or absent relation rows from silently deleting applicable control, shared-state, navigation, permission or recovery meaning.
- **Claim applicability and one-Claim Assertion closure** prevents proof on the wrong target, condition/input/state, journey or action sequence from covering an applicable fact and keeps every failure attributable.
- **Source AC to named Assertion semantic identity** prevents acceptance meaning from being weakened in the Contract; the same canonical resolver covers Outcome refs and `GLOBAL.<check>.<assertion>`, while Global ACs require an independently Source-backed Global Claim and cannot cross scope.
- **Shared Preflight/Compile activation-safety kernel** prevents skipping Preflight from bypassing activation rules.
- **First-Compile Authority Lock and Authority Revision** prevent Source, Contract, Controlling Context or verifier edits from washing away requirements during execution.
- **One-time execution-model checkpoint** uses an unconditional terminal-turn contract so implementation cannot silently pass the host-change boundary. The user handles any model change outside Harness and sends `【继续】`/`[continue]`; this resumes execution but cannot prove the host changed models. It lets the user exploit locked Authority and Final Gate protection without creating model routing, persisted acknowledgement or repeated pauses. It is a cost mechanism, not proof.
- **Controlling/Supporting Context classification** permits low-risk navigation/background updates during execution without discarding valid Progress while keeping explicit, verification, deployment and full-snapshot Context fail closed.
- **Executing Agent cannot originate its own weakening decision** prevents the implementer from lowering its own acceptance bar. Mechanically relaying an explicit current task instruction that exactly covers every listed reason is user decision transport, not Agent approval; generic blanket authorization never qualifies.
- **Decision-relevance revision classification** keeps formally monotonic strengthening, mechanically bounded execution/Source/Context repair and repo-bound scope expansion automatic, permits stateless scope diagnosis, and keeps semantic/proof/forbidden-boundary/verifier-kernel changes plus unknown reason codes behind the exact revision identity.
- **Exact material revision summary, self-contained decision brief and rolling return** explain what Authority Revision is, distinguish decision reasons from mechanically bounded changes, show Source/Product/proof/runner/scope/risk/external-confirmation changes, affected Outcomes, reject/previous-Authority behavior and no-completion effect, then make adoption return to implementation. The brief is a projection of canonical summary data, not another authority.
- **Stateless same-Contract candidate diagnosis** lets related scope discoveries accumulate in `delivery-contract.yaml`, coalesces withdrawn/replaced identities and can exercise existing active Check identities before the final Compile without creating a pending Draft authority, revision lifecycle, Progress, Receipt or acceptance result. The previous Authority remains the only active one throughout diagnosis.
- **Targeted verify is repair evidence only** prevents a local pass from being reported as whole-delivery completion; Counterfactual failure is part of the owning Check Result/Progress rather than a transient top-level Finding, so status/resume cannot recover a false `progress_passing` state.
- **Live target-runtime Check ownership** prevents a proxy pass or tracked self-report from proving a Claim that can fail independently in the target; the earliest owning Outcome executes the target in the current Check run and binds runtime-affecting inputs through existing fields.

This reuses Source, Claims, Assertions, Checks, Authority Revision and Final Gate rather than adding an authority or Gate.

Because it closes no independent Final-Gate false-completion path, cadence stays Goal-owned and advisory; no targeted pass is required before later edits or Final Gate, and no per-Outcome rebuild rule, scheduler or new state exists.
- **Protected implementation freedom** prevents acceptance/readiness structure from silently becoming development permission. Fixed phase/order/method/per-edit Gates are absent. The current positive-default carrier changes only the bounded parent-owned choice under its exact predicates, remains non-authoritative and converges before proof; the separate critical sentinel catches owner drift without adding another acceptance mechanism.

## Trusted Results And External Fulfillment

Declared delivery authority has two accepted terminals: fresh package evidence proves an all-machine blocking universe as `machine_accepted`, or that same machine proof plus complete exact current external fulfillment proves `delivery_accepted`. Otherwise at least one item is unsatisfied, insufficiently evidenced, stale, unreachable or externally pending and the delivery remains unfinished.

Legacy `machine_accepted_external_pending` means only that the historical machine-verifiable subset passed while external confirmation remained. It is compatibility-read-only, not `AcceptedDeliveryTerminal`, and cannot clear Authority. New pending blocking rows are `blocked_external`; failed/unable/invalid/stale/unreachable rows are `needs_work`; non-blocking confirmations are advisory.

That distinction remains continuous after Final Gate. Collapsing it into `last_gate_passed`, `{}`, or generic `closed` reopens a false-completion path for callers that only see status, a resumed session, the Stop Hook or close output. The exact workflow status and per-obligation external evaluations therefore propagate through each surface; stale Receipts lose their accepted projection. Stop/close rerun Final Gate and can end the lifecycle only for `machine_accepted` or `delivery_accepted`; an external record alone cannot convert machine acceptance into complete delivery.

Progress, status, Receipts and compiled cache are audit/recovery projections. Candidate diagnostic results are transient repair output and are never Progress or completion evidence. Source, Controlling Context, Contract, verifier, runner or workspace drift stales affected evidence. Supporting-only Context revisions may preserve scoped Progress, but every adopted protected revision invalidates derived evidence; `resume` restores current semantic state rather than a physical Turn, and historical or candidate evidence cannot be spliced into current acceptance.

## Known Limits

- The workflow cannot prove that the user declared every real requirement.
- It cannot guarantee that a model completes implementation or avoids intermediate drift.
- It cannot switch or verify the model selected by the host, and it does not observe or persist platform-internal delegation beyond official start-time boundary injection.
- It accepts only declared, falsifiable machine authority; CI, deployment and human product acceptance remain external.
- It does not prove arbitrary project verifier or external Oracle semantics. Material machine acceptance is limited to package-admitted observation/comparison capabilities with explicit frozen dependencies and current target/session provenance; unsupported custom, physical or externally interpreted predicates remain named TCB or External Confirmation.
- It cannot infer requirements the user never expressed or prove an arbitrary external Inspector/Oracle semantically sound. Formal authoring must derive the scoped obligation universe, freeze declared Inspector inputs/capabilities/Census and preserve explicit blockers; unsupported/unreadable facts fail closed, while hostile or omitted Source remains outside the theorem boundary. `surface_bindings` and per-Fact evidence make declared meaning machine-checkable only after those premises hold.
- Local mode trusts the installed package-owned Harness and admitted adapter/comparator bytes, Git metadata and explicitly declared external runtime/device boundaries; it is still not a hostile-host security boundary.
- Complete current-snapshot verification costs time; assurance-driven route selection plus risk-proportional internal proof and affected developer tests keep unnecessary cost off the default route without weakening Long-Task acceptance.
