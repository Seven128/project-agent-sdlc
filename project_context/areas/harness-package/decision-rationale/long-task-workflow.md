# Long-Task Workflow Design Rationale

## Decision

Single-Goal Long-Task Workflow exists to prevent false completion inside one complete declared delivery authority. It uses one native Goal, one selected verification workspace, one continuously authored Contract, semantic Outcome boundaries, optional repair-only targeted verification and one current-snapshot Final Gate. It does not own agent, process, model or Git orchestration; a fixed optional Codex worker profile and its boundary Hook are host affordances, not a control plane.

Source-quality rules and Contract Draft authoring form one Source-bound authoring loop, followed by Preflight repair, formal Compile, one terminal-turn host checkpoint, rolling implementation, verification and Final Gate in one `long-task-workflow` lifecycle. Pre-existing planning or proposal documents remain ordinary Source; no standalone authoring compatibility route participates in the lifecycle.

The shared Architecture Deliberation and applicable-quality assessment occur during Source/Contract authoring before formal Compile and implementation. Long-Task Final Gate is the sole post-implementation Engineering Quality/Architecture Conformance carrier; no default-workflow closure is nested around it.

## Workflow Selection And Assurance Boundary

Long-Task is an explicitly selected machine-trusted delivery-assurance mode, not the route for a task-size class. The stable selection rule is:

> Complexity determines execution and verification depth; required completion authority and recovery determine the workflow route; Long-Task internal risk determines proof strength.

The default Workflow remains eligible for local changes, cross-module features, large refactors and long-running implementation when model-led execution, project-native checks and an evidence-bounded human-review handoff are sufficient. Conversely, a small calculation, permission or billing rule may justify Long-Task when every declared condition must become a stable, independently failing, independently rerunnable and auditable obligation. Duration, complexity and file count neither activate Long-Task nor make a task ineligible; only explicit selection or a valid existing binding enters it.

The selection benefit is verifier-owned completion authority, cross-compaction/session semantic recovery and auditable requirement-to-proof traceability. “Minimal human intervention” means reducing routine progress supervision and item-by-item checking, not eliminating user or external authority: reserved product choices, conflicting or missing Source, preference-sensitive selection, high-risk irreversible actions and External Confirmations can still require a person. “Higher quality” means stronger implementation-conformance assurance for declared and observable product, technical, architecture and selected-design obligations; it does not prove undeclared requirements, global product excellence, optimal architecture, Oracle truth or model success. “Efficiency” means the lowest practical total cost while this complete machine closure is required; Long-Task is not presumed faster or cheaper than the default route.

This route correction removes the former L0 eligibility barrier only. Once Long-Task is selected, the existing `risk.requested_level: auto | standard | strict`, computed proof floor, Source/Contract/Authority lifecycle, exact Fact/obligation closure, Evidence Kernel, repair loop, Final Gate, External Confirmation and accepted-terminal theorem remain unchanged. `standard` is the standard internal proof profile; `strict` remains the compiler-enforced floor for affected high-risk Outcomes. No Schema, compiler or runtime change follows from route orthogonality.

## Controlling Objective

The irreducible input boundary is that authoritative Source is complete, accurate and fine-grained enough to state every intended requirement and AC; the workflow cannot discover an intention the user never expressed. Source authoring must nevertheless expose and close all material implications already present in requirements, controlling Context, repository contracts and declared inputs rather than treating the user's paragraph structure as the semantic ceiling. For non-UI scope it derives an Expected Semantic Fact Universe across product/business meaning and technical/backend/architecture meaning at `subject or relation × atomic applicability × atomic property`. For a formal selected Web/App handoff, authoring separately derives the complete scoped design Expected Fact Universe before generation from requirements, product semantics, design system and target environments. A frozen Inspector then enumerates the acquired canonical source and proves exact manifest/handoff equality for every `subject × target × condition × variation × property` Fact Cell and required proof. Unsupported or unreadable Facts block, and named Inspectors/Oracles remain explicit TCB. Once expressed or necessarily derived, Source mapping, universe closure, executable Oracle sensitivity, freshness and Final Gate completeness are obligations rather than assumed trust.

The design-purpose guarantee is **complete-delivery accepted-terminal-state safety**, not a termination guarantee. Define `AcceptedDeliveryTerminal(snapshot)` as a fresh Final Gate result of exactly `machine_accepted`, with no declared External Confirmation pending. Given complete and accurate authoritative Source at the declared observable granularity, a meaning-preserving Source-to-Contract-to-observer projection and non-bypassable Authority/freshness:

`AcceptedDeliveryTerminal(current snapshot) => DeclaredObservableDrift = empty`

`machine_accepted_external_pending` is deliberately outside that antecedent. It proves only `MachineVerifiableDeclaredDrift = empty` inside `declared_machine_authority`; the unresolved externally observed predicate remains unproved, the complete delivery is qualified rather than accepted, and the native Goal is not completed by Harness. “Deliver drift-free” therefore means that every artifact which reaches the complete accepted delivery state is drift-free inside the full declared and observable scope. If implementation, machine proof or required external observation never closes, the workflow remains unfinished or explicitly qualified; it does not claim that every Goal must eventually reach acceptance.

The enabling key logic is that drift can be judged only where authoritative meaning is precise, applicable and observable. Text authoring therefore cannot stop at prose paragraphs, Requirements, Product Controls, broad states or “all cases” labels. For non-UI scope it first enumerates subjects, relations and dynamic populations; closes standard and discovered custom semantic families; expands meaningful atomic condition cells; and preserves typed value semantics, provenance, disposition and proof. This includes product/business rules as well as backend and architecture contracts: APIs/data/schema, state/time, events/jobs, transactions/consistency/concurrency/idempotency, failure/recovery, configuration/migration/compatibility, performance/reliability, security/privacy, integration/deployment and observability. A Product Control is a semantic interaction unit, not either the minimum non-UI fact or the minimum UI/UX observation unit. Selected resources close visual/behavioral meaning at `subject × target × condition × variation × atomic property`, including component instances/Anatomy Parts/relations, dynamic populations, exact condition/variation axes, geometry/style/content/state/interaction properties and all property-required methods. Eight design dimensions and non-UI family names are roll-ups. Acceptance retains both `atomic Fact × required method` and `atomic Claim × applicability × proof surface`; exact expected/current sets prevent subject, relation, condition, property, comparison authority or verdict from collapsing.

The implementation logic has two jointly necessary parts. First, Source/design-resource authoring and Architecture Deliberation preserve enough product/business, technical/backend/architecture, Control/relation, applicability, engineering-quality and prederived selected-design meaning to define drift without current code inventing the reference; exact values remain with their unique authoritative Source/Context or canonical resource. Second, Source/Contract continuity, subject/relation Census and exact universe expansion, Claim-specific observers, per-Fact expected/current evidence, frozen verifier dependencies, Authority Lock/Revision and one-snapshot Final Gate fail closed on every unproved unit and revalidate the candidate; declared Engineering Quality/Architecture Conformance shares that Gate. The first part defines comparison authority but cannot enforce delivery; the second cannot recover omitted intent, a missing custom semantic family or Facts an unsupported Inspector/Oracle cannot observe.

That last condition is not an informal escape hatch. The Harness must compile a **Semantic Assurance Closure** inside the existing Contract/Authority/Final-Gate carrier:

1. Background may contain only text-free Markdown anchors/separators or fixed-field provenance syntax; text-bearing headings, free-form provenance and arbitrary prose cannot be hidden from Material Source classification.
2. Applicability is represented as atomic dimension/value cells. A profile cannot bundle mutually exclusive values, and every Claim is proved on every target/journey/cell it declares without representative or pairwise substitution. Selected-design conditions are themselves atomic cells rather than arrays of modes, states, content cases or input methods.
3. Every behavioral Claim-bearing Assertion has a Claim-relevant narrow semantic mutation plus a claimless target-liveness witness. Whole-file replacement may prove carrier loss but cannot by itself attest which sibling semantic value the observer reads.
4. Every property-required selected-design method emits method-specific evidence for every target/condition cell. Each cell freezes exact `fact_refs` and `fact_expectations`, record/observation paths, expected located digest, comparator/tolerance/mask, Oracle/environment and sensitivity. Runtime `fact_results` are set-equal and individually attributable; every verdict passes, protected raw values are not persisted, and observation identities remain distinct. Integrity/render evidence or aggregate pass cannot stand in for missing Facts or semantic methods.
5. Required runtime capabilities are explicit on the exact execution target and on every design-acceptance blocker. A blocker may close as a machine Claim only when its exact target declares every Source-required capability and the Claim is proved on that target; otherwise it remains a target-blocking External Confirmation. A browser specimen, simulator or detached route cannot substitute for a required physical device, sensor, haptic, assistive-technology or production-root capability.
6. Authority freezes the runner, declared verification inputs and the supported direct-literal local verifier graph: static imports/re-exports, literal dynamic imports, `require`/`require.resolve`/`module.require`, and literal `new URL(..., import.meta.url)` files recurse under the repository. Files explicitly owned by Check `input_paths`, `expected_output_paths` or `artifact_globs` remain candidate/runtime material rather than Oracle identity and are covered by final-snapshot execution/integrity. Non-literal loaders and `createRequire` fail closed; indirect runtime file/process access must be declared in `verification_inputs` or remain part of the named project Oracle TCB. Bare package/runtime/device dependencies that cannot be byte-frozen are likewise named TCB, never silently treated as Harness proof.
7. Long-Task Authority freezes the complete `project_context/**` graph. Population proof either closes a declared machine-enumerable universe or remains target-blocking external confirmation; a runner-created eligible list cannot prove that it enumerated the real universe.
8. Material Architecture Deliberation conclusions continue to use Source-backed Technical Obligations, Constraints/Forbidden Shortcuts, owners/paths/Bindings and executable Claims in the same Contract. At least one architecture-classified Source obligation and current-snapshot proof is required, without adding an architecture field, second Gate or state.
9. Material non-UI scope has one exact conservation chain: `Expected Semantic Fact Universe = Source Indexed Facts = Contract Fact Obligations`, and `required proof obligations = current attributable Fact results`. A result carries `fact_ref`, actual observation, comparison policy and parameters/tolerance where applicable, pass/fail verdict, Oracle identity and environment. Broad assertions or shared executions may reduce runtime cost but cannot collapse Fact identity or result attribution.
10. Applicability closure is standard-plus-custom and census-driven, not a fixed blind Cartesian product. Every standard family receives a grounded applicable/not-applicable/decision-required/unavailable disposition, every discovered domain-specific family remains first-class, relation and dynamic-population members are enumerated or externally blocked, and aggregate strings cannot impersonate member sets.

Natural-language completeness and physical-world truth are irreducible boundaries: no generic Harness can derive an intention the user omitted or mathematically prove that an arbitrary external sensor/oracle denotes the intended real-world predicate. It can and must, however, inventory the declared subject/relation scope, ask every standard semantic-family applicability question, preserve custom families, derive necessary consequences and expose unresolved choices instead of silently omitting them. The workflow therefore admits a complete no-drift terminal claim only when those facts are represented by authoritative Source plus the frozen observer binding above and no declared External Confirmation remains. An explicit External Confirmation preserves the unresolved fact and blocks or qualifies complete delivery; it never supplies machine proof. Merely declaring an oracle “sound”, emitting a passing Boolean, hashing an artifact, reusing current code as its own expected value or labeling a block “background” never satisfies the closure.

Mechanism changes use the Anti-Degradation Assurance two-stage hard gate. First prove `Coverage_new ⊇ Coverage_old`, `FalseNegative_new ⊆ FalseNegative_old`, and preserve non-bypassable Authority, fail-closed behavior and complete final-snapshot execution. Only then compare Authoring, Runtime, State, Recovery, maintenance and migration cost. Cost reduction never compensates for reduced drift detection; this semantic-assurance repair is admitted because it restores the controlling objective before cost optimization is considered.

For selected design resources, one explicit purpose is full implementation/acceptance/test conformance to every material scoped UI/UX Fact. This neither infers unexpressed meaning nor proves the user supplied every requirement. Open Design is the default generator, but formal Web/App authoring derives the Expected Universe before generation, binds the adopted design system, commissions/retrieves canonical source plus manifest, freezes Inspector Census and requires exact universe equality without sampling/truncation. Canonical source owns exact values; the residual handoff projects located identities, dispositions, proof authority and blockers. Exact targets require full-target layout/pixel Facts per condition; incomplete input remains a constraint or blocks. Long-Task preserves every Fact × required-method obligation through Source/Claims/Assertions, `fact_expectations`, `fact_results` and Final Gate.

Intermediate implementation may drift, fail or require rework. The workflow does not guarantee model success or a drift-free path. After the first-lock boundary, the parent Goal performs an internal Delegation Suitability judgment and proactively uses one or more fixed-profile Codex workers only for independent bounded packets whose expected benefit exceeds coordination cost; high-coupling/shared-owner work remains with the parent. Their reports are not Progress, Evidence, proof or completion authority and all proof-bearing changes converge into the selected verification workspace. The workflow constrains acceptance: compare Source Authority, Contract, relevant Context and the current artifact; block unsatisfied items; localize failures through Source Item, Outcome, Claim, Assertion, Check, Proof Surface, Binding and owner boundary; direct repair; and revalidate the complete final snapshot. Summary prose, delegated reports, progress, historical tests, Receipts and command exit alone never substitute for proof.

The efficiency target is **Fine-Grained Semantic Purpose-Fulfillment Efficiency**: attain the complete declared fine-grained semantic/proof effect at the lowest practical total workflow cost. Logical Fact and obligation identity may therefore be finer than physical storage, but no semantic or proof unit may disappear. Under the selected restricted DSL, canonical algorithms and named TCB, no known Authoring, persistent Authority, default Context reading, Compilation, Preflight, Runtime Verification, State/Recovery, maintenance, test, revision-blast-radius or migration cost may remain solely because of unrelated axes, derivable repetition, copied shared metadata or mechanical ground expansion. “Optimal” is bounded to the declared mechanism and known equivalent alternatives; it is not a universal mathematical-minimum claim.

The non-UI Long-Task Compact Carrier is the admitted persistence boundary for that separation. It reuses the existing Source/Contract Authority, Authority Lock/Revision, drift/repair, current-snapshot compilation and sole Final Gate; it does not reuse UI symbolic policy or join UI symbolic completion. Source owns one compact manifest made from shared catalogs/selectors, Fact sets, deterministic parameterized structure families, exact shared composite structures, proof templates and explicit exceptions. Contract owns one compact projection catalog and bindings rather than repeated rows. Structure-family templates recursively cover nested content while parameters carry only occurrence-specific scalar leaves such as positional locators; templates cannot reference one another, so the catalog remains acyclic. Package authoring chooses the byte-beneficial canonical representation before persistence, and package parsing revalidates catalog closure, canonical identities and the absence of any remaining known same-boundary lower-cost representation before ephemeral expansion. This catalog is part of the one compact Authority, never a second expanded Authority or a long-lived identity layer. Parsing may materialize only explicitly measured and bounded Fact, obligation and result sets through arrays and `Map` indexes, never the theoretical ground universe. Closure remains two exact sets—Facts independently from obligations—and every current result is keyed by stable `obligation_key`, carries its current `obligation_revision_digest`, projects to stable `fact_key`, and carries its current `fact_revision_digest`. Fact revisions include normalized meaning plus all explicitly linked current input revisions; obligation revisions include normalized proof meaning plus the current Fact revision. Repository-backed text input revisions remain exact raw-byte identities, so the repository freezes Git-classified text to LF across hosts instead of treating CRLF and LF as two accepted representations of one digest. A DAG or content digest authenticates current material but is not long-lived identity. Legacy expanded inputs remain readable for compatibility, while each adopted Authority persists one representation and migration removes the equivalent expansion instead of retaining a shadow copy.

Admission is lexicographic: Safety/Coverage; Semantic Granularity; Proof Strength/TCB plus non-bypassable Authority, fail-closed and complete-current-final-snapshot proof; Structural Closure Cost Non-Degradation; then total-cost ROI. For an equivalent-effect workload, persistent bytes, DAG work, Compile/Preflight/Final-Gate work, peak RSS, default Context bytes and one-Fact revision blast radius cannot grow for an unrelated structural reason. The package-owned structural-cost probe reports `K_fact`, `K_rule`, `M_total`, `N_dag`, Source/Contract/Evidence bytes, actual selected default-Context bytes, phase wall times, the isolated gate process's real peak RSS with its process boundary disclosed, and one-Fact changed files/lines/bytes against a reviewed fixed baseline or invariant formula that cannot rise from the current measurement. It also mutates one Fact and adds one unrelated axis to prove revision locality and zero unrelated growth in `K_fact`, `M_value` and persisted shared metadata. Passing measurements are always emitted as a CI artifact. The round-power-of-two capacity budget remains only a fail-closed capacity fuse and supplies no non-degradation baseline. Every justified increase maps to independent semantic coverage, proof strength, TCB hardening or necessary adaptation. Positive ROI then means incremental purpose-fulfillment benefit exceeds every incremental Authoring, Runtime, State, Recovery, maintenance, test, process, introduction and migration cost and permits consideration rather than automatic adoption. When the evidence boundary is uncertain, fail safe rather than silently accept. This is package mechanism admission, not `AcceptedDeliveryTerminal`, a deadline, a second Gate or runtime state.

## Anti-Degradation Assurance

Anti-Degradation Assurance preserves two mechanism properties plus two adjacent efficiency boundaries that are independently reviewable:

1. **Current causal-chain truth:** current Context must describe the actual current implementation, the indexed code/runtime must realize both jointly necessary responsibilities above, and those responsibilities plus the enabling precision/observability logic and explicit Source/semantic/TCB boundary must imply the controlling accepted-terminal-state purpose.
2. **Cross-version non-degradation:** an accepted mechanism change must not reduce declared drift coverage, increase known or constructible false negatives, or make Authority, fail-closed handling or complete-current-final-snapshot proof bypassable.
3. **`F = Implementation Freedom Boundary`:** because the guarantee is accepted-terminal-state safety rather than path safety or termination, Harness does not prescribe a fixed implementation sequence, development phase/method permission Gate, mandatory per-edit verification cadence or agent allocation. Within declared authority and architecture/security/forbidden-shortcut/irreversible/external-action boundaries, the parent Goal owns those choices. Its post-checkpoint suitability judgment may select one or more disjoint bounded fixed-profile workers without persisting an agent count, Outcome mapping, retry, queue, DAG, registry or state; delegation remains non-authoritative and converges into one verification workspace.
4. **`E = Structural Closure Cost Efficiency Boundary`:** the mechanism-design goal is not merely to keep the fine-grained effect unchanged, but to attain that effect efficiently. When Safety, the complete Long-Task causal chain, complete fine-grained denotation, Proof Strength/TCB and Authority/Final-Gate safety are equivalent on a named workload, mechanism structure must not regain cost from unrelated axes, mechanical Fact/obligation expansion or copied shared metadata. Source/Contract/evidence bytes, canonical DAG work, Compile/Preflight/Final-Gate work, peak memory, default Context reading and one-Fact revision blast radius are the observable structural cost family. A regression needs an independent mapped semantic/proof/TCB/adapter benefit and positive total-cost ROI; efficiency evidence never becomes delivery acceptance.

The first property closes the former theory/implementation seam. `PROJECT_SPEC.md` and this rationale own intended purpose, key logic, responsibilities and theorem boundary; `implementation-index.md` names the actual current owners; code is current implementation truth; `verification.md`, tests and runtime evidence prove selected properties. A current-implementation description that no longer matches code is stale Context, while code that no longer realizes the protected logic is implementation drift or missing work. Neither side may be silently relabelled to preserve a prose claim. Concrete modules and proof cases may change, so their owners and indexes change with them; the causal roles and boundary remain stable.

The current implementation realizes the first responsibility through Source-bound authoring, Control/relation/applicability and architecture meaning, Context/Design Authority reachability, `design-resource-fact-policy.ts`, strict per-resource fact inventory/closure and formal Source-to-Contract continuity, and realizes the second through complete Claim/applicability/fact/proof-surface expansion, exact fact-bound and target-qualified evidence, Counterfactual sensitivity, frozen proof inputs, Authority Lock/Revision, repair-localizing Findings and the source-recompiled one-snapshot Final Gate. The non-UI semantic-fact extension adds the equivalent standard-plus-custom family catalogue, subject/relation/applicability census, exact Source/Contract conservation and value-location boundary without copying exact values into Contract authority. Semantic-assurance counterexamples, critical sentinels, live lifecycle tests and the implementation index are the recoverable evidence map; no prose assertion alone establishes conformance.

The construction protecting these properties is deliberately layered but not authoritative: canonical design and Context; discovery triggers; the current implementation/proof index; behavior and counterexample suites; causal-chain, implementation-freedom and selected-design-fact critical-semantic sentinels; fail-safe affected-to-Trust-to-complete routing; managed-source, build and Context parity; and existing CI/release gates. Each layer closes a different accidental-degradation or discoverability path. Selected handoffs pay the additional authoring cost of atomic fact/resource closure and already-required method cells pay compact fact-reference equality; exact values stay in canonical resources, exploration pays no schema cost and execution order remains Goal-owned. The layers add no runtime acceptance result, second Authority/Gate/state, mechanism matrix or test-name registry beyond the existing small sentinel policy.

Admission is lexicographic. First prove Safety/Coverage non-degradation, then Semantic Granularity equality, then `FalseNegative_new ⊆ FalseNegative_old`, no weaker Proof Strength/TCB and non-bypassable Authority/fail-closed/complete-current-final-snapshot proof. Next prove Structural Closure Cost Non-Degradation under `E`: equivalent-effect work cannot grow from unrelated axes, mechanical expansion or shared-metadata replication. Only then require positive net ROI: incremental anti-degradation or purpose-fulfillment benefit must exceed every incremental Authoring, Runtime, State, Recovery, maintenance, test, process, introduction and migration cost. Cost savings never compensate for weaker interception, unchanged correctness never excuses unrelated structural cost growth, and positive net ROI admits consideration rather than adoption. A proposed safeguard with no independent protected path, duplicative proof or greater total cost than its expected benefit is not retained merely because it sounds safer.

The controlling purpose, enabling key logic, two jointly necessary responsibilities, explicit theorem boundary and adjacent `F`/`E` efficiency boundaries are protected design invariants. Neither `F` nor `E` is folded into the no-drift implication as another implementation responsibility: `F` protects path minimality/adaptability and `E` protects the structural efficiency of attaining the same fine-grained effect. Ordinary requirement and implementation work may strengthen these invariants and may replace concrete schemas/modules/tests. Weakening, reinterpreting or replacing one requires an explicit project-owner design-purpose decision recorded in `PROJECT_SPEC.md` and this owning Context. The decision names the old/new implication and boundary, coverage, granularity, proof/TCB and structural-cost effect, compatibility/migration consequence and replacement proof. A mandatory development-stage constraint additionally names a concrete independently uncovered safety, irreversible-effect, false-completion or total-cost path, explains why the existing Final Gate or a lighter project-owned check cannot cover it, preserves Goal ownership, passes non-degradation and has positive net ROI. A structural-cost regression additionally names its equivalent-effect workload, comparator/budget and independent necessitating semantic/proof/TCB/adapter benefit. Generic requirement change, Agent inference, a cost argument or coordinated edits to prose/code/tests do not silently supply that authority.

This assurance is strong against normal mistakes, omitted updates and known/constructible regressions, not absolute against every future governance failure. A maintainer authorized to change every owner can deliberately weaken the specification, implementation and sentinels together; external branch protection or human review may raise that governance cost but is outside the workflow theorem. Likewise, an omitted requirement or semantically unsound external oracle remains outside machine proof. These limits must stay explicit so “anti-degradation” is not mistaken for cryptographic immutability or universal correctness.

## Why Contract Draft Exists

Before the first successful formal Compile, `delivery-contract.yaml` is a non-authoritative Contract Draft. The Draft lets the author progressively preserve Source meaning, decompose it into atomic Claims and named Assertions, bind repository evidence, and resolve Preflight findings without prematurely creating Authority Lock.

The Draft is the same object that will later become formal Contract Authority. It may be edited across many repository reads and model responses. It needs no Draft Receipt, Authoring State, second plan, draft schema, draft CLI or draft runtime record.

## Why Outcomes Decompose Requirement Coupling

A Draft Outcome groups an independently observable and decidable result whose Claims and acceptance can be target-verified and whose dependencies and ownership boundary can be stated. This separates requirement coupling without splitting completion authority.

Outcome boundaries let one Goal project a smaller acceptance/verification-ready working set, shorten targeted verification, localize failures, restore findings on resume, and mark precisely which local result became stale. They do not constrain which in-scope code the Goal may implement next. An Outcome is not a response-length fragment, file group, frontend/backend layer, Agent-capacity unit or parallel-work allocation.

> Outcome decomposes execution and diagnosis, not completion authority.

## Protected Implementation Freedom Without A Scheduler

`depends_on` expresses acceptance and intermediate-proof readiness. The current Goal uses it with current findings to form a temporary Rolling Frontier while independently choosing implementation order as code reality becomes known. The Frontier is a derived view, not a runtime type and adds no schema field; it is not persisted, does not authorize or prohibit edits and does not prescribe a mandatory implementation schedule.

No Draft Outcome creates a Worker, scheduler item, queue, process tree, model route or durable execution DAG. Outcome decomposition does not guarantee parallelism or fewer model calls. It improves intermediate implementation, verification, diagnosis and recovery while leaving final acceptance to the complete Contract.

Harness never owns, persists, allocates, retries or recovers subagent dispatch, a Worker graph, branch/worktree fan-out or delegation state. After the one terminal-turn checkpoint, the parent Goal makes an internal suitability judgment and may choose one or more `long_task_implementation` instances only when the host can explicitly select that exact custom-agent profile and bounded independence plus implementation/localization benefit exceed coordination cost; parallel writes require disjoint owner/path/source-of-truth boundaries, and high-coupling work stays with the parent. A generic/built-in/null/unknown type, task name, prompt imitation or model-only selection is not the profile. If exact selection is unavailable, or an exposed spawned type is not exact, the parent executes or redoes the packet itself with no agent retry. This is Goal behavior rather than workflow state: Harness neither depends on nor records the choice, worker reports are not Progress, Evidence or proof, and all outputs must converge into the selected verification workspace before any declared Check can count. The parent retains Source/Contract/Authority, architecture, Context writeback, integration, current-candidate checks, formal verification, Final Gate, close and completion ownership.

This is the concrete `F` boundary. It does not remove Source/Contract scope, Architecture Deliberation/Conformance, security, forbidden shortcuts, irreversible/external-action approval boundaries or Final Gate proof. It prevents those end-state and path-safety boundaries from being silently expanded into a universal fixed development sequence, method Gate, per-edit check cadence or agent scheduler. A new constraint is admissible only through the explicit protected-invariant decision and distinct-path/lighter-alternative/non-degradation/positive-ROI proof above.

## Why One Host Model-Change Checkpoint Exists

The host and user own the parent Goal's model selection, and Harness cannot switch the model of a running conversation or Goal. It therefore creates no dynamic model router, tier scheduler, retry loop, persisted route or acknowledgement state.

The first successful Compile is nevertheless a distinct cost boundary: Source, Contract, relevant Context, risk and acceptance evidence are now under Authority Lock. At that point the user can handle any desired model change in the host while the locked Contract, targeted repair and Final Gate continue to constrain completion.

Compile emits `execution_model_checkpoint.required: true` only for the first Authority Lock. The Agent always ends that turn before product implementation, file edits, builds or tests, even if an earlier message already described a model strategy. It asks the user to handle the model change in the host and then send `【继续】` or `[continue]`. That token resumes execution but does not attest a change: Harness cannot observe or verify the active host model. Later revisions return `required: false`; no repeated cost-only pause occurs.

This checkpoint is an execution-cost optimization enabled by the workflow's drift protection, not acceptance evidence. Host model handling and the continuation never prove a Claim or weaken Final Gate requirements.

The old implication treated any packaged model-specific worker surface as prohibited because it could become a second routing/control plane. The project owner now explicitly permits one narrower host adapter: `ty-context enable long-task` may install a fixed Codex-native `long_task_implementation` custom agent profile whose current model and reasoning effort exist only in the canonical package-owned TOML, with child-local multi-agent disabled and an exact `SubagentStart` boundary injection. It is usable only for bounded rolling implementation/repair after the parent Goal's checkpoint. The profile is static, stateless, optional and non-authoritative; it never becomes Source, Contract, Authority, Context writeback, Progress, Evidence, Receipt or Final Gate, and its absence, invalidity or a preserved same-path user customization cannot change the formal acceptance path. It cannot select models dynamically, classify tasks into tiers, spawn/retry agents, schedule work, create a branch/worktree or persist delegation/model state. An active-binding `PreToolUse` guard denies generic agent invocation unless the official current-call selector is exactly this profile; it performs no prompt/transcript/model inference, input rewrite, retry, substitution or persistence. Static installation still does not prove that the host selected the profile, and installing/updating the Hook does not prove that Codex/user trusted it; `/hooks` review is host-owned and Tiny Context cannot observe or persist trust.

> 禁止的是动态或持久化模型路由、模型调度和第二控制平面；允许的是一个固定、无状态、非 Authority、可缺席的 Codex 原生滚动实现 worker profile。

## Why Context Remains Mutable During Execution

`Context Delta` is not a one-time pre-Compile decision. The current Goal must re-evaluate `Context Delta` whenever implementation or repair discovers a durable fact and update the owning Context rather than freezing a known error until the end.

The verifier distinguishes two classes in referenced snapshot mode:

- **Controlling Context** includes core Context, every explicit `context_ref`, verification and deployment Context, and every other selected file whose semantics can change ownership, architecture, contract, risk, recovery or repeatable verification. A change always requires Authority Revision and invalidates affected proof, but it requires a user decision only when the compiled Claims, targets, proof obligations or another decision boundary change. A raw snapshot update with those locked semantics unchanged is mechanically bounded rather than a reason to interrupt.
- **Supporting Context** is limited to graph-derived, non-explicit `implementation-index` and `archive` files. These files improve navigation or preserve background material but do not define acceptance. Their content may auto-revise through `compile --revise` without user approval, and a supporting-only revision does not invalidate otherwise fresh targeted Progress.

Full snapshot mode treats every Context file as controlling. Explicitly referencing an otherwise supporting role also makes it controlling. This prevents the executing Agent from relabeling a requirement-bearing file as support to bypass Authority Revision. Final Gate still recompiles and binds the complete current Context snapshot, so supporting updates remain visible without becoming an acceptance authority.

## Why Contract Draft Authoring Is Integrated

An early design considered having Web GPT independently emit a complete Contract Draft before repository work. That scenario was abandoned because a complete Draft can exceed Web GPT's reliable single-response length; requiring one response to contain the whole delivery Contract would make completeness depend on output capacity.

Once work enters Codex, the same Draft can be revised continuously in the real repository. Keeping Draft authoring inside `long-task-workflow` also has six architectural advantages:

1. real repository and Context reads are required to bind owners, paths, runners, verification inputs, proof surfaces and Bindings;
2. Preflight findings can directly repair the same Draft;
3. no extra Skill handoff can lose Source meaning, repository evidence or unresolved findings;
4. there is less pressure to create a second plan, Authoring Authority or Authoring Receipt;
5. Draft-to-Compile remains a lifecycle transition of one object rather than a conversion between products; and
6. the Skill can iterate across as many responses as necessary, then continue through Compile, the one-time host checkpoint, rolling execution, verification and Final Gate.

The platform-neutral form of this rationale belongs in `PROJECT_SPEC.md`. The Web GPT-to-Codex history remains source-workspace rationale only and must not enter package-managed Skills or public consumer guidance.

## Why Source Authoring Merged Into Long-Task

The earlier separate authoring-service boundary existed so an external conversational service could prepare a high-fidelity proposal before Codex. Once external proposal generation moved to the initial-proposal boundary—and selected design resources had to join that proposal—the extra handoff no longer provided independent protection. It added manual intervention, duplicate context transfer and a place to lose design provenance while saving little token cost.

The useful semantics remain: full mixed-input inventory, direct/derived/delegated/evidence-backed provenance, preference-sensitive research, stable keys, surface/control/state completeness, exact risk facts and falsifiable acceptance. They now live in `long-task-workflow/references/source-authoring.md` as on-demand rules within the same Source-bound Contract Draft loop. A writable initial proposal becomes the real Source; conversation-only input materializes one project-native Source. Draft mapping can begin immediately, while provenance, Source repair and markers converge before Preflight/Compile.

This removes a service boundary without creating a Source schema, Authoring Authority, gate, Receipt, cache or state. Pre-existing user planning documents remain valid ordinary Source and are never rewritten merely for compatibility. Retired package pointers are no longer installed: versioned migration removes only exact former package bytes, preserves modified same-name content for manual review, and normal sync keeps no deleted-Skill registry or blind removal rule. Machine-assurance/recovery/audit requests route to `long-task-workflow`; otherwise the default Workflow Contract applies.

Keeping Source Authority does not justify keeping Source Authoring as an internal phase. The Contract cannot become the sole owner of missing meaning, but forcing Source completion before opening the Draft adds a serial pass without independent protection. The fail-closed invariant is instead a convergence deadline: real Source, provenance, markers, repository bindings and complete mapping must all be ready before Preflight/Compile.

## Why Workspace Scope Is Classified Before Activation

The immutable baseline protects later verification only if the first Compile cannot absorb an already-dirty undeclared file. A Verify-only `scope_escape` check detects post-lock drift but misses that first-lock path, while a Preflight-only fix can be bypassed by direct Compile.

One pure classifier therefore owns protected authority, declared expected change, allowed support, forbidden and unclassified path categories. Preflight and direct Compile classify `HEAD` to current workspace before first lock; later Compile/Verify/Final Gate classify immutable `initial_task_base` to current workspace. A bounded input collector enumerates only actual current package-asset files for configured managed destinations plus exact config/hook files during first enable; it never exempts a managed directory root or broad `.codex/**`. This shares semantics without adding schema, persistent classification state or a blanket package-directory exemption.

## Why Stale Progress And Execution Preview Stay Advisory

`progress_stale` means historical targeted evidence no longer describes the current authority/input snapshot. It is not a scheduler event and cannot know the cheapest trustworthy feedback path for every project. The current Goal may coalesce relevant edits and use project-owned incremental feedback, and refreshes evidence only before an intermediate decision relies on that Progress. It may instead continue implementation or enter Final Gate, which ignores Progress and reruns every Check.

`verify --explain` lowers feedback-planning cost by projecting selected compiled main Raw Execution groups and applicable Counterfactual executions without running them. It reports only declared execution counts and boundaries; it cannot promise elapsed time or reveal how many internal builds/processes a project runner may perform. Because it writes no Progress and produces no proof, it adds no acceptance bypass, execution mode or persistent state.

A second executing `diagnose-check` would still invoke the same opaque project runner while adding another execution surface and ambiguous evidence semantics. It is therefore rejected. The lower-cost generic combination is project-owned fast feedback during edits, preview before an expensive declared run, targeted verify at a useful stability/dependency boundary and Final Gate for acceptance.

Likewise, glob width and carrier/root reachability are semantic rather than syntactic. Authoring requires the smallest sound causal `input_paths`/Binding envelope and a defensible target-root route for every Counterfactual carrier, but a generic path-name linter cannot know whether `apps/**` is necessary or whether a language/runtime actually imports a barrel. Repository evidence may support the authoring decision; otherwise the current-execution Counterfactual is the proof. Runtime-specific readiness probes, build-cache invalidation, streaming progress/heartbeat and descendant-process cleanup stay with the project runner. This avoids false confidence and business-specific Harness logic while addressing the expensive-rerun cause before execution.

Preference clarification and delegation semantics are unchanged: ask only when an unknown priority would change research/recommendation; use current authoritative evidence for unstable claims; record defensible recommendations in real Source; and leave payment/contract/deployment/destructive/permission/sensitive-data/legal-security actions as external confirmations. Contract YAML cannot introduce unrecorded product meaning.

## Why Visual Design Authority Resolves Before Compile

A material production UI can satisfy functional checks while still inventing its information hierarchy, layout and component language from an unconfigured starter or style-only prose. Screenshot-checking that implementation against a baseline created from the same implementation is circular and cannot prove fidelity to user intent.

Long-Task therefore supplies the strong machine carrier for the shared selected-design obligation while reusing existing Source and authoring boundaries rather than adding a visual lifecycle. Before Compile, visual references are classified as exact targets, partial constraints or inspiration; `DESIGN.md` names the authored token source/generation direction; and every material surface either has sufficient selected authority, is explicitly scoped as a prototype/non-fidelity result, or records delegated design Source after material preferences are known. A missing or user-reserved visual direction remains `decision_required`.

The selected target must exist as Context-reachable Source or a frozen verification input before fidelity implementation is accepted. Exactly one canonical adoption record connects its stable key to interpretation, selection basis, readable immutable adopted version/digest, declared conditions and editable upstream owner/locator/update route: project/system/component-family targets live in `DESIGN.md`, while one-screen/interaction-specific targets live in the owning Screen Contract. Other layers retain pointers and applicability only. Each affected workflow opens the target before deciding. Updating it creates a new immutable version rather than overwriting the adopted baseline. Generated implementation screenshots and diffs remain artifacts and cannot promote themselves into target authority. Browser Claims use `ui_browser`; native/mobile/desktop Control proof uses `runtime_behavior` on its declared product target. A typed `design_conformance` record is distinct from `visual_render`: it binds the selected target identity and declared conditions to current actual/comparison artifacts, while the project verifier remains responsible for the comparison observation. This closes hidden-resource, duplicate-adoption, circular-self-baseline and undeclared-design paths without adding a visual Claim kind, resource registry, new risk level, second Gate, approval state or required design directory.

## Why Control Projection Expands Instead Of Adding UI/UX Workflow State

The remaining false-completion path is lossy authoring: interactive Source can state a control's task, visibility, availability, validation, default, navigation, recovery, permission and accessibility while the Contract preserves only coarse states. The executing agent then invents discarded semantics and a broad UI check may pass without proving them. Every actual Control therefore closes all 22 canonical fields through `field_coverage`: each field is exactly one of `specified`, explicitly `not_applicable`, or blocking `unresolved`. The Outcome also closes cross-Control/shared-state/navigation/permission/recovery meaning through `control_relation_closure`; specified relations become their own Claims, and an unresolved relation closure blocks.

Preserving fields alone is insufficient: a real delivery demonstrated that all Control Claims could be proven on a support browser while the required native root shell remained a placeholder, because deep-linked page Checks and resource-integrity checks bypassed the production entry/owner. The smallest fail-closed invariant therefore has two parts: every applicable Control field survives as one Source-backed Claim, and every declared Control belongs to an aggregated production `surface_binding` that fixes product target, owner surface, route/component Binding carriers and a root-entry real-user Check. Every Control Claim must have target-local proof; for each bound Control the root journey proves its navigation result when declared, otherwise its interaction, trigger or location fallback, through interaction plus target-runtime evidence.

Selected exact/constraint targets extend that same binding with frozen input files, named conditions, a root-entry conformance Check/Assertion and current actual/comparison artifacts. The binding's explicit blocker inventory preserves Source-item/method lineage plus its required target capabilities, and maps every declared design-acceptance blocker to a capability-qualified target-local machine Claim or target-blocking External Confirmation. An empty inventory means none were declared; it cannot waive a known blocker, whose removal instead requires revised Source and protected Contract authority. Compile rejects Controls without the binding closure, so older V2 Contracts with Controls receive an actionable semantic-migration diagnostic instead of silent proxy acceptance; Contracts without Controls pay no new authoring cost.

This projection reuses existing Controls, Claims, Technical Bindings, Checks, Assertions, External Confirmations, protected revision and Final Gate. Repeated fields may share a coverage row and related semantic Claims may share one Check execution, while each applicability/Assertion failure remains attributable. Its cost is grouped declarative closure per Control and one entry per production surface/target rather than one screenshot per field, plus conformance only for selected targets. It closes independent omitted-field, cross-Control, proxy-target, deep-link/root-entry, integrity-versus-conformance and unmapped-blocker paths with no runtime/state/recovery plane. A prose-only repair was rejected because the observed all-green delivery already satisfied prose guidance; a universal screenshot matrix and a separate UI registry/Gate were rejected for higher cost without stronger coverage.

Combined design-and-implementation work likewise reuses ordinary Outcomes, Stages and Authority Revision. Design Outcomes may author candidates before a selected target exists, but candidate/planned artifacts authorize no fidelity Claim. Selection first becomes real Context-reachable Source plus its owning Context/`DESIGN.md` reference; after Authority Lock its adoption is an Authority Revision that returns to rolling implementation. This keeps one Contract, one Active Authority and one Final Gate while preventing a planned-target bypass.

## Why Closure Is Explicit At Every Semantic Loss Boundary

Eight closure families address distinct false-negative paths without adding a second authority:

1. **Source ownership and architecture closure:** every non-empty Source line is inside a Material Item marker, the one formally parsed design-resource handoff block, or a closed-grammar background block containing only text-free anchors/horizontal rules or fixed-field provenance. Text-bearing headings, free-form provenance, unclassified, overlapping, malformed, material-background or invalid formal content block. At least one architecture-classified technical obligation is independently mapped and proved.
2. **Control and relation closure:** every canonical Control field and the existence/absence of cross-Control relations receives an explicit semantic state and exact applicability. Omission and `unresolved` cannot silently mean not applicable; a declared N/A relation closes through its own negative Claim.
3. **Atomic applicability and target-capability closure:** profiles name exact target, journey, one duplicate-free dimension assignment, Given condition/input/state keys and ordered When actions. Every actual Claim × profile × required-proof-surface cell is covered without bundled mutually exclusive values, representative/pairwise sampling or proxy-target substitution, and required targets expose the exact runtime capabilities their proofs need.
4. **Semantic-oracle closure:** each behavioral Claim-bearing Assertion has a same-Check claim-local `replace_json_value` or `replace_text` witness that changes only the asserted semantic field/fragment, plus a claimless target-runtime liveness Assertion that remains passing. Whole-file replacement, presence loss, unrelated artifacts, another Check and a broken target cannot masquerade as semantic sensitivity.
5. **Selected-design method closure:** every declared method × target × atomic condition cell has an independent positive Assertion, typed `design_method` evidence, a declared method record and a primary observation whose current path and digest are both unique. Playwright requires explicit per-project attachments for both artifacts; resource integrity/render presence cannot substitute for interaction, motion, reflow, input or accessibility meaning.
6. **Population closure:** the owning Check snapshots a real universe Binding and proves `universe = eligible = observed + valid exclusions`; a runner-created eligible list cannot self-attest the real population.
7. **Verifier and Context closure:** Authority freezes full `project_context/**`, runner identity and the supported direct-literal module/config/data dependency graph, while candidate inputs/outputs/artifacts remain explicitly classified Check runtime material. Non-literal loaders fail closed; undeclared indirect runtime access plus installed package/runtime/device behavior remains an explicit named TCB rather than invisible proof.
8. **Final-execution and terminal-scope closure:** Final Gate rejects stale accepted inputs, recompiles before and after all Checks and compares semantic identity plus raw Contract, Source, full Context, verifier/dependencies and verification/workdir inputs on one candidate snapshot. Any race or failed recompile blocks. Only `machine_accepted` with no pending External Confirmation is the complete-delivery no-drift terminal.

These mechanisms expand existing Source, Contract, Claim, Assertion, Counterfactual and Final Gate carriers only. They create no Source Inventory file, persistent applicability matrix, second Authority, second Gate, scheduler, receipt or generic semantic analyzer.

## Why The Generation Engine Stays External And Commissioning Remains Thin

The page-level authority model can consume rich design resources without recreating mature generation workflows owned by Open Design/Product Design, design platforms, image-generation, prototype and human design systems. A local prompt/template fork, required Resource Pack, provider-specific schema or registry would duplicate upstream logic, drift from live capabilities and still provide no implementation or acceptance authority.

Live Open Design 0.15.1 research established two thin adapters. MCP exposes design systems as `od://design-systems/<id>/DESIGN.md` resources and accepts `create_project.designSystem`, but has no creation tool; therefore `design-system-authoring` feature-detects future MCP lifecycle support and otherwise uses the official same-daemon generation/revision/accept API. It is explicit-only because cold-start visual direction is a user-owned product choice. Candidate, selection and adoption stay separate; project `DESIGN.md`/token/Context remain canonical and provider identity is synchronization only.

`design-resource-authoring` closes the scoped commissioning gap. Style-bearing work requires configured authority and verified provider binding; non-fidelity structure/flow/state work does not. Candidate implications remain task-local until selection, then accepted decisions are reconciled into the initial proposal once. For an implementation Web/App handoff, the commission also requires a machine-readable canonical entry, an exact dependency closure, complete non-truncated retrieval, immutable digests, stable typed locators and explicit reachable state/interaction/responsive/motion/accessibility/asset facts for every claimed condition. PNG or a provider-success response may supplement that source but cannot be its only implementation representation.

The remaining independent gap is semantic and causal loss between provider output and downstream implementation/proof. Direct visual inspection can overlook or reinterpret layout, component anatomy, states, transitions, motion, breakpoints/input and accessibility. Free prose can omit a category; hashes can authenticate a file whose locator is fictional; one coverage row can falsely span a subject's unrelated targets or conditions; and a verification-method name or blocker key can exist without any proof carrier. Conversely, manually retyping every CSS/property value creates a drifting second fact source.

The admitted mechanism therefore has three owners:

1. the canonical implementation source owns directly code-expressible layout, size, style, content, state, interaction, responsive, motion, semantic and asset facts;
2. one strict provider-neutral `design-resource-handoff-v1` residual index owns scope, applicability, product semantics, exclusions/unresolved meaning and downstream indexes while referencing canonical facts through preflight-resolved typed locators; and
3. the consuming workflow owns production consumption through one carrier: task-local project checks plus Contract Conformance by default, or existing Contract Claims, Controls/`surface_bindings`, method-specific Assertions, typed evidence and Final Gate for Long-Task.

Shared design Source authority follows the same boundary. Source profiles prove complete canonical entry/dependency/manifest acquisition. Frozen Inspector inputs/Census, explicit axes/subjects/properties, Cartesian Fact Cells, all property-required proofs, generation counts/digests and exact manifest↔handoff equality prove the declared input universe is indexed or honestly blocked; exact targets add full-target layout/pixel Facts. Default work opens affected targets and conditions, routes them to production owners and current-candidate project checks, and reports conditions those checks do not establish without rebuilding exact production Fact/proof accounting. Long-Task binds methods to independent Assertions with canonical per-Fact expectations and exact current results; blockers retain Source/method/capability lineage. Final Gate remains the sole Long-Task carrier. Authoring/preflight proves input closure relative to named TCB only.

The provider decision follows independent-benefit ROI rather than format preference. Figma is useful when an existing design authority/team needs native Components/Variables/Variants, shared libraries, Dev Mode or Code Connect, but paid seats, MCP quota/authentication and second-representation synchronization make default Open Design-to-Figma conversion unjustified. Penpot is compelling when open/self-hosted multi-user design infrastructure is itself required, but its service/plugin/file/deployment/backup boundary likewise does not replace enforcement. OpenPencil is a low-cost MIT local static-layout sidecar, while its current prototype-flow, trigger/action/overlay and motion-model gaps prevent it from serving as the sole eight-dimension source. These tools remain optional upstream adapters; no provider-specific Resource Pack/schema/registry, new Authority or new Gate is admitted.

## Why One Contract And One Final Gate Remain

Draft Outcomes make rolling work cheaper to reason about, but they do not create separate authorities. The first successful formal Compile locks the complete Contract, including all Outcomes. Targeted verification is repair evidence for selected Checks or Outcomes and never accepts the task.

Final Gate rechecks all Global and Outcome Checks on one current snapshot. This prevents local passes, stale passes or historically compatible results from being aggregated into completion. There is always one selected delivery, one Contract Authority and one Final Gate.

## Why Engineering Quality Reuses The Final Gate

Long-Task shares the same thin engineering-quality obligation as default work: one visible repository-bound Architecture Deliberation before implementation includes triggered quality attributes or concrete preservation, Goal-owned implementation keeps the shared boundary/failure/abstraction discipline, and one current-candidate Engineering Quality Conformance includes Architecture Conformance after project verification. The deliberation is not a promise of universal future-proofing; it makes owner/source-of-truth/dependency/lifecycle/alternative/future-change/debt/check conclusions observable and routes durable results to Context.

Material, falsifiable conclusions already fit the Contract's Technical/Global authority: Source-backed obligations, constraints and forbidden shortcuts, owner/path envelopes, Bindings and project-owned executable Checks. When functional behavior can pass while one quality invariant fails, that invariant receives its own Assertion rather than an aggregate quality Boolean. Final Gate already recompiles that authority and reruns every Check on one current snapshot. Adding a second quality Gate, field, Receipt or default Contract Conformance pass would duplicate ownership and runtime cost without closing an independent false-completion path.

The invariant is therefore single-carrier: before Authority Lock, architecture and applicable engineering-quality conclusions that matter to acceptance are declared through existing fields; after implementation, only Final Gate may accept that declared, falsifiable, project-check-bound set. It does not prove overall code quality. A changed candidate, check input or authority invalidates the Gate and reruns the existing freshness path. Subjective quality remains engineering review, while undeclared or unforeseeable requirements remain outside machine proof.

## Semantic-Drift Closure Index

The anti-semantic-drift design is indexed by the following stable mechanism keys. They are sections of the one Contract and the one Evidence Kernel, not additional plans, authorities, receipts or workflow state.

- `LT-STAGE`: Source-declared ordered delivery stages group vertical Outcomes. A stage names one gate Outcome; the Outcome DAG must make that gate depend on the rest of the stage and make later stages depend on earlier gate Outcomes. Every required target is proved at the gate from its root entrypoint, and a multi-Outcome stage additionally declares cross-surface consistency evidence. Stage readiness and status are derived from existing Progress, never persisted separately.
- `LT-TARGET`: the task declares one precise target profile, its non-empty `required_target_refs`, and the execution targets that matter to it. Each required ref resolves to a product target with a runtime family and root entrypoint. A Check binds to one target and declares root or internal entry. Every Stage Gate and critical journey proves every required target; a passing Web/process route therefore cannot satisfy an unproved Native target.
- `LT-EVIDENCE`: every Assertion declares an all-of set of evidence capabilities. `presence` proves only static presence; behavioral capabilities require exactly one typed current-execution evidence record per declared capability. Records are bound to the Assertion, Check, target and artifact hashes where applicable; cross-surface records use distinct `surface_ref` values and may cover multiple surfaces inside one runtime target.
- `LT-SOURCE-CLOSURE`: every non-empty Source line has explicit Material/background/formal ownership; only Material Items project to `source_claims`, while unclassified text and malformed formal structure block.
- `LT-APPLICABILITY`: each Claim declares exact target/journey/Given/ordered-When applicability refs; a Claim-bearing Assertion has arity one, names one ref and must match the Check. Every applicable ref receives required-polarity and all-of proof-surface coverage.
- `LT-CONTROL-CLOSURE`: every actual Control closes all canonical fields and the Outcome closes cross-Control relation meaning as specified, explicit not-applicable or blocking unresolved.
- `LT-SEMANTIC-WITNESS`: behavioral Assertions require same-Check semantic replacement sensitivity and an independently preserved target-liveness Assertion.
- `LT-SCENARIO`: every Check declares one atomic Given/When scenario. Runtime evidence names the executed Given states and ordered actions; a materially different success path belongs in another Check or Outcome.
- `LT-PATH`: every Outcome declares whether success and degradation paths are required, and every Check declares its journey role. A degradation, recovery or unavailable result cannot prove the Outcome Result Claim or substitute for a required success Check.
- `LT-EXTERNAL`: external confirmations declare a kind, impacted Claim refs and whether they block the selected target. Functional prerequisites must block it; production-only gates do not block a lower target. Reclassification or impact removal is protected Authority change.
- `LT-ADEQUACY`: the existing read-only Preflight/Compile kernel checks stage closure, target/runner compatibility, scenario/evidence completeness, success/degradation separation, external impacts and risk-proportional conformance coverage before Authority Lock. There is no new lifecycle Gate or reusable adequacy receipt.
- `LT-CONFORMANCE`: an independent read-only Global product-conformance Check is required only when weak observability combines with multiple stages or multiple required product runtime families. It uses a distinct Raw Execution, starts from a declared root product target and participates in the existing Final Gate; a simple single-stage/single-family delivery keeps the cheaper existing sensitivity path. It is distinct from the shared Engineering Quality/Architecture Conformance obligation and is veto evidence, not a second acceptance authority.
- `LT-UI-SURFACE`: Controls require an aggregated production surface/product-target binding to existing route/component carriers and a root-entry real-user Check. Selected exact/constraint targets additionally require frozen inputs and typed `design_conformance`; explicit blocker dispositions reuse machine Claims or blocking External Confirmations. A support target, detached/deep route, resource-integrity result or render-only artifact cannot substitute.
- `LT-REVISION`: Authority change and user decision are separate. Monotonic strengthening, raw Source/Context snapshot updates with unchanged locked meaning, operational Runner/input repair, repository-bound scope expansion and machine-proven equivalent failure interception may auto-adopt; lost target/Claim/scenario/Evidence Capability/failure coverage, semantic/external/forbidden-boundary or verifier-kernel change and unknown reasons fail closed for one exact decision. Every pending decision derives a self-contained human brief from the canonical hash-bound summary, and every adopted revision returns to rolling implementation and invalidates affected evidence.
- `LT-TERMINAL`: terminal projections keep the existing workflow status vocabulary and additionally name the accepted target profile, target state and derived stage results. This removes ambiguous `machine_accepted` meaning without adding a second completion state machine.
- `LT-FINAL-INPUT-RACE`: Final Gate recompiles and compares all protected semantic inputs plus raw Contract bytes before and after Check execution; any concurrent change or second-Compile failure blocks.
- `LT-ROI`: first prove coverage/False-Negative non-degradation and non-bypassable acceptance boundaries; then admit a candidate to consideration when incremental purpose benefit exceeds all incremental costs. Positive ROI is not automatic adoption.
- `LT-IMPLEMENTATION-FREEDOM`: `F` keeps implementation sequence, methods, local feedback cadence and optional one-agent/multi-agent execution Goal-owned while all Authority and final-proof boundaries remain binding. Stages/frontiers never grant edit permission, delegated reports never become proof, and no Harness scheduler/state exists.

The evidence envelope stores bounded hashes, identifiers, changed-field names and artifact references rather than unrestricted raw payloads. Capability-specific observers remain project-owned and frozen as verifier authority; the Harness validates their declared structure, current execution, target binding and cross-record invariants but does not claim hostile-verifier attestation.

## Why Live Target-Runtime Feedback Reuses Existing Checks

A same-snapshot Gate is only as truthful as its declared Checks. When a result can pass on a proxy surface while failing in its target runtime, rereading a tracked status report during Final Gate reruns the reader, not the target. The accepting Check must therefore exercise the declared target during its current Raw Execution and derive the asserted Observation from that session. Historical reports, screenshots, binaries and logs remain review artifacts; build, install, process start or absence of fatal logs prove only those exact claims unless a product-owned sentinel or interaction is also observed.

The same Check belongs to the earliest Outcome that owns the first runnable target boundary instead of a terminal omnibus Outcome. Its declared execution target, root/internal entry mode, `input_paths`, Binding carriers, verification inputs and environment requirements bind the runtime-affecting surface. The first useful runnable slice and later coalesced relevant changes are the cheapest default feedback points when early localization is worth the run cost, but the current Goal owns that cadence. No targeted pass gates later implementation; a fresh Progress record is required only when an intermediate decision relies on it. Identical Raw Executions may still deduplicate, and a full target rebuild is not required per Outcome or per edit.

Live Check ownership plus the one Final Gate close the false-acceptance path from a current snapshot containing stale self-reported runtime status. Early targeted cadence closes no additional completion path; it is retained only as an adaptive late-rework cost recommendation and may be deferred or skipped. The bounded runtime-family and entrypoint schema prevents a browser or internal route from silently standing in for a native/root journey. Capability-specific probes remain project-owned and are required only for the Claims that need them. Targeted results remain repair-only; stale or absent Progress may enter Final Gate because that Gate reruns every declared live Check on the final snapshot.

## Mechanism Admission And Cost Boundary

A Long-Task change begins with the controlling design purpose and accounts for total cost by explicitly including the cost of introducing the change in its ROI judgment. A change to mechanism semantics, invariants, authority/proof boundaries or runtime behavior modifies the mechanism and its verification; a change that does not affect a mechanism stays at its owning point instead of being promoted into one.

A mechanism is considered only after proving `Coverage_new ⊇ Coverage_old`, `FalseNegative_new ⊆ FalseNegative_old`, Authority/fail-closed non-bypassability and complete-current-final-snapshot proof. It then needs a concrete insufficiently covered false-completion or delivery-drift path, a testable invariant, fail-closed behavior and positive ROI: incremental purpose-fulfillment benefit greater than all incremental Authoring, Runtime, State, Recovery, maintenance, test, process, introduction and migration cost. Positive ROI admits a candidate to consideration and never adopts it automatically. Prefer measured data, benchmarks or operational evidence. When none exists, discuss the decision with the user or project owner; rigorous causal reasoning plus simple, bounded validation is sufficient. The Long-Task Workflow itself began from that logic-and-basic-validation standard rather than mature longitudinal data. Unsupported intuition alone is not sufficient.

With the design purpose fixed, non-degradation proved and ROI positive, prefer stronger purpose fulfillment when total cost is comparable, or lower implementation and operating cost when purpose fulfillment is comparable. Prefer a cohesive one-time change when partial mechanisms would preserve semantic seams or create more aggregate migration and maintenance cost.

Review must identify the path, invariant, proof, overlap with existing mechanisms, the risk reopened by deletion, total cost, net benefit, fail-closed behavior and whether the proposal creates a second Authority, second plan or scheduling plane. This review is a design and code-review principle, not a matrix file, Receipt or runtime Registry.

The same review protects `F` against ceremony growth. A proposed fixed implementation phase/order, method Gate, mandatory per-edit/per-Outcome verification cadence or agent-allocation/orchestration rule must first show an independently uncovered safety, irreversible-effect, false-completion or total-cost path and why the existing final proof or a lighter project-owned check cannot cover it. It then needs explicit project-owner design-purpose authority, unchanged acceptance coverage/false-negative strength, preserved Goal ownership/no delegation proof or state, and positive net ROI. Otherwise it remains optional Goal behavior or stays outside the workflow.

The rule has two independent decisions. Route selection is explicit and assurance-driven: absent a binding or selection, any task remains on the artifact-free default Workflow; when machine completion authority, recovery or auditability is required, even a small task may select Long-Task and pay one complete Contract, rolling repair and a current-snapshot Final Gate. Inside Long-Task, `auto | standard | strict` remains risk-proportional and raises proof only on affected high-risk Outcomes. Internal risk may rise automatically or explicitly and cannot be downgraded by the executing Agent, but it never auto-activates Long-Task.

Affected-test selection follows the same rule. It shortens the developer feedback loop by mapping known hot spots to focused tests, widening unmapped Long-Task runtime changes to the canonical Trust Boundary Gate, and widening shared package, dependency or unknown changes to the full suite. One plan executes only its highest aggregate, so complete coverage supersedes a redundant Trust invocation. Inferred local discovery omits and reports only untracked `.work_products/**`; tracked or explicitly supplied paths remain inputs. Reviewed Trust/focused/hotspot budgets, a small stable critical-semantic mapping and the environment-bound `github-ubuntu-v1` profile prevent silent semantic/cost growth while complete discovery stays exhaustive. These mechanisms are fail safe and never replace complete CI/release gates or the workflow Final Gate.

Phase 4 runtime reduction and its anti-degradation closure stay below the acceptance boundary. A deterministic build-input fingerprint prevents stale `dist` from consuming a suite run; an immutable process-scoped fixture seed removes repeated Git initialization while each test still owns a copied repository, and those disposable copies locally disable optional fsync plus automatic maintenance/GC without changing production Git policy. Bulk revision field/semantic permutations execute through the canonical compiler's state-free diagnose mode and decision projector while existing real CLI, pending, protected-failure and adoption cases retain process/persistence coverage; verifier migration reuses one disposable package through actual locator renames and exact-byte restoration while bundle/schema/Hook identity, content-specific Verify and protected Compile remain live. Terminal sentinel coverage and per-file/top-10 timing derive from the same current event stream; concurrency applies only to explicit proven-isolated files while every unknown file fails closed to serial. The opt-in performance probe reuses the canonical schema-sensitive Global fixture, runs small semantic fixtures before the large repository, separates default/Windows catastrophic profiles and counts a shared runner only once. `resume` completes the workspace status/fingerprint, including its index-writing phase, before observing current Git state against the same repository; independent fixture repositories remain eligible for bounded concurrency after a real shared-seed probe. Stable IDs protect only independent critical invariants rather than freezing every test name, and Trust membership derives from the same records. These mechanisms reduce recurring cost and protect the design purpose without a duplicate classifier, persistent worker, cached result, retrying Git locks, weakened current-snapshot proof or a test authority/scheduler/state plane.

Authority Revision and terminal guidance use the same cost rule. The former `reduction_reasons == approval_required` rule paid a human interruption for execution repairs even though exact identity, evidence invalidation and Final Gate already carried the safety cost. The revised derived policy retains those protections but asks only for real user-decision reasons; Rev3-Rev36 read-only replay projects 33 approvals to two decision events (31/33, 93.94% fewer), and Rev12's exact existing instruction removes the duplicate prompt so only Rev3 needs a new question. This evidence is a regression corpus, not permission to auto-classify an uncertain change: missing preservation proof remains fail closed.

The implementation adds only derived fields/classification and tests. It adds no command, persistent state, editable review artifact, instruction ledger, native-Goal state, second Gate or positive Agent-judgment proof. Before asking, an Agent may mechanically relay an explicit current task instruction only when it exactly covers every listed decision reason; generic blanket authorization or inference cannot. Candidate diagnosis stays stateless so withdrawn identities do not produce questions. This yields positive ROI: negligible runtime/recovery cost versus removal of repeated high-cost interruptions while the unchanged Final Gate still proves the adopted snapshot.

When a rolling blocker motivates revision, implementation difficulty alone cannot move a machine-verifiable requirement behind an External Confirmation or erase it. A real scope change is marked Source meaning and follows Authority Revision; repo-bound implementation scope alone may auto-adopt, while any Product/Claim/target/acceptance/external boundary change requires the exact user-decision identity. After adoption, affected weak-observability or high-risk Outcomes pay an adversarial evidence review: the Check must reach the furthest independently failing boundary named by the Claim, provide the declared capability records, and use a causal Counterfactual or failure/input-variation record when carrier presence alone can diverge. Risk-proportional review is enforced by the existing activation kernel and Final Gate rather than a universal runtime suite.

Because it closes no independent Final-Gate false-completion path, cadence stays Goal-owned and advisory; no targeted pass is required before later edits or Final Gate, and no per-Outcome rebuild rule, scheduler or new state exists.

## Trusted Results And External Pending

Machine authority has only two trustworthy outcomes: fresh evidence on the current final snapshot proves all declared requirements and ACs, or at least one item is unsatisfied, unverifiable, insufficiently evidenced, stale or externally pending and the delivery remains explicitly unfinished or qualified.

`machine_accepted_external_pending` means the machine-verifiable scope passed while external confirmation remains. It is not `AcceptedDeliveryTerminal`, is not complete external delivery, must be reported with the pending confirmation, and is not a vague third completion state. The strongest valid implication is `machine_accepted_external_pending => MachineVerifiableDeclaredDrift = empty`; no full `DeclaredObservableDrift = empty` claim is authorized.

That qualification must remain continuous after Final Gate. Collapsing it into `last_gate_passed`, `{}`, or generic `closed` reopens a false-completion path for callers that only see status, a resumed session, the Stop Hook or close output. The accepted workflow status therefore propagates through each surface; stale Receipts lose their accepted projection, while external confirmations remain visible as current Contract declarations. Stop/close can end the machine Authority lifecycle without tracking external work, but their output cannot convert machine acceptance into complete external delivery.

Progress, status, Receipts and compiled cache are audit/recovery projections. Candidate diagnostic results are transient repair output and are never Progress or completion evidence. Source, Controlling Context, Contract, verifier, runner or workspace drift stales affected evidence. Supporting-only Context revisions may preserve scoped Progress, but every adopted protected revision invalidates derived evidence; `resume` restores current semantic state rather than a physical Turn, and historical or candidate evidence cannot be spliced into current acceptance.

## Known Limits

- The workflow cannot prove that the user declared every real requirement.
- It cannot guarantee that a model completes implementation or avoids intermediate drift.
- It cannot switch or verify the model selected by the host, and it does not observe or persist platform-internal delegation beyond official start-time boundary injection.
- It accepts only declared, falsifiable machine authority; CI, deployment and human product acceptance remain external.
- It trusts the installed project verifier and cannot semantically inspect whether an oracle truly exercised its claimed target; current-execution target proof is therefore a Contract-authoring and verifier-quality invariant, not hostile-verifier attestation.
- It cannot infer requirements the user never expressed or prove an arbitrary external Inspector/Oracle semantically sound. Formal authoring must derive the scoped obligation universe, freeze declared Inspector inputs/capabilities/Census and preserve explicit blockers; unsupported/unreadable facts fail closed, while hostile or omitted Source remains outside the theorem boundary. `surface_bindings` and per-Fact evidence make declared meaning machine-checkable only after those premises hold.
- Local mode trusts the installed verifier and Git metadata and is not a hostile-host security boundary.
- Complete current-snapshot verification costs time; assurance-driven route selection plus risk-proportional internal proof and affected developer tests keep unnecessary cost off the default route without weakening Long-Task acceptance.
