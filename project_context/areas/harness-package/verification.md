# Harness Package Verification

## Developer Feedback Tiers

Use the cheapest reliable feedback loop for the current change, then widen before release. These commands optimize development feedback only; they do not replace complete CI/release gates, the project tests declared by a Delivery Contract, or the Long-Task Final Gate.

- `npm run test:affected:list`: inspect the deterministic plan without building or running tests.
- `npm run test:affected`: discover changed paths, build at most once when required, and run mapped focused tests. In inferred local discovery only, untracked `.work_products/**` scratch is omitted and reported; tracked changes and explicit `--path` values are never omitted. Known bounded Long-Task hot spots select named regressions; the shared non-UI semantic Fact runtime and shared fixtures widen to the complete Long-Task suite; unmapped Long-Task runtime changes fail safe to the Trust Boundary Gate; package/dependency or unknown changes fail safe to complete suites.
- Deleting any direct `tests/ty-context/*.test.mjs` changes verification coverage, so affected routing fails safe to the complete release regression. It must never represent a deleted direct test as a successful selected plan with zero tests; a delete-plus-add rename pays the same low-frequency full-suite cost without rename inference.
- `npm run test:long-task:focused`: one-build focused Long-Task regression loop for Context evolution, authority/progress, design boundaries and workflow entry points.
- `npm run test:delivery-contract:focused`: one-build focused Contract authoring/compiler/coverage/risk loop.
- `npm run test:affected -- --no-build`: reuse `dist` only after a deterministic build-input fingerprint proves it was produced from the current package source, TypeScript configuration, package metadata, lockfile and fingerprint owner. Missing or stale metadata fails before any test starts.
- Package CI runs a lightweight `windows-latest` real-subprocess probe for the affected-test npm launcher; Windows must route npm through `ComSpec` rather than spawning `npm.cmd` directly.

Affected and focused results are non-authoritative developer feedback. Before release or any claim that the package is fully validated, run the complete package, source-parity, smoke, pack and release gates below.

## Suite Purpose And ROI Design Index

Package verification has three executable tiers with distinct purposes:

- affected and focused commands are non-authoritative task-local defect localization;
- `npm run test:long-task:trust` is the bounded Long-Task Trust Boundary Gate for high-impact false-completion and cross-module regressions after the candidate diff is frozen;
- `npm test` is the complete default plus Long-Task release regression for one final candidate.

`affected-test-plan-v2` reports `developer-feedback`, `trust-boundary` or `release-regression` plus its discovery source and reason. Stable discovery sources include `explicit-paths`, `local-worktree`, `local-head-parent`, explicit/environment bases and CI base SHA/ref forms. Explicit paths bypass inference; dirty local discovery uses only the current worktree; clean local discovery uses `HEAD^`; explicit/CI bases are exact and fail closed when missing. Inferred local discovery reports `ignored_untracked_local_artifacts` when it omits `.work_products/**`; comparison-tracked and explicit paths remain visible. An unmapped Long-Task runtime change widens to the Trust Boundary Gate while retaining affected tests not already contained by that gate. Every current or future `semantic-fact-*` / `long-task-semantic-fact-*` runtime owner and every shared Long-Task fixture instead widens to the complete Long-Task suite, because they can alter default authority or proof behavior across otherwise unrelated consumers; package/dependency boundaries and unknown changes continue to widen to complete suites.

Pull-request Package CI builds once and runs the complete default suite plus the Trust Boundary Gate through package `test:trust:built`. Its changed-source modularity check resolves the fetched PR base explicitly; a non-main push instead uses the exact valid `event.before` commit and falls back to the current `origin/main` merge-base only when that commit is unavailable, so an empty PR-only field can never become an `origin/` pseudo-ref. `main` and release preparation retain `npm test`. Trusted Publishing runs that complete gate exactly once in its prepare job, then the protected publish job reuses the same uploaded tarball and runtime attestation without rebuilding, retesting or repacking. Every package-suite runner emits ephemeral `test-suite-timing-v2` diagnostics with one terminal record per selected file, exact critical-sentinel coverage and a deterministic current-run top-10 slow-file summary; PR, main and publish upload those same-run reports without another test command. Controlled GitHub Ubuntu CI selects `github-ubuntu-v1`, whose 120/240/600-second suite ceilings reject unknown profiles or runner mismatch; no profile means local diagnostic timing without a cross-machine budget claim. Timing output is never Context, workflow state or acceptance authority.

The canonical affected plan executes exactly one highest selected aggregate. A complete Long-Task or release-regression selection contains the Trust files and therefore supersedes a separate Trust invocation; no persistent run history is needed or allowed to enforce this inside the canonical command.

The complete suite is not an edit/fix loop. Run it zero times during ordinary repair and once after diff freeze when routing or release requires it. After an aggregate failure, tracked source/test/config/shared-runner changes, suspected cross-suite contamination, or a run that itself owns the final validation claim must regain one clean complete pass on the newly frozen snapshot.

A proven local environment-only failure may stop at the failed test plus affected/Trust repair evidence without repeating the local complete suite only when tracked verification inputs are unchanged and a guaranteed downstream `main`/release gate will run the complete suite. The local aggregate remains failed and must never be reported as fully validated; without that downstream gate, a clean complete rerun is still required. A third run requires an explicit flaky, infrastructure or late release-mutation reason.

`dry_run: true` is an optional prepare-only diagnostic, not a mandatory rehearsal before a real publish. A real workflow dispatch prepares, tests, packs and smokes once; after the `npm-publish` environment approval, publication verifies the same workflow artifact against the dispatch commit, stable lockfile identity and tarball SHA-256. Node/npm versions are recorded as build provenance but the publisher job need not reproduce them because it never rebuilds. Lockfile identity normalizes CRLF/LF only; semantic or other byte changes still fail closed.

Sub-second status/resume budgets belong only to the `default-v1` profile of `test:long-task-performance`; its original phase ceilings remain unchanged. The same opt-in probe selects `windows-v1` on Windows, using separately observed generous catastrophic ceilings for filesystem/process-sensitive phases and explicit large-seed/total-probe bounds. Functional release-regression tests assert behavior without machine-load-sensitive local or cross-environment wall-clock thresholds. The package aggregate wall-time guard remains opt-in, environment-specific and generously above the measured Ubuntu path; local aggregate runs remain diagnostic.

Canonical policy also sets reviewed maximums for Trust files, focused-tier files and one hotspot's mapped fan-out. It owns 26 stable critical-semantic records, including the four Observer/TCB entries `observer-admission-no-bypass`, `static-carrier-pre-run-freeze`, `host-derived-target-runtime` and `counterfactual-production-observation-impact`. The records derive 18 unique Trust files without another suite invocation; the four Observer records share one black-box attack/control file but retain one exact canonical tag each. Each selected suite must observe every required `[critical:<id>]` exactly once, in its reviewed file, with passing status; missing, equal-count replacement, duplicate, misplaced, unexpected or non-passing IDs fail the existing aggregate. Ordinary test names are not frozen. An intentional stronger replacement keeps the ID or updates the single record/tag/rationale in review. These guards never limit complete discovery or justify deleting an independent invariant.

Long-Task fixture initialization may prepare default and external-confirmation Git seeds once per suite process, then copy the selected immutable seed into each unique temporary fixture. Every copy retains its own `.git`, common directory, worktree, local config and refs, has no remote and cannot observe another fixture's mutations. Because these repositories are disposable test inputs rather than production data, their local config fixes `core.fsync=none`, `maintenance.auto=false` and `gc.auto=0`; this removes optional durability/background-maintenance cost only inside the fixture and does not override the repository under delivery. Direct single-file execution lazily creates the same seed semantics and removes them at process exit.

Bulk revision permutations use `long-task-authority-revision-fixture.mjs` to call the real compiled `compileDeliveryContract` owner in state-free diagnose mode and project its canonical proposal; no test-only classifier or pending state exists. Every reduction scenario and Product semantic address still asserts its raw diff/reason/decision, while the classification, diagnosis, progress and semantic suites retain representative real CLI/pending/protected-failure/adoption boundaries. Verifier migration copies one disposable package, uses actual directory renames for locator changes, restores exact bytes between bundle/schema/Hook mutations and retains one content-specific Verify plus all three protected Compile/pending proofs. That representative Verify is sufficient only while Verify's `assertVerifierAuthorityCurrent` and Compile both consume the component-complete `verifierAuthorityDiff` without component-specific enforcement; changing that owner or branch shape requires restoring per-component runtime coverage before adoption. `test-suite-runtime.test.mjs` guards the canonical link, bounded copy count and retained components/commands; the behavioral suites remain the authoritative evidence for their named properties.

File-level concurrency uses explicit reviewed classes only: 18 pure/static plus 49 proven isolated temporary-repository files enter the bounded safe lane at the reviewed default of two; 11 performance-measurement, Hook/profile, environment, distribution, verifier-migration, Git-race or Playwright/child-process lifecycle files use the serial exclusive lane. The pure set includes side-effect-free policy/authority-plan and delivery-verifier tests; the isolated set includes the real Observer/TCB lifecycle file and verifier root-directory test because each owns a unique OS-temporary repository and no shared process state. Lane membership is disjoint and exhaustive, a new file fails classification until explicitly reviewed, and `TY_CONTEXT_LONG_TASK_ISOLATED_CONCURRENCY=1` is the mechanical serial rollback. The default was enabled only after bounded representative A/B evidence. Complete runs temporarily moved four files to exclusive after load-amplified `index.lock` failures, but a later single-file-concurrency-one reproduction and Git Trace2 showed that `resume` itself overlapped same-repository `write-tree` and `git status`; after repairing and deterministically proving that owner boundary, those four files return to isolated only when the six affected files pass the real shared-seed concurrency-two probe. `long-task-delivery-compiler.test.mjs` and `long-task-playwright-trust-boundary.test.mjs` remain exclusive because their separate cross-file interference and Windows `EBUSY` evidence was not explained by the `resume` defect. `long-task-authoring-preflight.test.mjs` is serial because its explicit sub-two-second assertion is not meaningful under competing aggregate load. The runner never retries or deletes Git locks to manufacture a pass.

Workspace manifest and fingerprint capture serializes its index-writing `git write-tree` before its own parallel read-only Git discovery, and `resume` serializes the complete status snapshot before `currentGitState` may start `git status` against the same repository. Git Trace2 verification binds both owner-level ordering boundaries. Distinct temporary repositories remain eligible for bounded file concurrency; observed lock evidence first requires a same-repository trace diagnosis and may move a file to exclusive only when the owner boundary is already sound.

The implementation, migration status, measurement rules and stable retrieval keys are indexed in `docs/test-suite-roi-redesign.md` under `TS-PURPOSE`, `TS-BASELINE`, `TS-VERIFY-COST-2026-07-28`, `TS-REVISION-COST-2026-07-28`, `TS-TIER-DEV`, `TS-TIER-TRUST`, `TS-TIER-RELEASE`, `TS-ROUTING`, `TS-RERUN`, `TS-RELEASE-HANDOFF`, `TS-OPTIMIZE`, `TS-ANTIDEGRADATION`, `TS-MIGRATION`, `TS-METRICS`, `TS-AC` and `TS-NONGOALS`. ## Anti-Degradation Assurance Evidence

The assurance is a composition of independently scoped evidence, not a new aggregate result:

- The first mechanism-admission layer is the declared-purpose validity floor. Every high-level critical sentinel pairs an independently grounded correct candidate with a direct semantic wrong candidate, mutates the real owner carrier, localizes failure to its claimed boundary and retains must-allow controls. A reproducible critical false acceptance is frozen before repair, invalid behavior is excluded from the valid baseline and the affected capability claim remains downgraded until the counterexample, required current-candidate regression and controlled real replay close. Test/Fact/tag counts, prose review and green CI are not Coverage.
- `long-task-design-context.test.mjs` carries `[critical:mechanism-causal-chain-continuity]` and checks that stable design, owning Context, current implementation/proof index, authoring guidance and public/managed surfaces preserve one recoverable purpose–key-logic–implementation–boundary chain plus the explicit project-owner change rule.
- The same static owner carries the independent `[critical:implementation-freedom-boundary]` sentinel. It proves that `F` remains outside the `R1`/`R2` theorem as an adjacent protected efficiency boundary; fixed phase/order/method/per-edit Gates remain absent; optional one-agent or multi-agent/subagent implementation stays Goal-owned, non-authoritative and single-workspace convergent; and a new development-stage constraint requires a distinct uncovered path, lighter-alternative analysis, explicit owner decision, non-degradation and positive net ROI.
- Semantic-assurance, semantic-drift and lifecycle tests execute false-completion counterexamples against the current implementation. The selected-design exact sentinel includes positive V1/V2 controls plus explicit `actual != expected`, project `passed: true`/`verdict: passed` negatives whose ground truth is test-owned; it proves rejection and Harness recomputation at the exact comparison owner, not arbitrary observer soundness.
- Critical-sentinel policy makes deletion, equal-count substitution, duplication, relocation, an unreviewed ID or non-passing status fail the existing selected aggregate. Each rationale is limited to its executable positive/negative controls. The one existing registry protects a small independent invariant set rather than every test name and is never evidence by name alone.
- The runtime source guard proves that bulk revision permutations still call the canonical compiler/projector, that real CLI/pending cases remain, and that verifier migration retains one package copy plus its locator/content component and command boundaries. It guards owner/cost shape only; the owning behavioral suites still prove revision and verifier semantics.
- Affected selection sends known owner changes to focused evidence, unmapped Long-Task runtime changes to Trust and shared/unknown changes to complete coverage. Source parity, build freshness, Context/harness validation and CI/release gates cover distribution and current-snapshot seams.

These checks establish current repository evidence only for their declared invariants. They do not make Context authoritative over contradictory code, prove omitted requirements, validate an arbitrary external oracle, or prevent an authorized maintainer from deliberately weakening all specification/code/test owners together. Deterministic attacks prove known-path rejection; black-box Final Gate proves lifecycle behavior; sanitized-real replay proves realistic shape; fresh-Agent pairs prove only adoption and ROI. Any changed implementation or verification owner must update the implementation index and this proof routing in the same candidate.

The real-capability paired experiment freezes its case/guidance/threshold/schema and candidate-identity set in `tools/long_task_real_capability_roi_policy.mjs`, recomputes score/summary/provenance and metric validity in `tools/long_task_real_capability_roi_scoring.mjs`, and leaves ephemeral Codex process collection plus sanitized report I/O in `tools/verify_long_task_real_capability_roi.mjs`. The identity includes those three owners and every bounded observer implementation dependency. This split adds no result authority: deterministic attacks, valid controls, Trust/full regression, real replay and the sole Final Gate remain independently required.
