# Harness Context Model

## Role

This foundation Context defines the durable vocabulary and fact-source priority for the Project Tiny Context Harness source workspace. Read it before changing Context roles, durable fact placement, fact-source authority, Context/code/evidence priority or the meaning of Minimal Context recovery.

## Core Terms

- Harness is the portable managed guidance, Context templates, default Skills and validators that shape expected agent behavior; it does not own project quality or ordinary task execution state.
- Context is the durable project-fact system rooted in `project_context/**` and `DESIGN.md`: it lets future agents recover intent, ownership, boundaries and repeat-execution paths and traverse to decision-relevant project Source without copying that Source into Context.
- Minimal Context is the durable fact layer: the smallest repo-owned facts needed to recover project intent, ownership, boundaries and repeat-execution paths.
- **Context workspace** is an optional centralized directory namespace at `project_context/workspaces/<workspace-id>/**` for the durable non-code Context of one repository-relative implementation workspace/root. Every represented Context workspace maps exactly one code root through existing `[[areas]].root` and `context`; the mapping is one-way and sparse, so implementation workspaces without durable Context have no empty mirror directory. Package-manager/build configuration remains the complete code-workspace authority.
- **Area** is a durable product/technical responsibility and Context-ownership unit plus a discovery entry. A workspace-local Area belongs to one Context workspace, and one represented Context workspace may contain several Areas for distinct semantic responsibilities. Genuinely cross-workspace, repository-wide, shared or governance Areas stay under top-level `project_context/areas/**`; single-workspace and non-monorepo projects keep that existing layout. Neither Context workspace nor Area is a read/edit permission model.
- A monorepo's **default Area** normally owns only the repository-common recovery minimum at top-level `project_context/areas/**`. Workspace-local Context uses `on-demand` unless its facts are genuinely near-universal; directory placement alone never makes it default.
- **Expandable Context working set** is the files selected by core/default rules, manifest/trigger routing, bounded search and later semantic dependency discovery for one task. The first three routes establish a low-cost minimum, never a maximum readable set, access-control list or promise that every relevant dependency has already been found.
- **Context application boundary** is the honest limit that Context stores and exposes durable intended facts but cannot force a soft-guided Agent to use them correctly. Missing/unreadable/conflicting authority can fail closed; code behavior still needs project-owned evidence and review.
- Workflow Contract is the model-led default behavior layer for implementation work of any complexity: read core/default Context, combine manifest routing with one bounded Context discovery search, widen to required dependencies, identify all expressed material requirements plus key conditions/failure boundaries at risk-proportional depth, surface one Architecture Deliberation with triggered quality attributes or concrete preservation, decide one `Context Delta: none|required`, update durable facts first when required, use the agent's internal planning, implement under shared quality guardrails, run fresh project-owned verification, localize and repair failures, then perform evidence-bounded Contract Conformance carrying Engineering Quality Conformance including Architecture Conformance and a separate Context drift check.
- Tiny Context has three cooperating capabilities: Minimal Context owns durable facts; Workflow Contract owns lightweight model-led default behavior without machine completion authority; explicitly enabled Long-Task Workflow owns one Canonical Delivery Contract and verifier-derived, recoverable and auditable current-snapshot completion authority for a platform-native Goal. Complexity determines execution/verification depth, completion-authority/recovery/audit need determines route selection, and Long-Task's existing internal risk floor determines proof strength.
- Repo-owned intent layer is the durable project fact surface that tells agents which product, architecture, ownership and dependency facts outrank current-code convenience.
- Durable facts include product/domain ownership, surface responsibility, information architecture, API/schema semantics, state/runtime/recovery semantics, cross-domain boundaries, security boundaries and repeatable verification/deployment paths.
- Workflow Contract is the automatically applicable prompt-level order of thought when no Long-Task binding is active, not a validator, phase gate, artifact schema, edit-order gate, persistent workflow state, machine-completion authority or long-task detector.
- **Design Authority Check** is the conditional default-workflow routing step for material production UI. It reads relevant screen/surface Context, `DESIGN.md`, the declared authored token source/generation direction and selected design references before implementation. It is not a lifecycle phase, required document tree, generic pixel gate or new `Context Delta`.
- **Design Context Depth Model** separates durable UI meaning into global experience principles, cross-surface responsibility, Screen Context, Control interaction Context, `DESIGN.md` visual-system authority, versioned authored targets and repeatable verification. It uses existing Context roles and on-demand selection; projects instantiate only the depth they need.
- **Screen Contract** is optional project-owned area/subdomain Context for one durable screen/surface slice: stable surface/route identity, entry/exit/shared state, information hierarchy, semantic layout regions, navigation/interaction, state/responsive/mode variants, Control inventory and target/verification references. A cross-area screen interface may use `contract`; no new `screen` or `design` role exists.
- **Task-level UI/UX analysis** is non-authoritative reasoning for material page/flow/complex-control, information hierarchy, interaction topology, primary-work-object/task-loop, operation-object-feedback, client adaptation, recovery/state/accessibility and UI/UX audit decisions. It compares candidates under Product/Surface/Screen/Design Source and may identify a required owner update or genuine decision, but it creates no durable task-level UI owner, visual authority, acceptance carrier or Context write authorization.
- **Content-sensitive Skill routing** uses the task's material decision content, not only an explicit Skill name and not ubiquitous verbs. Material engineering/UIUX reasoning may activate the relevant role adapter even inside an implementation request; generic implement/fix/refactor wording, role/agent mentions and ordinary local code/test/docs/style work do not activate it merely by themselves. Context manifest triggers remain Context discovery metadata and do not implement Skill activation.
- **UI Authority Closure** is the material-UI reconciliation before implementation or Long-Task Compile. Each affected item becomes `context-covered`, `context-update`, `task-local`, `out-of-scope` or `decision-required`; stable surface/control/target keys connect Source, Context, `DESIGN.md`, targets, Contract and checks. It is order-of-thought guidance, not a file, table, delta, readiness state or second authority.
- **Design Resource Handoff Adapter** is the shared provider-neutral residual input boundary between `design-resource-authoring` and either development workflow. A final selected implementation handoff is ordinary marked Markdown Source containing one strict `design-resource-handoff-v1` block. Each implementation Web/App target declares a complete source profile: one machine-readable canonical entry, its exact dependency closure, complete acquisition and immutable repository-readable digests. The handoff uses typed, preflight-resolved locators to index canonical facts rather than manually retyping them, then closes every applicable stable subject × selected target × declared condition across surface/flow, visual/content, component/control, state/interaction, motion, adaptation/input, accessibility and assets. It owns missing/not-applicable distinctions, non-code product semantics, blockers, Source Items and project verification methods. Preflight fails on unresolved, unsupported, unaddressable, incomplete or stale input. Exploration remains schema-free. The adapter proves semantic-input completeness and resource integrity only; it creates no Context role, Design Authority, provider registry, workflow readiness state, implementation evidence or acceptance result.
- Selected-design Source authority activates when a selected implementation handoff exists. Every resource still has complete authoring/preflight fact/supporting closure, exact targets still carry full-target layout and pixel facts per declared condition, and Product Controls remain semantic units rather than the smallest visual fact. Default work opens every affected exact target/constraint, identifies declared conditions, Source Items, blockers, production owners and real journeys, runs risk-proportional project-native final-candidate checks, and reports any unchecked condition; it does not rebuild the complete Fact × method result universe. Long-Task alone projects exact fact refs into existing Claims, Assertions, `surface_bindings`, `design_conformance`/`design_method` and Final Gate. Unread, conflicting or unsupported authority blocks the affected default claim, while unproved exact obligations block Long-Task machine acceptance.
- **Non-UI Semantic Fact Closure** is the Long-Task fine-grained machine-assurance obligation for material non-visual requirements. Before implementation it derives a scoped Expected Semantic Fact Universe from authoritative Source, controlling Context and declared material inputs. A fact is independently addressable as `subject or relation × atomic applicability × atomic property`, with stable identity, provenance, typed value semantics, disposition and required proof. The subject census and relationship/dynamic-population closure cover both product/business meaning and technical/backend/architecture meaning; standard families are mandatory applicability questions and any discovered domain-specific family is a first-class custom extension rather than discarded prose.
- The non-UI standard families include actors/roles/tenancy/entitlements; domain entities/fields/relations/invariants/calculations; commands/queries/workflows/state/time; validation/results/errors/partial success; APIs/protocols/events/messages/jobs; persistence/cache/search/data lifecycle; transactions/consistency/concurrency/idempotency; failure/degradation/retry/recovery; configuration/flags/secrets; versioning/compatibility/migration/rollout; architecture/dependency/topology; performance/capacity/cost and reliability/SLO; security/privacy/safety/compliance/audit; integration/deployment/observability/runbooks; and applicable localization, billing, file/media, hardware/sensor and AI/ML semantics. A family may be inapplicable only with a fact-grounded reason.
- Applicability is atomic and extensible: actor/role/tenant, operation/journey, object/data case, precondition/state/transition, time/window, version/configuration/flag, environment/runtime/platform/deployment, locale/timezone, load/concurrency, permission/security/privacy, failure/degradation/recovery and other Source-required axes remain separately queryable. The workflow expands only meaningful combinations, records exclusions/equivalence without blind Cartesian explosion and never lets one aggregate label such as “all states” substitute for its enumerated members.
- Long-Task non-UI closure requires exact set conservation: Expected Semantic Facts equal Source-indexed Facts and Contract-projected obligations; required proof obligations equal current attributable results at acceptance. Each machine result identifies the Fact, actual observation, comparison rule and parameters/tolerance where applicable, verdict, Oracle identity and execution environment. Precise values remain in the unique authoritative Source/Context or located machine-readable input; the Contract carries identity, locator/digest and proof binding rather than a second value authority. A repository-backed text input digest is the SHA-256 of its exact checkout bytes, not an LF/CRLF equivalence class; the repository must therefore freeze those bytes across hosts. This repository's root Git policy uses `text=auto eol=lf`, leaving detected binary content untouched and requiring a narrow explicit override for any future file whose contract genuinely requires another EOL.
- Outside Long-Task, all expressed Source and controlling Context remain binding, but the default route uses model-led material-requirement reconciliation rather than a complete census, stable Fact/obligation identities, Cartesian applicability closure, frozen Oracle graph or exact-set proof. It identifies the requirements, conditions and failure boundaries material to the task; uses project-native current-candidate evidence in proportion to risk; and reports anything unresolved, unverified or externally dependent instead of hiding it in a complete claim.
- Source authoring may derive necessary logical consequences and record a delegated engineering choice when authority and tradeoffs permit it. It must not infer a user-reserved product decision, use current implementation as the intended reference, or hide uncertainty in a default. `decision_required`, `unavailable`, unreadable, unresolved, unmapped, unimplemented, unexecuted, stale, failed or indistinguishable applicable Facts fail closed.
- **Design Source Projection** classifies selected-resource meaning into its existing durable owner without copying the handoff: durable surface/flow and Screen/Control/state behavior belongs in Product Surface or Screen/interaction Context; durable visual-system, token, motion-policy and rationale meaning belongs in `DESIGN.md`; exact compositions, values, timelines, condition-specific facts and asset bytes remain in immutable targets; repeatable proof paths belong in verification Context; provenance, applicability cells, delivery blockers and proof bindings remain task/Contract Source unless they reveal a durable decision or risk.
- **Canonical Design Target Adoption Record** is the exactly-one durable record for a selected target's interpretation, selection basis, immutable locator/digest, declared condition coverage and editable upstream owner/locator/update route. Project/system/component-family targets are canonically recorded in `DESIGN.md`; one-screen/interaction-specific targets are canonically recorded in the owning Screen Contract. Other layers keep only the stable target key, canonical owner/anchor and their local applicability relationship.
- A design reference has one declared interpretation: `exact-target` authorizes fidelity comparison for its named surface/viewport/mode/state, `constraint` authorizes only the named partial rule, and `inspiration` guides exploration but proves no reproduction claim. An unconfigured starter is not production design authority.
- **Design Authority closure identity** keeps root `DESIGN.md` as the one Authority entry, human revision owner and first-release exact Token owner. A true legacy project has neither the canonical `bundle-v1` format marker nor `design_system/authority.manifest.json` and therefore has a one-file closure. An adopted sparse bundle records that durable format marker in the first non-empty body position of `DESIGN.md`; the manifest lists subordinate authoritative files and deterministic generated files and binds their complete normalized closure digest without copying revision or Token semantics. Marker and manifest must exist together, so deleting or renaming only the manifest is an invalid Authority rather than an inferred legacy downgrade. DRA recovery/handoff and Long-Task Source freshness compare the complete entry-plus-digest identity rather than revision text alone.
- **Authority Delta Assessment** is a non-authoritative DRA judgment that a selected task resource is consistent with current Authority, contains a task-only variance, or proposes an Authority delta. It creates no adoption state or Gate. A reusable cross-task variance must reach its real Screen Contract or Design Authority owner; an Authority candidate stops DRA and requires the user to start DSA and separately adopt a new closure before rebinding and verification.
- **Context-reachable Source** is a selected external or project-native artifact whose durable meaning is linked from its owning Context/`DESIGN.md` by stable target key to a readable immutable adopted locator/digest, declared coverage and an editable upstream locator/owner/update route. It remains ordinary Source, not a new Context role or registry. A relevant workflow must traverse and read an affected `exact-target` or `constraint` before making a material product, design, implementation or acceptance decision. Candidate/inspiration resources remain optional and non-authoritative.
- A full material Control may independently specify surface, region/location, type/label, user task, visibility/availability, trigger/input/validation/default, interaction/navigation, loading/empty/success/failure/recovery/permission/feedback and accessibility. Durable reusable fields belong to owning Screen/interaction Context; delivery-local fields remain Source/Contract meaning. Non-applicable fields remain absent rather than receiving invented filler.
- Internal plan means the agent's current reasoning about goal, boundaries, controlling Context, implementation surfaces and verification. It has no mandatory file, name or schema.
- **Context discovery search** is one bounded text search over `project_context/**` before `Context Delta`, using a small set of high-signal terms from the task such as explicit area/module names and API/schema/state/security/verification/deployment language. It supplements manifest triggers and semantic judgment, reads relevant matches and permits later widening when the task reveals another dependency; it creates no index, cache, state, authority or read boundary.
- **Shared Context Catalog** is the one immutable package interpretation of `project_context/context.toml`, registered Context, discoverable unregistered Context files, normalized repository paths, validation diagnostics and the deterministic default footprint. Every discovered file separates its NFC repository-relative public identity from the exact physical repository-relative spelling and absolute path used for I/O; one Catalog resolver maps public keys back to that discovered physical file, so consumers never reconstruct an existing path from an NFC key. File discovery and externally rendered diagnostics use public paths and explicit UTF-8 byte-order tuple comparison rather than locale or filesystem enumeration order. Validate, Doctor, the experimental Router and Context maintenance commands consume this owner instead of maintaining parallel Manifest or physical-path semantics. It is a read model, not a Context registry, persisted index, cache, permission system or Authority.
- Schema v4 continues to accept `default`, `on-demand`, `always`, `optional` and `never-default`. Current direct default selection admits only `default`; transitive `default_children` selection admits a referenced registered child regardless of that child's policy. The legacy values may receive diagnostics, but 0.10 does not reinterpret or automatically migrate them. A future two-policy migration is explicit: `always` requires a maintainer choice, and `never-default` plus an incoming default-child edge is a conflict to remove rather than a silent precedence rule.
- **Experimental Context Router** is a read-only, stateless and versioned diagnostic over the Shared Context Catalog plus a bounded literal scan of all eligible `project_context/**`, including clearly labelled unregistered files. Its file, candidate, ambiguity, unresolved, budget and diagnostic arrays have explicit stable ordering; path-bearing values use normalized repository-relative UTF-8 byte order and diagnostic ties use severity, path, line, code and message. Its deterministic candidates, costs, ambiguities and incomplete-budget diagnostics are neither Authority nor a Gate and do not replace the default Workflow's required bounded search until separately admitted by fresh-Agent effect/cost evidence and a Workflow Contract change.
- **Context mutation transaction** is the owner for Manifest/file/link maintenance. It validates a complete staging overlay, protects full current snapshots with cooperative compare-and-swap, journals a deterministic multi-file commit and exposes recovery without claiming cross-file atomicity, hostile-writer filesystem CAS or power-loss durability. Logical Context keys remain NFC and public, while every operation on a pre-existing file records and uses its Catalog-discovered physical repository-relative spelling; a newly created target may use the requested canonical spelling. Move's bounded exact-reference scan covers both logical and physical spellings in POSIX, root-relative, Windows and percent-encoded forms. CommonMark identity remains the NFC key, but rewritten destinations are calculated from the exact source and target physical spellings; Doctor, staging and live validation require each raw local destination to resolve on the real or staged filesystem to that exact Catalog file and never heal a missing lexical path through NFC lookup. The live executor and recovery hold the existing Active Authority lock across the complete non-terminal lifecycle; first Compile, revision adoption and activation acquire that same lock and revalidate the compiled candidate's complete Context, Source and Design closure immediately before binding. Lock release is conditional on the exact persisted owner token, and force-clear/reclaim refuses a live owner. Every immutable journal successor names its exact predecessor sequence and canonical digest and compare-and-swaps the same live journal snapshot identity. New v3 journals require a canonical NFC logical key plus its same-identity physical spelling for every file, so an older v2 binary rejects the new schema rather than ignoring the physical binding; current readers retain exact v2 recovery with `physical_path = path`. Journal identity uses canonical decimal BigInt fields and validates complete present-before, temporary, published-before and published-after bytes, mode and identity. Publication records the exact temporary identity before replacement and the resulting endpoint in the next generation; deletion first persists an exact-owned hard-link tombstone and never treats bare absence as an owned transition. Recovery validates one deterministic live transition vector against the journal's applied prefix and accepts only a complete recorded endpoint or that exact owned interrupted transition, so mode-only, same-byte inode, hard-link, temporary-file and second-CAS races fail closed. Pre-v2 journals, a crash after mutation temporary creation but before identity persistence, and any journal-publication temporary that is not the exact same-sequence, same-inode, two-link remainder of a published snapshot require explicit manual recovery guidance rather than inferred ownership or filename-based deletion. These guarantees cover cooperative concurrent actors and process-crash recovery on the tested filesystem boundary; directory/file sync remains best-effort on platforms, including Windows, that cannot prove power-loss persistence. `create` first publishes only an unregistered scaffold; `register` requires a recoverable node and lossless Manifest patching; `move` uses the same transaction owner.
- **Read scope** is the expandable Context/code knowledge needed to reason about the task. **Intended workspace set** is the task-local implementation workspace or workspaces the user intends to change, resolved from explicit user/product/path/repository facts; supporting/shared Context or code may belong to read scope or a justified supporting change without silently joining that set.
- **Default Target-to-Change Conformance** is a lightweight task-local check for repositories with more than one plausible product workspace/target. If durable facts cannot distinguish materially different sibling targets, product edits wait for one concise clarification; intentional multi-workspace work enumerates every intended workspace and supporting/shared envelope. The final candidate compares actual task-attributable changed paths with that envelope, using a project-owned scope verifier when available. It creates no target declaration file, registry, workspace schema, persisted state, generic path/import analyzer or machine acceptance.
- **Default Context byte budgets** are advisory observability for recurring attention cost, not information authority or acceptance criteria. A genuine near-universal fact stays readable in its correct default owner even when it exceeds the heuristic; `doctor` warns, while validation and source release tests must not force omission, opaque compression or false `on-demand` classification.
- **Context Anti-Degradation** is an effect-first mechanism-change rule, not a workflow result. A candidate must preserve or improve current recovery and meet the durable design-purpose floor before recurring read/search/maintenance cost or total ROI is compared. It protects recoverable owners and boundaries, trigger-miss fallback, expandable reads, read-versus-change separation, honest `Context Delta`, fail-closed controlling authority and the prohibition on result/evidence state in Context. The complete rationale and safeguard-admission test are owned only by `decision-rationale/minimal-context.md`.
- **Default Workflow Anti-Degradation** applies the same ordering to the automatically paid protocol. A candidate first preserves authoritative material-requirement/condition/owner/failure understanding, universal Architecture Deliberation, current-candidate verification/repair, single-carrier Conformance and honest qualified handoff; only then may lower prompt/tool/test/maintenance cost justify it. The default route never regains Long-Task's complete semantic-family Census, stable Fact/Obligation identities, exact-set closure, frozen Oracle graph, per-Fact results, Authority or machine acceptance. The complete purpose, efficiency and new-rule admission logic is owned only by `contracts/workflow-contract.md`.
- **Next Safe Action** remains a required recovery heading for compatibility and fresh-agent re-entry, but its content is a stable safe-entry rule rather than task-local progress, a transient todo or a one-off next edit. Making the heading optional requires conclusion-grade Context-recovery evidence; byte reduction alone is insufficient.
- Small code task means a local implementation task where existing Context is sufficient and the change does not alter durable product, architecture, API/schema/data, runtime/state/recovery, verification/deployment, security/redaction or surface-ownership facts. It is not defined by lines changed and affects only the depth/cost of default reasoning or Long-Task proof, never workflow eligibility.
- **Architecture Deliberation** is the externally observable, repository-bound pre-implementation checkpoint shared by default and Long-Task routes. Its occurrence is universal and its depth is risk-proportional; it creates no persistent artifact, state or authority.
- **Applicable Quality Attributes** is the risk-triggered quality subset inside Architecture Deliberation: correctness/maintainability always receive preservation, while reliability/resource lifecycle, concurrency/consistency, performance/capacity/cost, security/privacy/safety, compatibility/migration/rollout and operability/observability/testability expand only when Source/Context or changed code triggers them. It is not a stage, matrix, Gate, state or artifact.
- **Implementation Quality Discipline** is the small set of owner/source-of-truth, real-boundary, failure/resource and justified-abstraction guardrails used during Goal-owned implementation. It does not prescribe order, methods, per-edit checks or a machine quality verdict.
- **Engineering Quality Conformance** is the post-verification current-candidate closure and contains the architecture-specific `Architecture Conformance`. Default work carries it inside Contract Conformance and Long-Task work carries it only inside Final Gate for declared falsifiable project-check-bound invariants; it never proves overall code quality. Candidate, declared check-input or authority changes stale it. Architecture Context Hit and Decision Rationale Hit remain internal routing questions and create no additional deltas, Context roles, files or validators.
- Source-to-Context judgment is the internal classification of each external product, architecture, technical or acceptance constraint as covered, requiring a Context update, task-local, explicitly out of scope or requiring a user decision. It is required thinking, not a Markdown table.
- Exact non-UI semantic accounting belongs only to Long-Task and embeds identities in existing Source Items, Claims, Assertions, applicability, Bindings and Final Gate. Default Contract Conformance instead checks that explicit Source/Context reached the correct owner, material success/failure boundaries received attributable fresh checks and unresolved or unverified scope is named. Neither route creates a second Source authority, second Contract, new Gate or acceptance state.
- Context-to-Implementation alignment is checked during Conformance by asking whether controlling Context actually reached the correct modules, surfaces, APIs, state machines and verification paths and whether forbidden shortcuts were avoided. It is not a Markdown table.
- Scratch files are optional, user/agent-owned temporary memory. They have no fixed name or schema, are not Context or completion proof, are not registered in `context.toml`, and never become Workflow or Long-Task authority.
- Source-quality rules are a progressive reference inside the same Source-bound Contract Draft loop in `long-task-workflow`, not a phase or separate Context/artifact lifecycle. The loop may refine one writable proposal or materialize one conversation-only Markdown Source while Draft mapping proceeds, but real Source/provenance/markers must converge before Preflight/Compile. It creates no standalone authoring schema, gate, state, Authority or proof. Pre-existing planning documents remain ordinary Source.
- Workspace path classification is a transient activation/verification computation over current Git/workspace facts. Before first lock it compares with `HEAD`; afterward it compares with immutable `initial_task_base`. Protected, expected and support paths remain distinct from forbidden or unclassified paths. First-enable protection enumerates actual current package-asset files for configured managed destinations plus exact config/hook files and cannot expand to a directory root or broad `.codex/**`; no classification registry or second scope authority is persisted.
- A verification execution preview is a read-only projection of compiled Check/Counterfactual declarations. It may report declared Raw Execution grouping/counts but runs no command, writes no Progress, predicts no internal process count or duration and creates no proof.
- Explicit `design-system-authoring` may adopt a selected Open Design system into canonical root `DESIGN.md`, one token source/direction and owning Context. Root `DESIGN.md` remains the current shared project Design Authority for both monorepo and non-monorepo layouts; a Context workspace directory does not imply an independent design system. Multiple workspace-local Design Authorities require a separate future mechanism that updates doctor, authoring, token-source and canonical-owner behavior deliberately. Externally authored resource candidates remain ordinary Source. `design-resource-authoring` gates style-bearing work, binds provider identity, commissions/iterates task-locally and may reconcile accepted final decisions into the initial proposal once; it never mutates caller-owned planning/proposal Source, Context/`DESIGN.md`, production UI or Contract state. A real interruption risk may opt into the single task-local non-authoritative replay checkpoint described by the DRA contract; simple previews create none, and live status/Provider/readiness/acceptance is never stored. For a final selected implementation handoff it explicitly commissions implementation-level source, retrieves the entry and dependencies without truncation, freezes them locally, emits the shared strict residual adapter Source and must obtain a successful package preflight before calling it ready. `decision_required` or `unavailable` meaning may be reported as a blocked authoring result but cannot authorize fidelity implementation. These flows add no Context role, provider pack, persistent registry or acceptance authority.
- One root V2 `delivery-contract.yaml` (optionally with Outcome fragments) is explicit long-task authoring authority. Original sources are provenance; compiled cache, per-Check progress, receipts and status are verifier-owned temporary audit/recovery state, never Context or acceptance authority.
- **Execution-model checkpoint** is the single unconditional terminal-turn pause after the first Authority Lock and before Long-Task implementation. The Agent tells the user to handle any model change in the host and send `【继续】`/`[continue]`; earlier model wording never skips it, and continuation resumes execution without proving that the host model changed. Later revisions do not repeat it. It creates no model route, acknowledgement file, checkpoint state or completion authority.
- **Controlling Context** is selected Context whose meaning can change current delivery ownership, architecture, product/technical contracts, risk, recovery, verification or deployment. Core files, explicit `context_refs`, verification/deployment Context and every file in full snapshot mode are controlling. Its change cannot be silently absorbed after Authority Lock.
- **Supporting Context** is selected only through graph expansion, is not explicitly referenced, and has role `implementation-index` or `archive`. It improves navigation or preserves background material without defining acceptance. A supporting-only revision may preserve targeted Progress, but it never becomes proof.
- **Retrieval metadata** is manifest guidance that changes how future agents find Context without changing the meaning of Context already selected for a delivery: `triggers`, `read_when`, `read_policy`, default selection and unselected nodes. It neither denies reading unselected Context, authorizes edits nor serves as package-managed Skill activation policy. Selected area ownership, role classification and selected dependency closure are Long-Task authority structure, not default-workflow retrieval isolation.
- Contract Conformance is the default path's broad, evidence-bounded handoff self-check against relevant Source, Context and current task constraints and carries Engineering Quality Conformance; Architecture Conformance is one required subset. It verifies evidence freshness after the last relevant change and separates implementation, verified scope, unverified scope and decisions/external confirmations. It is not an exact-set proof or machine acceptance. Context drift is separately named because it checks whether implementation or a new decision made durable Context stale. These checks create delivery evidence, not durable Context by themselves.

## Fact-Source Authority

- `project_context/**` is authoritative for ownership, responsibility, architecture boundaries, integration direction, dependency constraints and repeatable verification/deployment paths.
- Authoritative task Source owns delivery-specific product/business and technical/backend values, rules, conditions and delegated decisions that are not durable project facts. Current code may corroborate or expose a missing fact but cannot establish intended semantics merely because it exists. Contract projections preserve stable Fact identity, provenance and resolvable value location without copying those exact values into a competing authority.
- `DESIGN.md` is authoritative for durable visual design-system facts when a project uses it and indexes the selected authored token source/generation direction. It canonically owns project/system/component-family target adoption records; a screen-specific target is only a stable-key pointer to its owning Screen Contract. Versioned non-textual target assets remain Context-reachable project Source or verifier inputs at their project-native paths rather than being copied into Context.
- External design resources are ordinary upstream Source. Candidate resources authorize no fidelity; an adopted exact target or constraint needs a stable target key and exactly one canonical adoption record containing selection basis, declared condition coverage, readable immutable identity/digest and an editable upstream locator/owner/update route (or an explicit manual/external-update boundary). Mutable links and metadata-only or flattened responses are navigation/supporting evidence, not a complete immutable implementation source. Product Surface/Screen/interaction Context and `DESIGN.md` connect task/surface terms to the canonical record by stable key and owner/anchor so relevant workflows can actively open it without duplicating its metadata. For a selected implementation handoff, the strict residual adapter makes every declared subject/target/condition/dimension/evidence/verification mapping recoverable by both consumers; this changing coverage index never becomes the adoption record, replaces opening the resource or duplicates code-expressible facts. Static/default visuals prove only shown conditions; dynamic state, interaction, motion, responsive/platform/input and accessibility coverage must be explicitly specified or demonstrated. Tool-specific generation/extraction and scope review are authoring QA, adapter preflight proves only semantic-input completeness/resource integrity, and neither is Design Authority or product evidence.
- Updating an adopted target never silently overwrites its baseline. Edit through the recorded upstream route, produce or approve a new immutable version/digest, reconcile conflicts and update the owning target reference/coverage. Missing, unreadable, stale or conflicting adopted resources fail closed for the affected decision; a readable immutable target with no editable upstream can still inform implementation, but a requested resource change remains an explicit manual/external boundary.
- Product Surface Context owns cross-surface/main-versus-drilldown responsibility; Screen/interaction Context owns stable hierarchy and behavior plus screen-specific canonical target adoption records; `DESIGN.md` owns visual-system semantics plus project/system/component-family canonical target adoption records; an authored target owns its declared concrete composition; the Delivery Contract only freezes/references/projects those facts for one delivery. When owners conflict, update/resolve the owner or retain `decision_required`; neither code recency nor duplicated locator/coverage metadata in multiple layers wins silently.
- Foundation, contract, decision-rationale, architecture, verification and deployment Context interpret current implementation paths before code convenience is allowed to redefine product or architecture intent. Verification and deployment Context remain controlling because changing a repeatable proof or release boundary can change what the delivery means.
- `implementation-index` and `archive` may be Supporting Context only when they are graph-derived and non-explicit in referenced mode. An explicit reference or full snapshot makes them controlling.
- Code is current implementation evidence. It shows what is implemented now but cannot silently redefine intended product, architecture or ownership.
- Tests, smoke checks, CI, review, hidden probes and human acceptance prove product quality. Context can identify repeatable verification paths, but neither Context nor Harness validators claim that behavior passed.
- `PROJECT_SPEC.md` owns the full Harness design explanation and historical rationale in this source workspace. Role Context keeps only high-frequency durable facts.
- Agent internal plans are current execution state only. Existing `plan.md`, matrices, verdicts or other user files have no implicit authority.
- Explicit Long-Task authority is: one complete source V2 Contract (with `outcome_files` only as physical compatibility); generated Source/REQ/CTRL/OBL/AC coverage; immutable initial base and protected authority hashes; targeted per-Check repair progress; a common-dir Active Authority V3 record containing the complete compiled snapshot plus a task/revision/identity Git-config marker; and a source-recompiled same-snapshot Live Final Gate run by final-gate, Stop or close. The workdir compiled file is never previous-authority or baseline authority.
- In referenced mode, the `context.toml` entry in the Context snapshot uses a canonical selected-authority projection rather than raw retrieval text. Retrieval-only edits therefore do not revise active Authority or stale scoped Progress; selected structural changes and selected Context contents still do. A changed final Git tree still invalidates historical final acceptance and must pass the Live Final Gate again.

## Priority When Sources Disagree

1. Read the core/default Context, collect manifest candidates and run the bounded Context discovery search before deciding `Context Delta`; widen fail safe when a relevant owner, shared dependency or Source precedence remains uncertain.
2. Treat the resulting relevant Context as the intended target for ownership, boundaries, contracts and repeat-execution paths.
3. Let principle-like Context roles interpret current-code convenience.
4. Treat code as evidence of current state.
5. Treat tests and external evidence as proof only for the claims they exercise.
6. Treat an existing `plan.md`, matrix, verdict, local audit or prose completion claim as ordinary user/task data unless an explicitly invoked Skill owns it.
7. If Source owners conflict or Context and code disagree, report the conflict, implementation drift, missing work or stale Context; do not silently select by file order, recency, code shape or convenience. Default work blocks an unqualified handoff for the affected scope until authority is resolved or explicitly reported as decision-required.
8. Re-evaluate `Context Delta` throughout implementation and repair. If a task discovers a missing durable fact, set `Context Delta: required` and update the owning Context before implementation continues.
9. After Authority Lock, revise Controlling Context through Authority Revision. A Context snapshot-only change with unchanged locked Claims, targets and proof obligations is mechanically bounded and may auto-adopt while invalidating affected evidence; any mapped semantic/proof reduction still requires a user decision. Supporting-only Context may additionally preserve otherwise fresh targeted Progress. Final Gate always reads the complete current Context snapshot.

## Role Placement

- `area` / `domain` owns product or package responsibility.
- `subdomain` owns a smaller product/domain slice.
- `contract` owns API, schema, event, workflow or cross-surface interface semantics.
- `foundation` owns stable concepts, vocabulary and theory.
- `verification` owns repeatable test, smoke, CI, probe and validation paths.
- `deployment` owns repeatable deploy, runtime bootstrap, topology, health-check and rollback/degradation paths.
- `implementation-index` owns code navigation entry points, not behavior definitions.
- `decision-rationale` owns stable reasons that still affect future choices.
- `archive` owns non-default historical or external material.

## Evidence Boundaries

- Do not store one-off logs, command output, generated implementation screenshots/diffs, CI artifacts, release ledgers, temporary JSON, raw payloads, secrets, tokens, cookies or result claims in Context. Context/`DESIGN.md` may make a reviewed versioned design target Context-reachable without embedding its binary contents or a review log.
- Do not copy full implementation summaries into Context when code, tests or comments are clearer.
- Do not invent rationale from current code shape.
- Do not register scratch files, exported source packs, Delivery Contracts, optional source provenance, compiled long-task state or verification runs in `project_context/context.toml`.
- Do not require or validate a fixed `plan.md`, Source-to-Context table, Context-to-Implementation table, matrix, verdict or evidence ledger for the default workflow.
- Do not persist the bounded Context search, default selected-design accounting or execution-model checkpoint as a new artifact, registry or runtime state.
- Use Context to shorten future recovery and guide decisions; use code/tests/runtime evidence to prove current behavior.
