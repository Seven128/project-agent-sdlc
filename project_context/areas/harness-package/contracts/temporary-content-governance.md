# Temporary Content Governance Contract

## Classification Rule

A path name never determines authority, ownership or deletion. For every temporary, generated, recovery, benchmark, release or work-product class, classify the writer/reader, authority, location, tracked/ignored state, sensitivity/disclosure boundary, retention/TTL/capacity, atomicity/concurrency/collision/path-link behavior, cleanup owner/failure behavior, Windows/macOS semantics, recovery role and final-Source eligibility. Before deleting or migrating a class, search its current writer, reader, migration, tests, public documentation and tracked/user-owned content.

Only the creating owner removes content it can positively identify as its own. Missing, stale or corrupt temporary material may increase rework, but cannot create a passing or completed result. Cleanup failure is explicit; deletion never follows a symlink/junction or crosses the repository/declared temporary root.

Repository portability is checked through an explicit owner-scoped allowlist, not a repository-wide filename or history scan. Package-managed guidance, its generated package assets, public executable documentation, durable Context, source mappings and the runtime-resolved project Source documents are the default current surfaces. A caller may add an exact active Source or handoff path for the current delivery. Real Windows/POSIX user-home locators fail on those surfaces; portable placeholders and deliberately non-resolvable `attachment-provenance://` identities remain valid. Historical Contracts, Receipts, snapshots, migrations and fixtures stay outside the default scan unless their current owner promotes an exact path into active Source. This classification neither makes history portable nor authorizes rewriting or deleting it.

## Platform Boundary

Repository-relative identities use `/`; filesystem operations use Node path APIs. Same-directory rename is the atomic publication boundary on supported Windows/macOS filesystems. Owners must reject link/reparse-point parents and non-regular destinations, keep temporary files on the target volume, recheck current content before replacement and reread after material write when correctness depends on exact bytes. File data synchronization and rename semantics are OS/filesystem TCB; no owner claims crash-proof storage or hostile-writer isolation beyond its tested boundary.

## Non-Goals

There is no global Temporary Artifact Manager, retention daemon, directory-name deletion rule, session registry or acceptance cache. This contract does not move Long-Task Authority, turn benchmark/release artifacts into Context, or make ignored files safe to disclose.
