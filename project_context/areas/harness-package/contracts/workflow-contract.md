# Harness Workflow Contract

## Role

This contract defines the lightweight default workflow and the explicit Single-Goal Long-Task Workflow boundary. The default route is an automatically applicable prompt-level execution protocol for implementation work of any complexity: it controls order of thought and reporting, but creates no required plan file, validator result, Receipt, persisted workflow state, scheduler or machine-completion authority. Complexity determines execution and verification depth; required machine completion authority, recoverability or auditability determines the route; risk inside Long-Task determines its unchanged proof floor.

## Shared Engineering Quality Obligation

Every implementation delivery completes one `Architecture Deliberation` before its first implementation edit. The checkpoint is externally observable and repository-bound rather than hidden reasoning: it identifies affected owners, the current extension point and unique source of truth, dependency and interface/state/resource-lifecycle boundaries, selected design and material alternatives, one plausible future-change challenge, touched debt and its disposition, forbidden shortcuts, project-owned checks, and triggered quality attributes or a concrete preservation basis. Depth is risk-proportional. Small work still names the owner/extension point, shortest reliable verification route, unchanged quality attributes and why no debt is added or worsened. A material scope, owner, Context, dependency, design, quality-applicability or debt-disposition change makes the checkpoint stale.

Applicable quality is a risk-triggered subcriterion, not a separate phase or matrix. Correctness/invariants and maintainability receive at least preservation; reliability/resource lifecycle, concurrency/consistency, performance/capacity/cost, security/privacy/safety, compatibility/migration/rollout and operability/observability/testability expand only when Source/Context or the change exposes that risk. Exact required predicates remain owned by the existing Semantic Fact or selected-design obligation. A performance claim requires workload, metric, baseline/budget, environment, comparator/tolerance and project-owned measurement; without attributable measurement, make no improvement or budget-satisfaction claim.

Implementation remains Goal-owned. Reuse the owning service/facade/adapter/extension point, keep one source of truth, make the smallest complete semantic change, validate at the real boundary, preserve failure/resource/concurrency semantics when applicable and add abstractions only for an evidenced stable change axis. Do not swallow failure, invent defaults, create hidden mutable global state, duplicate owner-held rules or treat shorter files/more interfaces as proof of quality. These guardrails create no prescribed order, method Gate or per-edit mandate.

When non-trivial infrastructure, a mature protocol/security capability, a new dependency/shared abstraction or an existing near owner makes sourcing material, Architecture Deliberation records an allowed solution set, prohibited failure modes and risk-proportional rationale/evidence. Existing owners, standard capabilities, installed dependencies, mature external libraries and small self-implementation can all be valid; reasonable non-abstraction must remain allowed. Duplicate owner-held rules, extension-point bypass, unsupported heavy dependencies, incomplete security-sensitive reinvention, incompatible license/platform choices and second sources of truth fail Conformance. This is not a mandatory library answer, OSS/DRY rule, quality score or new Gate.

After implementation and project-owned verification, one `Engineering Quality Conformance` checks the current candidate and includes the existing `Architecture Conformance`. It checks scope/path escape and unattributed dirty changes; owner/dependency/extension-point bypass; duplicate authority; undeclared API/schema/data/state/persistence/lifecycle/recovery/compatibility change; triggered quality risks without attributable evidence; silent fallback, swallowed failure, resource/concurrency/partial-state defects when applicable; unsupported performance claims; forbidden shortcuts; missing project-native checks; and new/worsened debt. A correction returns to implementation and verification. Any later code, configuration, Contract, declared check-input or controlling-Context change invalidates the closure.

Default work carries Engineering Quality Conformance inside Contract Conformance. Long-Task carries it only through existing declared Technical/Global authority, Bindings, executable Checks and independent Assertions when an invariant can fail while functional behavior passes, all inside Final Gate. Final Gate proves only that declared, falsifiable, project-check-bound set—not overall code quality. The carriers are mutually exclusive. This obligation creates no quality artifact/matrix, second `Context Delta`, Contract, Source aspect, Claim/risk kind, Authority, Gate, state, scheduler, broad quality Boolean or language-generic analyzer.

Long-Task may serialize its non-UI semantic Source and Contract projection with the package-owned Compact Carrier. This changes persistence only: parser materialization feeds the same validation, compilation, Authority revision/freshness and sole Final Gate path. Shared catalogs/selectors, Fact sets, proof templates and explicit exceptions must preserve exact Fact and obligation sets independently. Stable `fact_key` plus current `fact_revision_digest` identifies a Fact revision; that digest includes normalized Fact meaning and every explicitly linked current input revision. Stable `obligation_key` plus current `obligation_revision_digest` identifies a proof-obligation revision; that digest includes normalized proof meaning and the current Fact revision. Typed results are attributed to the obligation and projected to the Fact. Capacity declarations bind measured materialized Fact/obligation/result collections; the theoretical ground universe is never an intermediate collection. A Source or Contract may use the legacy expanded form or compact form, never both, and compact mode cannot infer, sample or default omitted meaning.

## Default Workflow

When no active long-task binding or explicit selection of the logical `long-task-workflow` Skill applies:

1. Read `project_context/global.md`, `project_context/architecture.md`, `project_context/context.toml`, the default area root and graph/trigger candidate role Context.
2. Before deciding `Context Delta`, run one bounded text search over `project_context/**` using a small set of high-signal terms from the task, including explicit area/module names and relevant API/schema/state/security/verification/deployment terms. Merge matching Context with manifest candidates, read the relevant files and widen the working set whenever semantic dependencies reveal another needed Area, shared Context, design authority or code owner.
3. Separate the expandable read scope from the intended workspace set. Context-workspace/Area/default/read-policy selection never grants or denies edits. In a repository with several materially different sibling implementation workspaces, resolve the task-local intended workspace(s) from explicit user/product/path/repository facts; if the target remains genuinely ambiguous, ask one concise question before product edits rather than choosing the default Area, a recently changed client or a generic keyword match. Enumerate every intended workspace for cross-workspace work and keep shared/backend/supporting reads or changes explicit.
4. For product-surface or information-placement work, perform the lightweight positioning check for information ownership/layout and role placement before narrowing to code.
5. For material non-UI requirements, identify every expressed Source/Context requirement relevant to the task, its owner, key success condition, material applicability/edge cases, failure and recovery boundary, acceptance path and unresolved decision. Depth is risk-proportional: a local fix may collapse this to a few concrete judgments, while complex or high-impact work expands naturally. Do not let current code, a broad summary, an undocumented default or a convenient sample replace authoritative meaning. Author a necessary derivation or delegated engineering choice only when authority permits it; preserve conflicts and genuine user/product/legal/security/commercial/safety choices as `decision_required`. The default route creates no complete Census, stable Fact/obligation keys, exact-set equality, frozen Oracle/environment graph or per-obligation result ledger.
6. For a selected design-resource implementation handoff, first resolve provider output to repository-readable immutable resources. A formal Web/App target still requires a canonical entry, exact dependency closure, complete acquisition and a frozen-Inspector Fact manifest derived from the pre-generation Expected Fact Universe. Run `ty-context design-resource preflight <handoff.md>` and require `Expected Fact Universe = Canonical Resource Facts = Handoff Indexed Facts` across exact `subject × target × condition × variation × property` Fact Cells, Census, standard/custom axes/properties, explicit N/A/exclusions, property-required proofs, design-system lineage, assets and non-sampling/non-truncation. Product Controls/eight dimensions are not the Fact ceiling. New formal implementation handoffs also carry the separate current `design-resource-implementation-feasibility-v1` Source: every material component-family transitive subject closure × target × reachable condition has at least one Source-backed feasible realization or explicit blocker, while canonical resources remain the sole exact visual-value owner. Planned-owner authorization, required realization and blocker authority bind exact digest-current marked technical Source Items and exact target/family/applicability projections; role labels, file-level locators and unrelated same-file Claims do not qualify. Observed owner roots are real contained no-follow repository directories, and an unresolved formal-target substrate observation reaches an affected Source-backed blocker. A legacy missing input stays readable with the explicit `technical feasibility not declared` limitation and gains no capability. Deliberately partial design input remains an explicitly scoped constraint or blocking unresolved and never an exact target. Incomplete acquisition/Census/resource closure, aggregate labels, missing or mismatched Facts/proofs, unresolvable located digests, unsupported evidence, unresolved conflicts/blockers, ambiguous profiles, missing exact-target layout/pixel Facts, infeasible uncovered component cells or stale identity blocks the affected fidelity claim. Then perform UI Authority Closure and the Design Authority Check; open every affected exact target/constraint and feasibility Source, use Architecture Deliberation to select the actual production owner and cold-start real-user journey from current repository authority, and identify its declared conditions, blockers and candidate strategy set. DRA and feasibility input never make that selection. Select risk-proportional project-native checks and report any condition those checks do not cover as unverified. Compatible JSON `status: ready` and human `preflight valid` prove input closure only; neither preflight nor bundle publication evaluates production conformance/readiness.
7. Perform the shared `Architecture Deliberation`, including triggered quality attributes or concrete preservation, and surface its concise repository-bound conclusions before the first implementation edit.
8. Decide exactly one `Context Delta: none|required`; update owning Context or `DESIGN.md` first when required.
9. Use platform-internal planning with no required `plan.md` to keep goal, boundaries, controlling Context, likely implementation surfaces and verification clear.
10. Implement under the shared quality discipline and run project-owned verification in proportion to risk. A failed check or discovered omission returns to its requirement/owner/module/check, then to implementation and affected re-verification. After the last relevant code, configuration or check-input change, rerun every affected check before relying on it; historical CI, pre-fix results, delegated reports and code inspection alone are not current evidence. When the repository exposes a changed-path/target-scope verifier, give it exact task-attributable changed paths and intended/supporting targets; do not fold unrelated pre-existing dirty paths into the task. Otherwise review the final diff against durable owners during Conformance.
11. Perform current-candidate Contract Conformance carrying `Engineering Quality Conformance` including `Architecture Conformance`. Confirm that explicit Source/Context reached the correct owners; key success/failure boundaries have attributable fresh evidence; no undeclared API/schema/data/state/compatibility or target-scope change escaped; Source conflicts and genuine decisions remain visible; selected-design claims name the conditions actually checked; and later edits did not stale the evidence. This is not an exact Fact/obligation set proof and creates no machine acceptance. Then check Context drift and hand off `Implementation`, `Verification`, `Engineering / Architecture Conformance`, `Not verified / decision or external confirmation required`, and exactly one Context status without a result artifact.

The bounded search supplements manifest routing and Agent semantic judgment. The default/candidate set is an expandable minimum rather than a read ACL or complete-graph mandate. Unknown or conflicting owners, shared dependencies and verification boundaries widen fail safe until the relevant scope is understood; this is additional reading/judgment, not a full-graph default. The route creates no persistent index, cache, search state, Context registry or second authority. Target disambiguation and changed-path review are conditional task-local judgments; they create no required `plan.md`, target declaration, Task Contract, mapping table, matrix, verdict, evidence ledger, implementation-summary file, workspace registry or generic import/path/runtime scanner. Existing `plan.md` files remain ordinary user files; other existing artifacts likewise have no Harness authority.

## Default Workflow Purpose And Anti-Degradation

The default Workflow Contract exists to give every implementation task without an explicit or validly bound Long-Task one automatically applicable, risk-proportional and lightweight engineering protocol. It must let an Agent recover authoritative meaning, implement through the correct owner, verify the current candidate and hand off honestly without paying the fixed cost of machine Authority, exact Fact/Obligation identities or persistent recovery state. “Default” means automatically applicable at any complexity, not small, low-risk or lower quality.

Admission is lexicographic. First preserve or improve effect and meet the design-purpose/high-quality floor; only then compare efficiency and total ROI. A current defect is repaired rather than accepted as the floor, and lower prompt, runtime or test cost never compensates for missed Source, weaker evidence freshness or a false completion path.

### Effect Non-Degradation

Every default-workflow change must preserve or strengthen these properties:

- explicit user requirements, authoritative Source, controlling Context and selected constraints cannot be redefined by current code, a convenient sample or an undocumented default;
- material requirements, applicable conditions and edge cases, owner/source of truth, failure and recovery boundaries and real acceptance entries receive risk-proportional understanding;
- one visible Architecture Deliberation occurs for every implementation delivery, with correctness/invariants and maintainability preservation always addressed and other quality attributes triggered by real risk;
- implementation reaches the real owner and extension point without duplicate truth, reversed dependency or bypassed service/facade/adapter boundaries;
- only attributable project checks run after the last relevant change count as current evidence; historical CI, pre-fix results, delegated reports and prose inspection do not;
- a failure is localized to the requirement, owner, module and check, repaired, and followed by affected current-candidate verification;
- Contract Conformance checks `Source/Context -> implementation`, while the separately named Context drift check checks `implementation/new decision -> durable Context`;
- selected-design claims name only the targets, conditions and behavior actually checked in production paths; preflight input integrity does not prove production conformance;
- `Implemented`, `Verified`, `Unverified`, `Blocked / decision required` and externally pending scope remain distinct; and
- complexity may expand engineering depth but never weakens these obligations.

Default work uses risk-proportional material-requirement reconciliation. It never performs a complete standard/custom semantic-family Census, assigns stable Fact or Obligation identities, proves exact set equality, expands a universal condition product, freezes an Oracle/environment graph or records per-Fact observation/comparison/verdict rows. Those exact closure, freshness and machine-acceptance responsibilities remain exclusively with Long-Task Source/Contract/Authority and its sole Final Gate.

### Efficiency Non-Degradation

Once effect is preserved, the default route protects low fixed cost:

- a small task collapses to a few concrete judgments rather than expanding a complete catalogue;
- it creates no `plan.md`, Fact table, Evidence Ledger, Receipt, result artifact or persistent workflow state;
- it does not copy Long-Task Source/Contract/Authority/Final-Gate logic or create a third medium route;
- duration, complexity and file count never auto-upgrade the route;
- it reuses project-native types, lint, architecture, behavior and measurement checks;
- repair starts with failed and affected checks rather than a full suite after every edit;
- the required complete regression runs once on the frozen final candidate unless an actionable failure or later controlling input invalidates it; and
- text added to automatic AGENTS/default surfaces must be broadly valuable and nearly zero-cost on small tasks, with specialized detail routed on demand.

Total cost includes recurring prompt attention, Context reads/search and tool rounds, authoring, verification invocations, runtime, maintenance, migration, test expansion and future modification blast radius. A complete Fact-by-method account, even if kept only in memory, would make every default task pay much of Long-Task's cost while duplicating its machine-assurance responsibility and is therefore forbidden.

### Admission Of New Default Rules And Safeguards

Before adding a default instruction, test, benchmark or checker:

1. name the concrete wrong-implementation or false-completion path it closes;
2. determine whether Architecture Deliberation, an existing project check or Contract Conformance already closes it;
3. if it benefits only a minority of tasks, make it risk-triggered or on-demand instead of a fixed step;
4. add no artifact, state, Authority, Gate, stable ledger or workflow route;
5. compare prompt, Context, tool, verification, maintenance, test and migration cost;
6. adopt only when effect does not regress, the high-quality floor remains satisfied and total ROI is clearly positive; and
7. use the existing fresh-Agent benchmark for important behavioral or efficiency conclusions. Static guidance/parity tests prove distribution and known structure only.

Anti-degradation construction follows the same admission rule. Its first check is a declared-purpose validity floor: every critical sentinel has an independently grounded correct control and a direct semantic negative control, every open critical false-completion incident is frozen before repair, and the failure localizes to the owner/boundary the sentinel claims. Only a validity-established baseline participates in relative Coverage/false-negative comparison; Coverage is rejected erroneous completion paths, not test/Fact/tag counts. Prefer one owner-local or existing table-driven check over many files and permutations, retain every independently failing boundary and never describe a static string sentinel, prose review or fresh-Agent benchmark as proof of critical safety, provider execution or high ROI. A sentinel rationale cannot exceed its executable controls, and an open critical counterexample downgrades the formal capability claim. This creates no anti-degradation artifact, matrix, second registry, state, Contract, Authority or Gate.

## Context Priority And External Sources

- Context owns durable intent; code owns current implementation; tests/CI/smoke/browser/human observation own product evidence.
- The explicit `design-resource-authoring` upstream route owns its task-local Base/Delta decision authority and optional recovery checkpoint under [Design Resource Authoring](design-resource-authoring.md). That narrow ignored checkpoint is persistent recovery state but not default-workflow state, Source, Contract, Authority, Evidence, Gate or acceptance; default work and Long-Task consume only its authorized final Proposal/resources/handoff.
- A monorepo may use `project_context/workspaces/<workspace-id>/**` as a centralized sparse mirror only for implementation workspaces that own durable non-code Context. Each represented Context workspace maps exactly one code root through existing `[[areas]].root` and `context` and may contain several workspace-local Areas. Unrepresented package-manager workspaces need no empty Context directory; cross-workspace/repository Areas remain at top-level `project_context/areas/**`; non-monorepo projects keep the existing top-level Area layout.
- Prefer a small top-level repository-common Area as the monorepo default. Keep workspace-local Areas and role Context `on-demand` unless their facts are genuinely near-universal; one client's Context must not become the implicit global default merely because it is represented.
- Area owns durable product/technical meaning and discovery, not read or edit permission. A workspace-local Area belongs to one Context workspace; a top-level shared Area may be read by several clients without granting any client edit authority over another.
- Authoritative Source owns task-local product/business and technical/backend semantics that are not durable Context. Exact values remain at their unique Source/Context locator; a Contract indexes identity, provenance, digest and proof binding and does not become a second value owner. Repository-backed Semantic Fact inputs use strict raw-byte SHA-256; the repository therefore owns a checkout-invariant text-byte policy. This source repository fixes Git-classified text to LF with root `.gitattributes`, rather than accepting both LF and CRLF digests or letting ambient `core.autocrlf` revise Authority across hosts.
- `Context Delta: required` covers durable product capability, surface responsibility, ownership, architecture/interface/schema/data/state/recovery/dependency/security or repeatable verification/deployment changes. Local semantics-preserving fixes are `none`.
- For every material external source constraint, internally classify it as covered by Context, requiring a Context update, task-local, explicitly out of scope or requiring a genuine user decision. This judgment creates no table.
- Final Conformance checks that controlling Context reached the owning modules/surfaces/interfaces/state machines and verification paths and that no forbidden shortcut or duplicate authority was used. Context drift remains separately named because it asks the reverse question: whether implementation or a newly selected decision changed durable truth that Context does not yet record.

## Product Surface Responsibility

- Product-surface and surface/page responsibility remains project-owned Context using existing `contract`, area/subdomain and verification roles.
- Source-to-Context judgment replaces the former Context-to-Implementation Markdown table; Contract Conformance is the internal implementation-alignment check.
- Do not add Product, Architecture, Rationale or Verification delta fields. `Context Delta: none|required` remains the only durable-fact result.

## UI Authority Closure

- Use stable surface, control and target keys to reconcile current Source, owning Product Surface/Screen/interaction Context, `DESIGN.md`, authored targets and verification before material implementation. Product Surface Context owns cross-surface responsibility; Screen/interaction Context owns stable screen hierarchy and behavior; `DESIGN.md` owns visual-system semantics/reference interpretations; authored targets own concrete declared compositions; the Delivery Contract only binds this delivery.
- Project Design Source rather than copying it wholesale: durable surface/flow and Screen/Control/state meaning goes to Product Surface or Screen/interaction Context; durable visual-system/token/motion-policy/rationale meaning goes to `DESIGN.md`; exact composition/value/timeline/condition and asset bytes remain in the selected target; repeatable proof routes go to verification Context; provenance, applicability cells, blockers and proof bindings remain task/Contract-local unless they expose a durable decision or risk.
- Give every adopted target exactly one canonical adoption record. `DESIGN.md` owns project/system/component-family targets; the owning Screen Contract owns one-screen/interaction-specific targets. Other Context, handoffs and Contracts retain only the stable target key, canonical owner/anchor and local applicability instead of repeating interpretation, locator/digest, full condition coverage or upstream update metadata.
- Classify each affected item as `context-covered`, `context-update`, `task-local`, `out-of-scope` or `decision-required`. Update durable owners before code when required. Contract YAML, current code and implementation screenshots cannot become the sole owner of a missing product/design decision.
- Use an on-demand Screen Contract when stable screen identity, entry/exit/shared state, region order, fixed/scroll/overlay ownership, navigation, variants or material controls exceed the coarse Product Surface Contract. Do not require one for semantics-preserving local style/UI fixes or an explicit non-fidelity prototype.
- A material Control may need independent surface, region/location, type/label, user task, visibility/availability, trigger/input/validation/default, interaction/navigation, loading/empty/success/failure/recovery/permission/feedback and accessibility meaning. Missing applicable meaning is resolved through Source/Context/delegated design or remains a genuine decision; it is not silently filled by an implementation agent.
- Before implementation, identify how every selected material target will flow through `target key -> declared conditions -> production route/component owner -> cold-start real-user path -> rendered/interactive comparison evidence`. Use the first useful independently runnable production slice as a recommended real-entry feedback point when its expected early-localization value exceeds the run cost; it is not a prerequisite for expanding implementation. Always rerun the affected cold-start journey on the final candidate. Detached routes, specimens and deep links remain supplemental.
- Conflicting controlling owners fail closed. Resolve the stale Source/Context/design target, or preserve `decision-required`; file order, timestamps, code shape and Contract convenience do not establish precedence.

This closure is an internal reconciliation and routing check. It creates no required table/artifact, second `Context Delta`, UI state machine, readiness cache or acceptance authority.

## Design Authority Readiness

- Material production UI means a new or redesigned screen, primary layout/navigation/theme/component system, high-fidelity implementation or substantial visual polish. Local style bugs, narrow existing-component edits and explicitly throwaway prototypes remain on the lightweight path.
- Before a material product, design, implementation or acceptance decision, traverse the affected stable surface/control/target keys from owning Context through `DESIGN.md`, then open and inspect every selected `exact-target` or `constraint` for those routes/components. Read its one authored exact-value token source/generation direction, immutable adopted locator/digest, declared conditions and editable upstream locator/owner/update route. Do not treat a registry mention as consumption.
- Classify each material reference as `exact-target`, `constraint` or `inspiration`. An exact target supports only its declared surface/viewport/mode/state fidelity; a constraint supports only its named rule; inspiration and an unconfigured starter never authorize an implicit reproduction or invented production layout.
- Explicit project design-system initialization/adoption routes to `design-system-authoring`, which never auto-runs. For standalone resources, `design-resource-authoring` classifies style dependency: style-bearing work stops on unconfigured authority and points to that explicit Skill, while low-fidelity/IA/semantics-only work remains available. Configured style-bearing Open Design projects must verify the adopted `designSystemId`. For an implementation handoff, verify the source profile, complete local retrieval and locator addressability; a provider catalogue entry or latest-only link proves none of them. Do not promote an implementation screenshot into its own target.
- A configured project visual system is necessary but not sufficient page authority. Surface-level implementation readiness additionally depends on the owning Screen/Control meaning, the selected target/constraints for the claimed conditions and a project-owned verification path; `doctor` reports only advisory file-level signals.
- Root `DESIGN.md` remains the current shared project Design Authority regardless of Context workspace placement. A monorepo directory mirror does not create workspace-local design authorities; supporting multiple independent design systems is a separate mechanism change that must deliberately update canonical ownership, doctor and authoring/token-source behavior.
- Missing, unreadable, stale or conflicting selected resources are `decision-required` for the affected claim. If the immutable adopted target is readable but its editable upstream is unavailable, it may still guide implementation, but a request to alter that resource must stop at the named manual/external update boundary rather than silently editing the snapshot or inventing a replacement.
- Change an adopted target through its recorded upstream route, then create or approve a new immutable version/digest and update the owning target reference and coverage. Never overwrite the adopted baseline in place.
- Fidelity verification renders the production route/component in the declared combinations and compares it with the selected target when one exists. Call resource hash/count/registry checks `design_resource_integrity`; they cannot satisfy `design_implementation_conformance`. Token/raw-value and font checks, layout/DOM/accessibility/motion assertions, interaction traces and target-runtime checks remain project-owned. Report only checked combinations and keep subjective approval external.
- This is conditional order-of-thought guidance, not a required design directory, new Context role, new delta, workflow state, generic validator or pixel-perfect mandate.

## Routing And Activation

Routing order is:

1. A valid common-dir active record plus matching worktree Git-config marker runs `ty-context long-task resume`, then directly loads the installed package-managed `long-task-workflow` Skill; this recovery path does not depend on implicit invocation.
2. Explicit selection of `long-task-workflow` creates, preflights, compiles, executes or resumes exactly one complete V2 Contract authority for the selected delivery in the currently selected host execution Goal. In Codex, select it with `$long-task-workflow` or through `/skills`.
3. Otherwise remain on the default Workflow Contract, regardless of apparent duration, complexity or file count.

Do not auto-detect or auto-activate long-task state.

## Workflow Selection And Long-Task Proof Floor

- The default Workflow is eligible for local or complex work. Complexity, duration and file count change the depth of reasoning, implementation and project verification, not the route.
- Explicitly select Long-Task when the delivery requires verifier-owned completion authority, persistent recovery across compaction/session boundaries, or audit-grade requirement-to-proof traceability and the corresponding authoring/verification cost is justified. A small but high-consequence rule may use Long-Task; a large refactor or exploratory prototype may remain on the default route.
- After Long-Task is selected, its existing `auto | standard | strict` risk model remains unchanged. `standard` is the ordinary proof profile when no strict trigger applies. `strict` is the compiler floor for public API/schema, persistent data, migration, security/permission boundary, irreversible external effect, full population or critical-path work with weak end-to-end observability; multi-repository delivery remains rejected.

Risk classification never auto-activates Long-Task. An explicit user request may raise proof to strict, while neither Skill nor execution may lower the compiler floor. The route adjustment changes no Long-Task Source, Contract, Authority, Evidence Kernel, repair, Final Gate, External Confirmation or no-drift logic.

## Single-Goal Long-Task Workflow

The workflow is:

`initial/revised proposal + selected immutable design resources + complete implementation-source closure when applicable + separate validated implementation-feasibility Source when declared + validated residual design-resource handoff + relevant Context -> Architecture Deliberation / applicable-quality assessment -> one Source-bound Contract Draft loop (inventory/provenance/refinement/markers/mapping) -> target/stage/Outcome/Control/repository/method/blocker binding -> Preflight -> Compile / Authority Lock -> one-time unconditional host model-change checkpoint -> Goal-owned adaptive implementation discipline + non-authoritative acceptance/verification Frontier -> optional targeted feedback/repair -> protected revision when needed -> clean candidate commit -> source-recompiled one-snapshot Final Gate including Engineering Quality/Architecture Conformance -> qualified machine result -> Stop/close -> native Goal veto review -> external confirmations -> Context drift check`

Pre-existing planning/proposal documents and external design resources remain ordinary Source, not a Contract Draft. ## False-Completion And Drift-Control Objective

- When Source and Contract are sufficiently detailed and unambiguous, every atomic semantic Fact, requirement, control state, technical obligation and acceptance criterion must resolve to its Source-backed Claim or named falsifiable Assertion at every declared applicability cell. For material non-UI scope, Expected Semantic Facts, Source-indexed Facts and Contract-projected obligations are set-equal, and proof obligations are set-equal to attributable current results carrying Fact ref, actual observation, comparison policy/parameters or tolerance, verdict, Oracle identity and environment. Authoritative completion is impossible while any declared item remains unresolved or unproved, even if agent prose, a broad Requirement or an aggregate catalogue says otherwise.
- The Harness does not promise drift-free intermediate model behavior. Rolling implementation may diverge; Compile, scope/risk escalation, targeted findings, Final Gate and Stop must detect observable drift, block acceptance, identify the owning Outcome/Claim/Check or boundary and direct repair.
- Machine acceptance means the final current-snapshot artifact has no remaining machine-observable drift relative to the declared Contract and relevant Context inside the exact admitted observer/TCB boundary, and no External Confirmation remains pending. Every machine Claim or Fact × method obligation must bind unchanged expected Authority, package-admitted current actual, Harness-computed comparison/result identity/verdict, attributable frozen static structure or Harness-direct product-process execution, a package-observed causal Counterfactual and current Final-Gate evidence. It does not extend to omitted or non-falsifiable requirements, unsupported physical/UI/native semantics, hostile-host tampering or external CI/deployment/human confirmation.
- Targeted verify is scoped repair evidence only. `verify --explain` is a read-only projection of selected compiled main and Counterfactual Raw Executions: it runs no command, writes no Progress, predicts no duration/internal process count and creates no proof. Only the source-recompiled Final Gate may accept after rechecking the complete Contract on one current snapshot.
- Check `input_paths` and Binding carriers use the smallest sound causal envelope; broad repository/application/platform roots require a real any-matching-change invalidation reason. ## Scope And Risk Escalation

- The Contract declares Outcome expected change paths, allowed support paths, forbidden paths and relevant Context owners/boundaries.
- Repository patterns reuse the canonical safe-path AST. Parentheses are ordinary literal pattern characters, including framework route groups such as `apps/mobile/app/(map)/**`; they never enable capture groups or extglob. Existing `*`, `**` and `?` semantics remain unchanged, unsupported `[]`/`{}` syntax still fails closed, and matching, subset, overlap, containment and runner freezing consume the same parser.
- Actual changes outside the combined allowed envelope or a newly touched undeclared boundary return a `scope_escape` Finding.
- The same current Goal revises the Contract and recompiles. Harness never responds by starting a worker/new Goal or repeating the execution-model checkpoint.
- Authority Revision is the only replacement path for locked Contract or protected-input identity. It separates `authority_changed` from `user_decision_required`: monotonic strengthening, raw Source/Context snapshot changes with unchanged locked semantics, operational Runner/verification-input repair, repository-bound scope expansion and equivalent Counterfactual coverage with the same carrier, mutation and Check and no lost Claim/assertion-failure coverage may auto-adopt; Product/Source Claim/target/external-confirmation change, lost scenario/Claim/Evidence Capability/failure interception, forbidden/owner-Context removal, runner type/effect change, verifier-kernel change or any unknown reason fails closed for an exact user decision. A verifier-content identity change invalidates prior evidence and requires the complete Final Gate, but its digest change alone is not a concrete proof that acceptance semantics or proof coverage were reduced. Without independent preservation proof from the previous Authority or trusted external release provenance, semantic preservation remains unknown and automatic adoption remains forbidden. Risk downgrade remains rejected.
- Every adopted path keeps exact revision identity, previous-Authority continuity until CAS adoption, evidence invalidation and the complete source-recompiled Final Gate. Automatic adoption is therefore repair routing, never acceptance or completion.
- A pending decision summary begins with a plain-language Authority Revision introduction, enumerates user-decision reasons and mechanically bounded changes, material fields/Claims/proof/external-confirmation keys, affected Outcomes, reject/previous-Authority behavior, no-completion effect and mandatory Final Gate. For verifier-content changes it lists the changed verifier files, states that prior evidence is invalid and that semantic preservation is not independently established, without mislabeling the byte change as a proven reduction. An explicit current task instruction that exactly covers all listed decision reasons may be relayed once; generic prior authorization cannot approve a later identity. Diagnose and edit withdrawn candidates without asking, and invoke ordinary `compile --revise` only when the final blocking candidate is stable. No separate revision plan, editable brief, review artifact, instruction ledger or approval registry is created.

## Contract Conformance

Contract Conformance is the default path's internal implementation-alignment review, not a `delivery-contract.yaml`, independent verifier or additional Gate. Before handoff:

- fix implementation misses;
- update missing durable facts;
- reconcile every material Source/Context requirement relevant to the task, its applicable conditions and edge cases, owner/source of truth, failure and recovery boundary, and checked versus unverified or decision-required scope;
- confirm those material requirements reached their owners and have attributable current-candidate project checks at the strongest practical boundary, without building a complete semantic-family Census or per-Fact observation/comparison/verdict ledger;
- when a selected implementation handoff exists, open each affected exact target or constraint plus current matching feasibility Source, confirm canonical/technical separation and candidate-or-blocker coverage, verify that Architecture Deliberation—not DRA—selected the actual production owner/strategy, route it to that owner and root journey, and report which conditions current-candidate checks did and did not establish without reconstructing the complete Fact-by-method result universe;
- confirm controlling Context reached the correct owners and verification;
- confirm every intended workspace/product target is accounted for, supporting/shared reads did not silently expand edit scope, actual task-attributable changed paths match the intended/supporting envelope, and any available project-owned scope verifier passed;
- perform `Engineering Quality Conformance` on the current candidate snapshot, including `Architecture Conformance`, the deliberated owner/source-of-truth/dependency/lifecycle boundaries, triggered quality attributes, future-change extension point, debt disposition and declared project-native checks;
- confirm no forbidden shortcut, duplicate workflow artifact, stale authority or risk downgrade;
- confirm implementation, docs, Skills/assets and Context are aligned.

The following Context drift check remains explicit and directional: Contract Conformance asks whether implementation follows current Source and Context; Context drift asks whether implementation or new decisions made durable Context stale or incomplete. If either check finds a miss, repair the owner, rerun affected project verification and repeat conformance on the new candidate. A selected target, implementation or declared check-input change also stales selected-design closure. The default path reports only the checked scope and unresolved gaps and never persists its accounting as a matrix, ledger, Claim set, readiness state or Gate.
