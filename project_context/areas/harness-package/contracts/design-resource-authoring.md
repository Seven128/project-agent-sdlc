# Design Resource Authoring Contract

## Role And Authority Boundary

`design-resource-authoring` is an explicit, upstream commissioner. It owns bounded resource scope, task-local semantic replay, Provider adaptation, current-resource audit, selected-proposal writeback and optional interruption recovery. It does not own product/business/permission/data/algorithm/commercial/security meaning, durable Design Authority, Provider lifecycle, implementation acceptance or Long-Task completion.

Candidate resources remain ordinary Source. A selected resource may uniquely own exact visual values for its declared conditions, but selection cannot authorize the reason those values or any new material meaning are adopted. Material decisions keep four independent dimensions:

- `origin`: `user-direct`, `necessary-derived`, `repository-evidence-backed` or `provider-suggested`;
- `decision_authority`: `explicit-user`, `delegated:<bounded-scope>` or `none`;
- `evidence_refs`: resources which display or support the meaning; and
- `status`: `accepted`, `rejected` or `unresolved`.

A Provider suggestion becomes accepted only through explicit user acceptance or a bounded delegation which covers that choice. Repository evidence can support a decision but cannot silently create product authority. Every `explicit-user` authority, bounded delegation and accepted Delta `source_ref` resolves to an actual marked Source item in a repository-readable file and is bound to both the file's current raw-byte digest and the item's current semantic digest; an accepted delegated Delta also binds the delegation's decision Source itself. Deterministic authority additionally requires one strict package-owned `ty-dra-authority-v1` JSON projection inside that same marked item and therefore inside its text digest. An explicit-meaning projection closes exact target keys, semantic kinds, allowed origins and the canonical `after_semantics` SHA-256; a delegation projection closes the delegation key plus its allowed targets, semantic kinds and origins. The helper proves only equality between this Source-owned projection and the Delta. Free-text interpretation above that projection remains the Authoring TCB, and absence of the projection still permits ordinary conversational DRA but not an accepted deterministic checkpoint authority claim.

A free-form locator, anchor-like string or resource identity cannot create authority. Conversation-only authority is ineligible for deterministic checkpoint recovery until it has been safely materialized as project-native Source under the disclosure rules below. Accepted product, business, permission, data, algorithm, commercial, safety/security and technical meaning additionally binds an authoritative meaning Source item. A specific explicit-user decision may carry both meaning and acceptance, but its explicit projection target set must equal the Delta target set rather than merely contain it. A bounded delegation grants only choice authority and may cover a subset of its declared target range; it never becomes non-visual meaning Source. Exact visual Provider choices may use a matching delegation projection. A delegated non-visual accepted Delta additionally binds a different qualified Source item whose kind, exact target set, semantic kind, allowed origin and canonical `after_semantics` digest all match in that same item; a delegation item plus an unrelated kind-only Source cannot be composed into authority. Rejected and unresolved meaning never enters accepted requirements through resource selection or Proposal writeback.

## Scope, Incremental Selection And Owner Freshness

The explicit output/development scope is a hard ceiling. DRA computes selected existing coverage, new in-scope gaps and preservation obligations inside that ceiling; surrounding context may reveal an effect but cannot authorize generation, revision or detailed coverage outside it. An outside-ceiling effect returns the existing `decision-required` disposition with reason `scope-expansion-required`. Only an explicit user expansion changes the ceiling and causes coverage to be recomputed; no new state or automatic expansion exists.

Before generation or material revision, current Product/Surface/Screen Source owns product goals/rules, page duty, primary work object/task loop, information/action/feedback placement and interaction topology, while current Design Authority owns system/token/component-family grammar. A formal implementation commission also reads current repository technical Source for platform/framework, UI system, token adapter, component-owner roots and other target-material substrate facts. When a candidate or requested revision requires one of those durable owners to change, DRA stops, routes the decision/update to the actual owner and resumes only after rereading current Source. A candidate execution defect remains DRA-local and does not itself rewrite durable Source.

Before any style-bearing Provider generation or material revision, DRA closes every applicable current-slice style-application dimension. The minimum set is primary content priority, density, container treatment, visible-versus-hit geometry, preservation obligations and prohibited patterns, plus any other slice-specific dimension which materially changes Provider output. Each applicable dimension is task-locally dispositioned as `existing-covered`, `projected`, `not-applicable` or the existing `decision-required`; no applicable dimension may be silently omitted. A Provider run is allowed only when every applicable dimension is one of the first three. An undispositioned dimension, Source conflict or `decision-required` blocks the run before commission submission. Design-system identity, generic Token lineage or a general instruction to follow the system proves system binding only and cannot substitute for current-slice application closure.

`existing-covered` requires current controlling Source or a selected `exact-target`/`constraint` which explicitly governs the exact target, slice and declared conditions and is already carried through the Provider's existing input bindings. For every legally derivable but not directly and completely covered dimension, the existing task-local commission envelope must carry the current-slice value under `style_application`; the actual envelope contains only these `projected` fields and need not repeat `existing-covered` meaning. `not-applicable` remains a reasoned task-local judgment and creates no empty persisted field. Unresolved meaning uses the existing owner-first `decision-required` route above rather than Provider inference.

This closure reuses the current Source read and commission-building step; it is not a schema, file, persistent Projection, registry, state, Authority, Gate, readiness result or formal-handoff condition. Non-fidelity work, a read which starts no generation and a packaging, rename or byte-only export proved equivalent to the same canonical source do not trigger it. A simple high-fidelity preview still performs the task-local judgment, but gains no additional Provider generation, tool action, file, checkpoint, fixed user pause, required conversation turn, formal closure or persisted side effect. Every material revision reruns the closure before its Provider run; post-generation Design suitability remains a separate current-candidate review.

## Source-Bound Technical Feasibility And Quality Commission

For a formal `implementation_web` or `implementation_app` commission, DRA derives one ordinary `design-resource-implementation-feasibility-v1` Source input from current repository technical Source. Source records bind repository-relative paths, current SHA-256 identities and bounded locators. Consistent substrate observations cover platform, framework/runtime, UI system, token/theming adapter and component/route owner roots with exactly one `observed`, `not_applicable`, `decision_required` or `unavailable` disposition. Platform, framework/runtime and UI-system observations use identifiers; component/route owner roots use current repository-relative directory paths which pass containment and no-follow checks; a token/theming adapter may use either form. Only `observed` carries a Source-backed value; every other disposition carries a concrete reason and no value. `decision_required` or `unavailable` on a formal implementation target must reach at least one affected feasibility cell through a Source-backed blocker, while `not_applicable` requires a non-empty reason. This observation is input to generation and later Architecture Deliberation; it is not a production binding, technical Authority, implementation plan or proof that the future code uses any candidate.

The feasibility input covers every material design-side component family for its target across the declared condition partition. A family's members are its family subject, direct `family_ref`/`instance_of_ref` members and the transitive fixed-point descendants reached through `parent_ref`, `instance_of_ref` or `override_of_ref`; cycle-safe V1/V2 projection must include every matching Fact or intersecting Rule for that closure. Each exact family × target × condition cell binds that complete set and has either at least one capability/feasibility-Source-backed feasible realization or explicit blockers, never neither. A realization may compose several ordered steps and several primitives, vary by platform/profile and name multiple existing-path or authorized planned-logical-owner candidates. Browser-only evidence cannot support a native-App/React Native `native_substrate`; an independent Web carrier needs a proved `mapped_substrate` mapping or a blocker. `planned` describes only owner existence.

An authorization, mandatory realization or blocker decision is authoritative only when its technical Source record locates an exact current marked Source Item by key and `text_sha256`, and that item contains one unique strict `ty-design-feasibility-decision-v1` projection for the exact target, family and applicability digest. V1 applicability hashes canonical sorted condition references; V2 reuses the canonical compiled profile-region digest. Projection modes are limited to planned-owner authorization, required realization and feasibility blocker; a role label, file-level locator, unrelated item or same-file claim cannot substitute. The projection is a machine-checkable view of the owning marked Source Item, not another Technical Authority. A `required_realization` is empty unless that exact independent technical Source selects it; DRA preference, Provider output and the feasibility file cannot create that authority. The file references Fact/family/condition identities and technical basis, risks and blockers but carries no exact visual values in observation reasons, costs, risks or blocker descriptions. `native_substrate` describes a design-side component model corresponding to observed substrate, `mapped_substrate` describes a complete feasible mapping from an independent design carrier, and `reference` makes no complete technical-feasibility claim. None means production implementation.

Style-bearing commission content additionally names the artifact archetype, primary design challenges, desired and avoided visual character, real copy/data requirements, reference roles, design-side shared-family reuse and substrate input refs. Repeated instance-specific styling is forbidden only inside the design artifact's component model; it is not a production-code claim. Provider selection matches live target/platform, surface count, conditions/states, interaction, actual-render, bounded revision, canonical-source acquisition and formal-handoff capabilities. Direct Agent authoring remains allowed when its current capabilities fit. No remembered Provider rank, registry or automatic router is created.

Every high-fidelity candidate receives at least one actual render and one current Design suitability review. The single umbrella covers scope/Source, mechanical integrity, Design-System application, composition/hierarchy/typography/rhythm/density/content realism, coherent but non-invented design language and distinctiveness, design-side family reuse, technical feasibility, state/condition coverage and preservation. Grounded defects block; subjective aesthetics inform selection only. A candidate with no material finding may proceed directly to selection. When a material finding exists, repair the highest-impact issue with the smallest bounded patch, rerender and repeat applicable review; no revision count is mandatory.

## Base And Replayable Delta

Every material authoring/revision loop has one Base identified by repository-relative locator, raw-byte digest, encoding, EOL policy, scope ceiling, in-scope keys and explicitly excluded keys. Deterministic recovery is promised only when the Base is repository-readable, immutable or raw-digest verifiable, an already materialized project-native Proposal, or a Provider resource whose identity can be re-read and verified.

Conversation-only input, expiring external documents, unavailable attachments and sensitive material are not recoverable from a locator alone. Materialization requires explicit user authorization and either creates user-authorized project-native Source or a task-local non-authoritative snapshot after disclosure review. Credentials, keys, tokens, protected raw values and sensitive originals never enter DRA recovery state. Without safe materialization, report `cross-session deterministic recovery unavailable`.

Each Delta retains complete replay meaning rather than only an ID: stable ID and sequence, earlier accepted identities it legally supersedes, unresolved/rejected proposal identities it merely `proposes_replacement_of`, operation, target keys, before and after semantics, origin, decision authority, evidence and Source refs, explicitly unchanged keys and current status. Sequence and replacement relationships must be valid and recoverable; all accepted, rejected and unresolved rows remain visible. Only an accepted superseder with the same exact target set, matching prior semantics and a valid replacement meaning deactivates an earlier accepted Delta. Rejected or unresolved proposals never change effective requirements, and cross-target supersession fails closed. After legal supersession, every stable semantic target has at most one active accepted Delta owner; a collision blocks rather than inventing merge/composition semantics. Missing actual semantics, stale Base identity, an out-of-scope target or invalid authority fails closed.

Each effective round is rebuilt from:

`current Base@raw digest + ordered active accepted Delta semantics + current unresolved decisions + current scope/exclusions + current Design Authority identity`.

An Agent summary or a prior generated resource is never the next Base.

## Narrow Recovery-State Exception

The project owner explicitly permits one versioned, task-local, non-authoritative and deletable DRA recovery checkpoint when a real cross-interruption recovery need exists. This is persistent workflow recovery state and is the sole exception to the earlier absolute no-DRA-state wording. It is not Context, Source, a Contract, Authority, Evidence, Receipt, Gate, Provider registry, scheduler, acceptance state or a completion conclusion, and it never enters Long-Task Source/Contract/Authority/Final Gate/Evidence.

The default simple preview creates no checkpoint, persisted recovery bytes, helper write transaction, fixed user pause, additional Provider generation, formal handoff/preflight or Proposal writeback. There is no global session registry, event log, state-machine service, heartbeat, polling owner or automatic scheduler.

The checkpoint stores only non-rederivable recovery inputs: schema and session identity; an immutable Base reference or explicitly authorized safe snapshot; the exact raw-digest-bound marked Source items which carry `ty-dra-authority-v1`; complete ordered Delta semantics plus selected/rejected/unresolved identities; one set-exact `audit_expectations` catalog for changed, unchanged, resource-decision, blast-radius and inactive-Delta-leakage rows; the unique frozen final disposition for every resource-decision binding; selected-resource immutable identity and declared condition bindings; Design Authority identity; immutable Provider project/run/resource references; and, only when at least one active accepted `Delta × target` is `proposal-written`, the target locator/pre-write raw digest, exact Proposal-only patch identity/content and expected post-write raw digest. It never persists current activity, live Provider execution, Artifact readiness, Design suitability, next action or ready/not-ready conclusions. Resume re-reads the current Base, Source items, selected resource snapshots, Provider/resource identities, optional writeback target and fresh audit inputs and derives those views again. Changing a final owner is a checkpoint-input change and therefore requires the existing checkpoint CAS update.

## Owner-Local Helper

`ty-context design-resource recovery` is a narrow deterministic helper for checkpoint codec/schema validation, raw-byte and Source-item identity, replay validation, repository containment and no-follow checks, symlink/junction and collision rejection, checkpoint/Base/writeback CAS, same-directory atomic publication, encoding/EOL preservation, post-write readback, current Proposal–Resource reconciliation and helper-owned temporary cleanup. It reuses the package's strict codec, marked-Source parser, shared repository-path guard and atomic writer. Recovery input/checkpoint/audit use explicit v4 schemas and exact patch uses v3; v3 recovery/audit and v2 patch state are rejected with an explicit version error and are recreated from current Source rather than inferred or registered for migration. `update <session> --input ... --expected-sha256 ...` replaces one existing checkpoint only when its current raw digest matches, preserves the old checkpoint on conflict, rereads the published bytes and creates no registry; this supports multiple authoring rounds and frozen-owner changes without treating a prior status projection as state.

The helper does not inspect aesthetics, discover or manage Provider lifecycle, choose a design, create a second Contract/result, run Long-Task, scan unrelated temporary directories or remove unowned files. Sensitive-data admission remains an explicit disclosure decision; no generic secret scanner is claimed.

Writeback state is derived rather than stored:

- current target digest equals the pre-write digest: patch is not yet applied;
- current target digest equals the expected post-write digest: patch is already idempotently applied;
- any other digest: concurrent modification/conflict, fail closed.

The implementation uses a same-directory exclusive temporary file, write/readback and atomic rename at the filesystem boundary. Pre-rename and post-rename digest checks catch ordinary same-user concurrent modification; the local filesystem and OS rename implementation remain the named TCB rather than a hostile-writer linearizability claim. Windows and macOS behavior is exercised separately. Before removing a checkpoint, cleanup inventories the exact session directory and completes deletion only when every entry is helper-owned; an unowned entry yields an explicit partial result without deleting that entry or pretending full cleanup. A race or later cleanup failure reports the exact removed/retained boundary and never hides the primary failure.

## Current Audits, Status And Writeback

Material generation/revision performs three upstream audits over current Base/Delta and current resource bytes:

1. Requirements → Resource checks every accepted changed key against its exact frozen Delta, resource and condition sets; arbitrary resource or condition strings, missing, extra, duplicate, unresolved or falsely claimed coverage block.
2. Resource → Requirements inventories the frozen resource-decision catalog. Every binding has a stable identity and exact `(resource_ref, requirement_key, delta_id)` tuple, and independently validates origin, decision authority, target, semantic kind and raw-digest-bound Source projection; authorization for one key cannot cover another and the same tuple cannot appear in two rows. The checkpoint catalog, not the audit, freezes one exact final disposition per binding. Audit rows may only repeat and prove the current owner is equal to that frozen value. Every active `(delta_id, target_key)` has exactly one owner: `proposal-written` bound to a real patch operation, or `resource-owned-exact-visual` only for exact visual meaning bound to one selected repository-readable immutable resource, its frozen conditions and a structured `selected-source-record` owner. Inactive rejected/superseded bindings are `not-adopted`; unresolved bindings are `unresolved`. Product, business, permission, data, algorithm, commercial and safety/security meaning always resolves to independent authoritative Source and cannot use resource-owned disposition.
3. Unexpected Blast Radius closes the frozen catalog, including every explicitly excluded key, across out-of-scope pages, controls, copy, layout, tokens, states and reappearance of inactive meaning. Missing, extra, duplicate or unresolved rows fail closed. Explicitly unchanged rows likewise equal the frozen resource, condition and Source-basis sets rather than merely naming known entries. The inactive universe is exactly rejected + unresolved + superseded accepted Delta, with one reasoned no-leakage row per identity; missing, extra, duplicate, leaked or active rows block.

A material/recoverable loop may claim bounded change and preservation only from that complete current catalog and its bindings. A simple preview or ordinary loop without complete bindings performs conservative impact analysis from readable Source, marks the unverified remainder and either regenerates conservatively within the ceiling or returns `decision-required`; it cannot claim a complete dependency closure or that only the named resources are affected, and it cannot expand the ceiling for safety.

Provider success, complete fields or repeated values never prove suitability. `Design suitability` is one freshly derived umbrella review, distinct from Provider execution, Artifact readiness and human selection. It covers scope/Source suitability, mechanical checks, Design-System application, visual craft and language, design-side component reuse, technical feasibility, state/condition coverage and preservation, at depth proportional to intent; every material revision re-runs applicable subchecks and reports unchecked conditions. Direct/Design-Authority conflicts, wrong targets/conditions, missing material states, placeholder-final content, unauthorized material meaning, unresolved promotion, stale technical/design identities and incomplete formal closure block suitability. Repeated values are an investigation signal only: a valid shared Token or inherited component variant remains allowed. Passing a visual or mechanical subcheck cannot select a resource, establish formal completeness or independently produce `handoff-ready`.

Status cards are derived from current facts and show Base identity; accepted/rejected/unresolved Delta; current changed and explicitly unchanged keys; Provider run identity; live Provider execution; live Artifact readiness; freshly audited Design suitability; bidirectional/blast-radius findings; writeback CAS state; and next action. No stale checkpoint conclusion supplies those fields.

Before selected Proposal writeback, freeze target locator, pre-write raw digest, exact patch and patch identity, expected post-write bytes/digest, selected resource identities and `proposal_written_delta_ids`. The expected patch universe is exactly the active accepted `Delta × target` bindings whose checkpoint-frozen disposition is `proposal-written`; a resource-owned exact value remains in effective requirements and the audit universe but cannot appear in any Proposal patch binding or Proposal projection. Every exact-patch-v4 operation has exactly one operation ID, one Delta, one target, one semantic binding, before/after text and hashes, canonical before/after semantic hashes, an explicit restricted scalar-to-text-span projection and one original-preimage `utf16-code-unit-v1` source span. Each non-null Proposal-owned semantics contains exactly one JSON scalar leaf. Replace projects one before and one after leaf, rejects control-character scalar injection and requires the prefix and suffix outside those scalar projections to remain byte-for-text identical. Add preserves one exact insertion anchor and adds exactly one package-canonical `ty-dra-proposal-scalar-v1` carrier containing only target key, semantic path and canonical scalar value. Remove deletes only one already canonical target-matching carrier, projects its before leaf to null and requires empty `after_text`; it cannot widen across an adjacent heading, requirement or other target. Writing `disabled`, `removed`, `deprecated` or any other non-empty substitute for a remove is new meaning and requires another Delta. Unsupported free-text add/remove reports deterministic Proposal writeback unavailable instead of falling back to a generic replacement. A text span cannot carry multiple semantic targets.

Checkpoint create/update resolves every operation span against the same decoded pre-write Proposal before any mutation, requires the frozen text/hash to match that original interval and rejects overlapping, nested, shared-character or same-position insertion spans. Apply uses those original offsets in descending order rather than sequential search, so a later operation cannot consume text produced by an earlier one. The computed postimage is derived only by replacing the frozen disjoint intervals; readback checks the whole-file digest and each length-adjusted output interval, which jointly prove that all inter-operation gaps and untouched prefix/suffix content stayed identical. UTF-8 with or without BOM, UTF-16 LE/BE and uniform LF/CRLF/CR retain the existing codec and CAS behavior. The helper therefore proves Delta-to-declared-Proposal-scalar conservation and bounded carrier non-interference without claiming arbitrary natural-language entailment; inactive/unknown/resource-owned bindings are forbidden, changing red semantics to a purple patch fails create/update, and an active superseder's prior exact text projection must be absent from both computed and reread post-write bytes. Recovery input/checkpoint/audit remain v4; a v4 writeback containing exact-patch-v3 fails closed and is recreated from current Source and Proposal rather than migrated. The immutable replay Base and mutable writeback target are distinct locators; updating the Proposal itself therefore requires an explicitly authorized immutable Source or recovery snapshot as Base.

The helper checks current identity, applies only Proposal-owned accepted meaning, writes atomically, rereads, verifies expected bytes, operation-specific after-text occurrence or remove absence and whole-file digest, and evaluates a fresh reconciliation input against the complete checkpoint catalog. When no frozen binding is Proposal-owned, the checkpoint omits writeback entirely and `recovery reconcile <session> --audit <audit.json>` re-reads current Source, resource and downstream-owner bytes and performs the same catalog reconciliation without a Proposal transaction or fabricated empty patch. `reconciliation-balanced` requires exact accepted coverage, audit equality with every frozen final owner, complete resource/blast/inactive dispositions, Source/resource/condition-bound unchanged semantics, no unresolved audit row, no leakage and no unintended changes; otherwise it is `blocked`. Apply reports only `writeback-applied`, `writeback-idempotent`, `external-resource-revalidation-pending` or `blocked`; read-only reconcile reports only `reconciliation-balanced`, `external-resource-revalidation-pending` or `blocked`. The helper never reports `handoff-ready`. Recovery identities prove only `repository-snapshot`, `selected-source-record` or `external-immutable`; the stronger formal Web/App handoff identity remains exclusively with `ty-context design-resource preflight`. The Skill may report handoff readiness only after balanced helper output, current Provider/resource revalidation, durable final owners, applicable formal handoff/preflight and no unresolved blocker. Reconciliation is diagnostic upstream handoff information only and never replaces Proposal, selected resources, formal handoff, downstream UI Authority Closure or Final Gate.

## Review, Selection And Formal Closure

`Design Resource Review & Selection Stop` is a user-facing interaction point for direction review, correction and candidate selection. It is not an approval record, persisted status, Gate, acceptance result, formal-completeness claim or mandatory extra turn for a small request. Design suitability informs the stop but never performs selection. Ordinary conversational selection creates no persistent state and must be reconfirmed if lost; deterministic cross-interruption recovery uses only the existing raw-digest-bound marked Source, `ty-dra-authority-v1`, selected-source binding and conditional checkpoint path.

Selection binds the canonical selected-source digest, target, declared conditions and controlling Source/Design-Authority identity. A preview, PNG, export archive, file name or wrapper is derived output: proved equivalence to that canonical source preserves selection, while a visible or semantic difference requires fresh suitability review and another Review & Selection Stop.

For a selected formal Web/App implementation handoff, the formal handoff owner runs complete canonical-source/dependency/Census/manifest/bundle/preflight closure and the separate current technical-feasibility-input closure after direction selection. A newly exposed state, resource, condition, visible/semantic change or decision returns to the Review & Selection Stop. The one consolidated idempotent Proposal reconciliation occurs only after the selected direction, complete formal closure and absence of a new visible decision; non-formal small requests retain their existing one-turn option. Product/business/permission/data/algorithm/technical meaning remains equal to its independent authoritative Source, resource-owned exact visual facts remain equal to the selected canonical resource under declared conditions, and Proposal/handoff bindings must preserve those owner boundaries without loss, unsupported gain, tampering or scope overreach. Feasibility candidates remain choices for downstream Architecture Deliberation and never select the production owner here.

## Long-Task Boundary

Proposal → resource → revision history is DRA upstream quality responsibility. Long-Task may prove only the final Proposal, selected immutable resources, formal handoff, Contract bindings, current implementation and current Evidence which actually enter its Source authority. DRA checkpoints, status cards, audit findings and reconciliation cannot be used to claim that historical Provider execution was correct.

The protected Long-Task `P/K/R1/R2/B/F/E` model and accepted-terminal theorem remain unchanged. Semantic Granularity, Semantic Fidelity and Delegated-Choice Validity refine whether `K`, `B` and `R1` form adequate comparison authority; they do not replace `R1`/`R2`. `R2` remains the existing Source/Contract continuity, Authority, observer, repair-localization, freshness and sole Final-Gate responsibility.
