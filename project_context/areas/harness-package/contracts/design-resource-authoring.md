# Design Resource Authoring Contract

## Role And Authority Boundary

`design-resource-authoring` is an explicit, upstream commissioner. It owns bounded resource scope, task-local semantic replay, Provider adaptation, current-resource audit, selected-proposal writeback and optional interruption recovery. It does not own product/business/permission/data/algorithm/commercial/security meaning, durable Design Authority, Provider lifecycle, implementation acceptance or Long-Task completion.

Candidate resources remain ordinary Source. A selected resource may uniquely own exact visual values for its declared conditions, but selection cannot authorize the reason those values or any new material meaning are adopted. Material decisions keep four independent dimensions:

- `origin`: `user-direct`, `necessary-derived`, `repository-evidence-backed` or `provider-suggested`;
- `decision_authority`: `explicit-user`, `delegated:<bounded-scope>` or `none`;
- `evidence_refs`: resources which display or support the meaning; and
- `status`: `accepted`, `rejected` or `unresolved`.

A Provider suggestion becomes accepted only through explicit user acceptance or a bounded delegation which covers that choice. Repository evidence can support a decision but cannot silently create product authority. Every `explicit-user` authority, bounded delegation and accepted Delta `source_ref` resolves to an actual marked Source item in a repository-readable file and is bound to both the file's current raw-byte digest and the item's current semantic digest; an accepted delegated Delta also binds the delegation's decision Source itself. Deterministic authority additionally requires one strict package-owned `ty-dra-authority-v1` JSON projection inside that same marked item and therefore inside its text digest. An explicit-meaning projection closes exact target keys, semantic kinds, allowed origins and the canonical `after_semantics` SHA-256; a delegation projection closes the delegation key plus its allowed targets, semantic kinds and origins. The helper proves only equality between this Source-owned projection and the Delta. Free-text interpretation above that projection remains the Authoring TCB, and absence of the projection still permits ordinary conversational DRA but not an accepted deterministic checkpoint authority claim.

A free-form locator, anchor-like string or resource identity cannot create authority. Conversation-only authority is ineligible for deterministic checkpoint recovery until it has been safely materialized as project-native Source under the disclosure rules below. Accepted product, business, permission, data, algorithm, commercial, safety/security and technical meaning additionally binds an authoritative meaning Source item. A specific explicit-user decision may carry both meaning and acceptance, but its explicit projection target set must equal the Delta target set rather than merely contain it. A bounded delegation grants only choice authority and may cover a subset of its declared target range; it never becomes non-visual meaning Source. Exact visual Provider choices may use a matching delegation projection. A delegated non-visual accepted Delta additionally binds a different qualified Source item whose kind, exact target set, semantic kind, allowed origin and canonical `after_semantics` digest all match in that same item; a delegation item plus an unrelated kind-only Source cannot be composed into authority. Rejected and unresolved meaning never enters accepted requirements through resource selection or Proposal writeback.

## Base And Replayable Delta

Every material authoring/revision loop has one Base identified by repository-relative locator, raw-byte digest, encoding, EOL policy, scope ceiling, in-scope keys and explicitly excluded keys. Deterministic recovery is promised only when the Base is repository-readable, immutable or raw-digest verifiable, an already materialized project-native Proposal, or a Provider resource whose identity can be re-read and verified.

Conversation-only input, expiring external documents, unavailable attachments and sensitive material are not recoverable from a locator alone. Materialization requires explicit user authorization and either creates user-authorized project-native Source or a task-local non-authoritative snapshot after disclosure review. Credentials, keys, tokens, protected raw values and sensitive originals never enter DRA recovery state. Without safe materialization, report `cross-session deterministic recovery unavailable`.

Each Delta retains complete replay meaning rather than only an ID: stable ID and sequence, earlier accepted identities it legally supersedes, unresolved/rejected proposal identities it merely `proposes_replacement_of`, operation, target keys, before and after semantics, origin, decision authority, evidence and Source refs, explicitly unchanged keys and current status. Sequence and replacement relationships must be valid and recoverable; all accepted, rejected and unresolved rows remain visible. Only an accepted superseder with the same exact target set, matching prior semantics and a valid replacement meaning deactivates an earlier accepted Delta. Rejected or unresolved proposals never change effective requirements, and cross-target supersession fails closed. After legal supersession, every stable semantic target has at most one active accepted Delta owner; a collision blocks rather than inventing merge/composition semantics. Missing actual semantics, stale Base identity, an out-of-scope target or invalid authority fails closed.

Each effective round is rebuilt from:

`current Base@raw digest + ordered active accepted Delta semantics + current unresolved decisions + current scope/exclusions + current Design Authority identity`.

An Agent summary or a prior generated resource is never the next Base.

## Narrow Recovery-State Exception

The project owner explicitly permits one versioned, task-local, non-authoritative and deletable DRA recovery checkpoint when a real cross-interruption recovery need exists. This is persistent workflow recovery state and is the sole exception to the earlier absolute no-DRA-state wording. It is not Context, Source, a Contract, Authority, Evidence, Receipt, Gate, Provider registry, scheduler, acceptance state or a completion conclusion, and it never enters Long-Task Source/Contract/Authority/Final Gate/Evidence.

The default simple preview creates no checkpoint, persisted recovery bytes, helper write transaction, fixed user pause, additional Provider generation, formal handoff/preflight or Proposal writeback. There is no global session registry, event log, state-machine service, heartbeat, polling owner or automatic scheduler.

The checkpoint stores only non-rederivable recovery inputs: schema and session identity; an immutable Base reference or explicitly authorized safe snapshot; the exact raw-digest-bound marked Source items which carry `ty-dra-authority-v1`; complete ordered Delta semantics plus selected/rejected/unresolved identities; one set-exact `audit_expectations` catalog for changed, unchanged, resource-decision, blast-radius and inactive-Delta-leakage rows; the unique frozen final disposition for every resource-decision binding; selected-resource immutable identity and declared condition bindings; Design Authority identity; immutable Provider project/run/resource references; and, only when at least one active accepted `Delta × target` is `proposal-written`, the target locator/pre-write raw digest, exact Proposal-only patch identity/content and expected post-write raw digest. It never persists current activity, live Provider execution, Artifact readiness, Design suitability, next action or ready/not-ready conclusions. Resume re-reads the current Base, Source items, selected resource snapshots, Provider/resource identities, optional writeback target and fresh audit inputs and derives those views again. Changing a final owner is a checkpoint-input change and therefore requires the existing checkpoint CAS update.

## Owner-Local Helper

`ty-context design-resource recovery` is a narrow deterministic helper for checkpoint codec/schema validation, raw-byte and Source-item identity, replay validation, repository containment and no-follow checks, symlink/junction and collision rejection, checkpoint/Base/writeback CAS, same-directory atomic publication, encoding/EOL preservation, post-write readback, current Proposal–Resource reconciliation and helper-owned temporary cleanup. It reuses the package's strict codec, marked-Source parser, shared repository-path guard and atomic writer. Recovery input/checkpoint/audit use explicit v4 schemas and exact patch uses v3; v3 recovery/audit and v2 patch state are rejected with an explicit version error and are recreated from current Source rather than inferred or registered for migration. `update <session> --input ... --expected-sha256 ...` replaces one existing checkpoint only when its current raw digest matches, preserves the old checkpoint on conflict, rereads the published bytes and creates no registry; this supports multiple authoring rounds and frozen-owner changes without treating a prior status projection as state.

The helper does not inspect aesthetics, discover or manage Provider lifecycle, choose a design, create a second Contract/result, run Long-Task, scan unrelated temporary directories or remove unowned files. Sensitive-data admission remains an explicit disclosure decision; no generic secret scanner is claimed.

Writeback state is derived rather than stored:

- current target digest equals the pre-write digest: patch is not yet applied;
- current target digest equals the expected post-write digest: patch is already idempotently applied;
- any other digest: concurrent modification/conflict, fail closed.

The implementation uses a same-directory exclusive temporary file, write/readback and atomic rename at the filesystem boundary. Pre-rename and post-rename digest checks catch ordinary same-user concurrent modification; the local filesystem and OS rename implementation remain the named TCB rather than a hostile-writer linearizability claim. Windows and macOS behavior is exercised separately. Before removing a checkpoint, cleanup inventories the exact session directory and completes deletion only when every entry is helper-owned; an unowned entry yields an explicit partial result without deleting that entry or pretending full cleanup. A race or later cleanup failure reports the exact removed/retained boundary and never hides the primary failure.

## Current Audits, Status And Writeback

Material generation/revision performs three upstream audits over current Base/Delta and current resource bytes:

1. Requirements → Resource checks every accepted changed key against its exact frozen Delta, resource and condition sets; arbitrary resource or condition strings, missing, extra, duplicate, unresolved or falsely claimed coverage block.
2. Resource → Requirements inventories the frozen resource-decision catalog. Every binding has a stable identity and exact `(resource_ref, requirement_key, delta_id)` tuple, and independently validates origin, decision authority, target, semantic kind and raw-digest-bound Source projection; authorization for one key cannot cover another and the same tuple cannot appear in two rows. The checkpoint catalog, not the audit, freezes one exact final disposition per binding. Audit rows may only repeat and prove the current owner is equal to that frozen value. Every active `(delta_id, target_key)` has exactly one owner: `proposal-written` bound to a real patch operation, or `resource-owned-exact-visual` only for exact visual meaning bound to one selected repository-readable immutable resource, its frozen conditions and a structured `selected-source-record` owner. Inactive rejected/superseded bindings are `not-adopted`; unresolved bindings are `unresolved`. Product, business, permission, data, algorithm, commercial and safety/security meaning always resolves to independent authoritative Source and cannot use resource-owned disposition.
3. Unexpected Blast Radius closes the frozen catalog, including every explicitly excluded key, across out-of-scope pages, controls, copy, layout, tokens, states and reappearance of inactive meaning. Missing, extra, duplicate or unresolved rows fail closed. Explicitly unchanged rows likewise equal the frozen resource, condition and Source-basis sets rather than merely naming known entries. The inactive universe is exactly rejected + unresolved + superseded accepted Delta, with one reasoned no-leakage row per identity; missing, extra, duplicate, leaked or active rows block.

Provider success, complete fields or repeated values never prove suitability. Direct/Design-Authority conflicts, wrong targets/conditions, missing material states, placeholder-final content, unauthorized material meaning, unresolved promotion, stale identities and incomplete formal closure block suitability. Repeated values are an investigation signal only: a valid shared Token or inherited component variant remains allowed.

Status cards are derived from current facts and show Base identity; accepted/rejected/unresolved Delta; current changed and explicitly unchanged keys; Provider run identity; live Provider execution; live Artifact readiness; freshly audited Design suitability; bidirectional/blast-radius findings; writeback CAS state; and next action. No stale checkpoint conclusion supplies those fields.

Before selected Proposal writeback, freeze target locator, pre-write raw digest, exact patch and patch identity, expected post-write bytes/digest, selected resource identities and `proposal_written_delta_ids`. The expected patch universe is exactly the active accepted `Delta × target` bindings whose checkpoint-frozen disposition is `proposal-written`; a resource-owned exact value remains in effective requirements and the audit universe but cannot appear in any Proposal patch binding or Proposal projection. Every exact-patch-v3 operation has exactly one operation ID, one Delta, one target, one semantic binding, before/after text and hashes, canonical before/after semantic hashes and an explicit restricted scalar-to-text-span projection. Each non-null Proposal-owned semantics contains exactly one JSON scalar leaf: replace projects one before and one after leaf, add uses null before semantics plus a structural text anchor and projects the one after leaf, and remove projects one before leaf to null, requires empty `after_text` and proves the old text disappeared. Writing `disabled`, `removed`, `deprecated` or any other non-empty substitute for a remove is new meaning and requires another Delta. A text span cannot carry multiple semantic targets. The helper therefore proves Delta-to-declared-Proposal-text conservation without claiming arbitrary natural-language entailment; inactive/unknown/resource-owned bindings are forbidden, changing red semantics to a purple patch fails create/update, and an active superseder's prior exact text projection must be absent from both computed and reread post-write bytes. The immutable replay Base and mutable writeback target are distinct locators; updating the Proposal itself therefore requires an explicitly authorized immutable Source or recovery snapshot as Base.

The helper checks current identity, applies only Proposal-owned accepted meaning, writes atomically, rereads, verifies expected bytes, operation-specific after-text occurrence or remove absence and whole-file digest, and evaluates a fresh reconciliation input against the complete checkpoint catalog. When no frozen binding is Proposal-owned, the checkpoint omits writeback entirely and `recovery reconcile <session> --audit <audit.json>` re-reads current Source, resource and downstream-owner bytes and performs the same catalog reconciliation without a Proposal transaction or fabricated empty patch. `reconciliation-balanced` requires exact accepted coverage, audit equality with every frozen final owner, complete resource/blast/inactive dispositions, Source/resource/condition-bound unchanged semantics, no unresolved audit row, no leakage and no unintended changes; otherwise it is `blocked`. Apply reports only `writeback-applied`, `writeback-idempotent`, `external-resource-revalidation-pending` or `blocked`; read-only reconcile reports only `reconciliation-balanced`, `external-resource-revalidation-pending` or `blocked`. The helper never reports `handoff-ready`. Recovery identities prove only `repository-snapshot`, `selected-source-record` or `external-immutable`; the stronger formal Web/App handoff identity remains exclusively with `ty-context design-resource preflight`. The Skill may report handoff readiness only after balanced helper output, current Provider/resource revalidation, durable final owners, applicable formal handoff/preflight and no unresolved blocker. Reconciliation is diagnostic upstream handoff information only and never replaces Proposal, selected resources, formal handoff, downstream UI Authority Closure or Final Gate.

## Long-Task Boundary

Proposal → resource → revision history is DRA upstream quality responsibility. Long-Task may prove only the final Proposal, selected immutable resources, formal handoff, Contract bindings, current implementation and current Evidence which actually enter its Source authority. DRA checkpoints, status cards, audit findings and reconciliation cannot be used to claim that historical Provider execution was correct.

The protected Long-Task `P/K/R1/R2/B/F/E` model and accepted-terminal theorem remain unchanged. Semantic Granularity, Semantic Fidelity and Delegated-Choice Validity refine whether `K`, `B` and `R1` form adequate comparison authority; they do not replace `R1`/`R2`. `R2` remains the existing Source/Contract continuity, Authority, observer, repair-localization, freshness and sole Final-Gate responsibility.

## Verification And Admission

Behavior tests cover strict v3→v4 recovery/audit and v2→v3 patch failure, Source projection exact-target/semantic/origin/meaning mismatch and conversation-only rejection, delegated non-visual independent same-item meaning binding, Base/Delta replay, active-target collision, status-aware same-target supersession and inactive leakage, exact per-key/global-unique decision binding, catalog-exact requirement/unchanged/resource/condition/basis/blast rows and checkpoint-frozen single final owners, Proposal-only atomic replace/add/remove projection, multi-leaf/shared-span/multi-binding and null-remove substitution rejection, resource-only read-only reconciliation, stale Base, checkpoint and writeback pre/post/conflict CAS, path escape, symlink/junction/hardlink and collision rejection, encoding/EOL preservation, atomic failure/partial cleanup, writeback idempotence, fresh balanced/blocked/external-pending reconciliation and the no-write simple path. Managed/generated/package parity proves distribution only.

The independent frozen DRA benchmark track measures semantic loss/distortion/unsupported gain, rejected/unresolved leakage, fake/conversation-only authority, multi-key authorization spread, illegal supersession, incomplete audit universes/final ownership, wrong-target/blast-radius handling, correct blocking, false blocking and simple-path token/wall/tool/persistence cost. Requested model/effort/Provider values are not reported as effective provenance: the runner verifies effective values from authoritative execution events when observable and otherwise marks them `unverified` with environment/trace doubt, which forces the five-pair rule. A sanitized admission attestation binds the frozen configuration, result identities and exact candidate Git tree without raw prompts, events or sensitive content. Static guidance, an attestation or one pair cannot establish Agent effect or ROI.
