# Project Tiny Context Harness — Product And Workflow Specification

## 1. Product Purpose

Project Tiny Context Harness is repo-native memory and delivery-drift protection for AI coding agents. Its design is intentionally small:

1. **Minimal Context** preserves durable project facts that code cannot reliably explain: goals/non-goals, ownership, architecture/interface/state boundaries and repeatable verification/deployment paths.
2. **Workflow Contract** defines the lightweight default loop: core/default Context, manifest routing plus one bounded Context search, dependency-driven read widening, conditional multi-target disambiguation, semantic/design obligations when applicable, one externally observable Architecture Deliberation with risk-triggered applicable-quality assessment, one `Context Delta`, platform-internal planning, Goal-owned implementation under a thin implementation-quality discipline, project verification including any repository-owned changed-path scope check, Contract Conformance carrying Engineering Quality Conformance (including Architecture Conformance), semantic-Fact closure and selected-design closure when applicable, and a separate Context drift check.
3. **Long-Task Workflow** turns an ordinary user request or external implementation proposal into one complete Canonical Delivery Contract, then adds verifier-owned current-snapshot acceptance for work that needs pause/compaction/new-session recovery or multiple observable outcomes.

These are the three product mechanisms. Every delivery reads Minimal Context. Ordinary delivery uses the automatically applicable prompt-level Workflow Contract; an explicitly selected or already-bound delivery uses the logical `long-task-workflow` Skill as the sole Long-Task execution and completion carrier. The default route creates no validator result, Receipt, persisted workflow state or machine-completion authority. `design-system-authoring` and `design-resource-authoring` are independent optional upstream Skills, not Long-Task stages: selected resources may feed either route, and Long-Task requires no design-resource step when the delivery needs none.

Raw/revised proposals, selected design resources and mixed attachments enter one Source-bound Contract Draft loop in `long-task-workflow` immediately. Source inventory/refinement, direct and traceable derived/delegated/evidence-backed meaning, complete standard/custom non-UI semantic Fact expansion, interactive surface/region/control/state/feedback detail, preference-sensitive research, real Markdown Source completeness, markers, repository binding and Contract mapping converge together before Preflight/Compile. This removes both the external handoff and the internal serial Source-authoring pass without adding a separate Source stage, gate, state or second plan. `source-plan-authoring` remains only as a retired compatibility pointer, while existing Source Plans remain valid ordinary Source.

The complete approved Source Plan for the page-level UI/UX authority upgrade is indexed at [`docs/page-level-uiux-authority-source-plan.md`](docs/page-level-uiux-authority-source-plan.md). It records input provenance, stable requirement/outcome/acceptance keys, the Design Context Depth Model, UI Authority Closure, Control field semantics, non-goals, risks and verification impact. It is upstream Source/navigation rather than registered Context or completion authority.

The actual design-generation engine stays outside Tiny Context. The base package includes explicit-only `design-system-authoring`: normally selected at project cold start, it discovers live Open Design MCP resources/tools, feature-detects lifecycle methods, uses the official same-daemon generation/revision/accept API when current MCP lacks creation, separates candidate/selection/adoption and reconciles the selected result into canonical `DESIGN.md`, exactly one authored token source/direction and owning Context. Open Design ID/revision/digest/project binding remains synchronization provenance, not a second authority; no init/default/downstream workflow auto-runs the Skill.

The base also includes `design-resource-authoring`, a thin explicitly triggered Open Design commissioner. It accepts an initial proposal and other product/technical/design Source, fixes the requested output/development content as a hard ceiling and commissions only the smallest sufficient resource set. Style-bearing resources require configured Design Authority and an Open Design project whose `designSystemId` matches the adopted system; if missing, the Skill stops and points to explicit `design-system-authoring` without invoking it. Low-fidelity structure, IA/flow and semantics-only state studies remain ungated. Candidate iteration keeps a task-local decision delta; after final selection the Skill performs one consolidated idempotent reconciliation of accepted decisions into the initial proposal, excluding rejected/unresolved choices. It never edits a Source Plan, Context, `DESIGN.md`, code or Contract.

The complete research and implementation Source Plan for these Open Design adapter capabilities is indexed at [`docs/design-resource-authoring-source-plan.md`](docs/design-resource-authoring-source-plan.md). It records live provider findings, requirements, amendments, bounded experiments, failure semantics and verification impact. It remains upstream Source/navigation rather than registered Context, Design Authority or approval. Generated candidates remain ordinary Source and authorize no fidelity; only explicit design-system adoption changes authority, while development workflows own UI Authority Closure, implementation and proof.

Minimal Context optimizes two purposes: preserve durable non-implementation facts, and let an Agent recover and update those facts with low search and attention cost. Near-universal facts use the core files and default area root; specialized role Context is `on-demand`. Before `Context Delta`, manifest candidates are supplemented by one bounded text search over `project_context/**` using a small set of high-signal task terms. The result is an expandable working set rather than a maximum readable set: later semantic or code dependencies may add any relevant Area/shared Context without turning the complete graph into the global default. The search creates no index, cache, registry, state, authority or read ACL. `ty-context doctor` reports the deterministic default read set, byte footprint, soft-budget overages, exact duplicate default files and `DESIGN.md` authority status; this is advisory observability only. A byte heuristic never authorizes omitting, compressing beyond readability or misclassifying required recovery facts, and the source release suite verifies the advisory behavior rather than imposing an absolute Context-size acceptance gate.

Material production UI adds UI Authority Closure and one conditional readiness question rather than a design phase or artifact chain. The depth model assigns global principles, cross-surface responsibility, Screen/Control semantics, visual-system facts, concrete targets and verification to distinct owners. Design Source Projection maps durable surface/flow/Screen/Control/state meaning to existing Product Surface or Screen/interaction Context; durable visual-system/token/motion-policy/rationale meaning to `DESIGN.md`; exact compositions, values, timelines, condition-specific facts and asset bytes to versioned targets; repeatable proof routes to verification Context; and delivery-local provenance, applicability, blockers and proof bindings to Source/Contract meaning. Stable surface/control/target keys connect them without copying the handoff.

Each adopted decision-relevant exact target/constraint has exactly one canonical adoption record. `DESIGN.md` owns project/system/component-family targets; the owning Screen Contract owns one-screen/interaction-specific targets. That record owns interpretation, selection basis, readable immutable locator/digest, declared condition coverage and editable upstream owner/locator/update route; every other layer keeps only the stable target key, canonical owner/anchor and local applicability. A registry mention or handoff coverage-index mention alone is not consumption. Affected workflows actively open the target before deciding, and updates create a new immutable version rather than overwrite the adopted baseline. `exact-target` permits fidelity comparison only for its named conditions, `constraint` governs only its stated scope, and `inspiration`, a candidate or an unconfigured starter never authorizes invented production layout. Dedicated external design systems may author candidates and selected targets upstream; a material unresolved preference remains a genuine decision, and downstream adoption remains separate.

The Long-Task Workflow V2 product equation is:

> one complete delivery = one authoritative target-qualified Contract + one currently selected platform-native execution Goal + one selected verification workspace + one user model-choice checkpoint + Goal-owned adaptive technical implementation + one non-authoritative acceptance/verification Frontier + one trustworthy capability-aware Evidence Kernel + one Final Gate

The controlling objective, trusted-result boundary, Draft lifecycle, upstream Source boundary and mechanism-admission rule below govern every later Long-Task section. Existing implementation convenience, historical progress or local wording cannot weaken them.

## Sparse Context Workspaces / Monorepo Change Scope

Context stores durable product, technical, UI/UX-authority and verification facts in one recoverable project-owned tree. It does not promise that a prompt-guided Agent applies every recovered fact correctly; project tests, runtime evidence and review remain the behavior boundary. Exact visual values/resources remain in canonical design Source while Context/`DESIGN.md` owns stable authority, applicability and update routes.

For a monorepo, `project_context/workspaces/<workspace-id>/**` is an optional centralized, sparse mirror of implementation workspaces that actually own durable non-code facts:

```text
project_context/
  global.md
  architecture.md
  context.toml
  areas/                         # cross-workspace, repository-wide and shared owners
  workspaces/
    mobile/
      areas/
        product.md
        screens.md
        verification.md
    wechat-miniapp/
      areas/
        product.md
        screens.md
    api/
      areas/
        contract.md
        verification.md
```

Every represented Context workspace corresponds to exactly one repository-relative implementation/code root through existing `[[areas]].root` and `context`. It may contain several Areas for distinct durable semantic responsibilities. The reverse mapping is intentionally optional: an npm/Nx/Bazel/Cargo/Maven workspace with no durable Context gets no empty directory, placeholder or manifest row. Package-manager/build files remain the complete implementation-workspace inventory; Context does not duplicate or auto-discover that topology.

Workspace-local Areas stay under their Context workspace. Genuinely cross-workspace, repository-wide, shared, infrastructure or governance Areas stay under top-level `project_context/areas/**` and are not copied into every consumer. Single-workspace and non-monorepo projects retain the existing top-level `areas/**` layout, initialization and validation. Existing `[[areas]]`, `[[context]]`, `root`, `context`, role, read-policy and trigger fields are sufficient; there is no `[[workspaces]]` block or mandatory `workspace`, `owner_area`, `applies_to` or `requires` field.

The monorepo default Area should normally be a small top-level repository-common owner. Workspace-local Area/role Context stays `on-demand` unless its facts are genuinely near-universal; representing a client workspace never makes that client the implicit global default. This keeps the default path public/common while preserving precise on-demand discovery.

The input to this placement is ordinary repository fact: the code-root path and the durable semantic owner. The transformation is only a stable central directory plus the existing explicit `root -> context` mapping. Workspace placement is therefore an ownership/discovery namespace, not another Authority, package graph, permission model or runtime state. The design avoids an abstract scope layer, exhaustive empty mirrors, scattered Context and universal topology scanning because they add maintenance or a second mental model without improving that ownership truth.

Default reading remains adaptive. The Agent starts with core/default Context, manifest/trigger candidates and one bounded search, reads semantically relevant matches and widens to shared backend, sibling-client, cross-workspace contract, `DESIGN.md`, selected resources or code owners as dependencies emerge. A Context workspace can prioritize where to look, but it is never a read ACL, a maximum readable set or a mandate to read every file below the target workspace. A full-graph read does not become the ordinary default.

Read scope and intended workspace set are separate. The workflow resolves task-local intended workspace(s) from explicit user/product/path/repository facts. If those facts still leave materially different sibling workspaces plausible, it asks one concise target question before product edits rather than choosing the default Area, nearest/recently changed client or a generic keyword collision. Intentional cross-workspace work enumerates every intended workspace. Shared/backend Context or code may be read freely and may be changed when it is an attributable supporting requirement, but reading alone does not authorize that edit.

After implementation, the preferred objective extension point is a repository-owned changed-path/target-scope verifier. It compares exact paths attributable to the current task against intended workspaces plus declared supporting/shared scope and must not charge unrelated pre-existing dirty paths to the task. Without such a checker, Contract and Architecture Conformance review the final diff against durable Context/code owners. Tiny Context adds no universal package-manager mapper, path/import/runtime dependency scanner, persisted target declaration, applicability matrix, workspace registry, orphan/overlap doctor Gate or second Authority. Active Long-Task retains its existing expected/supporting/forbidden/unclassified path classifier and `scope_escape`; the default route does not duplicate it.

Root `DESIGN.md` remains the current shared project Design Authority for both monorepo and non-monorepo layouts. Creating a Context workspace does not create an independent design system. Multiple workspace-local Design Authorities would require a separate future mechanism that deliberately changes canonical ownership, doctor, authoring, token-source and update-route behavior.

Compatibility and cost remain bounded: non-monorepo behavior is unchanged, monorepos opt in only where Context exists, and unambiguous tasks add no clarification or full-read cost. Core/default/manifest/trigger/bounded-search coverage is not reduced; later reading remains unconstrained; the wrong-sibling rejection path is added without weakening Long-Task's full Context Authority, existing scope classifier, Final Gate or `F = Implementation Freedom Boundary`. Static tests prove directory/schema compatibility, guidance distribution, parity and non-degradation sentinels only. Claims about improved real-Agent recall, target selection or total ROI require fixed independent fresh-Agent paired runs with hidden product probes.

## Shared Engineering Quality Assurance

Every implementation delivery has one thin Shared Engineering Quality Obligation. Before the first implementation edit, the Agent surfaces one externally observable, repository-bound `Architecture Deliberation` that also records triggered quality attributes or a concrete preservation basis. During implementation, a small `Implementation Quality Discipline` preserves the existing owner, unique source of truth, real failure/resource boundaries and minimum justified abstraction while leaving order, methods and feedback cadence Goal-owned. After project-owned verification, one `Engineering Quality Conformance` closure includes the existing `Architecture Conformance` and checks the triggered falsifiable invariants on the current candidate.

`Applicable Quality Attributes` and `Implementation Quality Discipline` are subcriteria, not stages, Gates, states or artifacts. Occurrence is universal and depth is risk-proportional. A small semantics-preserving change names the current owner, extension point, shortest reliable verification route, unchanged applicable quality attributes and why it creates no new or worsened debt. Material work additionally resolves the unique source of truth, dependency direction, interface/state/persistence/resource/runtime lifecycle, selected and rejected alternatives, one plausible adjacent change and its extension point, touched debt, forbidden shortcuts, project-owned executable checks and applicable failure/load/threat scenarios. A material scope, owner, controlling-Context, dependency, selected-design, quality-applicability or debt-disposition change stales the deliberation.

Exact product, business and technical predicates—including explicit SLO, performance budget, security, reliability or compatibility requirements—remain owned by the existing Non-UI Semantic Fact closure; exact selected UI/UX Facts remain owned by selected-design closure. Shared Engineering Quality owns implementation boundaries, engineering-risk treatment and proof method, and creates no second quality Fact manifest/matrix or expected-value source. Correctness/invariants and maintainability receive at least preservation; reliability/resource lifecycle, concurrency/consistency, performance/capacity/cost, security/privacy/safety, compatibility/migration/rollout and operability/observability/testability expand only when Source/Context or the changed code exposes the corresponding risk. Untriggered families do not produce an empty matrix.

A performance obligation or improvement claim requires a workload, metric, baseline or budget, environment, comparator/tolerance and attributable project-owned benchmark/probe. A preservation-only risk uses the cheapest existing evidence; no current measurement means no performance claim. Static complexity or modularity shape proves only its supported structural signal, never target runtime behavior.

The post-implementation closure checks scope/path escape and unattributed dirty changes; owner/dependency/extension-point bypass; duplicate authority; undeclared API/schema/data/state/persistence/lifecycle/recovery/compatibility change; silent fallback, swallowed failure, resource/concurrency/partial-state defects when applicable; missing triggered-quality evidence; unsupported performance claims; forbidden shortcuts; and new/worsened duplication, responsibility growth, fragile coupling or unsupported abstraction. A finding returns to implementation and affected verification. A later code, configuration, Contract, declared check-input or controlling-Context change invalidates closure.

The two workflow entries are execution carriers, not nested quality workflows. Default Contract Conformance carries Engineering Quality Conformance. An active Long-Task uses only existing Source-backed Technical Obligations, Global Constraints/Forbidden Shortcuts, owners/paths/Bindings, Checks and independent Assertions where a quality invariant can fail while functional behavior passes. At least one architecture-classified obligation remains required; `SourceItemAspect` remains only `architecture`. A broad quality Boolean, functional pass or prose cannot replace independently failing invariants. Final Gate is the sole Long-Task Engineering Quality/Architecture Conformance carrier and proves only that declared, falsifiable, project-check-bound set—not overall code quality.

Contract Conformance primarily asks whether current Source and Context reached implementation and verification. The separate Context drift check asks whether implementation or a newly selected decision changed durable truth that Context does not yet record. No engineering-quality plan, stage, matrix, ADR, new Contract field/aspect/Claim kind/risk, second Authority, Gate, scheduler, persistent state or language-generic analyzer is introduced. The detailed purpose, implementation discipline, modularity capability, debt policy, update invariants and evidence limits retain the stable locator `project_context/areas/harness-package/decision-rationale/architecture-quality.md`.

## Long-Task Workflow Controlling Objective

The highest Long-Task objective is to prevent false completion inside declared authority. Its irreducible upstream trust boundary is that authoritative Source is complete, accurate and fine-grained enough to state every intended requirement and AC, including Control and cross-Control relations. For a formal selected Web/App handoff, “complete” additionally means that authoring derives the material Expected Fact Universe before generation from requirements, product semantics, adopted design system and target environments; a frozen Inspector then enumerates canonical resources and the residual handoff is exactly equal at `subject × target × condition × variation × atomic property` Fact Cell and required-proof granularity. A named Inspector/Oracle remains TCB and cannot discover meaning its format/capability cannot observe. The workflow cannot discover a requirement the user never expressed. Once Source exists, exact universe projection, falsifiable observers, fail-closed aggregation, protected freshness and complete Final Gate execution are proof obligations. No declared Plan Item, Fact or AC may be accepted before satisfaction.

The formal guarantee is complete-delivery accepted-terminal-state safety, not guaranteed termination. Define `AcceptedDeliveryTerminal(snapshot)` as a fresh Final Gate result of exactly `machine_accepted`, with no declared External Confirmation pending:

`AcceptedDeliveryTerminal(current snapshot) => DeclaredObservableDrift = empty`

This implication is admitted only when every declared atomic Claim/applicability/proof-surface unit has an authoritative observation binding inside the protected proof boundary. A generic Harness cannot infer requirements absent from Source or mathematically prove that an arbitrary physical-world observer denotes the intended predicate. Such meaning must be conserved into a frozen, Claim-relevant and falsifiable observer, or preserved as an explicit External Confirmation which blocks or qualifies complete delivery. “The project oracle is sound” is not a free hidden premise and a passing Boolean is not evidence of correct semantic binding.

For non-UI meaning, “complete and accurate Source at the declared observable granularity” has a concrete lower bound. Authoring inventories every Material Source item and all declared attachments, controlling Context, canonical specifications, external constraints, delegated instructions and repository-preservation inputs. It explicitly dispositions the complete standard family floor—product goal/scope/glossary; actor/role/tenant/entitlement; business rules/calculations; data; operation/workflow/state/time; input/output/error/API/protocol/event/job; persistence/cache/search/transactions/consistency/concurrency/idempotency; fault/recovery/backup; configuration/compatibility/migration/rollout; performance/capacity/cost/reliability; security/privacy/safety/compliance; observability/deployment/operations; integrations/localization/commercial; hardware; AI/ML; architecture ownership/boundaries/debt—and every custom family discovered from Source or repository structure. Ordinary Material Source cannot be reclassified as supporting-only to escape the universe.

The semantic unit is not a paragraph, Requirement, Product Control, broad state label or implementation module. It is one independently decidable Fact at `Outcome × subject/relation/population × exact condition combination × atomic property × typed expected predicate`, with stable owner, Source locator/digest, authority provenance, quantifier, observation boundary and sensitivity. Subjects, typed relations and static/dynamic populations are fully inventoried. Standard/custom condition axes enumerate every applicable atomic value and exact combination, or an exact basis-backed exclusion; continuous domains use explicit partitions/ranges/rules. Standard/custom properties are partitioned per unit and condition. Aggregate strings, default paths, representative/pairwise samples, ungrounded N/A and implementation-generated expected values are invalid.

Fact identity is separate from proof obligation. Every Fact expands to all required methods, the furthest independently failing boundary, frozen comparator/parameters/tolerance/mask, Oracle capability/identity, deterministic environment, observers and protected-value policy. A Source-embedded `semantic-fact-manifest-v1` is the Long-Task task-local canonical index and freezes the Inspector Census plus complete-generation count/identity digests. Exact values remain Source/Context truth; Contract projects stable identities and comparison authority. Compile enforces `Expected Semantic Facts = Source Indexed Facts = Contract Indexed Facts` and `Source Fact × required-method obligations = Contract proof bindings`. Final Gate requires one and only one current typed `semantic_fact` result per machine obligation with actual observation/environment/comparison/Oracle/verdict; named external obligations remain explicit confirmations. Missing, extra, duplicate, unresolved, unreadable, unmapped, unimplemented, unexecuted, stale, failed, proxy-only, reused or indistinguishable identities block.

Default Workflow carries the same equations ephemerally through current-candidate Contract Conformance without persisting a manifest, matrix, Claim set, state or Gate. Long-Task uses the one Source manifest, existing Claims/Assertions/Checks/bindings and sole Final Gate; the carriers are mutually exclusive. Durable product/API/schema/data/state/security/privacy/architecture/verification/deployment semantics still project to existing Context owners, while task-exact facts/provenance remain Source. The mechanism can enforce complete treatment of expressed, logically entailed, explicitly delegated and evidence-backed meaning, but cannot discover unstated intent or prove an arbitrary custom Inspector/Oracle sound. Genuine product/legal/security/commercial/safety/external choices remain blocking rather than being invented.

One shared conditional objective is full implementation/acceptance/test conformance to every material scoped UI/UX Fact. Its unit is a **complete observable design Fact Cell**, not a coarse Control/page/dimension: every addressable Surface, component instance, Anatomy Part, primitive, text/icon/media/asset/relation under each exact condition and subject-local variation retains each atomic geometry/style/content/behavior/accessibility/system property. Product Controls and eight dimensions are semantic/roll-up owners, not the Fact ceiling. Direct visual inspection, default pages, state-catalog strings and sampled screenshots are lossy. The expression boundary remains: no workflow invents unshown meaning, treats unsupported formats as inspected or proves the user omitted nothing. Missing/unreadable meaning is authored, source/basis-backed excluded/N/A, or blocking `decision_required`/`unavailable`.

The transformation has three complementary owners. First, `design-resource-authoring` derives the Expected Universe before provider execution, passes the verified Open Design design-system binding and commissions canonical implementation source, exact dependencies and one `design-resource-observable-fact-manifest-v1`. The manifest freezes Inspector inputs/capabilities/Census, 33 condition axes, five variation axes, subject hierarchy, complete atomic property catalog, Fact Cells/Facts, design-system lineage, Fact × required-method proofs, comparator/tolerance/mask, Oracle/environment, assets/blockers and non-sampling/non-truncation digests. Authoring iterates until `Expected Fact Universe = Canonical Resource Facts`; provider success alone cannot. This Inspector/manifest pass is source QA over immutable design input, never production conformance. Second, `design-resource-handoff-v1` remains the provider-neutral residual adapter. New authoring uses `representation: manifest_backed`: the canonical per-target manifest is the sole complete Fact index, while YAML carries only residual Source/scope/resource/target/closure/coverage/proposal binding and preflight hydrates the same full V1 validation object. Older embedded V1 remains read-compatible. Exact values stay in canonical resources (`design_fact_values_stay_in_canonical_resources`); handoff preserves semantic/downstream bindings without copied CSS or duplicated manifest collections (`no_second_design_fact_authority`).

UI symbolic V2 is explicit opt-in; V1 remains the default. An opted-in target uses `design-resource-observable-rule-manifest-v2` and `design-resource-handoff-v2` with `representation: symbolic_rules_v2`. Equivalence is the pointwise equality of disposition, located expected semantics and complete proof-obligation denotation over the full `subject/relation × target × reachable condition/variation × applicable atomic property × population/quantifier` universe; physical V1 ground Fact Cell row identity is not required. V2 Rules carry constant located expected values over mutually exclusive canonical regions. Applicability closes from the package property catalog, frozen Inspector capability/Census and exact basis-backed remainder dispositions. `ready` is returned only when no unresolved disposition or acceptance blocker remains. V2 reuses V1 method/dimension, comparator/method, Oracle trust/digest/capability, environment/resource, exact/tolerance/mask and protected-value policy. Each exact target separately proves that the union of full-target `layout_geometry` regions and the union of full-target `visual_pixel` regions equal the complete reachable domain. Fact Rule, semantic proof-obligation and set-valued non-interference certificate identities are separate. Until a package-owned trusted non-interference proof establishes otherwise, any canonical Rule, disposition or population exclusion that omits an axis fails closed; a provider declaration or a self-consistent dependency list cannot prove independence. One Contract may mix V1 and V2 targets; current typed Rule-method and certificate results converge through the existing sole Final Gate.

V1 capacity admission uses file stat and a bounded prefix generation header before full parsing or hydration, with repository-measured thresholds and actionable V2 guidance; it never samples, truncates, lowers granularity or expands then deduplicates. Non-interference admission records semantic-obligation count, certificate-obligation count, exact covered omitted axes/dependency edges and canonical DAG node/edge/byte metrics. One certificate may cover multiple axes, but overall representation and runtime work cannot grow with theoretical ground cardinality. Purpose-fulfillment efficiency non-degradation is a package mechanism-change admission property, not an AcceptedDeliveryTerminal condition. Non-UI symbolic admission and Provider/P0 trust-boundary work remain out of scope.

Third, downstream authority conserves exact Fact Cell/Fact/proof/Source/blocker/target/condition sets into one carrier. Default work keeps ephemeral owner/journey mapping and an attributable final-candidate result for every Fact. Long-Task projects canonical per-condition `fact_expectations`—subject/variation/property, sensitivity, expected located digest, comparator/parameters/tolerance/mask, Oracle/environment—into existing Assertions/bindings, then requires exact current `fact_results` with actual observation/environment/comparison/verdict in its sole Final Gate. Every verdict passes; protected observations are digest/redacted without raw persistence. Missing/extra/duplicate/stale/failed/authority-drifted or indistinguishable rows block. Carriers remain mutually exclusive. Blockers retain Source/method/capability lineage. Provider/preflight/integrity proves input closure only. No matrix, Claim kind, registry, second Authority/Gate/state or acceptance lifecycle is added.

An `exact_target` is a claim that the selected resource completely specifies the target surface under each declared condition. It therefore requires a full-target layout-geometry fact and a full-target `visual_pixel` fact for every condition; if those facts cannot be extracted and compared, the resource must remain a partial `constraint` or blocking unresolved input. Pixel comparison closes visible output only, so interaction, state, motion, reflow/input, accessibility and asset facts still require their own methods. Control fields remain product-interaction semantics, while design-fact granularity may be smaller than any Control (`control_granularity_is_not_design_fact_granularity`).

The workflow does not promise that implementation stays on course at every intermediate step, and it does not promise that a model can finish the work. The current Goal may explore, fail, rework, change implementation sequence and optionally use one or multiple platform-native agents/subagents as implementation means. Delegated output is never Progress, proof or completion authority and must converge into the selected verification workspace. The workflow constrains the final acceptable state by requiring it to:

1. compare Source Authority, the Contract, relevant Context and the current final artifact continuously enough to identify delivery drift;
2. block false completion whenever a declared requirement or AC remains unsatisfied;
3. localize the problem to its Source Item, Stage, Outcome, Claim, Assertion, Check, Evidence Capability, execution target, Binding or ownership boundary;
4. give the current Goal an actionable repair direction;
5. revalidate the complete Contract against the current final snapshot before delivery; and
6. reject summaries, progress, historical tests, Receipts, a single command exit code and Agent judgment as completion substitutes.

Current-snapshot evidence outranks implementation narrative and historical results. If any declared item is unsatisfied, unverifiable or no longer backed by fresh evidence, the workflow must keep the task unfinished rather than soften the completion wording. This guarantee covers only declared and verifiable authority; it cannot prove that the user never omitted a real requirement.

### Semantic Assurance Closure

The closure is compiled into the existing Contract, Authority and Final Gate rather than becoming a second workflow:

- Source background is restricted to text-free Markdown anchors/separators and fixed-field provenance (`input`, `mode`, conditional `source`, optional `sha256`). Text-bearing headings, free-form provenance fields and arbitrary prose must be Material Items or rejected; a reason label cannot exempt their meaning.
- One Source `semantic-fact-manifest-v1` inventories all Material Source and full Context inputs, the standard/custom family and semantic-unit Census, exact condition/property/Fact cells, every Fact×method obligation, Oracle/environment and blockers. Collection counts and identity digests reject truncation; ordinary Material Source cannot be hidden as supporting-only, while validated design-owned Source remains independently classified.
- Every Outcome's semantic bindings are set-equal to manifest Facts and proofs. Machine obligations bind one generated `semantic_fact.<fact_ref>` Claim, one atomic applicability profile, one single-Claim Assertion and typed result; external obligations bind impact-complete confirmations. Runtime cannot rewrite Source-located expected/comparison/tolerance/mask/Oracle/environment authority.
- Applicability is an atomic dimension/value cell. Mutually exclusive values cannot share one profile; all declared targets, journeys and cells are proved without representative/pairwise substitution. A selected-design condition contains exactly one mode, state, content case and input method so its condition key denotes one real cell.
- Every behavioral Claim-bearing Assertion is protected by a Claim-relevant narrow semantic mutation and a claimless target-liveness Assertion. Whole-file removal/replacement remains useful for carrier reachability but cannot alone prove that the observer reads the correct sibling field/value.
- Every selected-design verification method emits a separately attributable method record plus a method-native primary observation over every exact target/condition cell. Each declared evidence cell and current-execution record carries the exact immutable handoff `fact_refs`; unequal, empty or reused fact sets fail independently from artifact presence. Primary-observation path and current digest are both unique across cells; Playwright requires explicit record/observation attachments from every project instance, so one indistinguishable screenshot/session cannot silently satisfy layout, pixels, tokens/content, interaction, motion, reflow, input and accessibility at once.
- Every execution target declares exact runtime capabilities, and each design-acceptance blocker explicitly preserves the capabilities required by Source. A machine Claim closes the blocker only on that exact capability-qualified target; otherwise it stays a target-blocking External Confirmation. Missing physical-device, sensor, camera, orientation, haptic, assistive-technology, input, viewport/motion or production-root capability therefore cannot be replaced by a browser/proxy declaration.
- Runner target, declared verification inputs and the supported direct-literal local verifier graph are frozen. Static imports/re-exports, literal dynamic imports, `require` forms and literal `new URL(..., import.meta.url)` files recurse; Check inputs/outputs/artifacts remain explicitly classified runtime material. Non-literal loaders and `createRequire` fail closed. Indirect runtime access, external packages, installed runtime, Git implementation and physical devices remain named trusted-computing boundaries unless explicitly frozen, and are never presented as byte-attested by the Harness.
- Long-Task freezes the full `project_context/**` graph. Population coverage closes against a bound machine-enumerable universe; when the real universe cannot be closed by machine evidence, target completion waits for an External Confirmation rather than trusting a runner-created eligible list.
- Architecture and every material independently falsifiable engineering-quality invariant remain in existing Source-backed Technical Obligations, Constraints/Forbidden Shortcuts, owner/path/Binding boundaries, executable Checks and separate Assertions when functional behavior can pass independently. The efficiency objective is **Fine-Grained Semantic Purpose-Fulfillment Efficiency**: attain the complete declared fine-grained semantic and proof effect at the lowest practical total workflow cost. ## Long-Task Anti-Degradation Assurance

**Anti-Degradation Assurance** is the high-priority evolution objective that keeps the Long-Task causal chain valid and its drift-interception strength from degrading across accepted versions. **Anti-degradation construction** means the concrete Context, design, implementation-index, test, routing, parity and maintenance work used to establish that continuing assurance. It is an evolution layer around the mechanism, not a third implementation responsibility, and it creates no second Authority, Gate, state, matrix or registry.

Let `P` be the controlling accepted-terminal-state purpose above, `K` the enabling logic that authoritative meaning must be sufficiently precise, accurate, applicable and observable for drift to be defined, `R1` the meaning-capture/architecture responsibility, `R2` the fail-closed observation/repair/final-snapshot responsibility, `B` the explicit Source-completeness, semantic-binding, observability and trusted-computing-boundary conditions, `F` the **Implementation Freedom Boundary**, `E` the **Structural Closure Cost Efficiency Boundary**, and `I_current` the actual current repository implementation. A valid current-version claim requires:

1. Context statements labelled as current implementation truthfully describe `I_current`;
2. the code and configured workflow actually realize both `R1` and `R2`, rather than merely resembling their prose; and
3. the bounded implication `Realizes(I_current, R1 ∧ R2) ∧ K ∧ B => P` remains independently recoverable and falsifiable.

`F` is a protected efficiency and anti-process-bloat boundary, not a third implementation responsibility or another premise of that implication. Because `P` is accepted-terminal-state safety rather than path safety or guaranteed termination, a fixed implementation sequence, development Stage/phase permission Gate, prescribed method, mandatory per-edit verification cadence or Harness-owned agent allocation is not logically necessary when `R1`/`R2` and `B` still govern the accepted final snapshot. Within declared Source/Contract authority, architecture, security, forbidden-shortcut, irreversible-effect and external-action boundaries, the current Goal owns implementation order, local planning, tool and repair choices, and whether one or multiple platform-native agents/subagents are useful. Harness owns no delegation scheduler, retry/recovery state or proof from those agents; every proof-bearing result converges into the one selected verification workspace.

`E` protects the efficiency of attaining the same fine-grained effect, not merely the presence of the effect. For a named workload `W`, let `EquivalentEffect(new, old, W)` mean equal declared semantic denotation and granularity, no weaker proof/TCB, and unchanged Authority/Final-Gate safety. Let `StructuralCost` observe persistent Source/Contract/evidence bytes, canonical DAG nodes/edges/bytes, Compile/Preflight/Final-Gate work, peak RSS, default Context bytes and one-Fact revision blast radius. Admission requires that an equivalent-effect change introduce no known increase in any of those costs caused only by unrelated axes, derivable repetition, copied shared metadata or mechanical ground expansion. A cost increase is justified only when it maps to independent new semantic coverage, proof strength, TCB hardening or necessary adaptation and still passes total-cost ROI. `E` adds no Authority, Gate, delivery deadline, runtime state or universal benchmark; its measurements and structural counterexamples remain package mechanism-admission evidence.

`PROJECT_SPEC.md` and owning Context state intended semantics, the implementation index navigates the current owners, code is current implementation truth, and tests/runtime evidence prove selected properties of that implementation. A disagreement is implementation drift, missing work or stale Context; it is never a license to keep a “theoretical implementation” that no longer describes reality. Concrete modules, schemas and tests may evolve, but the index and current-implementation statements must evolve with them.

Cross-version admission is lexicographic: Safety/Coverage, Semantic Granularity, Proof Strength/TCB and non-bypassable Authority/fail-closed/current-final-snapshot proof, then Structural Closure Cost Non-Degradation under `E`, then positive total-cost ROI. Positive net ROI permits consideration, not automatic adoption; lower cost cannot compensate for weaker interception, coarser semantics or weaker proof, and unchanged correctness does not justify unrelated structural cost growth.

The protected design invariants are `P`, `K`, the two jointly necessary responsibilities `R1`/`R2`, boundary `B`, and the adjacent `F` and `E` efficiency boundaries. Ordinary requirement, implementation or optimization work may strengthen them or replace concrete implementation details without changing their meaning. Weakening, reinterpreting or replacing a protected invariant requires an explicit project-owner design-purpose decision recorded in this specification and owning Context. That decision must name the old and new purpose/implication/boundary, the coverage, granularity, proof/TCB and structural-cost effect, compatibility and migration consequences, and replacement proof. Agent inference, simultaneous edits to prose/code/tests or a generic cost argument alone cannot silently authorize either change.

## Authority Scope And Trusted Results

The complete authority and evidence chain is:

1. **Source** preserves original delivery meaning.
2. **`project_context/**`** preserves durable project facts.
3. **Contract Draft** is the still-editable structured expression before Authority Lock.
4. **Compiled Contract / Authority Lock** is the formal declared authority created by the first successful formal Compile.
5. **Execution-model choice** is a strict first-lock turn boundary: unless an explicit task-specific choice already names current-model continuation or a switch, the Agent stops before implementation/edit/build/test work; it is not authority or proof.
6. **Current Code** is implementation reality.
7. **Check Evidence** is typed, current-execution behavior evidence for declared Claims and Assertions, bound through one exact applicability ref to the declared target, journey role, Given state/condition/input refs, ordered When actions, production surface binding and Evidence Capabilities when those semantics apply.
8. **Final Gate** computes machine acceptance on one current final snapshot.
9. **External Confirmation** owns CI, deployment, Git-hosting, human product acceptance and other non-machine authorities.

Across machine authority and complete delivery, only two result classes are trustworthy:

1. reliable evidence on the current final snapshot proves every declared requirement and AC is satisfied; or
2. something is unsatisfied, unverifiable, insufficiently evidenced, stale or awaiting external confirmation, so the task remains explicitly unfinished or qualified.

`machine_accepted_external_pending` is the second class with a precise boundary: all machine-verifiable authority passed, but complete external delivery did not. Its strongest valid implication is `MachineVerifiableDeclaredDrift = empty`, not full `DeclaredObservableDrift = empty`. Public reporting must name the pending external confirmations. It is not `AcceptedDeliveryTerminal`, is not full delivery completion and is not a vague third state between complete and incomplete.

Qualification continuity is end-to-end. `final-gate`, `status`, `resume`, `stop-check`, the package-owned Stop Hook and `close` preserve the same accepted `workflow_status` and complete declared `external_confirmations`. A stale Final Receipt exposes no accepted workflow status. Stop/close may clear the accepted machine Authority through CAS, but `closed` means only that the machine lifecycle ended, never that external delivery completed. This adds no external-confirmation state, Receipt or completion tracker.

Authority conflict indicates drift, omission, stale information or a genuine decision. Source or Contract meaning must never be silently changed to fit current code. Progress, Receipt, status and compiled cache are recovery or audit projections, not acceptance authority. `resume` restores semantic state rather than a previous physical Turn. Source, Controlling Context, raw Contract, workdir Outcome fragments, verifier, runner, verification inputs or workspace changes stale affected results. A supporting-only Context revision may preserve otherwise-fresh scoped Progress, but it clears the Final Receipt and Final Gate still binds the complete current Context snapshot. Historical evidence cannot be spliced into current completion.

The currently selected platform Goal is the execution owner for the delivery/workspace. Harness does not create, simulate, persist or reconnect a Goal identifier or physical Turn; compaction may continue inside that Goal, while a later physical Goal/session reconstructs semantic workflow state through `resume`. Git history remains the ordinary record of Contract edits rather than a second plan or completion authority.

Authority Revision adoption likewise is not a delivery completion. When rolling implementation meets a blocker, implementation difficulty alone cannot reclassify machine-verifiable work as external or remove it. Authority change is separated from user decision: mechanically bounded repair may auto-adopt, while a real Product, Acceptance, proof, forbidden-boundary or machine/external change first becomes marked Source and then one exact user-decision revision. Every pending output begins with a plain-language Authority Revision introduction and derives decision reasons, bounded changes, material deltas, affected Outcomes and previous-Authority/adoption/Final-Gate effects from the canonical hash-bound summary. An explicit current-task instruction that exactly covers every listed decision reason may be mechanically relayed; blanket authorization or Agent inference cannot. Adoption invalidates affected evidence and returns the current Goal to rolling implementation or repair under the revised Authority.

Machine acceptance remains limited to declared machine Authority and has no direct effect on the platform-native Goal. Before completing that Goal, the Agent performs a veto-only conformance review against the current user/Goal meaning and accepted marked Source, including pending revisions, blockers and omitted requirements. A mismatch keeps the Goal active and triggers Source/Contract repair; a clean review is not positive acceptance evidence and never substitutes Agent judgment for Final Gate proof.

## Contract Draft And Draft Outcome Semantics

`delivery-contract.yaml` is a **Contract Draft** until the first successful formal Compile. The Draft is one continuously revised, non-authoritative object: it may take multiple model responses and multiple rounds of repository reading, Context reading, Preflight diagnostics and repair before it is complete. It has no separate Draft Receipt, Authoring State, second plan, draft schema, draft CLI or draft runtime state. The first successful formal Compile creates Authority Lock; that lifecycle change does not replace the file with another authoring product.

A **Draft Outcome** is simply an Outcome in that pre-lock Contract Draft. It is a lifecycle qualifier, not a new entity. Formal Compile places the same Outcome under Contract Authority without converting a `DraftOutcome` runtime type or creating `draft_outcomes`, a state file, Worker, scheduling queue or independent completion authority.

**Plan Item** is a design-level collective term, not V2 schema. It covers atomic Requirements; applicable Control fields, locations and states; Non-completing Outcomes; Technical Obligations; Global Non-goals, Constraints and Forbidden Shortcut Claims; and every other declared requirement that must be expressed as a non-Result Claim. An AC corresponds to one stably named Acceptance Assertion. An Outcome Result cannot substitute for a Plan Item or AC. V2 therefore adds no `plan_items` field, PI file/state/Worker or restored three-input execution chain.

Draft Outcomes decompose requirement coupling. Create an Outcome only when its result is independently observable, independently decidable, target-verifiable, able to express dependencies and localizable to its own Claim, Assertion, Check and owner boundary. That decomposition lets the current Goal:

1. project a smaller acceptance/verification-ready working set without restricting implementation order;
2. run targeted verification for one Outcome or Check and shorten feedback;
3. localize failure to an Outcome, Claim, Assertion, Check, Proof Surface, Binding and path;
4. resume ready Outcomes, findings and the next safe action without re-deriving the whole task;
5. mark formerly passing local results stale when their authority or evidence changes; and
6. use Outcome dependencies to order acceptance/readiness projection and localize verification without turning them into an implementation gate.

`depends_on` means acceptance and intermediate-proof readiness. Source-declared delivery stages add only a product-delivery acceptance order: each vertical Outcome belongs to one stage, each stage names a gate Outcome, the gate transitively depends on the rest of that stage, and later stages transitively depend on prerequisite gates. Every Stage Gate executes from the root entrypoint of every required product target and proves `target_runtime`; a Stage containing multiple Outcomes additionally proves `cross_surface_consistency` over at least two distinct surfaces in one current runtime state. The current Goal derives an advisory Rolling Frontier from those existing edges and current Outcome Progress while choosing implementation order independently. No Stage Receipt, implementation gate, persisted scheduler, Worker queue, model-routing plane, process tree, second Gate or separate execution DAG exists, and Final Gate still revalidates the complete Contract on one current snapshot.

Outcome boundaries must not be based on model-output length, YAML/file length, frontend/backend layers, file/module count, Agent capacity, Worker assignment or desired parallelism.

## Integrated Contract Authoring Rationale

Contract Draft authoring belongs inside `long-task-workflow`; there is no separate `contract-authoring`, `draft-authoring` or `prepare-long-task-draft` Skill. A separate single-response authoring surface was rejected because a complete Contract may exceed one response and cannot reliably be required to emerge complete in one pass.

The integrated design is also required because:

1. a Contract Draft must inspect the real repository and relevant Context before binding owners, paths, runners, verification inputs, proof surfaces and Bindings;
2. Preflight findings feed directly back into the same Draft;
3. a separate Skill adds a handoff where Source meaning, repository evidence or unresolved findings can be lost;
4. a separate product tends to create a second plan, Authoring Authority or Authoring Receipt;
5. Draft-to-Compile is a lifecycle transition of one authority object, not a handoff between two products; and
6. one Skill can keep revising the same Draft across as many responses as needed, then continue through Preflight, Compile, the one-time model choice, rolling execution, verification and Final Gate.

Source-quality rules and Contract Draft authoring remain one Source-bound authoring loop inside `long-task-workflow`; their separate reference files are progressive instruction loading, not serial phases or a service handoff. External design resources remain ordinary Source and do not replace repository-aware Contract authoring.

## Mechanism Admission Rule

Every Long-Task change starts from the controlling design purpose. Before cost is considered, prove `Coverage_new ⊇ Coverage_old`, `FalseNegative_new ⊆ FalseNegative_old`, Authority and fail-closed non-bypassability, and complete-current-final-snapshot proof. If non-degradation cannot be proved, preserve the current formal acceptance path and place any experiment outside it. Cost reduction never compensates for weaker drift detection. Only after this first gate, account for total cost by explicitly including the cost of introducing and migrating the change in the subsequent ROI judgment. If the change alters mechanism semantics, an invariant, an authority/proof boundary or runtime behavior, change the mechanism and its verification. Otherwise change only the owning point; do not turn a local correction into a new mechanism.

Every proposed or retained Long-Task mechanism must answer:

1. Which concrete false-completion or delivery-drift path does it close?
2. Which invariant does it establish?
3. Which test, verification or current-snapshot evidence proves that invariant?
4. Does another mechanism already cover the same risk?
5. Which exact false-completion path would reopen if it were removed?
6. What Authoring, Runtime, State, Recovery and maintenance cost does it add?
7. Does its incremental purpose-fulfillment benefit exceed every incremental Authoring, Runtime, State, Recovery, maintenance, test, process, introduction and migration cost?
8. Does it fail closed?
9. Does it create a second Authority, second plan or scheduling plane?

Expected ROI is positive exactly when incremental purpose-fulfillment benefit exceeds all incremental costs. That is sufficient to place a non-degrading candidate in the consideration set, not sufficient to adopt it automatically. Prefer measured data, benchmarks or operational evidence. When none exists, discuss the decision with the user or project owner; a rigorous causal argument plus simple, bounded validation is sufficient. The Long-Task Workflow itself was admitted before mature longitudinal data existed because its logic and basic validation were sound. Unsupported intuition alone is insufficient.

Keep the design purpose fixed while optimizing. When total cost is comparable, prefer the change that fulfills the mechanism purpose more effectively; when purpose fulfillment is comparable, prefer the change with lower implementation and operating cost.

Retain an acceptance mechanism only when it provides non-substitutable drift-prevention value with positive total ROI after the non-degradation gate. A non-authority workflow affordance may additionally be retained when existing fail-closed protection makes its incremental benefit exceed all incremental costs and the affordance adds no acceptance bypass, second Authority, second plan, scheduler or persistent control state. The first-lock execution-model choice uses this second rule. Positive ROI permits consideration rather than automatic adoption. This remains a specification and code-review principle, not a new mechanism matrix, Receipt or runtime Registry.

The protected `F` boundary applies the same rule in reverse to proposed development-stage constraints. A fixed phase/order/method Gate, mandatory per-edit or per-Outcome verification cadence, agent-allocation rule or Harness-owned multi-agent orchestration is rejected unless an explicit project-owner design-purpose decision proves that it closes a concrete path not covered by final-current-snapshot acceptance or a lighter project-owned check, is necessary for an irreversible/safety boundary or has independently positive total-cost value, remains non-authoritative and non-bypassable, and passes both non-degradation and positive-net-ROI admission. Optional one-agent or multi-agent implementation chosen by the current Goal needs no Harness state; delegation output remains non-authoritative and must converge before declared verification.

The UI production-surface binding satisfies this admission rule. An observed delivery proved four independent gaps under the existing prose-only model: support-target Control Claims substituted for a required native target, deep links bypassed the production root shell, resource hashes/counts were mislabeled as implementation conformance, and declared acceptance blockers were not projected into the Final Gate. One aggregated `surface_binding` per production surface/target plus typed `design_conformance` only for selected exact/constraint targets closes those paths through existing Product/Technical/Acceptance authority. It adds no scheduler, state, Receipt or Gate; authoring grows by surface/target rather than Control-field count. Prose-only repair, a universal per-Control screenshot matrix and a separate UI registry/Gate have respectively insufficient interception strength or materially worse total cost.

The shared design-resource adapter satisfies the same admission rule one boundary earlier. Direct visual-only consumption is not a reliable Contract interface: a prose summary, Control list, broad dimension row or generic condition label can omit one image, Anatomy Part, state, geometry/style property or behavior. Earlier strengthening froze canonical resources and indexed facts, but a handoff could still define its own narrower universe; `all-21-state-catalog` could stand in for atoms; an Inspector `complete` flag could hide skipped nodes; a Fact needing token and pixel proof could retain one method; runtime could return aggregate pass without its actual observation/comparator/Oracle/environment. Starward exposed this remaining false-green class.

The current adapter closes it through pre-generation Expected Universe derivation, frozen input/Census enumeration, first-class condition/variation/property axes, exact Cartesian Fact Cells, complete standard catalog, design-system lineage, dynamic/relation/asset closure, all property-required Fact × method obligations, collection count/digest and no sampling/truncation, then exact manifest↔handoff equality. Long-Task freezes per-Fact comparison authority and requires exact passing current results including sensitive-evidence policy. Existing source profiles, typed locators, resource closure, full-target layout/pixel defaults, blockers, Assertions and Final Gate remain necessary. Exploration pays no schema cost, non-Web `reference` remains valid, and selected handoffs may group thousands of Facts into a compact source set without duplicating values or creating one artifact per Control. Alternatives—prose-only strengthening, trusting provider/Inspector completion, embedding CSS in Contract, a second registry/Gate or exhaustive files per component—respectively miss the failure path or add worse authority/synchronization cost. This is monotone and positive-ROI after the non-degradation gate.

Revision-return and terminal-scope affordances use that same non-authority rule. Compile/revision JSON reports `delivery_completed_by_this_event: false` and a rolling next action; Final Gate/Stop/close output reports `acceptance_scope: declared_machine_authority` and `native_goal_effect: none`; close additionally reports `closed_scope: machine_authority`; and the Stop Hook emits one non-blocking scope message. These fields and guidance close state-transition ambiguity without a persistent `authority_revision_in_progress`, native-Goal state, second semantic Gate or Goal restoration runtime.

Apply protection proportionally: L0 work must not pay Contract cost; L1 pays for one complete Contract, rolling execution and a current-snapshot Final Gate; L2 raises proof only on affected high-risk Outcomes. Risk must escalate automatically or explicitly and can never be downgraded by the executing Agent.

## 3. Workflow Levels

### L0 — Default Local Work

Use the default Workflow Contract when work is local, reversible, directly testable, covered by current Context, needs no cross-session recovery and does not change durable API/schema/data/security/recovery/product semantics. No Delivery Contract or long-task binding is created.

That result is the first working set, not a read sandbox. Widen it whenever shared or indirect dependencies require more Context/code. Context workspace, Area and `read_policy` never authorize edits. Resolve intended workspace(s) from user/product/path/repository facts; if materially different siblings remain plausible, clarify the target before product edits, otherwise proceed without ceremony. Cross-workspace work names all intended targets and supporting/shared scope. During final Conformance, use any repository-owned changed-path scope checker on task-attributable paths, or review the final diff against durable owners when no checker exists.

`Architecture Context Hit` and `Decision Rationale Hit: existing|required|none` remain internal routing questions. They are not durable facts, roles, validators or artifacts, and the checkpoint never creates a rationale delta or required file. `Context Delta` remains the only durable-fact decision point.

Architecture Deliberation is universal while its depth and applicable-quality assessment are risk-triggered. New durable modules/capabilities, public API/schema/data/persistence, source-of-truth or state ownership, dependency direction, cross-area boundaries, migration/security/recovery/compatibility, material performance/resource/concurrency risk and reusable abstractions require the corresponding analysis. Small local fixes record concrete architecture and quality-attribute preservation instead of paying full ceremony or skipping. Harness may route repository-native type/lint/AST/dependency/contract/behavior/benchmark checks but does not become a language-generic architecture or quality analyzer.

Product Surface Contract work uses `context_surface_contract` and the existing `contract`, area/subdomain and verification roles. It must not add a new product-surface role; Source-to-Context judgment and Contract Conformance remain internal workflow checks.

The Design Context Depth Model adds no role: global principles, cross-surface Product Surface Contracts, optional on-demand Screen/Control Context, `DESIGN.md`, project-native authored targets and verification remain distinct fact depths. `product-surface-contract.md` owns cross-surface responsibility; `screen-contract.md` is the portable Screen/Control structure. UI Authority Closure reconciles stable surface/control/target keys as Context-covered, Context update, task-local, out of scope or decision-required before material implementation.

When a selected implementation handoff exists, L0 remains lightweight but not lossy. It keeps one task-local exact accounting of covered observable facts, Source Items, declared verification methods, blockers, targets and conditions; routes each item through the production route/component owner and cold-start real-user journey; and requires attributable project checks on the final current candidate. One check may cover several methods only when each method and fact can fail distinctly. Any unread, unsupported, unresolved, unmapped, unimplemented, unexecuted, stale or indistinguishable applicable fact blocks a complete selected-design-conformance claim. No Delivery Contract, persisted map, evidence ledger, readiness state or extra Gate is created.

### L1 — Standard Long Task

Use one Delivery Contract, one native Goal and one workspace when work has multiple observable Outcomes, crosses modules or needs pause/compaction recovery, but does not hit an L2 risk floor and has reliable executable proof.

### L2 — Strict Long Task

The compiler requires strict when any declared fact is true:

- public API or schema change;
- persistent data change;
- data migration;
- security boundary change;
- permission boundary change;
- irreversible external effect;
- full-population operation;
- multi-repository change is rejected as unsupported;
- critical user path with weak end-to-end observability.

Users may raise risk to strict. A requested `standard` level below the computed floor fails with `risk_level_below_required`. Skill or executor logic can never lower risk. L1 and L2 use the same workflow and Outcome model; L2 only raises proof requirements on affected Outcomes.

## 4. Single-Goal Rolling Delivery

The active flow is:

```text
initial or revised proposal plus selected design resources and other Source
-> minimum relevant Context
-> one continuously revised Source-bound Contract Draft
   (inventory/provenance/refinement/markers and mapping converge in this loop)
-> Draft Outcome decomposition
-> repository/Context binding and Source -> REQ/CTRL/OBL/NCOMP/AC coverage
-> read-only Authoring Preflight repair loop
-> first formal static Compile and Authority Lock
-> one-time execution-model choice
-> current native Goal chooses implementation method/order in the selected workspace
-> temporary acceptance/verification-ready Outcome Frontier
-> optional targeted feedback and repair verification
-> same-Goal repair and Context Delta updates as needed
-> optional stateless diagnosis of the same Contract's revision candidate
-> automatic bounded repair or one exact pending user decision and atomic Authority replacement
-> one-snapshot complete Final Gate
-> Stop freshness
-> external Git/PR/CI/deployment/human confirmation
```

Outcome is an independently decidable and target-verifiable acceptance-result unit. It is not a Goal, branch, worktree, worker, frontend/backend layer, file group, output-length fragment or fixed implementation slice. `depends_on` determines acceptance and intermediate-proof readiness only. The current Goal may implement, inspect or repair any in-scope Outcome in any order that fits current code reality; the derived Frontier only localizes the next independently meaningful verification/repair boundary and never authorizes or prohibits implementation edits.

The Frontier is not persisted as a scheduler graph and is not an implementation gate. Full file/function/component/test order, local hypotheses, tool choice and platform-native opaque delegation are intentionally left to the current Goal.

The host and user own model selection. Harness cannot switch the model of a running conversation or Goal and creates no model-tier scheduler, model-route state or checkpoint acknowledgement. The first Authority Lock is the one deliberate exception to uninterrupted execution: Compile emits `execution_model_checkpoint.required: true` plus terminal-turn and explicit-choice fields. Unless an explicit task-specific choice already names `continue_current_model` or a switch-and-resume strategy, the Agent ends that turn before product implementation, file edits, builds or tests and asks the user. Generic “continue”, “resume”, “finish” or “continue the Goal” language does not satisfy the checkpoint. Later revisions return `required: false`; no repeated model pause occurs. The choice reduces execution cost by using the already locked Contract and Final Gate protection, but it is not completion authority.

Harness never provides, persists, retries or recovers a parallel-subagent scheduler, Worker graph, branch/worktree fan-out or delegation state. The current Goal may use platform-native internal delegation or user-authorized Git parallelism as an opaque implementation choice, but Harness neither depends on nor records it and never treats it as progress or proof. Every accepted change must converge into the selected verification workspace before Contract-declared verification can count.

`Context Delta` remains live after Authority Lock. When implementation or repair discovers a durable fact, the current Goal updates the owning Context rather than preserving a known stale fact until the end. Long-Task always freezes the full `project_context/**` graph and treats every file as **Controlling Context**: a caller-selected referenced subset cannot prove that an unselected requirement-bearing or architecture file is irrelevant. Changes require Authority Revision, invalidate affected evidence and require a user decision when mapped Claims/targets/proof obligations or another decision boundary change. Final Gate recompiles and records that same complete current Context snapshot. The lightweight default Workflow retains manifest routing plus bounded search; the stronger full-graph rule applies only after explicit Long-Task selection.

Target-runtime feedback is also rolling, but remains non-authoritative. If a declared result can pass on a proxy surface while failing in its target runtime, the earliest Outcome that owns the first runnable boundary declares a project-owned Check that exercises the target during the current Raw Execution and derives its asserted Observation from that session. A tracked status report, screenshot, binary, log or historical run cannot be the sole proof of that Claim. The Check declares its runtime-affecting `input_paths`, Binding carriers, verification inputs and environment requirements through existing Contract fields.

The Contract declares one bounded target profile, its exact non-empty required product target refs and each target's runtime family, root entrypoint and exact capability set. A Web/process proxy cannot satisfy an independently required Native/desktop target. Browser target execution uses `playwright_test`; Native and desktop target execution uses `project_binary`. Runtime-family base capability plus condition/method-derived input, viewport, motion, assistive-technology, physical-device, sensor and haptic capabilities are mandatory on the Check's exact target. Every `critical_user_path` Outcome and every Stage Gate proves every required target from its root entrypoint.

The cheapest reliable feedback default is to targeted-verify those Checks after the first useful runnable slice and after coalesced relevant changes when early localization is worth its cost. This cadence is Goal-owned and never gates implementation order or another Outcome's edits. A Progress record must be fresh only when the Goal relies on it for an intermediate readiness, diagnosis or resume decision; stale or absent Progress may flow directly to Final Gate because that Gate ignores Progress and reruns every declared target-runtime Check on the final snapshot. There is no mandatory full environment rebuild per Outcome/edit, open-ended `platform_impact` taxonomy, per-platform progress state, scheduler or alternate acceptance path.

## 5. Canonical Delivery Contract V2

The root authoring file is `delivery-contract.yaml`, schema `long-task-delivery-v2`. It remains a non-authoritative Contract Draft until the first successful formal Compile. New authoring uses inline Outcomes in one file. Existing `outcome_files` parsing remains compatible only as a physical storage choice; fragments create no additional semantic boundary, state or completion authority. Every complete delivery selected by the user stays in one Contract and one Final Gate even when its Outcomes are weakly related.

Every Long Task has at least one real Source file, and every declared Source file contains at least one Material Source Item. The Source-bound Draft loop may refine a writable initial proposal or materialize one conversation-only delivery Source while Contract mapping proceeds and before marker insertion. Every Material Source Item is wrapped in its original Markdown with a non-rendering `<!-- ty-source-item:start key=... kind=... -->` / `<!-- ty-source-item:end -->` pair without rewriting direct text. A `ty-source-background` block accepts only an allowlisted reason whose content conforms to its machine grammar: text-free Markdown anchors/separators for `markdown-structure`, or non-rendering `ty-source-provenance` comments with fixed `input`, `mode`, conditional `source` and optional `sha256` fields for `provenance`. Text-bearing headings, free-form provenance and arbitrary visible prose are always Material or invalid even if a marker calls them background. The one strict design-resource handoff block is parsed as formal Source structure. Every other non-empty line is `source_text_unclassified` and blocks Preflight/Compile. A research proposal, ordinary prose plan or legacy Source Plan remains ordinary input and does not need to become strict Contract YAML, but its complete content still needs explicit ownership.

When Source contains stable semantic keys and Markdown anchors, Contract authoring preserves their meaning and reuses them where practical. Meaning-preserving structural decomposition and evidence-backed repository binding may add control states, Assertions, owners, paths, runners and proof. A defensible recommended plan choice may proceed only after its delegation, basis and exact meaning are recorded in real Source; it cannot be an implicit Contract expansion. Conflicting, user-reserved or unsupported product semantics remain real `decision_required` blockers, and high-risk external actions remain External Confirmations.

The Contract keeps three logical authorities in one file:

- **Product Authority**: complete observable end states, first-class atomic Requirements, ownership/surfaces/controls, non-goals and non-completing results.
- **Technical Boundary Authority**: stable obligations, allowed/forbidden path and architecture boundaries, bindings/forbidden shortcuts and strict rollback/recovery constraints.
- **Acceptance Authority**: falsifiable executable Checks, named acceptance criteria, claimed proof surfaces, positive/negative assertions, population/counterfactual obligations and environment requirements.

The required top-level shape is:

```yaml
schema_version: long-task-delivery-v2
task:
  id: stable-task-key
  title: Human title
  goal: Complete delivery goal
  target_profile:
    key: selected-delivery
    description: Exact target scope
    required_state: target_profile_usable
    required_target_refs: [product-runtime]
  execution_targets:
    - key: product-runtime
      description: Required product runtime
      role: product
      runtime_family: process
      root_entrypoint: package-script
      capabilities: [process-runtime, cold-start]
  source_paths: [plans/source.md]
  context_refs: []
  context_snapshot_mode: full
stages:
  - key: delivery
    title: Complete delivery
    depends_on: []
    gate_outcome: delivery-result
risk:
  requested_level: auto
  facts:
    public_api_or_schema_change: []
    persistent_data_change: []
    data_migration: []
    security_boundary_change: []
    permission_boundary_change: []
    irreversible_external_effect: []
    critical_user_path: []
    full_population_operation: []
    multi_repository_change: []
    weak_observability: []

  applicability: []
  product:
    non_goals: []

    constraints: []

```

Each Outcome has a stable `key`, title, exactly one `stage`, dependencies, applicability profiles, Product, Technical and Acceptance sections. Product explicitly declares whether success and degradation paths are required and contains a complete set of atomic `requirements`; the Result, each Requirement, Technical Obligation, Non-completing item and other Claim-bearing fact names every applicable profile. A profile fixes one execution target, journey role, one value for every declared applicability dimension, Given state/condition/input key set and ordered When action sequence. Profiles within a scope use one dimension-key set; duplicate target/journey/dimension cells and a dimension with multiple values in one profile fail closed. Interactive Controls require a stable key and independently declare surface, region/location, type/label, user task, visibility/availability, trigger/input/validation/default, interaction/navigation, loading/empty/success/failure/recovery/permission/feedback and accessibility. `field_coverage` assigns every one of those 22 fields exactly once as `specified`, `not_applicable` with explicit meaning, or `unresolved`; `unresolved` blocks Compile, while specified and not-applicable semantics both become independently falsifiable Claims of the correct polarity. `control_relation_closure` likewise states `specified`, `not_applicable` or blocking `unresolved`; its not-applicable meaning and specified cross-Control/shared-state/navigation/permission/recovery relations are first-class Claims with their own applicability and proof surfaces. No empty field or absent relation is silently treated as “nothing required.” Every Outcome has at least one executable Check.

Checks support `package_script`, `project_binary`, `node_oracle` and `playwright_test` runners and `ui_browser`, `runtime_behavior`, `api_contract`, `data_state`, `security_boundary`, `population_coverage` and `implementation_structure` proof surfaces. Every Check declares a bounded journey role, a product/support/observer execution target and root/internal entrypoint, plus keyed Given and When scenario steps. Every Claim-bearing Assertion proves exactly one Claim and names exactly one applicability ref; the Check target, journey, dimension cell, unordered Given set and ordered When list must equal that profile. Every applicability ref of every Claim must have the Claim's required polarity and all required proof surfaces, so only actual applicable units are authored and none may be replaced by risk-based, pairwise or sampled coverage. Semantically equivalent units may share a Check execution, but their Claim/Assertion failures remain independently attributable. Each Assertion declares an all-of Evidence Capability set. `presence` proves static existence only; behavioral capabilities require exactly one typed V3 current-execution record. Required success and degradation journeys use distinct Checks, and an Outcome Result may be proved only by a success Check.

Boundary invocation or external-side-effect evidence executes from an observer target instead of trusting the producing component's self-report. `input_variation` includes at least two distinct inputs, two distinct output hashes and a failing case. `cross_surface_consistency` names at least two distinct `surface_ref` values and one matching state hash; multiple surfaces may share one runtime target. Unknown, undeclared, duplicate or missing capability records fail closed.

Model-authored identifiers stop at task, Outcome and Check keys. The compiler generates internal `OUT.<outcome-key>`, `CHECK.<outcome-key>.<check-key>` and `CHECK.GLOBAL.<check-key>` identities plus canonical Outcome-qualified Requirement, control-field, non-completing, obligation and forbidden-shortcut Claim ids and Global Claim ids. Non-empty control location requires `ui_browser` proof. Global non-goals and forbidden shortcuts require negative proof; Global constraints accept either polarity. Global forbidden paths remain static changed-path authority.

The Source marker key set and `source_claim` key set must be exactly equal across all Source files. Marker keys are globally unique; nested, overlapping, unclosed, empty, unknown-reason, grammar-invalid item/background markers are rejected, and formal handoff content must parse under its owning schema. Every visible sentence is therefore Material rather than merely “owned by a background block.” Each Source Claim `statement` equals its marked text after limited whitespace normalization. A technical-obligation marker may classify `aspect=architecture`; every delivery requires at least one such Source-backed obligation and an ordinary covered Claim, keeping Engineering Quality/Architecture Conformance in the existing carrier. `SourceItemAspect` remains only `architecture`; other engineering-quality meaning uses existing item kinds and proof bindings. The compiled Source inventory records key, kind, aspect, source path, normalized text and text hash inside authority/revision/explain projections; it is not a second authoring file or state surface.

Typed dispositions preserve meaning. Every non-decision Source item owns exactly one canonical target of the same semantic kind and normalized text; a target has one Source owner. Outcome `acceptance` points to one stable `<outcome>.<check>.<assertion>` whose criterion is Source-text-identical and proves an independently Source-backed non-Result Claim. The Source-bound Draft loop uses the exact ten Runtime risk names, including `data_migration`, separate `critical_user_path` and `weak_observability`, and retained `multi_repository_change`. `out_of_scope` is retired.

Compile derives canonical Product, target-profile, Stage, Acceptance and Global semantic projections and combines them with Source hashes/mappings plus the complete Context authority projection and file hashes. Retrieval metadata such as `triggers`, `read_when` and `read_policy` remains retrieval support rather than product acceptance evidence, but the manifest topology and every `project_context/**` byte are protected so an omitted selection cannot hide controlling meaning. The Controlling Context projection determines whether a Context revision needs approval and whether scoped Progress remains fresh; Long-Task has no unselected Supporting Context.

The first successful Compile is Authority Lock. It also emits the additive one-time execution-model checkpoint. From Authority Lock onward, revision classification is fail closed but distinguishes authority change from user decision. Machine-proven monotonic strengthening; raw Source/Context snapshot updates with unchanged locked Claims/targets/proof obligations; operational Runner target/argv/cwd/timeout/retry or verification-input repair; risk strengthening; repository-bound owner/expected/support/Binding-carrier expansion; and equivalent Counterfactual coverage with the same carrier, mutation and Check and no lost Claim/assertion-failure coverage may auto-adopt. Product/Source Claim/target/global/external semantic change, lost Check/scenario/Claim/Evidence Capability/failure interception, reduced `input_paths`/expected outputs/artifacts/obligations/recovery/population, owner-Context or forbidden-path removal, runner type/effect change, verifier-kernel change and unknown reasons require an exact decision and are never candidate-executed. Risk downgrade is rejected.

`ty-context long-task diagnose-revision <workdir> [--outcome <key>] [--check <key>]` recompiles the current `delivery-contract.yaml` against Active Authority without enforcement side effects. It may run only existing active Check identities with unchanged runner/verifier authority and only when every protected reason is repo-bound scope expansion. It returns `acceptance_authorized: false`, writes no pending/user-decision file, Active Authority, marker, compiled cache, Progress or Receipt, and disposes its temporary snapshot. Other mechanically bounded repairs return an automatic-revision preview without project execution. Product/Source Claim/target/external-confirmation changes, lost acceptance capabilities or failure interception, removed forbidden/owner Context, runner type/effect, verifier-kernel and unknown changes return a deterministic decision preview without running project code; risk downgrade is rejected. Repeated diagnosis creates no revision Draft object: edits accumulate only in the same Contract authoring file.

Ordinary `compile --revise` remains the only pending-decision boundary. For a decision-relevant candidate it writes one exact revision identity plus a concise deterministic summary separating `user_decision_reasons` and `mechanically_bounded_reasons` across semantic, Source/Claim, proof, verifier/runner, scope, risk, external-confirmation and verification-dependency changes. Compile/status/resume derive the same self-contained human brief and present it first. If explicit current-task user instructions exactly cover every reason, the Agent may relay that decision for this identity without another question; generic continue/blanket approval/Agent inference does not count. Stateless diagnosis and ordinary edits coalesce withdrawn candidates so only the final stable blocking identity asks once. The brief is neither hashed editable authority nor persisted review state. The previous Authority remains active until exact decision and compare-and-swap adoption. Any candidate edit changes the identity and invalidates old approval. Every adoption invalidates affected evidence and still requires the complete source-recompiled same-snapshot Final Gate; candidate diagnostics never count as Progress or acceptance.

Contract length, model output capacity, implementation layers, module count, parallelism and Agent preference never split a delivery or Outcome. Existing `outcome_files` are only a compatible physical representation of the same one-Contract authority. An incomplete Draft is never formally compiled.

## 6. Composition, Authority And Finalization

One user-selected delivery always produces one Contract and one Final Gate. The workflow does not perform a top-level Contract-capacity or separation decision. `delivery-set` remains a fixed non-executing retirement tombstone.

The first formal Contract Compile freezes `initial_task_base` with commit, tree and workspace manifest and immediately becomes Authority Lock. The complete `CompiledDeliveryContractV2` becomes an internal `active-long-task-authority-v3` snapshot under Git common-dir; its hash and the worktree Git-config marker bind task id, authority revision and compiled identity. `.ty-context/compiled-contract.json` is only a rebuildable projection and can never define previous authority, the initial base, risk floor or Final Gate identity. The additive execution-model checkpoint is returned to the caller but is not stored in Authority, Progress or Receipt state.

Authority publication is compare-and-swap against the expected previous compiled identity. Commit, verifier migration, accepted clear, valid abandon and corrupt cleanup share one active-state lock. Compile stages the cache, commits common-dir authority and marker, then publishes the cache. It clears the Final Receipt for every changed compiled identity and invalidates derived Progress unless the revision changes only Supporting Context while preserving every Progress freshness identity. Stop/close clear only the exact identity accepted by the Live Gate. Failed compile/revision/CAS leaves the previous snapshot, initial base and progress intact.

Targeted verification persists independent per-Check Progress Records scoped to protected authority, check/runner/verifier identity, Controlling Context, input paths, binding carriers and dependency interfaces. Counterfactual Findings are projected into their owning Check Result before Progress creation. Immediately before writing, targeted verification re-reads active task/revision/compiled/worktree identity; a concurrent revision writes no stale progress.

Live Final Gate requires a clean candidate commit after all required Context updates. It captures active identity, recompiles the source Contract and complete current Context snapshot, validates the common-dir snapshot/marker, creates one Git-tree snapshot and reruns the complete Contract without historical proof reuse. It re-reads active identity after the checks; a concurrent revision yields `needs_work`, never an accepted Receipt. Verify, status and resume read common-dir authority rather than workdir cache. Receipts remain audit-only.

## 7. Authoring Preflight And Static Compile

`ty-context long-task preflight <workdir>` is a read-only, model-free Authoring check. After parseable structure is normalized, it calls the same activation-safety kernel as Compile in collecting mode and returns every independent diagnostic reliably discoverable from that structure. The activation boundary also classifies every current workspace path against protected authority, declared expected change, allowed support, forbidden and unclassified categories: before the first lock it compares the current workspace with `HEAD`; after a lock it compares with the immutable `initial_task_base`. During first enable, only exact files present in the current package asset tree for configured managed destinations plus the exact harness config/hook files are added to protected input; managed directory roots and broad `.codex/**` are never exempt. Preflight never creates or updates Active Authority, initial base, worktree marker, compiled cache, progress, Receipt or pending revision; it never runs project verification.

Preflight diagnostics are repair-oriented without becoming repair authority. Exact duplicate diagnostics are emitted once with `occurrences`; known codes may expose stable `refs` and safe `repair_hint`. When a structural duplicate makes the same Claim ambiguous, only the deterministic pair receives `diagnostic_id`, `repair_group`, `repair_priority` and `blocked_by`. No finding is hidden, reclassified or treated as resolved; no repair state, YAML location registry or second authoring schema is added.

New authoring uses Compact V2 YAML. The parser fills only deterministic defaults. Goal, target profile and required target refs, execution targets/root entrypoints/capabilities, Stages, Source/Source Claims, full Context, vertical Outcomes, atomic applicability dimensions/profiles and refs, required success/degradation paths, owners/paths, Requirements, complete Control field/relation closure, obligations, proof surfaces, journey roles, keyed Given/When scenarios, Evidence Capabilities, runner targets, verification inputs, one-Claim Assertions, narrow semantic Counterfactual/liveness witnesses, risk facts, forbidden shortcuts and typed external confirmations remain explicit. Compact and expanded forms normalize to the same Contract object, hashes, risk, Claim Coverage and compiled identity.

Compile is deterministic, static and model-free. It calls the shared activation-safety kernel in fail-fast mode, so skipping Preflight bypasses no safety rule. The kernel strictly parses YAML, validates schema, Stage closure/dependencies and vertical Outcome placement, classifies every Source byte under the restricted grammar, inventories Source Items, validates canonical targets and architecture-aspect coverage, complete Control field/relation closure, atomic applicability-to-target/journey/dimension/Given/When equality, required-target/root/runtime-capability/runner bindings, scenario and success/degradation separation, Evidence Capability and selected-design method/cell adequacy, typed external impact, bounded Product Conformance, full Context, safe paths, owners, Bindings, runners and the transitive local verification dependency closure, rejects unsafe authority/proof files, compiles and requires all-of Claim × applicability × proof-surface Coverage, validates Source-to-Claim/Acceptance/Result/Global/Risk/external/decision mappings, enforces explicit one-Claim Assertions and compatible adapters, computes risk, enforces narrow semantic Counterfactual/liveness, Population-universe/security/environment/recovery proof and freezes Source, Contract, all Context, verifier, runner, workdir and repository identity.

Every path-bearing Contract field uses one canonical segment grammar. Windows separators and one leading `./` normalize to `/`; internal `.`/`..`, control characters, empty segments, absolute/drive/UNC paths and unsupported wildcard syntax fail closed. Pattern matching, subset and overlap/disjoint use the same AST.

Preflight and Compile never implement code, invoke or switch a model, create a process/worktree/branch or run project verification. First Compile creates Authority Lock and emits the user model-choice signal; it does not persist a Preflight receipt or checkpoint acknowledgement.

Forbidden or unclassified actual workspace paths block Preflight and direct Compile through the shared classifier, so skipping Preflight cannot absorb an undeclared dirty file into the first baseline. The first-enable package-managed exception enumerates actual package asset files for configured destinations and exact enabled Skill files; it does not trust an entire managed directory or arbitrary `.codex` path. Verify and Final Gate reuse the same classification semantics and return a `scope_escape` Finding for later drift. The same current Goal reviews risk/ownership, updates the Contract and recompiles.

## 8. Evidence Kernel

The Evidence Kernel retains only low-level capabilities that directly close false-completion paths:

- repository/workspace snapshot and identity;
- explicit argv command runner with bounded timeout/output and a minimal environment whitelist;
- Raw Execution identity derived from frozen runner identity plus declared Environment Requirements;
- AC-level observation and positive/negative assertion evaluation;
- implementation binding/path evaluation;
- population coverage evaluation;
- Claim-relevant narrow semantic Counterfactuals plus independent target-liveness witnesses for every behavioral Claim-bearing Assertion;
- complete Context/source/runner/oracle/verifier hashes, including the supported direct-literal local verifier module/config/data graph, plus Controlling Context freshness;
- current-execution target-runtime observation when a declared Claim can fail independently from its proxy surface;
- typed, Assertion-bound Evidence Capability records for interaction, state change, cross-surface consistency, durable readback, boundary invocation, external effect, failure injection, rendered UI, selected-target aggregate conformance, method/condition-specific design observation, target runtime and input variation;
- exact Stage closure, required-target qualification and bounded Product Conformance rules;
- Git common-dir Active Authority V3 snapshot plus matching worktree marker;
- outcome/check projection and derived status;
- source-recompiled Live Final Gate and audit-only Receipt;
- Stop Hook preflight and decision.

The compiled internal graph is deliberately small:

```text
Task -> Outcome -> Check -> Observation/Assertion
```

Agent/worker prose, hand-written state and command exit code alone cannot create accepted authority. Every Assertion needs an explicit Observation and its declared all-of Evidence Capabilities. Except for static `presence`, each capability has exactly one typed current-execution record keyed to that Assertion. Missing, duplicate, unknown, undeclared or type-incomparable evidence fails closed; negative proof uses explicit values such as `equals: false`.

Evidence adapters are compiler-derived: `playwright_test` produces `playwright_json_v1` and is the only adapter compatible with `ui_browser`; package scripts, project binaries and Node oracles use the `structured_json_v2` adapter for non-browser surfaces and emit the additive `long-task-check-result-v3` payload when capability records are required. V2 payloads remain decodable for compatibility but cannot satisfy non-presence capabilities and therefore cannot create false behavioral proof. Adapter identity participates in Acceptance Authority, Raw Execution, compiled authority, Progress freshness and Final Receipt.

Across all Checks sharing one Raw Execution identity, one claim-bearing Observation belongs to exactly one Assertion. Claim-bearing Playwright proof uses `playwright.case.<ac-key>.passed equals true`; one Test Instance binds at most one declared AC through `[ac:<assertion-key>]`. Missing, skipped, flaky, unexpected, timed-out, interrupted, failed, multi-AC, duplicate-within-project or structurally invalid cases fail closed. The same AC across distinct projects aggregates only when every instance executes and passes.

Claim-bearing Product/Global assertions use explicit expected-value comparisons; `truthy`/`falsy` are prohibited and `exists` is limited to an `implementation_structure` obligation. Each proves one Claim in one declared applicability cell. Every behavioral Claim-bearing Assertion has a same-Check claim-local `replace_json_value` or `replace_text` Counterfactual that changes only the asserted semantic field/fragment while preserving the implementation carrier and target execution, plus at least one claimless `equals true` `target_runtime` liveness Assertion that must remain passing. `replace_file` is compatibility-only and cannot establish semantic binding. Outcome Counterfactuals name an Outcome Binding; Global Counterfactuals use an Outcome-owned `binding_ref`. Both mutate only a proven subset of carriers and may cover related Claims only when every expected failure remains distinct. Structured evidence requires completed exit-zero execution with exactly designated `assertion_value_mismatch` failures and every `preserved_assertion` still passing. Weak-observability Playwright Counterfactuals accept exit one only under complete exact accounting of every unexpected instance; ordinary Baselines still require exit zero. Population retains its scoped coverage semantics but does not replace the semantic witness required for a behavioral Assertion. Claim and Population proofs are empty unless the complete Check and its applicable Counterfactuals pass.

For target-runtime Claims, “current snapshot” and “current execution” are both required. Rerunning an oracle that merely reads a committed or generated status file proves only the file's contents, not the target runtime. Build, installation, process start and absence of fatal logs likewise prove only those named assertions. A broader runnable-result Claim needs a stable product-owned sentinel or declared interaction observed from the same target session. Artifacts remain review material; they may accompany but never replace the structured Observation produced by the live Check.

For Outcomes with Controls, Product `surface_bindings` close the additional owner/journey gap. Every Control is grouped under at least one declared owner surface and required product target; existing Technical Bindings identify route and component carriers; a named root-entry success Check and scenario action exercise the real user path; and every Control Claim is proved on that target with its runtime-appropriate proof surface. For each bound Control, the root journey must prove its navigation result when declared, otherwise its interaction, trigger or location in that order, with all-of `interaction_trace` and `target_runtime`. Binding carriers are included in that Check's invalidation inputs. A support target, detached component route or deep/internal entry cannot satisfy this invariant.

A selected exact/constraint design target additionally names immutable verification inputs, condition keys, bound Control Claims, one root-entry conformance Check/Assertion and current actual/comparison artifact paths. That Assertion requires `design_conformance`, `interaction_trace` and `target_runtime`; the typed conformance record must match the compiled target/conditions/artifact paths and both artifacts must be present in the current Check result. Each declared verification method has its own Assertion and exact condition cells, and each cell names a method-record path plus a method-native `observation_path`; current primary-observation paths and digests are pairwise unique, while Playwright evidence appears only after every project instance attaches both artifacts. `visual_render` proves only render existence, while file hash/count/registry validation is `design_resource_integrity`; neither proves `design_implementation_conformance`. Each surface binding explicitly inventories declared design-acceptance blockers with exact Source-item/method/required-capability lineage; every entry resolves through a machine Claim proved on the capability-qualified target or a target-blocking External Confirmation with matching impact. An empty array means none were declared, not that a known blocker was waived; removing one requires revised Source/Contract authority. The Harness trusts the frozen project verifier's comparison result but does not infer undeclared blockers from arbitrary external formats.

The Evidence Kernel separates required success, degradation and recovery journeys. The same Check cannot be both success and degradation, and honest degradation is not successful Result proof. A boundary or external effect is observed at a declared observer target, never solely by its producer. Input-sensitive behavior requires varied inputs and distinguishable outputs, including failure. A multi-Outcome Stage Gate proves distinct declared surfaces against the same runtime state; merely repeating one surface or one status value is insufficient.

Semantic Product Conformance is deliberately risk-proportional. A separate read-only Global `conformance` Check is required only when `weak_observability` is combined with either multiple Stages or multiple required product runtime families. It starts at a required root product target, declares `target_runtime`, has a Raw Execution identity independent from Outcome Checks and runs inside the existing Final Gate. Single-Stage, single-family work keeps the ordinary same-Check sensitivity path and pays no extra conformance execution.

## 9. Verification And Recovery Semantics

### Targeted Verify

`verify` can select one Outcome, one Check or all repair checks. It runs on a current snapshot, records precise findings and projects current status, but always has `acceptance_authorized: false`. Findings carry the owning Source/Claim/Assertion/Observation/owner-path repair context without exposing secrets.

`verify --explain` is a read-only execution preview over the selected compiled Checks. It reports the declared main Raw Execution groups and applicable Counterfactual executions, including a bounded declared execution-count summary, without invoking runners, writing Progress or claiming duration, internal build-process count or acceptance. It is a feedback-cost planning aid, not another verification mode or Receipt.

Contract authoring keeps each Check's `input_paths` and Binding carriers at the smallest sound causal envelope. A repository/application/platform root is not a convenience default; it is valid only when any matching change can invalidate the declared result. Every Counterfactual mutation names a current production carrier with a defensible path from the declared target root. `verify --explain` makes those declarations reviewable before an expensive run, but Preflight does not pretend that a language-neutral path graph proves runtime reachability. When repository evidence cannot prove the route, current-execution Counterfactual behavior remains the proof.

There is no second executing `diagnose-check`: it would pay the same opaque runner cost while creating a competing execution surface. The current Goal may use project-owned fast feedback during edits, preview for declared cost shape and targeted verify whenever their expected localization value exceeds their cost; Final Gate alone owns acceptance. Machine-checkable prerequisites use existing environment requirements; runtime-specific API health, incremental build caching, streaming phase output, heartbeat and descendant-process cancellation remain project-runner responsibilities.

When a target-runtime Check exists, its cheapest reliable default feedback point is the first useful runnable boundary and later coalesced changes to declared runtime inputs. The Goal may defer or skip those non-accepting runs; only an intermediate decision that actually relies on their Progress requires a fresh run. Continuing implementation and entering Final Gate never depend on targeted Progress because the complete Gate reruns the Check. This is a feedback-cost recommendation, not a persisted trigger queue or implementation gate: no per-Outcome rebuild is required, identical Raw Execution may still deduplicate, and only the later complete Final Gate can accept.

### Status

`status` reports each Outcome as `unverified`, `progress_passing`, `progress_failing`, `progress_stale` or `blocked_external`. It is not completion authority. `final_workflow_status` reports a fresh Final Receipt's exact workflow status or `null`; `external_confirmations` reports current declarations from active authority.

User-facing reporting must preserve those meanings. `progress_passing` is described as current targeted repair evidence, never “Outcome complete”; `progress_stale` is only a freshness fact, cannot be reported as a current pass and does not itself command an immediate rerun after every edit. The Goal may coalesce relevant changes and use the cheapest reliable project-owned feedback, and refreshes a record only before relying on that targeted result. It may instead continue implementation or enter Final Gate, which ignores Progress and reruns all Checks. `final_workflow_status: null` means the Goal remains unfinished. Status derives `ready_stages`, Stage blockage and an acceptance/verification-ready Outcome frontier from current Outcome Progress; legacy `ready_for_implementation` output is a compatibility alias for that advisory projection, not an implementation gate, and no Stage pass is persisted. `machine_accepted_external_pending` is reported exactly with its pending confirmations.

Terminal reporting uses only the Contract's bounded target vocabulary. Before a fresh accepted Final Gate, `target_state` is `not_accepted`; a target-blocking external confirmation produces `blocked_external`; machine acceptance produces the declared `implementation_complete`, `target_profile_usable` or `production_release_ready`. A Final Receipt derives each Stage as `passed`, `failed`, `blocked_external` or `blocked_dependency`. These are terminal qualification projections, not per-platform or per-Outcome progress state.

### Resume

`resume` is read-only and reports Contract/compiled identity, effective risk, relevant Context, current Git state, freshness, `final_workflow_status`, target profile/state, the Progress-derived acceptance/verification Frontier, external confirmations, ready Outcomes, findings and the next safe action. That action is advice for verification and repair, never permission to edit only one Outcome. Its workspace status/fingerprint completes before current Git-state observation starts against the same repository, so index-writing `write-tree` cannot overlap a status refresh. Final Gate output/Receipt—not resumed Progress—owns terminal `stage_results`. Resume starts no persistent process and does not reconnect a physical Turn.

### Final Gate

`final-gate` first recompiles the raw source Contract and captures its complete protected identity, including Contract bytes and workdir fragments, Source, Controlling Context, verifier bundle, runner definitions, verification inputs and workdir inputs. It then creates one current workspace snapshot and reruns all Global and Outcome Checks. Identical Raw Execution identities may execute once inside the Gate while each Check still evaluates its own Assertions and artifacts. Before acceptance it recompiles again and requires both the semantic compiled identity and raw Contract hash to equal the pre-execution identity; any change or recompile failure yields `protected_inputs_changed_during_final_gate`. It separately rejects workspace/tree and Active Authority races. Bottom-up machine acceptance succeeds only when all executable Checks, Outcomes, global constraints and risk obligations pass on that one frozen candidate. External confirmations never contribute machine proof; a machine pass with pending confirmations reports `machine_accepted_external_pending`, remains outside the complete-delivery no-drift antecedent and has no native-Goal completion effect.

For behavioral Claims changed by a blocker-driven revision, Contract authoring reviews only the affected weak-observability or high-risk Outcomes. Their evidence must reach the furthest independently failing boundary named by the Claim; proxy/self-reported success cannot prove a downstream result, and a Counterfactual should disrupt the claimed causal capability rather than only carrier existence when those can diverge. This uses the bounded target profile, Stages, scenarios, Evidence Capabilities, proof surfaces, Checks, Bindings and mutation forms; it creates no open-ended platform taxonomy or universal runtime mandate.

### Freshness And Stop

Receipts and status describe the last audit only. Status/resume never project a stale Receipt as accepted. Verifier content changes require protected revision. `stop-check` returns the Live Gate result; external pending is a successful machine stop with a precise non-blocking message, while `needs_work`, `blocked_external`, Gate error and CAS failure remain fail-closed. `close` runs the Gate and clears only accepted identity. Doctor provides deterministic corrupt-state recovery without removing Contract, Source, Context or Git content.

Every accepted Stop result emits a non-blocking terminal-scope message, not only external-pending results. CLI output identifies machine acceptance and Authority cleanup without claiming native-Goal completion. This message causes no approval pause and owns no state.

## 10. Retry And Decision Boundaries

- Static Contract errors block implementation and are fixed in the same current Goal before product code work.
- First Authority Lock requires the one explicit task-specific execution-model choice before product implementation unless the user already stated that model strategy. The Agent ends the current turn at the emitted checkpoint; generic continuation/resume/finish language cannot satisfy it.
- Local test/Check failures are repaired in the same Goal with no new Agent or mandatory model session.
- Retry defaults to none. A transient verification command gets one mechanical retry only when it declares `transient_once`, idempotency and a read-only/test-sandbox effect.
- Product, acceptance or architecture semantic conflicts, explicitly user-reserved choices, missing decision-changing preferences and choices with no defensible recommendation pause for user decision and are not disguised as implementation failures. Preference clarification happens before choice-sensitive research; a later defensible recommended plan choice is recorded as delegated Source instead of creating an approval pause. Any real high-risk external action remains an External Confirmation.
- A rolling blocker does not by itself authorize scope reduction or External Confirmation reclassification. When the selected delivery genuinely changes, record the exact marked Source change, expose a derived human brief over the material Claim/proof/runner/scope/risk/external-confirmation deltas in the hash-bound approval summary, adopt only the exact approved identity and resume rolling execution under it. Revision completion vocabulary must never be used for delivery or native-Goal completion.
- Outside the one first-lock checkpoint, a healthy Goal is not paused solely for a model downgrade. Harness cannot switch the host-selected model, and model choice provides no completion authority.
- Harness owns no parallel-subagent scheduler or delegation lifecycle. The current Goal may use opaque platform-native delegation, but it cannot create Progress, authority or proof and must converge into the selected verification workspace.
- If the current Goal truly ends, a new session uses `resume` for semantic recovery. Harness does not simulate the old Turn or invent a Campaign identity.

## 14. Performance And Cost Boundaries

Release update mode is part of the release contract. Optional dry runs stop after preparation; they are not a mandatory second full-suite invocation. Build-tool versions remain provenance, while retry after a partial publish proceeds only when npm registry integrity matches the prepared bytes exactly.

- The near-universal default Context set is measured against advisory byte budgets; `doctor` reports but does not block overages, required recovery facts take precedence, and source regression tests do not convert the absolute byte heuristic into a release gate.
- Bounded Context discovery searches only `project_context/**`, uses a small high-signal term set and creates no persistent retrieval infrastructure.
- Sparse Context workspace routing retains the same minimum read path and allows dependency-driven widening without a full-graph default. Unmapped Long-Task runtime changes widen to the canonical Trust Boundary Gate; shared fixtures, package/dependency boundaries and unknown broad changes still widen to complete suites. - Local timing may report wall time, invocation count and failure stage. Harness does not fabricate token/model-call or platform Goal accounting.

## 15. Completion And Honest Limits

The architecture is complete only when CLI, Compact/expanded normalization, marked Source/REQ/CTRL/OBL/NCOMP/AC coverage, shared activation safety, Evidence Kernel, precise findings, Skill/profile/Hook/assets, compatibility diagnostics, docs/Context, tests, consumer smoke, package tarball and source sync all agree; the active runtime contains none of the retired orchestration plane; controlled temporary repositories prove Preflight non-mutation and repair/final/stale/close behavior; and a local commit records the change.

Stable honest limits:

- Harness does not create or restore a platform physical Goal.
- Harness cannot switch the model selected by the host or user; it can only request the one post-lock choice.
- Harness does not observe opaque platform-internal delegation and never treats it as authority.
- Harness does not prove the user never omitted an undeclared requirement.
- Complete selected-design conformance is bounded to facts explicitly covered by the selected handoff and the conditions actually checked. The default path provides fail-closed scoped conformance but not Long-Task's durable machine authority or cross-session recovery.
- Bounded keyword search cannot guarantee every synonym or indirect Context dependency is found during default-workflow discovery; explicit Long-Task Authority therefore freezes the full Context graph rather than claiming a referenced subset is complete.
- Prompt guidance cannot force an Agent to apply every Context fact or make target ownership mechanically correct. Default multi-workspace work can fail closed on unresolved target ambiguity and use project-owned changed-path proof, but repositories without such an oracle retain a review-bound soft Conformance limit.
- Harness provides no core parallel mutation.
- Harness does not observe platform token/model-call accounting.
- Git/PR/CI/deployment/human product confirmation remain external.
- Local mode trusts the installed package-owned verifier, Git metadata, the declared external package/runtime TCB and any physical device/observer whose bytes and real-world behavior cannot be frozen.
- Harness cannot derive the intended denotation of arbitrary natural language or independently establish physical-world truth. It instead requires exact Source/Contract observer binding, Claim-relevant semantic probes, typed method/cell evidence, target capabilities and frozen local dependency closure; anything still outside that boundary is explicitly trusted or target-blocking external confirmation. A typed record or passing Boolean alone never closes this limit.
- Network isolation remains the responsibility of the external platform.

## 16. Historical Design Boundary

Earlier pre-0.5 designs experimented with stage document chains and later with multi-SFC campaign orchestration, including Source Unit inventories, Scope Fit, Packets, workers, Waves, worktrees and integration/finalization gates. Those designs provided useful evidence-freshness lessons but made Harness own platform/process/Git responsibilities with diminishing delivery-drift benefit.

Version 0.6.0 keeps the reusable Evidence Kernel lesson—static falsifiability, current-snapshot recomputation, identity binding and Stop freshness—while retiring the orchestration plane. It closes declared-authority and evidence bypasses through machine-enumerated Source Items, shared activation validation, runner-derived adapters, all-of proof coverage, globally owned observations, value-sensitive Counterfactuals and passed-Check-only proof. The bounded Context search and one-time model choice improve retrieval and execution cost without recreating a retrieval service or model-routing plane. The later compatibility-only `normal-long-task` Skill was removed because ordinary work already has the default Workflow Contract and `long-task-workflow` is the sole explicit Long-Task route; upgrade removes only an exact legacy package-owned copy and leaves modified collisions for manual review. Historical names may appear only in explicit history, migration tests or command tombstones, never as current product behavior.
