# Project Tiny Context Harness — Product And Workflow Specification

## Underlying Engineering Problem

Large plans, durable project truth, design intent, implementation and proof commonly drift into disconnected representations as work crosses agents and sessions. Project Tiny Context Harness is designed to reduce that drift by keeping durable ownership recoverable, giving ordinary work a lightweight evidence-bounded contract and reserving explicit machine closure for deliveries that actually require recoverability, auditability or machine completion authority; this is a design purpose, not a measured effect claim.

## 1. Product Purpose

Project Tiny Context Harness is repo-native memory and delivery-drift protection for AI coding agents. Its design is intentionally small:

1. **Minimal Context** preserves durable project facts that code cannot reliably explain: goals/non-goals, ownership, architecture/interface/state boundaries and repeatable verification/deployment paths.
2. **Workflow Contract** defines the automatically applicable model-led lightweight loop for implementation work of any complexity: core/default Context, manifest routing plus one bounded Context search, dependency-driven read widening, conditional multi-target disambiguation, risk-proportional material-requirement and design understanding, one externally observable Architecture Deliberation, one `Context Delta`, platform-internal planning, Goal-owned implementation under a thin implementation-quality discipline, fresh project verification including any repository-owned changed-path scope check, failure localization and repair, evidence-bounded Contract Conformance carrying Engineering Quality Conformance (including Architecture Conformance), and a separate Context drift check.
3. **Long-Task Workflow** turns a user request or external implementation proposal into one complete Canonical Delivery Contract and adds verifier-owned current-snapshot machine acceptance when the delivery explicitly requires machine completion authority, recoverability or auditability.

These are the three product mechanisms. Every delivery reads Minimal Context. Unless Long-Task is explicitly selected or already validly bound, the prompt-level Workflow Contract applies regardless of duration, complexity or file count. An explicitly selected or already-bound delivery uses the logical `long-task-workflow` Skill as the sole Long-Task execution and completion carrier. Complexity determines execution and verification depth; required completion authority and recoverability determine the workflow route; risk inside Long-Task determines its proof strength. The default route creates no validator result, Receipt, persisted workflow state, exhaustive ephemeral Fact/Obligation ledger or machine-completion authority. `design-system-authoring` and `design-resource-authoring` are independent optional upstream Skills, not Long-Task stages: selected resources may feed either route, and Long-Task requires no design-resource step when the delivery needs none.

Raw/revised proposals, selected design resources and mixed attachments enter one Source-bound Contract Draft loop in `long-task-workflow` immediately. Source inventory/refinement, direct and traceable derived/delegated/evidence-backed meaning, complete standard/custom non-UI semantic Fact expansion, interactive surface/region/control/state/feedback detail, preference-sensitive research, real Markdown Source completeness, markers, repository binding and Contract mapping converge together before Preflight/Compile. This removes both the external handoff and the internal serial Source-authoring pass without adding a separate Source stage, gate, state or second plan. Pre-existing user planning/proposal documents remain ordinary Source; exact former package pointers are handled only by isolated versioned migration and modified same-name content is preserved for manual review.

The approved historical implementation Source for the page-level UI/UX authority upgrade is indexed at [`docs/page-level-uiux-authority-design-source.md`](docs/page-level-uiux-authority-design-source.md). It records input provenance, stable requirement/outcome/acceptance keys, the Design Context Depth Model, UI Authority Closure, Control field semantics, non-goals, risks and verification impact. It is ordinary upstream Source/history rather than registered Context or completion authority.

The actual design-generation engine stays outside Tiny Context. The base package includes explicit-only `design-system-authoring`: normally selected at project cold start, it discovers live Open Design MCP resources/tools, feature-detects lifecycle methods, uses the official same-daemon generation/revision/accept API when current MCP lacks creation, separates candidate/selection/adoption and reconciles the selected result into canonical `DESIGN.md`, exactly one authored token source/direction and owning Context. Open Design ID/revision/digest/project binding remains synchronization provenance, not a second authority; no init/default/downstream workflow auto-runs the Skill.

The base also includes `design-resource-authoring`, a thin explicitly triggered Open Design commissioner. It accepts an initial proposal and other product/technical/design Source, fixes the requested output/development content as a hard ceiling and commissions only the smallest sufficient resource set after subtracting selected existing coverage and naming preservation obligations. An outside-ceiling effect is existing `decision-required` with reason `scope-expansion-required`; a durable Product/Surface/Screen/Design change updates its actual owner before DRA resumes. Style-bearing resources require configured Design Authority and an Open Design project whose `designSystemId` matches the adopted system; if missing, the Skill stops and points to explicit `design-system-authoring` without invoking it. Low-fidelity structure, IA/flow and semantics-only state studies remain ungated. Formal Web/App work first reads real platform/framework/UI-system/token-adapter/component-owner/route-owner Source and requires a Source-backed realization candidate or blocker for every material component-family × target × condition profile. Provider execution, Artifact readiness, real-render Design suitability and human selection stay distinct; a defect-free first candidate may proceed without a cosmetic revision. A non-authoritative `Design Resource Review & Selection Stop` supports direction choice; selected formal work then completes canonical source/dependency/Census/manifest plus separate feasibility/preflight closure and returns to review for any newly visible decision before one consolidated idempotent reconciliation of accepted decisions into the initial proposal. It never edits other caller-owned Source, Context, `DESIGN.md`, code or Contract and never selects a required production realization without current technical authority.

The historical research and implementation Source for these Open Design adapter capabilities is indexed at [`docs/design-resource-authoring-implementation-source.md`](docs/design-resource-authoring-implementation-source.md). It records provider findings at their stated dates, requirements, amendments, bounded experiments, failure semantics and verification impact. It remains ordinary upstream Source/history rather than registered Context, Design Authority or approval. Generated candidates remain ordinary Source and authorize no fidelity; only explicit design-system adoption changes authority, while development workflows own UI Authority Closure, implementation and proof.

The audit-converged development Source for incremental DRA authoring, suitability review and selection-loop closure is indexed at [`docs/dra-incremental-authoring-review-development-source.md`](docs/dra-incremental-authoring-review-development-source.md). It preserves the original proposal/Web GPT/Codex audit provenance, accepted non-goals, owner allocation, sync order and evidence limits for recovery of this development decision; it is ordinary Source/history rather than a protocol, Context owner, review record or completion authority.

The approved workflow-assurance correction is indexed at [`docs/workflow-assurance-boundary.md`](docs/workflow-assurance-boundary.md). It is the current Source for route positioning, default-route evidence boundaries, formal benchmark criteria and the explicit prohibition on Long-Task internal workflow changes. It supersedes only historical Source clauses that extended exact production Fact/Obligation accounting into the default Workflow; formal handoff input completeness and all Long-Task closure semantics remain intact.

Minimal Context optimizes two purposes: preserve durable non-implementation facts, and let an Agent recover and update those facts with low search and attention cost. Near-universal facts use the core files and default area root; specialized role Context is `on-demand`. Before `Context Delta`, manifest candidates are supplemented by one bounded text search over `project_context/**` using a small set of high-signal task terms. The result is an expandable working set rather than a maximum readable set: later semantic or code dependencies may add any relevant Area/shared Context without turning the complete graph into the global default. The search creates no index, cache, registry, state, authority or read ACL. `ty-context doctor` reports the deterministic default read set, byte footprint, soft-budget overages, exact duplicate default files and `DESIGN.md` authority status; this is advisory observability only. A byte heuristic never authorizes omitting, compressing beyond readability or misclassifying required recovery facts, and the source release suite verifies the advisory behavior rather than imposing an absolute Context-size acceptance gate.

Context evolution is effect-first: a candidate must preserve current recovery and meet the stable design-purpose floor before repeated-read, search, authoring, runtime, state, migration, maintenance or verification cost is compared. A current recovery defect is repaired instead of frozen as the baseline. The complete purpose, mechanism, effect/efficiency non-degradation and safeguard-admission rule has one owner in `project_context/areas/harness-package/decision-rationale/minimal-context.md`; default Context keeps only near-universal summaries and pointers, while low-frequency Hook/worker/exact-proof/migration/history detail remains on demand.

The default Workflow follows the same lexicographic rule. It must preserve authoritative material requirements, applicable conditions, owner/source of truth, failure/recovery boundaries, fresh attributable project checks and honest checked/unverified/decision-required reporting before cost is optimized. It deliberately does not perform a complete standard/custom family Census, stable Fact/Obligation identity, exact set equality or per-Fact observation/comparison/verdict ledger; those are Long-Task-only machine-assurance responsibilities. New default safeguards must close a broad real false-implementation/completion path, reuse the lightest existing owner/check, add no artifact/state/Authority/Gate and show positive total ROI. The complete rule is owned by `project_context/areas/harness-package/contracts/workflow-contract.md`.

Material production UI adds UI Authority Closure and one conditional readiness question rather than a design phase or artifact chain. The depth model assigns global principles, cross-surface responsibility, Screen/Control semantics, visual-system facts, concrete targets and verification to distinct owners. Design Source Projection maps durable surface/flow/Screen/Control/state meaning to existing Product Surface or Screen/interaction Context; durable visual-system/token/motion-policy/rationale meaning to `DESIGN.md`; exact compositions, values, timelines, condition-specific facts and asset bytes to versioned targets; repeatable proof routes to verification Context; and delivery-local provenance, applicability, blockers and proof bindings to Source/Contract meaning. Stable surface/control/target keys connect them without copying the handoff.

Each adopted decision-relevant exact target/constraint has exactly one canonical adoption record. `DESIGN.md` owns project/system/component-family targets; the owning Screen Contract owns one-screen/interaction-specific targets. That record owns interpretation, selection basis, readable immutable locator/digest, declared condition coverage and editable upstream owner/locator/update route; every other layer keeps only the stable target key, canonical owner/anchor and local applicability. A registry mention or handoff coverage-index mention alone is not consumption. Affected workflows actively open the target before deciding, and updates create a new immutable version rather than overwrite the adopted baseline. `exact-target` permits fidelity comparison only for its named conditions, `constraint` governs only its stated scope, and `inspiration`, a candidate or an unconfigured starter never authorizes invented production layout. Dedicated external design systems may author candidates and selected targets upstream; a material unresolved preference remains a genuine decision, and downstream adoption remains separate.

The Long-Task Workflow V2 product equation is:

> one complete delivery = one authoritative target-qualified Contract + one currently selected platform-native execution Goal + one selected verification workspace + one unconditional host model-change checkpoint + Goal-owned adaptive technical implementation + one non-authoritative acceptance/verification Frontier + one trustworthy capability-aware Evidence Kernel + one Final Gate

The controlling objective, trusted-result boundary, Draft lifecycle, upstream Source boundary and mechanism-admission rule below govern every later Long-Task section. Existing implementation convenience, historical progress or local wording cannot weaken them.

## Sparse Context Workspaces / Monorepo Change Scope

Context stores durable product, technical, UI/UX-authority and verification facts in one recoverable project-owned tree. It does not promise that a prompt-guided Agent applies every recovered fact correctly; project tests, runtime evidence and review remain the behavior boundary. Exact visual values/resources remain in canonical design Source while Context/`DESIGN.md` owns stable authority, applicability and update routes.

For a monorepo, `project_context/workspaces/<workspace-id>/**` is an optional centralized, sparse mirror of implementation workspaces that actually own durable non-code facts:

```text
project_context/
  global.md
  architecture.md
  context.toml
  areas/                         # cross-workspace, repository-wide and shared owners
  workspaces/
    mobile/
      areas/
        product.md
        screens.md
        verification.md
    wechat-miniapp/
      areas/
        product.md
        screens.md
    api/
      areas/
        contract.md
        verification.md
```

Every represented Context workspace corresponds to exactly one repository-relative implementation/code root through existing `[[areas]].root` and `context`. It may contain several Areas for distinct durable semantic responsibilities. The reverse mapping is intentionally optional: an npm/Nx/Bazel/Cargo/Maven workspace with no durable Context gets no empty directory, placeholder or manifest row. Package-manager/build files remain the complete implementation-workspace inventory; Context does not duplicate or auto-discover that topology.

Workspace-local Areas stay under their Context workspace. Genuinely cross-workspace, repository-wide, shared, infrastructure or governance Areas stay under top-level `project_context/areas/**` and are not copied into every consumer. Single-workspace and non-monorepo projects retain the existing top-level `areas/**` layout, initialization and validation. Existing `[[areas]]`, `[[context]]`, `root`, `context`, role, read-policy and trigger fields are sufficient; there is no `[[workspaces]]` block or mandatory `workspace`, `owner_area`, `applies_to` or `requires` field.

The monorepo default Area should normally be a small top-level repository-common owner. Workspace-local Area/role Context stays `on-demand` unless its facts are genuinely near-universal; representing a client workspace never makes that client the implicit global default. This keeps the default path public/common while preserving precise on-demand discovery.

The input to this placement is ordinary repository fact: the code-root path and the durable semantic owner. The transformation is only a stable central directory plus the existing explicit `root -> context` mapping. Workspace placement is therefore an ownership/discovery namespace, not another Authority, package graph, permission model or runtime state. The design avoids an abstract scope layer, exhaustive empty mirrors, scattered Context and universal topology scanning because they add maintenance or a second mental model without improving that ownership truth.

Default reading remains adaptive. The Agent starts with core/default Context, manifest/trigger candidates and one bounded search, reads semantically relevant matches and widens to shared backend, sibling-client, cross-workspace contract, `DESIGN.md`, selected resources or code owners as dependencies emerge. A Context workspace can prioritize where to look, but it is never a read ACL, a maximum readable set or a mandate to read every file below the target workspace. A full-graph read does not become the ordinary default.

Read scope and intended workspace set are separate. The workflow resolves task-local intended workspace(s) from explicit user/product/path/repository facts. If those facts still leave materially different sibling workspaces plausible, it asks one concise target question before product edits rather than choosing the default Area, nearest/recently changed client or a generic keyword collision. Intentional cross-workspace work enumerates every intended workspace. Shared/backend Context or code may be read freely and may be changed when it is an attributable supporting requirement, but reading alone does not authorize that edit.

After implementation, the preferred objective extension point is a repository-owned changed-path/target-scope verifier. It compares exact paths attributable to the current task against intended workspaces plus declared supporting/shared scope and must not charge unrelated pre-existing dirty paths to the task. Without such a checker, Contract and Architecture Conformance review the final diff against durable Context/code owners. Tiny Context adds no universal package-manager mapper, path/import/runtime dependency scanner, persisted target declaration, applicability matrix, workspace registry, orphan/overlap doctor Gate or second Authority. Active Long-Task retains its existing expected/supporting/forbidden/unclassified path classifier and `scope_escape`; the default route does not duplicate it.

Root `DESIGN.md` remains the current shared project Design Authority for both monorepo and non-monorepo layouts. Creating a Context workspace does not create an independent design system. Multiple workspace-local Design Authorities would require a separate future mechanism that deliberately changes canonical ownership, doctor, authoring, token-source and update-route behavior.

Compatibility and cost remain bounded: non-monorepo behavior is unchanged, monorepos opt in only where Context exists, and unambiguous tasks add no clarification or full-read cost. Core/default/manifest/trigger/bounded-search coverage is not reduced; later reading remains unconstrained; the wrong-sibling rejection path is added without weakening Long-Task's full Context Authority, existing scope classifier, Final Gate or `F = Implementation Freedom Boundary`. Static tests prove directory/schema compatibility, guidance distribution, parity and non-degradation sentinels only. Claims about improved real-Agent recall, target selection or total ROI require fixed independent fresh-Agent paired runs with hidden product probes.

## Shared Engineering Quality Assurance

Every implementation delivery has one thin Shared Engineering Quality Obligation. Before the first implementation edit, the Agent surfaces one externally observable, repository-bound `Architecture Deliberation` that also records triggered quality attributes or a concrete preservation basis. During implementation, a small `Implementation Quality Discipline` preserves the existing owner, unique source of truth, real failure/resource boundaries and minimum justified abstraction while leaving order, methods and feedback cadence Goal-owned. After project-owned verification, one `Engineering Quality Conformance` closure includes the existing `Architecture Conformance` and checks the triggered falsifiable invariants on the current candidate.

`Applicable Quality Attributes` and `Implementation Quality Discipline` are subcriteria, not stages, Gates, states or artifacts. Occurrence is universal and depth is risk-proportional. A small semantics-preserving change names the current owner, extension point, shortest reliable verification route, unchanged applicable quality attributes and why it creates no new or worsened debt. Material work additionally resolves the unique source of truth, dependency direction, interface/state/persistence/resource/runtime lifecycle, selected and rejected alternatives, one plausible adjacent change and its extension point, touched debt, forbidden shortcuts, project-owned executable checks and applicable failure/load/threat scenarios. A material scope, owner, controlling-Context, dependency, selected-design, quality-applicability or debt-disposition change stales the deliberation.

Exact product, business and technical predicates—including explicit SLO, performance budget, security, reliability or compatibility requirements—remain owned by the existing Non-UI Semantic Fact closure; exact selected UI/UX Facts remain owned by selected-design closure. Shared Engineering Quality owns implementation boundaries, engineering-risk treatment and proof method, and creates no second quality Fact manifest/matrix or expected-value source. Correctness/invariants and maintainability receive at least preservation; reliability/resource lifecycle, concurrency/consistency, performance/capacity/cost, security/privacy/safety, compatibility/migration/rollout and operability/observability/testability expand only when Source/Context or the changed code exposes the corresponding risk. Untriggered families do not produce an empty matrix.

A performance obligation or improvement claim requires a workload, metric, baseline or budget, environment, comparator/tolerance and attributable project-owned benchmark/probe. A preservation-only risk uses the cheapest existing evidence; no current measurement means no performance claim. Static complexity or modularity shape proves only its supported structural signal, never target runtime behavior.

When a change adds foundational machinery, implements a mature protocol or security boundary, introduces a dependency/shared abstraction or approaches an existing extension point, Architecture Deliberation also performs a risk-triggered **Build / Reuse / Buy** judgment. It records an allowed solution set, prohibited failure modes and sufficient rationale/evidence rather than prescribing one library or abstraction. Reusing an owner, a standard capability, an installed dependency, a mature external library, a small self-contained implementation and intentional non-abstraction may all be valid. If at least one member has current support, the task is allowed and may select any supported member even when its initial proposal is rejected; block is reserved for no supported member/evidence, and decision-required for genuine external choice rather than equivalent implementation freedom. Duplicate owner-held rules, extension-point bypass, unsupported heavy dependencies, plainly incomplete security-sensitive reinvention, incompatible license/platform choices, forced abstraction over merely similar shapes and a second source of truth are prohibited. This adds no mandatory open-source/DRY rule, generic score, stage or Gate.

The post-implementation closure checks scope/path escape and unattributed dirty changes; owner/dependency/extension-point bypass; duplicate authority; undeclared API/schema/data/state/persistence/lifecycle/recovery/compatibility change; silent fallback, swallowed failure, resource/concurrency/partial-state defects when applicable; missing triggered-quality evidence; unsupported performance claims; forbidden shortcuts; and new/worsened duplication, responsibility growth, fragile coupling or unsupported abstraction. A finding returns to implementation and affected verification. A later code, configuration, Contract, declared check-input or controlling-Context change invalidates closure.

The two workflow entries are execution carriers, not nested quality workflows. Default Contract Conformance carries Engineering Quality Conformance. An active Long-Task uses only existing Source-backed Technical Obligations, Global Constraints/Forbidden Shortcuts, owners/paths/Bindings, Checks and independent Assertions where a quality invariant can fail while functional behavior passes. At least one architecture-classified obligation remains required; `SourceItemAspect` remains only `architecture`. A broad quality Boolean, functional pass or prose cannot replace independently failing invariants. Final Gate is the sole Long-Task Engineering Quality/Architecture Conformance carrier and proves only that declared, falsifiable, project-check-bound set—not overall code quality.

Contract Conformance primarily asks whether current Source and Context reached implementation and verification. The separate Context drift check asks whether implementation or a newly selected decision changed durable truth that Context does not yet record. No engineering-quality plan, stage, matrix, ADR, new Contract field/aspect/Claim kind/risk, second Authority, Gate, scheduler, persistent state or language-generic analyzer is introduced. The detailed purpose, implementation discipline, modularity capability, debt policy, update invariants and evidence limits retain the stable locator `project_context/areas/harness-package/decision-rationale/architecture-quality.md`.

## Long-Task Workflow Controlling Objective

The highest Long-Task objective is to prevent false completion inside declared authority. Its irreducible upstream trust boundary is that authoritative Source is complete, accurate and fine-grained enough to state every intended requirement and AC, including Control and cross-Control relations. For a formal selected Web/App handoff, “complete” additionally means that authoring derives the material Expected Fact Universe before generation from requirements, product semantics, adopted design system and target environments; a frozen Inspector then enumerates canonical resources and the residual handoff is exactly equal at `subject × target × condition × variation × atomic property` Fact Cell and required-proof granularity. A named Inspector/Oracle remains TCB and cannot discover meaning its format/capability cannot observe. The workflow cannot discover a requirement the user never expressed. Once Source exists, exact universe projection, falsifiable observers, fail-closed aggregation, protected freshness and complete Final Gate execution are proof obligations. No declared Plan Item, Fact or AC may be accepted before satisfaction.

Mechanism evolution therefore has one constrained compound objective: preserve the complete `Source/Contract Authority → Authority Lock/Revision → implementation drift → current-candidate observation → localization → repair → revalidation → one current-snapshot Final Gate` chain and the finest independently decidable non-UI/UI Fact and proof-obligation granularity, while minimizing the total cost of attaining that same complete effect. “Efficiency” means efficiency of purpose fulfillment under those hard invariants; it never permits a coarser Fact, sampled UI/UX coverage, weaker TCB, historical proof substitution or another completion path.

The formal guarantee is complete-delivery accepted-terminal-state safety, not guaranteed termination. Define `AcceptedDeliveryTerminal(snapshot)` as a fresh Final Gate result of exactly `machine_accepted`, with no declared External Confirmation pending. Inside the complete and accurate declared scope and the explicitly admitted observation TCB, the required implication is:

`AcceptedDeliveryTerminal(current snapshot) => DeclaredMachineObservableDrift = empty ∧ ExternalConfirmationPending = empty`

This implication is admitted only when every machine Claim or Fact × method obligation has all six links on the one current Final-Gate snapshot: unchanged expected Authority; package-admitted current actual; Harness-computed comparison, result identity and verdict; attribution to either a pre-existing frozen static production structure or a Harness-direct product-process observation; a Counterfactual whose package-observed actual changes as declared while preserved observations and target liveness remain stable; and current Final-Gate evidence. Unsupported meaning remains a blocking External Confirmation and therefore cannot coexist with `machine_accepted`. A generic Harness cannot infer requirements absent from Source, prove an arbitrary physical-world observer denotes the intended predicate or guarantee model termination. “The project oracle is sound” is not a free hidden premise, and a passing Boolean is not evidence of semantic binding.

The project owner explicitly places ordinary model-authored verifier error inside the Long-Task threat model for material machine acceptance. Four authorities remain separate: Source/Context/canonical selected resources and Contract own expected; a package-admitted observation adapter owns actual; the shared Harness exact evaluator or a Harness-direct admitted adapter owns comparison/result identity/verdict; and the existing sole current-snapshot Final Gate owns terminal status. A project runner may launch a product, provide input, emit raw product output and diagnostics, and submit compatibility fields. It cannot own authoritative actual/digest, comparison, `passed`, verdict, target-runtime authenticity, interaction authenticity or production reachability. Observation trust is decided by admitted capability, expected/actual separation, frozen dependency closure, current snapshot/execution provenance, production attribution, replayable comparison and causal sensitivity—not file age. An unrecognized or custom project Oracle is never a fallthrough to legacy validation: it must be changed to an admitted package path or to the existing blocking External Confirmation authority.

Compile projects each machine Fact × method obligation into an internal `CompiledObservationAuthority` carrying its obligation/Fact/Assertion/target identity, proof surface, method, expected identity/value, locator policy, carrier refs and runtime requirements. Its authority is exactly `package_static_json_exact`, `package_process_json_exact` or `external_confirmation`. This is an ephemeral compiled projection of existing Source and Contract, not a public schema field, Contract Authority, registry, lifecycle state or second Gate. Method, proof surface, target family and observer capability must match at Compile and runtime; a claim-bearing record with no matching compiled authority fails closed. Selected-design layout geometry, visual pixels, accessibility and motion, plus protected raw values, tolerance/mask, custom locators and unsupported physical predicates, compile only with explicit External Confirmation in the first version.

External-only authoring remains a real typed proof route rather than an invalid empty Contract. An existing External Confirmation closes Claim Coverage only for the exact ordinary/global/semantic Fact Claim identities named in `impact_claims`; each Semantic Fact proof additionally retains its explicit `confirmation_ref`, and no confirmation creates a machine result. A Stage Gate may omit a machine gate Check only when a `blocks_target: true` confirmation explicitly impacts that gate's `result` Claim. A non-blocking confirmation, a confirmation that omits the gate result, or `success_path_required: true` without a real success Check cannot substitute. An external-only Outcome therefore declares `success_path_required: false`, binds every unsupported Claim to the confirmation and reaches only `blocked_external`; it can never reach `machine_accepted` or `machine_accepted_external_pending`. This reuses the existing External Confirmation and Final Gate owners and adds no generic external-proof registry or second completion state.

The first package observation scope is deliberately bounded and split by what it proves. Before any runner starts, Harness prepares and freezes the observation inputs for every Raw Execution group, preventing an earlier group from priming a later group's carrier. `package_static_json_exact` reads UTF-8 JSON already present in the protected candidate snapshot, uses bounded RFC 6901 and canonical JSON, and supports plain `exact_value` for static implementation/configuration structure plus directly represented selected-design `content`/`component_state`. The runner cannot choose an arbitrary locator: the adapter fixes `/observations/<RFC6901-escaped stable Fact or obligation identity>`. After the runner identifies the artifact, Harness requires that path to have existed in the pre-run manifest and that pre/post bytes, digest, file identity, size, containment and no-follow semantics remain unchanged. Source/Contract/Context/expected resources and verifier/evidence/report/status/comparison/Receipt/Long-Task outputs are ineligible. A runner-created, modified, replaced or symlink-switched carrier fails before its new content is read. Static observation proves only that frozen carrier's current structure; it never proves runtime consumption, interaction, target-runtime or final render. A generated configuration is eligible only when it pre-exists and is frozen as the structure being proved.

`package_process_json_exact` is a separate minimal runtime adapter. It supports only `runtime_family: process`, a required target whose role is `product`, a `project_binary` Check whose runner target and complete argv exactly equal the declared direct root invocation, a root journey, `read-only` or `test-sandbox` effect, plain exact JSON and the admitted method set. Contract-internal equality is necessary but insufficient: every required target is also owned by one Source-backed technical obligation whose canonical `execution_target.<key>` projection covers target key, role, runtime family, root entrypoint, complete `root_argv` and required capabilities. The root, every argv repository file admitted by the finite production-Binding match and required product configuration/module carriers belong to the production owner and a production Binding; runner, verification-input, test-fixture or ordinary `input_paths` membership cannot establish product-root authority. Root/family/role/argv/capability change is a protected Source/Contract and Authority Revision that invalidates earlier Progress, Evidence and Receipt.

Compile derives one internal `CompiledProcessRuntimeClosure` alongside the existing observation-authority plan. It is an ephemeral projection, not a public schema, Authority, state or registry. Its only eligible members are the exact Source-backed direct-root invocation, exact production carriers required by the current Claim or Counterfactual, and finite argv values that resolve to production Binding members. Every `root_argv` array member is the exact child-visible token: classification does not split whitespace, unwrap quotes, rewrite backslashes or otherwise canonicalize execution argv. The closed first-version grammar examines an independent token or the value of one explicit `--name=value` token; `--name`, `--name=` and other supported standalone switches remain labels, while unrecognized embedded-delimiter or compound forms receive no machine closure. Raw token and derived repository locator remain distinct. Quote-bearing, POSIX/UNC absolute, drive-prefixed absolute or drive-relative, platform-ambiguous slash/backslash, every scheme-shaped colon prefix except the exact lowercase decimal `node:<number>` allowlist and other unsupported external-reference forms fail closed before execution unless the Contract explicitly routes their semantics outside machine closure through the existing external TCB/External Confirmation boundary. The only other colon scalar is a digits-only `<hours>:<minutes>` token; neither a known-protocol blacklist nor an arbitrary alphabetic-prefix rule is admissible. Parent segments are resolved with the declared `cwd` and fail only when the resulting locator actually escapes the repository, so a nested cwd may legally resolve `..` to another in-repository Binding. A remaining safe repository-relative value is normalized only for locator comparison and admitted only when an exact or pattern production Binding covers it; glob-owned, extensionless and space-containing single-token files are valid. An unmatched safe relative value or either closed colon scalar is not copied and is not rejected. This is not a shell parser, URI parser, file-extension guess, output-flag allowlist or dependency-language parser. `check.input_paths` remains an ordinary scope/freshness description and is neither broadly role-scanned nor copied merely because it is listed; a glob sibling appearing or disappearing cannot change closure identity. An exact `planned` root, matched argv file or carrier may be absent during authoring and Compile because its declaration already fixes identity, but Final Gate requires every closure member to exist in the current candidate; materializing those exact paths does not itself require Authority revision. One closure owner applies role separation only to actual compiled members and rejects Source, Context, Contract, canonical expected resources, verification inputs, `expected_output_paths`, `artifact_globs`, status/report/comparison/Receipt/Long-Task workdir, historical session/evidence and other proof-only material. Harness—not the project verifier—copies only this compiled closure into the per-Raw-Execution OS-temporary snapshot, directly spawns the Source-backed root with the unchanged raw argv, owns process lifecycle cleanup and captures one bounded stdout `ty-context-product-observation-v1` envelope that may carry several stable obligation observations. Checks with the same Raw Execution and compatible observation plan reuse that execution/envelope; Claim-local and implicit-preservation Facts retain independent comparison identities rather than starting one process per Fact. The admitted Actual is only the exact value emitted on that declared product-root JSON output surface; project-specific instrumentation cannot map an arbitrary internal, UI or device assertion into this adapter, and a Claim without a direct binding to that output surface remains External Confirmation. The child receives no observation-output path, challenge or protocol environment variable. Harness validates bounded stdout and binds its internal `HostExecutionAttestation` to the compiled closure identity in addition to Raw Execution, executable/root/argv, PID, timestamps, exit, candidate and observation digest. ## Long-Task Anti-Degradation Assurance

**Anti-Degradation Assurance** is the high-priority evolution objective that keeps the Long-Task causal chain valid and its drift-interception strength from degrading across accepted versions. **Anti-degradation construction** means the concrete Context, design, implementation-index, test, routing, parity and maintenance work used to establish that continuing assurance. It is an evolution layer around the mechanism, not a third implementation responsibility, and it creates no second Authority, Gate, state, matrix or registry.

2. run targeted verification for one Outcome or Check and shorten feedback;
3. localize failure to an Outcome, Claim, Assertion, Check, Proof Surface, Binding and path;
4. resume ready Outcomes, findings and the next safe action without re-deriving the whole task;
5. mark formerly passing local results stale when their authority or evidence changes; and
6. use Outcome dependencies to order acceptance/readiness projection and localize verification without turning them into an implementation gate.

`depends_on` means acceptance and intermediate-proof readiness. Source-declared delivery stages add only a product-delivery acceptance order: each vertical Outcome belongs to one stage, each stage names a gate Outcome, the gate transitively depends on the rest of that stage, and later stages transitively depend on prerequisite gates. Every Stage Gate executes from the root entrypoint of every required product target and proves `target_runtime`; a Stage containing multiple Outcomes additionally proves `cross_surface_consistency` over at least two distinct surfaces in one current runtime state. The current Goal derives an advisory Rolling Frontier from those existing edges and current Outcome Progress while choosing implementation order independently. No Stage Receipt, implementation gate, persisted scheduler, Worker queue, model-routing plane, process tree, second Gate or separate execution DAG exists, and Final Gate still revalidates the complete Contract on one current snapshot.

Outcome boundaries must not be based on model-output length, YAML/file length, frontend/backend layers, file/module count, Agent capacity, Worker assignment or desired parallelism.

> Outcome decomposes execution and diagnosis, not completion authority.

## Source-Bound Contract Draft Boundary

**Source** may be a user request, initial/revised proposal, research proposal, external proposal, pre-existing planning document or externally authored design resource. It preserves original delivery semantics and need not follow a recommended format.

Raw, mixed, attachment-heavy or incomplete input enters the same Source-bound Contract Draft loop immediately; Source-quality work is not an earlier lifecycle stage. While the Draft is progressively mapped, `long-task-workflow` inventories every supplied artifact, refines or synthesizes the writable real Source as needed, preserves direct requirements/qualifiers, and records derived, delegated and evidence-backed meaning with traceable basis. An instruction to synthesize/refine/complete/use judgment delegates authoring but does not invent tradeoff priorities. Unknown preferences that would materially change comparative research or selection trigger one targeted clarification; known preferences and recommendation-insensitive reversible choices do not.

After the preference envelope is clear, current changing external claims use authoritative/primary evidence. A defensible recommendation is written into real Source with authoring instruction, basis and exact added meaning before the corresponding Draft meaning may pass Preflight or Compile. High impact alone is not unresolved. Delegation authorizes plan meaning, not payment/purchase, contracting, production deployment/publication, destructive production mutation, permission grants, sensitive-data transmission or required legal/security/human approval; those remain External Confirmations. Conflicting authority, user-reserved choices, missing material preferences or no defensible recommendation remain `decision_required`.

Interactive textual Source reaches in-scope surface/region/Control semantic granularity, preserving type/label, placement/task, visibility/availability, trigger/input/validation/default, interaction/navigation, loading/empty/success/failure/recovery/permission/feedback/accessibility, stable keys/anchors, exact risk Fact/Affected Outcome pairs and one scenario per AC with accepted REQ/CTRL/OBL/NCOMP keys. A Contract Control is not the smallest visual atom. Selected implementation design resources additionally contribute their complete observable fact inventory down to any addressable element/primitive and style/layout/state/behavior fact, with stable resource/surface/control/state/target keys, declared conditions, provider/project/run/entry provenance, immutable identity and per-resource inspection closure. `HINT` remains non-material advice.

If a writable initial proposal is supplied, it is revised as the real Source; conversation-only delivery materializes exactly one project-native Markdown Source. This creates no standalone intermediary planning product, schema, CLI, gate, Receipt, cache, Authority or state. Exact former compatibility-pointer bytes are removed only by versioned migration, modified same-name content is preserved for manual review, and ordinary sync keeps no deletion registry. Pre-existing user documents remain valid ordinary Source and are never rewritten merely for compatibility.

Externally authored design resources are ordinary Source regardless of whether they arrive as Figma frames, images, prototypes, token exports, component specifications or another project-native format. Tiny Context requires no common pack or upstream sequence. A candidate, inspiration reference, mutable latest locator or implementation-generated screenshot authorizes no fidelity Claim. A selected exact target needs recorded selection basis, declared condition coverage and stable immutable identity, but remains upstream Source until the consuming workflow reconciles it against Context/`DESIGN.md` and adopts it. Tool-specific generation/export validation creates no Design Authority, Contract authority or acceptance.

Before Long-Task activation, every Material Source Item receives a non-rendering, meaning-preserving marker in the original Source without rewriting its text. Every non-empty Source line must be owned by exactly one Material Item, an explicit keyed `ty-source-background` block with a non-authoritative reason, or one formally parsed `design-resource-handoff-v1`/`design-resource-handoff-v2` block. Unclassified text, malformed/overlapping ownership and invalid formal blocks fail closed. A background block may hold only genuine structure, navigation or provenance; it cannot be used to hide requirement, acceptance, technical, risk or decision meaning. Contract authoring may add only:

- meaning-preserving structural decomposition; and
- repository bindings for owners, Context, paths, runners, verification inputs, proof surfaces and Bindings that are supported by real repository or Context evidence; and
- a defensible recommended plan choice after material preferences are known and after appending or revising real Source to record its delegation, basis and exact meaning without rewriting the user's original text.

The executing Agent must not place a new business rule, default, threshold, permission, recovery behavior, platform/data scope, persistence/retention policy, irreversible behavior or other product choice only in Contract YAML or relabel it as a necessary derivation. If an unknown user preference could materially change comparative research or selection, Authoring asks before proceeding. If a defensible recommendation then exists, it first becomes delegated real Source and any high-risk external action remains an External Confirmation. If authority conflicts, the user reserves the choice, a material preference remains unknown or no defensible recommendation exists, it remains `decision_required`. Missing preferred formatting does not block; missing genuine Source resolution does.

## Integrated Contract Authoring Rationale

Contract Draft authoring belongs inside `long-task-workflow`; there is no separate `contract-authoring`, `draft-authoring` or `prepare-long-task-draft` Skill. A separate single-response authoring surface was rejected because a complete Contract may exceed one response and cannot reliably be required to emerge complete in one pass.

The integrated design is also required because:

1. a Contract Draft must inspect the real repository and relevant Context before binding owners, paths, runners, verification inputs, proof surfaces and Bindings;
2. Preflight findings feed directly back into the same Draft;
3. a separate Skill adds a handoff where Source meaning, repository evidence or unresolved findings can be lost;
4. a separate product tends to create a second plan, Authoring Authority or Authoring Receipt;
5. Draft-to-Compile is a lifecycle transition of one authority object, not a handoff between two products; and
6. one Skill can keep revising the same Draft across as many responses as needed, then continue through Preflight, Compile, the one-time unconditional host checkpoint, rolling execution, verification and Final Gate.

Source-quality rules and Contract Draft authoring remain one Source-bound authoring loop inside `long-task-workflow`; their separate reference files are progressive instruction loading, not serial phases or a service handoff. External design resources remain ordinary Source and do not replace repository-aware Contract authoring.

## Mechanism Admission Rule

Every Long-Task change starts from the controlling design purpose. Before cost is considered, first prove the declared-purpose validity floor, then prove `Coverage_new ⊇ Coverage_valid_baseline`, `FalseNegative_new ⊆ FalseNegative_valid_baseline`, Authority and fail-closed non-bypassability, and complete-current-final-snapshot proof. A known-invalid old behavior is a defect outside the valid baseline. If non-degradation cannot be proved, preserve the current formal acceptance path and place any experiment outside it. Cost reduction never compensates for weaker drift detection. Only after this hard admission sequence, account for total cost by explicitly including the cost of introducing and migrating the change in the subsequent ROI judgment. If the change alters mechanism semantics, an invariant, an authority/proof boundary or runtime behavior, change the mechanism and its verification. Otherwise change only the owning point; do not turn a local correction into a new mechanism.

Every proposed or retained Long-Task mechanism must answer:

1. Which concrete false-completion or delivery-drift path does it close?
2. Which invariant does it establish?
3. Which test, verification or current-snapshot evidence proves that invariant?
4. Does another mechanism already cover the same risk?
5. Which exact false-completion path would reopen if it were removed?
6. What Authoring, Runtime, State, Recovery and maintenance cost does it add?
7. Does its incremental purpose-fulfillment benefit exceed every incremental Authoring, Runtime, State, Recovery, maintenance, test, process, introduction, adoption and migration cost?
8. Does it fail closed?
9. Does it create a second Authority, second plan or scheduling plane?

Expected total-cost ROI is positive exactly when incremental purpose-fulfillment benefit exceeds all incremental costs. Admission targets high ROI/high efficiency: the benefit has a significant, stable margin over the complete verified cost set rather than merely exceeding zero. That is sufficient to place a non-degrading candidate in the consideration set, not sufficient to adopt it automatically, and it requires neither exhaustive comparison nor proof of a global/local optimum. Prefer measured data, benchmarks or operational evidence. When none exists, discuss the decision with the user or project owner; a rigorous causal argument plus simple, bounded validation may guide bounded experimentation but cannot manufacture a missing formally required cost metric. The Long-Task Workflow itself was admitted before mature longitudinal data existed because its logic and basic validation were sound; that historical admission does not supply missing formal cost evidence for a Level 4 claim. Unsupported intuition alone is insufficient.

Keep the design purpose fixed while improving it. When total cost is comparable, prefer the change that fulfills the mechanism purpose more effectively; when purpose fulfillment is comparable, prefer the change with lower implementation and operating cost. Stop construction after the declared-purpose validity floor, relative non-degradation, must-allow, structural-cost and applicable measured total-cost thresholds close; reopen only for a new real counterexample, repeated material cost hot spot or evidence of significant additional net benefit.

Retain an acceptance mechanism only when it provides non-substitutable drift-prevention value with positive total ROI after the non-degradation gate. A non-authority workflow affordance may additionally be retained when existing fail-closed protection makes its incremental benefit exceed all incremental costs and the affordance adds no acceptance bypass, second Authority, second plan, scheduler or persistent control state. The first-lock execution-model checkpoint uses this second rule. Positive ROI permits consideration rather than automatic adoption. This remains a specification and code-review principle, not a new mechanism matrix, Receipt or runtime Registry.

The protected `F` boundary applies the same rule in reverse to proposed development-stage constraints. A fixed phase/order/method Gate, mandatory per-edit or per-Outcome verification cadence, agent-allocation rule or Harness-owned multi-agent orchestration is rejected unless an explicit project-owner design-purpose decision proves that it closes a concrete path not covered by final-current-snapshot acceptance or a lighter project-owned check, is necessary for an irreversible/safety boundary or has independently positive total-cost value, remains non-authoritative and non-bypassable, and passes both non-degradation and positive-net-ROI admission. The current canonical positive-default selection stays parent-owned and ephemeral: qualifying work makes actual calls for multiple exact workers, while non-qualifying work names one admitted solo reason. It needs no Harness state; delegation output remains non-authoritative and must converge before declared verification.

The UI production-surface binding satisfies this admission rule. An observed delivery proved four independent gaps under the existing prose-only model: support-target Control Claims substituted for a required native target, deep links bypassed the production root shell, resource hashes/counts were mislabeled as implementation conformance, and declared acceptance blockers were not projected into the Final Gate. One aggregated `surface_binding` per production surface/target plus typed `design_conformance` only for selected exact/constraint targets closes those paths through existing Product/Technical/Acceptance authority. It adds no scheduler, state, Receipt or Gate; authoring grows by surface/target rather than Control-field count. Prose-only repair, a universal per-Control screenshot matrix and a separate UI registry/Gate have respectively insufficient interception strength or materially worse total cost.

The shared design-resource adapter satisfies the same admission rule one boundary earlier. Direct visual-only consumption is not a reliable Contract interface: a prose summary, Control list, broad dimension row or generic condition label can omit one image, Anatomy Part, state, geometry/style property or behavior. Earlier strengthening froze canonical resources and indexed facts, but a handoff could still define its own narrower universe; `all-21-state-catalog` could stand in for atoms; an Inspector `complete` flag could hide skipped nodes; a Fact needing token and pixel proof could retain one method; runtime could return aggregate pass without its actual observation/comparator/Oracle/environment. Starward exposed this remaining false-green class.

The current adapter closes it through pre-generation Expected Universe derivation, frozen input/Census enumeration, first-class condition/variation/property axes, exact Cartesian Fact Cells, complete standard catalog, design-system lineage, dynamic/relation/asset closure, all property-required Fact × method obligations, collection count/digest and no sampling/truncation, then exact manifest↔handoff equality. Long-Task freezes per-Fact comparison authority and requires exact passing current results including sensitive-evidence policy. Existing source profiles, typed locators, resource closure, full-target layout/pixel defaults, blockers, Assertions and Final Gate remain necessary. Exploration pays no schema cost, non-Web `reference` remains valid, and selected handoffs may group thousands of Facts into a compact source set without duplicating values or creating one artifact per Control. Alternatives—prose-only strengthening, trusting provider/Inspector completion, embedding CSS in Contract, a second registry/Gate or exhaustive files per component—respectively miss the failure path or add worse authority/synchronization cost. This is monotone and positive-ROI after the non-degradation gate.

Revision-return and terminal-scope affordances use that same non-authority rule. Compile/revision JSON reports `delivery_completed_by_this_event: false` and a rolling next action; Final Gate/Stop/close output reports `acceptance_scope: declared_machine_authority` and `native_goal_effect: none`; close additionally reports `closed_scope: machine_authority`; and the Stop Hook emits one non-blocking scope message. These fields and guidance close state-transition ambiguity without a persistent `authority_revision_in_progress`, native-Goal state, second semantic Gate or Goal restoration runtime.

Apply protection along three independent dimensions: task complexity expands implementation and verification depth; required machine completion authority, recoverability and auditability select the route; Long-Task's existing `auto | standard | strict` risk floor raises proof only on affected high-risk Outcomes. Risk must escalate automatically or explicitly and can never be downgraded by the executing Agent.

## 3. Workflow Route And Long-Task Proof Profiles

### Default Model-Led Route

Use the default Workflow Contract whenever no valid Long-Task binding is active and the user has not explicitly selected Long-Task. This is an automatic lightweight protocol for implementation work of any complexity, not a local/simple-task tier. A complex cross-module change can remain on this route when model-led execution, project-native verification and an evidence-bounded handoff are sufficient. No Delivery Contract or long-task binding is created.

Default Context discovery reads the core/default set, collects manifest area/role/trigger candidates and then performs one bounded text search over `project_context/**` before `Context Delta`. The search uses a small set of high-signal task terms, reads only relevant matches and creates no vector/persistent index, cache, registry or search state. Keyword matching supplements semantic judgment and final Conformance rather than replacing them.

That result is the first working set, not a read sandbox. Widen it whenever shared or indirect dependencies require more Context/code. Context workspace, Area and `read_policy` never authorize edits. Resolve intended workspace(s) from user/product/path/repository facts; if materially different siblings remain plausible, clarify the target before product edits, otherwise proceed without ceremony. Cross-workspace work names all intended targets and supporting/shared scope. During final Conformance, use any repository-owned changed-path scope checker on task-attributable paths, or review the final diff against durable owners when no checker exists.

`Architecture Context Hit` and `Decision Rationale Hit: existing|required|none` remain internal routing questions. They are not durable facts, roles, validators or artifacts, and the checkpoint never creates a rationale delta or required file. `Context Delta` remains the only durable-fact decision point.

Architecture Deliberation is universal while its depth and applicable-quality assessment are risk-triggered. New durable modules/capabilities, public API/schema/data/persistence, source-of-truth or state ownership, dependency direction, cross-area boundaries, migration/security/recovery/compatibility, material performance/resource/concurrency risk and reusable abstractions require the corresponding analysis. Small local fixes record concrete architecture and quality-attribute preservation instead of paying full ceremony or skipping. Harness may route repository-native type/lint/AST/dependency/contract/behavior/benchmark checks but does not become a language-generic architecture or quality analyzer.

Product Surface Contract work uses `context_surface_contract` and the existing `contract`, area/subdomain and verification roles. It must not add a new product-surface role; Source-to-Context judgment and Contract Conformance remain internal workflow checks.

The Design Context Depth Model adds no role: global principles, cross-surface Product Surface Contracts, optional on-demand Screen/Control Context, `DESIGN.md`, project-native authored targets and verification remain distinct fact depths. `product-surface-contract.md` owns cross-surface responsibility; `screen-contract.md` is the portable Screen/Control structure. UI Authority Closure reconciles stable surface/control/target keys as Context-covered, Context update, task-local, out of scope or decision-required before material implementation.

The default route preserves every explicit Source and Context requirement, but does not construct an Expected Fact Universe, stable Fact/Obligation identities, an exact set-equality proof or per-Fact result ledger. It identifies material requirements, conditions, owners, failure boundaries and real acceptance entries at risk-proportional depth; runs attributable project-native checks on the final candidate; localizes and repairs failures; reruns every check affected by a later change; and reports `Implemented`, `Verified`, `Unverified` and `Blocked / decision required` scope separately. Missing or conflicting Source, an unresolved qualified handoff, or an unobservable claim blocks an unqualified completion statement without creating a Contract, persisted map, evidence ledger, readiness state, Receipt or Gate.

For a selected implementation handoff, default work still runs formal preflight to prove the named input's completeness and integrity, opens every affected exact target or constraint and its declared conditions, routes the design to the production owner and cold-start user journey, executes the applicable final-candidate project checks and reports conditions those checks did not establish. Formal input completeness does not become a claim of exact production Fact×method closure. Choose Long-Task explicitly when that exact, independently failing and re-runnable machine proof is required.

### Explicit Machine-Assurance Route

Select Long-Task explicitly when the delivery requires declared requirements to become stable, independently locatable and independently re-verifiable machine obligations; when current-snapshot machine acceptance rather than a model-led handoff is required; when recovery across compaction or sessions is material; or when auditability and reduced routine process supervision justify the authoring and verification cost. A small billing rule can use Long-Task; a large refactor can remain on the default route. Duration, complexity, file count and agent preference never activate it automatically. A valid existing binding resumes it.

This route keeps the existing Source, Contract, Authority Lock, protected Revision, Fact/Obligation, Evidence Kernel, repair/reverification, External Confirmation, Final Gate and no-drift logic unchanged. Its goal is stronger implementation-conformance assurance for declared and observable obligations, not proof of undeclared requirements, universal product quality, Oracle soundness or optimal architecture. “Lower supervision” means less routine progress and item-by-item inspection, not zero user decisions or external confirmation. “Efficiency” means minimizing total cost subject to complete machine closure, not promising fewer tokens or less wall time than the default route.

### Long-Task Internal Proof Floor

Long-Task retains one Delivery Contract, one native Goal, one selected workspace and the existing `auto | standard | strict` proof-floor semantics. `auto` computes the required floor, `standard` requests the standard profile and `strict` requests the strict profile; these values, their schema and compiler behavior are unchanged by workflow-route positioning.

The compiler requires strict when any declared fact is true:

- public API or schema change;
- persistent data change;
- data migration;
- security boundary change;
- permission boundary change;
- irreversible external effect;
- full-population operation;
- multi-repository change is rejected as unsupported;
- critical user path with weak end-to-end observability.

Users may raise risk to strict. A requested `standard` level below the computed floor fails with `risk_level_below_required`. Skill or executor logic can never lower risk. Standard and strict use the same workflow and Outcome model; strict only raises proof requirements on affected Outcomes.

## 4. Single-Goal Rolling Delivery

The active flow is:

```text
initial or revised proposal plus selected design resources and other Source
-> minimum relevant Context
-> one continuously revised Source-bound Contract Draft
   (inventory/provenance/refinement/markers and mapping converge in this loop)
-> Draft Outcome decomposition
-> repository/Context binding and Source -> REQ/CTRL/OBL/NCOMP/AC coverage
-> read-only Authoring Preflight repair loop
-> first formal static Compile and Authority Lock
-> one-time unconditional host model-change checkpoint
-> current native Goal chooses implementation method/order in the selected workspace
-> temporary acceptance/verification-ready Outcome Frontier
-> optional targeted feedback and repair verification
-> same-Goal repair and Context Delta updates as needed
-> optional stateless diagnosis of the same Contract's revision candidate
-> automatic bounded repair or one exact pending user decision and atomic Authority replacement
-> one-snapshot complete Final Gate
-> Stop freshness
-> external Git/PR/CI/deployment/human confirmation
```

Outcome is an independently decidable and target-verifiable acceptance-result unit. It is not a Goal, branch, worktree, worker, frontend/backend layer, file group, output-length fragment or fixed implementation slice. `depends_on` determines acceptance and intermediate-proof readiness only. The current Goal may implement, inspect or repair any in-scope Outcome in any order that fits current code reality; the derived Frontier only localizes the next independently meaningful verification/repair boundary and never authorizes or prohibits implementation edits.

The Frontier is not persisted as a scheduler graph and is not an implementation gate. Full file/function/component/test order, local hypotheses and tool choice remain with the parent Goal. After the first-lock boundary, the parent applies the packet-first positive-default rule in `F`; the Workflow Contract owns its predicates, six stable parent-only reasons and partial-delegation semantics, while the package-managed Skill owns exact dispatch and integration procedure. The judgment, packet count and assignment remain ephemeral, and no generic/built-in/null/unknown, task-name-, prompt- or model-only substitute is admitted.

The host and user own the parent Goal's model selection. Harness cannot switch or verify the model of a running conversation or Goal and creates no model-tier scheduler, model-route state or checkpoint acknowledgement. The first Authority Lock is the one deliberate exception to uninterrupted execution: Compile emits `execution_model_checkpoint.required: true`, `action: change_model_in_host_then_continue`, `resume_token: model checkpoint cleared, continue`, `generic_continue_satisfies: false` and `turn_boundary: end_current_turn`. The Agent always ends that turn before product implementation, file edits, builds or tests, even if a prior user message already stated a model strategy. It asks an English-speaking user to reply exactly `model checkpoint cleared, continue`; Chinese guidance instead says `处理好模型更换后，请仅回复：模型切换卡点解除，继续`. This is an exact package-managed prompt protocol, not a Harness-enforced unlock: Harness cannot observe the next host message or attest that the host changed models, and it stores no acknowledgement. Later revisions return `required: false`; no repeated model pause occurs. The boundary reduces execution cost by using the already locked Contract and Final Gate protection, but it is not completion authority.

The old boundary prohibited every Harness-owned model worker because any model-specific execution surface risked becoming routing state or a second control plane. The explicit project-owner decision now permits the package to install one optional Codex-native `long_task_implementation` custom agent profile whose fixed model and reasoning effort have one machine-readable source in the canonical package-owned TOML and whose child-local `[agents].enabled = false`, usable only for a bounded rolling implementation or repair packet after the parent Goal has crossed the checkpoint. The file is a static, stateless host affordance: it is not a checkpoint option and belongs to no Source, Contract, Authority, Context writeback, Progress, Evidence, Receipt or Final Gate. Missing exact custom-agent selection, a host schema that rejects the required leaf-agent field, a missing/invalid profile or a preserved same-path user customization never changes formal Long-Task acceptance; the parent Goal executes directly. Compatibility must not be obtained by deleting the leaf boundary or substituting a generic child. Static installation does not prove host discovery or selection. The package may not expand this profile into dynamic/task-tier model selection, automatic model retry, a scheduler or persisted delegation/model state.

The parent remains the only owner of Source, Contract, Authority, architecture, Context writeback, integration, current-candidate checks, formal verification, Final Gate, close and native-Goal completion. A delegated worker receives only a bounded packet, cannot run Long-Task lifecycle commands, choose models, spawn/retry/schedule agents, create a branch/worktree or claim acceptance, and returns an advisory report rather than Progress/Evidence. With an active binding, a package-owned `PreToolUse` Hook matching `^(spawn_agent|Agent)$` reads only the official current-call `tool_input.agent_type` selector and denies creation unless it equals `long_task_implementation`; an exact `SubagentStart` matcher then injects the bounded-worker context using official `agent_type` and `agent_id`. These Hooks do not rewrite input, infer identity from task names/prompts/models/transcripts, retry, substitute or persist state. Hook install/update uses no-follow type checks and snapshot/compare/atomic publication, preserves non-package Hooks and emits a non-blocking `/hooks` review notice; host/user trust remains unobservable and unpersisted, so installation never proves the guard is active. No transcript/model/path inference, thread registry, polling, App Server, fixed agent count, Outcome-to-Agent mapping, queue, DAG or state is created.

Before allowing an exact active spawn, the same Hook freshly reuses the profile owner's no-follow bootstrap-path inspection and requires the installed regular profile to parse and remain byte-identical to the current package asset. Missing, invalid, outdated, symlinked, non-regular or otherwise conflicting state denies the spawn and returns the packet to the parent without substitution; inactive work remains unrestricted.

> 禁止的是动态或持久化模型路由、模型调度和第二控制平面；允许的是一个固定、无状态、非 Authority、可缺席的 Codex 原生滚动实现 worker profile。

Harness never provides, persists, retries or recovers a parallel-subagent scheduler, Worker graph, branch/worktree fan-out or delegation state. The current Goal applies the bounded positive-default rule when platform-native delegation is available and may separately use user-authorized Git parallelism as an opaque implementation choice, but Harness neither depends on nor records either path and never treats it as progress or proof. Every accepted change must converge into the selected verification workspace before Contract-declared verification can count.

`Context Delta` remains live after Authority Lock. When implementation or repair discovers a durable fact, the current Goal updates the owning Context rather than preserving a known stale fact until the end. Long-Task always freezes the full `project_context/**` graph and treats every file as **Controlling Context**: a caller-selected referenced subset cannot prove that an unselected requirement-bearing or architecture file is irrelevant. Changes require Authority Revision, invalidate affected evidence and require a user decision when mapped Claims/targets/proof obligations or another decision boundary change. Final Gate recompiles and records that same complete current Context snapshot. The lightweight default Workflow retains manifest routing plus bounded search; the stronger full-graph rule applies only after explicit Long-Task selection.

Target-runtime feedback is also rolling, but remains non-authoritative. If a declared result can pass on a proxy surface while failing in its target runtime, the earliest Outcome that owns the first runnable boundary declares a project-owned Check that exercises the target during the current Raw Execution and derives its asserted Observation from that session. A tracked status report, screenshot, binary, log or historical run cannot be the sole proof of that Claim. The Check declares its runtime-affecting `input_paths`, Binding carriers, verification inputs and environment requirements through existing Contract fields.

The Contract declares one bounded target profile, its exact non-empty required product target refs and each target's runtime family, root entrypoint and exact capability set. A Web/process proxy cannot satisfy an independently required Native/desktop target. `playwright_test` and Native/Desktop `project_binary` remain compatible project runner forms, but their project-submitted runtime records are diagnostic only. The current package derives runtime authority only when Harness directly spawns an admitted `runtime_family: process` product root; Browser, Native, Desktop and device families have no package runtime adapter and therefore require target-blocking External Confirmation. Runtime-family base capability plus condition/method-derived input, viewport, motion, assistive-technology, physical-device, sensor and haptic capabilities remain mandatory for any future admitted target proof and cannot be supplied by a proxy.

The cheapest reliable feedback default is to targeted-verify those Checks after the first useful runnable slice and after coalesced relevant changes when early localization is worth its cost. This cadence is Goal-owned and never gates implementation order or another Outcome's edits. A Progress record must be fresh only when the Goal relies on it for an intermediate readiness, diagnosis or resume decision; stale or absent Progress may flow directly to Final Gate because that Gate ignores Progress and reruns every declared target-runtime Check in the current Gate execution on the final snapshot. There is no mandatory full environment rebuild per Outcome/edit, open-ended `platform_impact` taxonomy, per-platform progress state, scheduler or alternate acceptance path.

## 5. Canonical Delivery Contract V2

The root authoring file is `delivery-contract.yaml`, schema `long-task-delivery-v2`. It remains a non-authoritative Contract Draft until the first successful formal Compile. New authoring uses inline Outcomes in one file. Existing `outcome_files` parsing remains compatible only as a physical storage choice; fragments create no additional semantic boundary, state or completion authority. Every complete delivery selected by the user stays in one Contract and one Final Gate even when its Outcomes are weakly related.

Every Long Task has at least one real Source file, and every declared Source file contains at least one Material Source Item. The Source-bound Draft loop may refine a writable initial proposal or materialize one conversation-only delivery Source while Contract mapping proceeds and before marker insertion. Every Material Source Item is wrapped in its original Markdown with a non-rendering `<!-- ty-source-item:start key=... kind=... -->` / `<!-- ty-source-item:end -->` pair without rewriting direct text. A `ty-source-background` block accepts only an allowlisted reason whose content conforms to its machine grammar: text-free Markdown anchors/separators for `markdown-structure`, or non-rendering `ty-source-provenance` comments with fixed `input`, `mode`, conditional `source` and optional `sha256` fields for `provenance`. Text-bearing headings, free-form provenance and arbitrary visible prose are always Material or invalid even if a marker calls them background. The one strict design-resource handoff block is parsed as formal Source structure. Every other non-empty line is `source_text_unclassified` and blocks Preflight/Compile. A research proposal, ordinary prose plan or pre-existing planning document remains ordinary input and does not need to become strict Contract YAML, but its complete content still needs explicit ownership.

When Source contains stable semantic keys and Markdown anchors, Contract authoring preserves their meaning and reuses them where practical. Meaning-preserving structural decomposition and evidence-backed repository binding may add control states, Assertions, owners, paths, runners and proof. A defensible recommended plan choice may proceed only after its delegation, basis and exact meaning are recorded in real Source; it cannot be an implicit Contract expansion. Conflicting, user-reserved or unsupported product semantics remain real `decision_required` blockers, and high-risk external actions remain External Confirmations.

The Contract keeps three logical authorities in one file:

- **Product Authority**: complete observable end states, first-class atomic Requirements, ownership/surfaces/controls, non-goals and non-completing results.
- **Technical Boundary Authority**: stable obligations, allowed/forbidden path and architecture boundaries, bindings/forbidden shortcuts and strict rollback/recovery constraints.
- **Acceptance Authority**: falsifiable executable Checks, named acceptance criteria, claimed proof surfaces, positive/negative assertions, population/counterfactual obligations and environment requirements.

Each Outcome has a stable `key`, title, exactly one `stage`, dependencies, applicability profiles, Product, Technical and Acceptance sections. Product explicitly declares whether success and degradation paths are required and contains a complete set of atomic `requirements`; the Result, each Requirement, Technical Obligation, Non-completing item and other Claim-bearing fact names every applicable profile. A profile fixes one execution target, journey role, one value for every declared applicability dimension, Given state/condition/input key set and ordered When action sequence. Profiles within a scope use one dimension-key set; duplicate target/journey/dimension cells and a dimension with multiple values in one profile fail closed. Interactive Controls require a stable key and independently declare surface, region/location, type/label, user task, visibility/availability, trigger/input/validation/default, interaction/navigation, loading/empty/success/failure/recovery/permission/feedback and accessibility. `field_coverage` assigns every one of those 22 fields exactly once as `specified`, `not_applicable` with explicit meaning, or `unresolved`; `unresolved` blocks Compile, while specified and not-applicable semantics both become independently falsifiable Claims of the correct polarity. `control_relation_closure` likewise states `specified`, `not_applicable` or blocking `unresolved`; its not-applicable meaning and specified cross-Control/shared-state/navigation/permission/recovery relations are first-class Claims with their own applicability and proof surfaces. No empty field or absent relation is silently treated as “nothing required.” Every Outcome has at least one executable Check.

Checks support `package_script`, `project_binary`, `node_oracle` and `playwright_test` runners and `ui_browser`, `runtime_behavior`, `api_contract`, `data_state`, `security_boundary`, `population_coverage` and `implementation_structure` proof surfaces. Every Check declares a bounded journey role, a product/support/observer execution target and root/internal entrypoint, plus keyed Given and When scenario steps. Every Claim-bearing Assertion proves exactly one Claim and names exactly one applicability ref; the Check target, journey, dimension cell, unordered Given set and ordered When list must equal that profile. Every applicability ref of every Claim must have the Claim's required polarity and all required proof surfaces, so only actual applicable units are authored and none may be replaced by risk-based, pairwise or sampled coverage. Semantically equivalent units may share a Check execution, but their Claim/Assertion failures remain independently attributable. Each Assertion declares an all-of Evidence Capability set. `presence` proves static existence only; behavioral capabilities require exactly one typed V3 current-execution record. Required success and degradation journeys use distinct Checks, and an Outcome Result may be proved only by a success Check.

Boundary invocation or external-side-effect evidence executes from an observer target instead of trusting the producing component's self-report. `input_variation` includes at least two distinct inputs, two distinct output hashes and a failing case. `cross_surface_consistency` names at least two distinct `surface_ref` values and one matching state hash; multiple surfaces may share one runtime target. Unknown, undeclared, duplicate or missing capability records fail closed.

Model-authored identifiers stop at task, Outcome and Check keys. The compiler generates internal `OUT.<outcome-key>`, `CHECK.<outcome-key>.<check-key>` and `CHECK.GLOBAL.<check-key>` identities plus canonical Outcome-qualified Requirement, control-field, non-completing, obligation and forbidden-shortcut Claim ids and Global Claim ids. Non-empty control location requires `ui_browser` proof. Global non-goals and forbidden shortcuts require negative proof; Global constraints accept either polarity. Global forbidden paths remain static changed-path authority.

The Source marker key set and `source_claim` key set must be exactly equal across all Source files. Marker keys are globally unique; nested, overlapping, unclosed, empty, unknown-reason, grammar-invalid item/background markers are rejected, and formal handoff content must parse under its owning schema. Every visible sentence is therefore Material rather than merely “owned by a background block.” Each Source Claim `statement` equals its marked text after limited whitespace normalization. A technical-obligation marker may classify `aspect=architecture`; every delivery requires at least one such Source-backed obligation and an ordinary covered Claim, keeping Engineering Quality/Architecture Conformance in the existing carrier. `SourceItemAspect` remains only `architecture`; other engineering-quality meaning uses existing item kinds and proof bindings. The compiled Source inventory records key, kind, aspect, source path, normalized text and text hash inside authority/revision/explain projections; it is not a second authoring file or state surface.

Typed dispositions preserve meaning. Every non-decision Source item owns exactly one canonical target of the same semantic kind and normalized text; a target has one Source owner. Outcome `acceptance` points to one stable `<outcome>.<check>.<assertion>` whose criterion is Source-text-identical and proves an independently Source-backed non-Result Claim. The Source-bound Draft loop uses the exact ten Runtime risk names, including `data_migration`, separate `critical_user_path` and `weak_observability`, and retained `multi_repository_change`. `out_of_scope` is retired.

Compile derives canonical Product, target-profile, Stage, Acceptance and Global semantic projections and combines them with Source hashes/mappings plus the complete Context authority projection and file hashes. Retrieval metadata such as `triggers`, `read_when` and `read_policy` remains retrieval support rather than product acceptance evidence, but the manifest topology and every `project_context/**` byte are protected so an omitted selection cannot hide controlling meaning. The Controlling Context projection determines whether a Context revision needs approval and whether scoped Progress remains fresh; Long-Task has no unselected Supporting Context.

The first successful Compile is Authority Lock. It also emits the additive one-time execution-model checkpoint. From Authority Lock onward, revision classification is fail closed but distinguishes authority change from user decision. Machine-proven monotonic strengthening; raw Source/Context snapshot updates with unchanged locked Claims/targets/proof obligations; operational Runner target/argv/cwd/timeout/retry or verification-input repair; risk strengthening; repository-bound owner/expected/support/Binding-carrier expansion; and equivalent Counterfactual coverage with the same carrier, mutation and Check and no lost Claim/assertion-failure coverage may auto-adopt. Product/Source Claim/target/global/external semantic change, lost Check/scenario/Claim/Evidence Capability/failure interception, reduced `input_paths`/expected outputs/artifacts/obligations/recovery/population, owner-Context or forbidden-path removal, runner type/effect change, verifier-kernel change and unknown reasons require an exact decision and are never candidate-executed. A verifier-content digest change always invalidates prior evidence and remains decision-relevant unless preservation is independently established by the previous Authority or trusted external release provenance; the digest change alone is not classified as a concrete acceptance/proof reduction and cannot authorize its own adoption. Risk downgrade is rejected.

`ty-context long-task diagnose-revision <workdir> [--outcome <key>] [--check <key>]` recompiles the current `delivery-contract.yaml` against Active Authority without enforcement side effects. It may run only existing active Check identities with unchanged runner/verifier authority and only when every protected reason is repo-bound scope expansion. It returns `acceptance_authorized: false`, writes no pending/user-decision file, Active Authority, marker, compiled cache, Progress or Receipt, and disposes its temporary snapshot. Other mechanically bounded repairs return an automatic-revision preview without project execution. Product/Source Claim/target/external-confirmation changes, lost acceptance capabilities or failure interception, removed forbidden/owner Context, runner type/effect, verifier-kernel and unknown changes return a deterministic decision preview without running project code; risk downgrade is rejected. Repeated diagnosis creates no revision Draft object: edits accumulate only in the same Contract authoring file.

Ordinary `compile --revise` remains the only pending-decision boundary. For a decision-relevant candidate it writes one exact revision identity plus a concise deterministic summary separating `user_decision_reasons` and `mechanically_bounded_reasons` across semantic, Source/Claim, proof, verifier/runner, scope, risk, external-confirmation and verification-dependency changes. Compile/status/resume derive the same self-contained human brief and present it first. A verifier-content brief lists the changed verifier files, says prior evidence is invalid and identifies semantic preservation as independently unproven; it does not turn a byte delta into a proved reduction. If explicit current-task user instructions exactly cover every reason, the Agent may relay that decision for this identity without another question; generic continue/blanket approval/Agent inference does not count. Stateless diagnosis and ordinary edits coalesce withdrawn candidates so only the final stable blocking identity asks once. The brief is neither hashed editable authority nor persisted review state. The previous Authority remains active until exact decision and compare-and-swap adoption. Any candidate edit changes the identity and invalidates old approval. Every adoption invalidates affected evidence and still requires the complete source-recompiled same-snapshot Final Gate; candidate diagnostics never count as Progress or acceptance.

Contract length, model output capacity, implementation layers, module count, parallelism and Agent preference never split a delivery or Outcome. Existing `outcome_files` are only a compatible physical representation of the same one-Contract authority. An incomplete Draft is never formally compiled.

## 6. Composition, Authority And Finalization

One user-selected delivery always produces one Contract and one Final Gate. The workflow does not perform a top-level Contract-capacity or separation decision. `delivery-set` remains a fixed non-executing retirement tombstone.

The first formal Contract Compile freezes `initial_task_base` with commit, tree and workspace manifest and immediately becomes Authority Lock. The complete `CompiledDeliveryContractV2` becomes an internal `active-long-task-authority-v3` snapshot under Git common-dir; its hash and the worktree Git-config marker bind task id, authority revision and compiled identity. `.ty-context/compiled-contract.json` is only a rebuildable projection and can never define previous authority, the initial base, risk floor or Final Gate identity. The additive execution-model checkpoint is returned to the caller but is not stored in Authority, Progress or Receipt state.

Authority publication is compare-and-swap against the expected previous compiled identity. Commit, verifier migration, accepted clear, valid abandon and corrupt cleanup share one active-state lock. Compile stages the cache, commits common-dir authority and marker, then publishes the cache. It clears the Final Receipt for every changed compiled identity and invalidates derived Progress unless the revision changes only Supporting Context while preserving every Progress freshness identity. Stop/close clear only the exact identity accepted by the Live Gate. Failed compile/revision/CAS leaves the previous snapshot, initial base and progress intact.

Targeted verification persists independent per-Check Progress Records scoped to protected authority, check/runner/verifier identity, Controlling Context, input paths, binding carriers and dependency interfaces. Counterfactual Findings are projected into their owning Check Result before Progress creation. Immediately before writing, targeted verification re-reads active task/revision/compiled/worktree identity; a concurrent revision writes no stale progress.

Live Final Gate requires a clean candidate commit after all required Context updates. It captures active identity, recompiles the source Contract and complete current Context snapshot, validates the common-dir snapshot/marker, creates one Git-tree snapshot and reruns the complete Contract without historical proof reuse. It re-reads active identity after the checks; a concurrent revision yields `needs_work`, never an accepted Receipt. Verify, status and resume read common-dir authority rather than workdir cache. Receipts remain audit-only.

## 7. Authoring Preflight And Static Compile

`ty-context long-task preflight <workdir>` is a read-only, model-free Authoring check. After parseable structure is normalized, it calls the same activation-safety kernel as Compile in collecting mode and returns every independent diagnostic reliably discoverable from that structure. The activation boundary also classifies every current workspace path against protected authority, declared expected change, allowed support, forbidden and unclassified categories: before the first lock it compares the current workspace with `HEAD`; after a lock it compares with the immutable `initial_task_base`. During first enable, only exact files present in the current package asset tree for configured managed destinations plus the exact harness config/hook files and the exact byte-identical managed Codex implementation profile are added to protected input; customized collisions, sibling agent files, managed directory roots and broad `.codex/**` are never exempt. Preflight never creates or updates Active Authority, initial base, worktree marker, compiled cache, progress, Receipt or pending revision; it never runs project verification.

Preflight diagnostics are repair-oriented without becoming repair authority. Exact duplicate diagnostics are emitted once with `occurrences`; known codes may expose stable `refs` and safe `repair_hint`. When a structural duplicate makes the same Claim ambiguous, only the deterministic pair receives `diagnostic_id`, `repair_group`, `repair_priority` and `blocked_by`. No finding is hidden, reclassified or treated as resolved; no repair state, YAML location registry or second authoring schema is added.

New authoring uses Compact V2 YAML. The parser fills only deterministic defaults. Goal, target profile and required target refs, execution targets/root entrypoints/capabilities, Stages, Source/Source Claims, full Context, vertical Outcomes, atomic applicability dimensions/profiles and refs, required success/degradation paths, owners/paths, Requirements, complete Control field/relation closure, obligations, proof surfaces, journey roles, keyed Given/When scenarios, Evidence Capabilities, runner targets, verification inputs, one-Claim Assertions, narrow semantic Counterfactual/liveness witnesses, risk facts, forbidden shortcuts and typed external confirmations remain explicit. Compact and expanded forms normalize to the same Contract object, hashes, risk, Claim Coverage and compiled identity.

Compile is deterministic, static and model-free. It calls the shared activation-safety kernel in fail-fast mode, so skipping Preflight bypasses no safety rule. The kernel strictly parses YAML, validates schema, Stage closure/dependencies and vertical Outcome placement, classifies every Source byte under the restricted grammar, inventories Source Items, validates canonical targets and architecture-aspect coverage, complete Control field/relation closure, atomic applicability-to-target/journey/dimension/Given/When equality, required-target/root/runtime-capability/runner bindings, scenario and success/degradation separation, Evidence Capability and selected-design method/cell adequacy, typed external impact, bounded Product Conformance, full Context, safe paths, owners, Bindings, runners and the transitive local verification dependency closure, rejects unsafe authority/proof files, compiles and requires all-of Claim × applicability × proof-surface Coverage, validates Source-to-Claim/Acceptance/Result/Global/Risk/external/decision mappings, enforces explicit one-Claim Assertions and compatible adapters, computes risk, enforces narrow semantic Counterfactual/liveness, Population-universe/security/environment/recovery proof and freezes Source, Contract, all Context, verifier, runner, workdir and repository identity.

Every path-bearing Contract field uses one canonical segment grammar. Windows separators and one leading `./` normalize to `/`; internal `.`/`..`, control characters, empty segments, absolute/drive/UNC paths and unsupported wildcard syntax fail closed. Repository patterns treat parentheses as ordinary escaped literal characters, so framework route groups such as `apps/mobile/app/(map)/**` are valid without adding capture-group, regex or extglob semantics. Existing `*`, `**` and `?` retain their meanings, while `[]` and `{}` remain unsupported. Pattern matching, subset, overlap/disjoint, containment and runner freezing use the same AST.

Preflight and Compile never implement code, invoke or switch a model, create a process/worktree/branch or run project verification. First Compile creates Authority Lock and emits the unconditional terminal-turn host checkpoint; it does not persist a Preflight receipt, checkpoint acknowledgement or model observation.

Forbidden or unclassified actual workspace paths block Preflight and direct Compile through the shared classifier, so skipping Preflight cannot absorb an undeclared dirty file into the first baseline. The first-enable package-managed exception enumerates actual package asset files for configured destinations and exact enabled Skill files; it does not trust an entire managed directory or arbitrary `.codex` path. Verify and Final Gate reuse the same classification semantics and return a `scope_escape` Finding for later drift. The same current Goal reviews risk/ownership, updates the Contract and recompiles.

## 8. Evidence Kernel

The Evidence Kernel retains only low-level capabilities that directly close false-completion paths:

- repository/workspace snapshot and identity;
- explicit argv command runner with bounded timeout/output and a minimal environment whitelist;
- Raw Execution identity derived from frozen runner identity plus declared Environment Requirements;
- AC-level observation and positive/negative assertion evaluation;
- implementation binding/path evaluation;
- population coverage evaluation;
- Claim-relevant narrow semantic Counterfactuals plus independent target-liveness witnesses for every behavioral Claim-bearing Assertion;
- complete Context/source/runner/oracle/verifier hashes, including the supported direct-literal local verifier module/config/data graph, plus Controlling Context freshness;
- current-execution target-runtime observation when a declared Claim can fail independently from its proxy surface;
- typed, Assertion-bound Evidence Capability records for interaction, state change, cross-surface consistency, durable readback, boundary invocation, external effect, failure injection, rendered UI, selected-target aggregate conformance, method/condition-specific design observation, target runtime and input variation;
- exact Stage closure, required-target qualification and bounded Product Conformance rules;
- Git common-dir Active Authority V3 snapshot plus matching worktree marker;
- outcome/check projection and derived status;
- source-recompiled Live Final Gate and audit-only Receipt;
- Stop Hook preflight and decision.

The compiled internal graph is deliberately small:

```text
Task -> Outcome -> Check -> Observation/Assertion
```

Agent/worker prose, hand-written state and command exit code alone cannot create accepted authority. Every Assertion needs an explicit Observation and its declared all-of Evidence Capabilities. Except for static `presence`, each capability has exactly one typed current-execution record keyed to that Assertion. Missing, duplicate, unknown, undeclared or type-incomparable evidence fails closed; negative proof uses explicit values such as `equals: false`.

Evidence adapters are compiler-derived: `playwright_test` produces `playwright_json_v1` and is the only adapter compatible with `ui_browser`; package scripts, project binaries and Node oracles use the `structured_json_v2` adapter for non-browser surfaces and emit the additive `long-task-check-result-v3` payload when capability records are required. V2 payloads remain decodable for compatibility but cannot satisfy non-presence capabilities and therefore cannot create false behavioral proof. Adapter identity participates in Acceptance Authority, Raw Execution, compiled authority, Progress freshness and Final Receipt.

Across all Checks sharing one Raw Execution identity, one claim-bearing Observation belongs to exactly one Assertion. Claim-bearing Playwright proof uses `playwright.case.<ac-key>.passed equals true`; one Test Instance binds at most one declared AC through `[ac:<assertion-key>]`. Missing, skipped, flaky, unexpected, timed-out, interrupted, failed, multi-AC, duplicate-within-project or structurally invalid cases fail closed. The same AC across distinct projects aggregates only when every instance executes and passes.

Claim-bearing Product/Global assertions use explicit expected-value comparisons; `truthy`/`falsy` are prohibited and `exists` is limited to an `implementation_structure` obligation. Each proves one Claim in one declared applicability cell. Every behavioral Claim-bearing Assertion has a same-Check claim-local `replace_json_value` or `replace_text` Counterfactual that changes only the asserted semantic field/fragment while preserving the implementation carrier and target execution, plus at least one claimless `equals true` `target_runtime` liveness Assertion that must remain passing. `replace_file` is compatibility-only and cannot establish semantic binding. Outcome Counterfactuals name an Outcome Binding; Global Counterfactuals use an Outcome-owned `binding_ref`. Both mutate only a proven subset of carriers and may cover related Claims only when every expected failure remains distinct. Structured evidence requires completed exit-zero execution with exactly designated `assertion_value_mismatch` failures and every `preserved_assertion` still passing. Weak-observability Playwright Counterfactuals accept exit one only under complete exact accounting of every unexpected instance; ordinary Baselines still require exit zero. Population retains its scoped coverage semantics but does not replace the semantic witness required for a behavioral Assertion. Claim and Population proofs are empty unless the complete Check and its applicable Counterfactuals pass.

For target-runtime Claims, “current snapshot” and “current execution” are both required. Rerunning an oracle that merely reads a committed or generated status file proves only the file's contents, not the target runtime. Build, installation, process start and absence of fatal logs likewise prove only those named assertions. A broader runnable-result Claim needs a stable product-owned sentinel or declared interaction observed from the same target session. Artifacts remain review material; they may accompany but never replace the structured Observation produced by the live Check.

For Outcomes with Controls, Product `surface_bindings` close the additional owner/journey gap. Every Control is grouped under at least one declared owner surface and required product target; existing Technical Bindings identify route and component carriers; a named root-entry success Check and scenario action exercise the real user path; and every Control Claim is proved on that target with its runtime-appropriate proof surface. For each bound Control, the root journey must prove its navigation result when declared, otherwise its interaction, trigger or location in that order, with all-of `interaction_trace` and `target_runtime`. Binding carriers are included in that Check's invalidation inputs. A support target, detached component route or deep/internal entry cannot satisfy this invariant.

A selected exact/constraint design target additionally names immutable verification inputs, condition keys, bound Control Claims and exact method/condition cells. A machine conformance Check/Assertion is valid only when every required observation compiles to a package-admitted channel; its typed rows and artifacts remain diagnostic unless the package derives their Actual and comparison. In the current slice, aggregate `design_conformance`, `interaction_trace`, Browser/Native target runtime, layout, pixel, accessibility and motion therefore bind target-blocking External Confirmation instead of a fictitious root-entry conformance Check. Project Playwright evidence may localize failures but cannot close those cells. `visual_render` proves only render existence, while file hash/count/registry validation is `design_resource_integrity`; neither proves `design_implementation_conformance`. Each surface binding explicitly inventories declared design-acceptance blockers with exact Source-item/method/required-capability lineage; every entry resolves through a machine Claim proved on the capability-qualified target or a target-blocking External Confirmation with matching impact. An empty array means none were declared, not that a known blocker was waived; removing one requires revised Source/Contract authority. For admitted exact comparison Harness re-extracts the current Actual, computes comparison and result identity, and treats project-submitted `passed`/`verdict` as non-authoritative compatibility assertions that must agree. Unsupported observation remains External Confirmation. Harness does not infer undeclared blockers or semantics from arbitrary external formats.

The Evidence Kernel separates required success, degradation and recovery journeys. The same Check cannot be both success and degradation, and honest degradation is not successful Result proof. A boundary or external effect is observed at a declared observer target, never solely by its producer. Input-sensitive behavior requires varied inputs and distinguishable outputs, including failure. A multi-Outcome Stage Gate proves distinct declared surfaces against the same runtime state; merely repeating one surface or one status value is insufficient.

Semantic Product Conformance is deliberately risk-proportional. A separate read-only Global `conformance` Check is required only when `weak_observability` is combined with either multiple Stages or multiple required product runtime families. It starts at a required root product target, declares `target_runtime`, has a Raw Execution identity independent from Outcome Checks and runs inside the existing Final Gate. Single-Stage, single-family work keeps the ordinary same-Check sensitivity path and pays no extra conformance execution.

## 9. Verification And Recovery Semantics

### Targeted Verify

`verify` can select one Outcome, one Check or all repair checks. It runs on a current snapshot, records precise findings and projects current status, but always has `acceptance_authorized: false`. Findings carry the owning Source/Claim/Assertion/Observation/owner-path repair context without exposing secrets.

`verify --explain` is a read-only execution preview over the selected compiled Checks. It reports the declared main Raw Execution groups and applicable Counterfactual executions, including a bounded declared execution-count summary, without invoking runners, writing Progress or claiming duration, internal build-process count or acceptance. It is a feedback-cost planning aid, not another verification mode or Receipt.

Contract authoring keeps each Check's `input_paths` and Binding carriers at the smallest sound causal envelope. A repository/application/platform root is not a convenience default; it is valid only when any matching change can invalidate the declared result. Every Counterfactual mutation names a current production carrier with a defensible path from the declared target root. `verify --explain` makes those declarations reviewable before an expensive run, but Preflight does not pretend that a language-neutral path graph proves runtime reachability. When repository evidence cannot prove the route, current-execution Counterfactual behavior remains the proof.

There is no second executing `diagnose-check`: it would pay the same opaque runner cost while creating a competing execution surface. The current Goal may use project-owned fast feedback during edits, preview for declared cost shape and targeted verify whenever their expected localization value exceeds their cost; Final Gate alone owns acceptance. Machine-checkable prerequisites use existing environment requirements; runtime-specific API health, incremental build caching, streaming phase output and heartbeat remain project-runner responsibilities. The admitted direct-process adapter is the narrow lifecycle exception: Harness owns its bounded timeout, descendant inspection and cleanup because those are part of the package observation TCB.

When a target-runtime Check exists, its cheapest reliable default feedback point is the first useful runnable boundary and later coalesced changes to declared runtime inputs. The Goal may defer or skip those non-accepting runs; only an intermediate decision that actually relies on their Progress requires a fresh run. Continuing implementation and entering Final Gate never depend on targeted Progress because the complete Gate reruns the Check. This is a feedback-cost recommendation, not a persisted trigger queue or implementation gate: no per-Outcome rebuild is required, identical Raw Execution may still deduplicate, and only the later complete Final Gate can accept.

### Status

`status` reports each Outcome as `unverified`, `progress_passing`, `progress_failing`, `progress_stale` or `blocked_external`. It is not completion authority. `final_workflow_status` reports a fresh Final Receipt's exact workflow status or `null`; `external_confirmations` reports current declarations from active authority.

User-facing reporting must preserve those meanings. `progress_passing` is described as current targeted repair evidence, never “Outcome complete”; `progress_stale` is only a freshness fact, cannot be reported as a current pass and does not itself command an immediate rerun after every edit. The Goal may coalesce relevant changes and use the cheapest reliable project-owned feedback, and refreshes a record only before relying on that targeted result. It may instead continue implementation or enter Final Gate, which ignores Progress and reruns all Checks. `final_workflow_status: null` means the Goal remains unfinished. Status derives `ready_stages`, Stage blockage and an acceptance/verification-ready Outcome frontier from current Outcome Progress; legacy `ready_for_implementation` output is a compatibility alias for that advisory projection, not an implementation gate, and no Stage pass is persisted. `machine_accepted_external_pending` is reported exactly with its pending confirmations.

Terminal reporting uses only the Contract's bounded target vocabulary. Before a fresh accepted Final Gate, `target_state` is `not_accepted`; a target-blocking external confirmation produces `blocked_external`; machine acceptance produces the declared `implementation_complete`, `target_profile_usable` or `production_release_ready`. A Final Receipt derives each Stage as `passed`, `failed`, `blocked_external` or `blocked_dependency`. These are terminal qualification projections, not per-platform or per-Outcome progress state.

### Resume

`resume` is read-only and reports Contract/compiled identity, effective risk, relevant Context, current Git state, freshness, `final_workflow_status`, target profile/state, the Progress-derived acceptance/verification Frontier, external confirmations, ready Outcomes, findings and the next safe action. That action is advice for verification and repair, never permission to edit only one Outcome. Its workspace status/fingerprint completes before current Git-state observation starts against the same repository, so index-writing `write-tree` cannot overlap a status refresh. Git-index snapshot materialization includes skip-worktree entries and uses a new temporary root for every attempt. An exit-one `checkout-index` failure may be replayed exactly once only when it has no signal or diagnostic bytes, partial-root cleanup succeeds and a fresh fingerprint is unchanged; diagnosed or index-lock failure, candidate drift, cleanup failure and a second failure all remain fail-closed. Final Gate output/Receipt—not resumed Progress—owns terminal `stage_results`. Resume starts no persistent process and does not reconnect a physical Turn.

### Final Gate

`final-gate` first recompiles the raw source Contract and captures its complete protected identity, including Contract bytes and workdir fragments, Source, Controlling Context, verifier bundle, runner definitions, verification inputs and workdir inputs. It then creates one current workspace snapshot and reruns all Global and Outcome Checks. Identical Raw Execution identities may execute once inside the Gate while each Check still evaluates its own Assertions and artifacts. Before acceptance it recompiles again and requires both the semantic compiled identity and raw Contract hash to equal the pre-execution identity; any change or recompile failure yields `protected_inputs_changed_during_final_gate`. It separately rejects workspace/tree and Active Authority races. Bottom-up machine acceptance succeeds only when all executable Checks, Outcomes, global constraints and risk obligations pass on that one frozen candidate. External confirmations never contribute machine proof; a machine pass with pending confirmations reports `machine_accepted_external_pending`, remains outside the complete-delivery no-drift antecedent and has no native-Goal completion effect.

For behavioral Claims changed by a blocker-driven revision, Contract authoring reviews only the affected weak-observability or high-risk Outcomes. Their evidence must reach the furthest independently failing boundary named by the Claim; proxy/self-reported success cannot prove a downstream result, and a Counterfactual should disrupt the claimed causal capability rather than only carrier existence when those can diverge. This uses the bounded target profile, Stages, scenarios, Evidence Capabilities, proof surfaces, Checks, Bindings and mutation forms; it creates no open-ended platform taxonomy or universal runtime mandate.

### Freshness And Stop

Receipts and status describe the last audit only. Status/resume never project a stale Receipt as accepted. Verifier content changes require protected revision. `stop-check` returns the Live Gate result; external pending is a successful machine stop with a precise non-blocking message, while `needs_work`, `blocked_external`, Gate error and CAS failure remain fail-closed. `close` runs the Gate and clears only accepted identity. Doctor provides deterministic corrupt-state recovery without removing Contract, Source, Context or Git content.

Every accepted Stop result emits a non-blocking terminal-scope message, not only external-pending results. CLI output identifies machine acceptance and Authority cleanup without claiming native-Goal completion. This message causes no approval pause and owns no state.

## 10. Retry And Decision Boundaries

- Static Contract errors block implementation and are fixed in the same current Goal before product code work.
- First Authority Lock always ends the current turn before product implementation, file edits, builds or tests. The Agent asks the user to handle any model change in the host and send `【继续】`/`[continue]`; a prior textual model strategy cannot skip the boundary, and the continuation token does not prove a model change.
- Local test/Check failures are repaired in the same Goal with no new Agent or mandatory model session.
- Retry defaults to none. A transient verification command gets one mechanical retry only when it declares `transient_once`, idempotency and a read-only/test-sandbox effect.
- Product, acceptance or architecture semantic conflicts, explicitly user-reserved choices, missing decision-changing preferences and choices with no defensible recommendation pause for user decision and are not disguised as implementation failures. Preference clarification happens before choice-sensitive research; a later defensible recommended plan choice is recorded as delegated Source instead of creating an approval pause. Any real high-risk external action remains an External Confirmation.
- A rolling blocker does not by itself authorize scope reduction or External Confirmation reclassification. When the selected delivery genuinely changes, record the exact marked Source change, expose a derived human brief over the material Claim/proof/runner/scope/risk/external-confirmation deltas in the hash-bound approval summary, adopt only the exact approved identity and resume rolling execution under it. Revision completion vocabulary must never be used for delivery or native-Goal completion.
- Outside the one first-lock checkpoint, a healthy Goal is not paused solely for a model change. Harness cannot switch or observe the host-selected model, and the checkpoint/continuation provides no completion authority or evidence that a change occurred.
- Harness owns no parallel-subagent scheduler or delegation lifecycle. The parent Goal performs one ephemeral suitability judgment and uses multiple disjoint exact fixed-profile workers when the admitted predicates hold; otherwise it names one applicable solo reason. Delegated output cannot create Progress, Authority, Evidence or proof and must converge into the selected verification workspace under parent integration and formal verification.
- If the current Goal truly ends, a new session uses `resume` for semantic recovery. Harness does not simulate the old Turn or invent a separate orchestration identity.

## 14. Performance And Cost Boundaries

Release update mode is part of the release contract. Every published version declares `sync-only`, `upgrade-required` or `manual-required`; `ty-context upgrade --check` reports `safe_pending`, `manual_required` and `blocked`, and direct `sync` does not run migrations. Release fixtures prove the same marked Source/Binding/Counterfactual Contract against the prepared tarball before publish.

Trusted publication requires one non-advisory Windows Level-4 runtime prerequisite plus one Ubuntu prepare/test/pack/smoke execution per source commit. The Windows job builds once and serially runs only the acquisition and package-promotion boundary files; Ubuntu remains the complete release-suite owner and cannot prepare the tarball if Windows fails or is skipped. The protected publisher reuses that exact workflow artifact and verifies source commit, stable lockfile identity and tarball hash without rebuilding, retesting or repacking. Optional dry runs stop after preparation; they are not a mandatory second full-suite invocation. Build-tool versions remain provenance, while retry after a partial publish proceeds only when npm registry integrity matches the prepared bytes exactly.

Mechanism admission keeps **DRA semantic recovery/writeback** and **Build / Reuse / Buy judgment** as two independent frozen fresh-Agent tracks; neither may hide a category regression inside one aggregate score. Before any candidate run, the runner freezes one global execution-envelope digest for requested model/reasoning, Provider/fixture, environment, pairing and shared execution/scoring mechanics, plus one track-local digest for that track's cases, hidden probes, result schema, guidance, allowed/prohibited sets, thresholds, deterministic checks and track-specific scoring. A global-envelope change invalidates both tracks. A DRA-only or Build / Reuse / Buy-only input change invalidates only its owning track, and an older aggregate is reusable only when both its global and exact track-local identities still match; the attestation discloses reuse and still requires a fresh deterministic report bound to the exact current `main` tree. The runner separately verifies effective model/reasoning/Provider from authoritative execution output; unobservable values are `unverified` and set environment/trace doubt rather than inheriting the request. All deterministic fixtures must pass: no semantic loss/distortion/unsupported gain or inactive-Delta leakage; real raw-digest-bound scoped Source authority, exact per-key decisions, safe supersession, complete audit catalogs/final owners, scalar-carrier/scaffold non-interference, original-preimage disjoint spans and Delta-to-patch conservation; stale Base/checkpoint/writeback CAS conflict/corrupt or unknown checkpoint/path escape/link/collision detection; writeback idempotence and correct balanced/blocked reconciliation; and zero false rejection of a legal shared Token, reasonable small self-implementation or intentional non-abstraction. A sanitized attestation binds both identity layers, qualified provenance, bounded results and the exact candidate Git tree while excluding raw prompts/events/model output and sensitive content. The optional manual CI transport first validates the complete local deterministic/pair/aggregate inputs and attested source digests, then transports only size-bounded digest-bound summaries containing exact identities, trace/score/threshold outcomes, provenance qualification and simple-path aggregates. It verifies the exact commit/tree on `main`, pins Node 24, checks the package engine before dependency installation and independently recomputes deterministic results. The report and attestation separately bind the frozen Fresh-Agent benchmark environment/provenance and the actually observed deterministic process platform, architecture, full Node version, runner class and engine conformance; neither identity can substitute for the other, and unsupported runtime fails deterministic publication even when child checks return zero. CI uploads JSON for 30 days; neither the local bundle nor CI artifact is Context, Authority, Evidence, Receipt, a Gate or acceptance state.

Each track begins with at least three independent baseline/candidate pairs and requires at least two pairwise wins. It expands to five and requires at least three wins when any primary metric has coefficient of variation above 20%, pair direction is inconsistent, a primary result is within five percentage points of its threshold, or environment/Provider trace determinism is doubtful; provenance doubt stays explicit rather than being hidden by excluding every otherwise complete pair. Per track, no critical failure category may regress; targeted critical-plus-major defects must fall by at least 25%; must-allow false blocking is zero and all other false blocking is no worse than baseline. A simple DRA preview creates zero checkpoint files/bytes, pauses, extra Provider generations, formal handoffs/preflights, Proposal writes and helper write transactions; fresh-Agent median token and wall-time overhead is at most 10%, with no unexplained tool turn or automatic scope expansion. If a candidate closes no independent path, misses quality, increases false blocking, violates that simple path or costs more than its benefit, it is narrowed to a trigger, reduced/reused or removed. A zero-defect baseline cannot be credited with invented improvement; hardening then requires an independent deterministic failure path and near-zero fixed cost.

The existing delivery-benchmark owner additionally contains one opt-in DRA visual diagnostic, not another admission track. It freezes eight representative archetypes, five concretely pinned generation routes, ten visual/craft/reuse/cost review dimensions, at least three repeats and blinded randomized order. Its helper emits a public review schedule plus private route mapping and deliberately has no score, threshold, majority rule, winner, Provider ranking, automatic route, publication block or design-selection effect. Results remain descriptive for the observed cases with raw limitations. Any later durable routing policy requires a separate owner change that freezes evaluators, order, baseline, threshold and expiry before collection.

Active-Source portability is a separate owner-scoped diagnostic. `tools/verify_active_source_portability.mjs` scans the fixed managed guidance/assets, public executable docs, durable Context, source mappings and runtime-resolved Source plus exact caller-declared active files. It rejects real Windows/macOS/Linux user-home locators, permits explicit placeholders and non-resolvable provenance identities, follows no links and performs no mutation. It never derives an inventory from `git ls-files`, treats history as active, rewrites frozen Contracts/Receipts/fixtures or creates a registry, Gate, state or acceptance claim.

- The near-universal default Context set is measured against advisory byte budgets; `doctor` reports but does not block overages, required recovery facts take precedence, and source regression tests do not convert the absolute byte heuristic into a release gate.

## 15. Completion And Honest Limits

The architecture is complete only when CLI, Compact/expanded normalization, marked Source/REQ/CTRL/OBL/NCOMP/AC coverage, shared activation safety, Evidence Kernel, precise findings, Skill/profile/Hook/assets, compatibility diagnostics, docs/Context, tests, consumer smoke, package tarball and source sync all agree; the active runtime contains none of the retired orchestration plane; controlled temporary repositories prove Preflight non-mutation and repair/final/stale/close behavior; and a local commit records the change.

Stable honest limits:

- Harness does not create or restore a platform physical Goal.
- Harness cannot switch or verify the model selected by the host or user; it can only emit the one post-lock terminal-turn request.
- Harness observes only official Hook start fields needed to inject the fixed worker boundary; it does not persist or treat platform-internal delegation as authority.
- Harness does not prove the user never omitted an undeclared requirement.
- Selected-design claims are bounded to the selected handoff and conditions actually established by current-candidate checks. The default path reports unverified conditions and blocks an unqualified completion claim on unresolved authority, conflicts or unsupported observations; it does not provide Long-Task's exact per-Fact machine closure, durable machine authority or cross-session recovery.
- Bounded keyword search cannot guarantee every synonym or indirect Context dependency is found during default-workflow discovery; explicit Long-Task Authority therefore freezes the full Context graph rather than claiming a referenced subset is complete.
- Prompt guidance cannot force an Agent to apply every Context fact or make target ownership mechanically correct. Default multi-workspace work can fail closed on unresolved target ambiguity and use project-owned changed-path proof, but repositories without such an oracle retain a review-bound soft Conformance limit.
- Harness provides no core parallel mutation.
- Harness does not observe platform token/model-call accounting.
- Git/PR/CI/deployment/human product confirmation remain external.
- Local mode trusts the installed package-owned Harness and admitted observer/comparator implementations, Git metadata, and every explicitly declared external runtime or physical-device TCB whose bytes or real-world behavior cannot be frozen. An ordinary project verifier remains a named input/adapter boundary; its self-reported material result is not by itself a trust root, and unsupported observations stay external-confirmation-blocking.
- Harness cannot derive the intended denotation of arbitrary natural language or independently establish physical-world truth. It instead requires exact Source/Contract observer binding, Claim-relevant semantic probes, typed method/cell evidence, target capabilities and frozen local dependency closure; anything still outside that boundary is explicitly trusted or target-blocking external confirmation. A typed record or passing Boolean alone never closes this limit.
- Network isolation remains the responsibility of the external platform.

## 16. Historical Design Boundary

Earlier pre-0.5 designs experimented with stage document chains and later with multi-SFC campaign orchestration, including Source Unit inventories, Scope Fit, Packets, workers, Waves, worktrees and integration/finalization gates. Those designs provided useful evidence-freshness lessons but made Harness own platform/process/Git responsibilities with diminishing delivery-drift benefit.

Version 0.6.0 keeps the reusable Evidence Kernel lesson—static falsifiability, current-snapshot recomputation, identity binding and Stop freshness—while retiring the orchestration plane. It closes declared-authority and evidence bypasses through machine-enumerated Source Items, shared activation validation, runner-derived adapters, all-of proof coverage, globally owned observations, value-sensitive Counterfactuals and passed-Check-only proof. The bounded Context search and one-time unconditional host checkpoint improve retrieval and execution cost without recreating a retrieval service or model-routing plane. The later compatibility-only `normal-long-task` Skill was removed because ordinary work already has the default Workflow Contract and `long-task-workflow` is the sole explicit Long-Task route; upgrade removes only an exact legacy package-owned copy and leaves modified collisions for manual review. Historical names may appear only in explicit history, migration tests or command tombstones, never as current product behavior.
