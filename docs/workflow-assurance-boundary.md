# Workflow Assurance Boundary Source

This Source records the approved correction to the relationship between the automatically applicable default Workflow Contract and the explicitly selected Long-Task Workflow. It supersedes only prior statements that classified the routes by task size or required the default route to maintain Long-Task-equivalent exact production Fact/Obligation accounting ephemerally. It does not revise Long-Task's internal workflow, proof model, schema or runtime.

<!-- ty-source-item:start key=workflow-assurance-boundary-result kind=outcome_result -->
Tiny Context offers two delivery-assurance levels rather than two task-size classes: the default Workflow Contract is a model-led lightweight engineering protocol for implementation work of any complexity, while Long-Task is the explicit machine-assurance route for stable, locatable, independently re-verifiable delivery obligations and current-snapshot machine acceptance.
<!-- ty-source-item:end -->

<!-- ty-source-item:start key=three-orthogonal-workflow-dimensions kind=requirement -->
Complexity determines execution and verification depth; required completion authority and recoverability determine the workflow route; risk inside Long-Task determines proof strength. Duration, complexity, file count and agent preference are never sufficient to activate Long-Task automatically.
<!-- ty-source-item:end -->

<!-- ty-source-item:start key=default-route-any-complexity kind=requirement -->
Unless Long-Task is explicitly selected or a valid active binding is resumed, the default Workflow Contract applies automatically and may handle local fixes, cross-module features, large refactors, long-running implementation or other work of any complexity. “Default” means automatically applicable, not small, low quality, short or non-serious.
<!-- ty-source-item:end -->

<!-- ty-source-item:start key=long-task-explicit-assurance-selection kind=requirement -->
Long-Task is selected when the user requires declared requirements to become stable machine obligations whose drift can be detected, localized, repaired and reverified on the current candidate; requires machine completion authority; materially needs recovery across compaction or sessions; or requires auditability and reduced routine process supervision enough to justify the authoring and verification cost. A small but consequential rule may use Long-Task, and a large change may remain on the default route.
<!-- ty-source-item:end -->

<!-- ty-source-item:start key=long-task-internal-logic-preserved kind=constraint -->
This change must not alter any Long-Task internal workflow logic: Source inventory/refinement, Canonical Delivery Contract, Authority Lock, protected Revision, Fact and proof-obligation identities, Evidence Kernel, Progress/frontier semantics, failure localization, repair and re-verification, External Confirmation, current-snapshot Final Gate, machine-accepted terminal, no-drift theorem, lifecycle commands, Compact Carrier, Stop Hook and recovery behavior all remain unchanged.
<!-- ty-source-item:end -->

<!-- ty-source-item:start key=long-task-proof-floor-preserved kind=constraint -->
Long-Task's existing `risk.requested_level: auto | standard | strict`, computed risk floor, strict escalation triggers, schema, compiler and runtime enforcement remain unchanged. Workflow-route eligibility and Long-Task-internal proof strength are separate decisions.
<!-- ty-source-item:end -->

<!-- ty-source-item:start key=default-removes-exact-ephemeral-ledger kind=requirement -->
The default Workflow Contract must no longer require a complete Expected Fact Universe, stable Fact or Obligation keys, exact set-equality conservation, universal condition Cartesian expansion, per-Fact-by-method result rows, frozen Oracle/environment graph, revision digest or other exact ephemeral production-conformance ledger. It creates no Contract, Authority, Receipt, persisted workflow state, Final Gate or machine-accepted result.
<!-- ty-source-item:end -->

<!-- ty-source-item:start key=default-source-authority-and-material-understanding kind=requirement -->
Removing the exact default ledger does not remove or weaken Source. Every explicit user requirement, controlling Context fact, canonical specification and selected design constraint remains authoritative. Default work must understand material requirements, conditions, owners, failure boundaries and acceptance entries at risk-proportional depth; missing authority remains decision-required rather than becoming a silent implementation default.
<!-- ty-source-item:end -->

<!-- ty-source-item:start key=default-shared-engineering-judgment kind=requirement -->
Default work retains Minimal Context recovery, bounded Context search and dependency-driven widening, target/supporting-scope separation, Architecture Deliberation, risk-proportional engineering-quality judgment, the single `Context Delta`, Goal-owned implementation freedom, project-native verification, Engineering and Architecture Conformance, and the separate Context drift check. Complexity expands the depth of these judgments without adding fixed phases or artifacts.
<!-- ty-source-item:end -->

<!-- ty-source-item:start key=default-current-candidate-evidence kind=requirement -->
A default-route completion report may rely only on relevant checks run after the last change that could invalidate them. Historical CI, pre-fix tests, agent reports, prose inspection or a test result made stale by later code, configuration, Source or controlling-Context changes cannot establish current-candidate verification.
<!-- ty-source-item:end -->

<!-- ty-source-item:start key=default-failure-localization-and-repair kind=requirement -->
When default verification exposes a missed requirement, wrong owner or dependency, failed check, design mismatch, scope escape, Context drift, stale evidence or new/worsened debt, the Agent must localize the failure to the requirement, owner, module and check entry, repair it, rerun affected checks and then repeat final Conformance on the current candidate. This loop creates no persisted frontier or state machine.
<!-- ty-source-item:end -->

<!-- ty-source-item:start key=default-evidence-bounded-handoff kind=requirement -->
The default final handoff must distinguish `Implemented`, `Verified`, `Unverified`, `Blocked / decision required` and `Context: updated ... | no durable fact change`. It must not fold unverified or externally pending scope into a complete claim and must never imply machine acceptance or zero declared drift.
<!-- ty-source-item:end -->

<!-- ty-source-item:start key=default-qualified-handoff-and-fail-safe-widening kind=requirement -->
An unreadable, missing, stale or conflicting controlling Source; unresolved qualified handoff; materially ambiguous target workspace; unsupported observation boundary; or failed/stale project check blocks an unqualified completion statement for the affected scope. The Agent widens reading, verification or reporting only as required by discovered dependencies and risk, and reports the remaining qualification when trustworthy closure is unavailable; widening must not silently become an exhaustive Context read, a duplicate Long-Task classifier or invented authority.
<!-- ty-source-item:end -->

<!-- ty-source-item:start key=default-non-ui-assurance-boundary kind=requirement -->
For non-UI work, both routes share the rules that current code cannot redefine Source, explicit requirements cannot be silently omitted, user-retained choices stay decision-required, current evidence outranks old summaries and claims remain bounded to observed scope. Only Long-Task requires the complete semantic Census, stable Fact identity, exact condition/Fact/obligation conservation, typed current result rows, Authority freshness and Final-Gate set equality; default work uses risk-proportional material understanding and honestly reports anything it did not establish.
<!-- ty-source-item:end -->

<!-- ty-source-item:start key=default-selected-design-assurance-boundary kind=requirement -->
For a formal selected Web/App handoff, both routes preserve canonical design Source authority and exact handoff preflight input completeness. Default work opens every affected exact target or constraint and its declared conditions, routes it to the real production owner and cold-start journey, runs applicable project-native visual, interaction, accessibility or runtime checks on the final candidate and reports conditions not established. It does not rebuild the complete UI Fact Cell universe or per-Fact-by-method production result ledger. Long-Task retains exact Fact/Rule, condition/variation, method and current-result closure in its sole Final Gate.
<!-- ty-source-item:end -->

<!-- ty-source-item:start key=default-workflow-admission-boundary kind=constraint -->
A new default Workflow rule is admissible only when it is broadly useful, collapses to minimal cost for small changes, scales with risk, creates no artifact/state/authority, reuses project checks, does not duplicate Long-Task and has sufficiently positive total ROI for a cost paid by every task. Stable identities, exact sets, Authority freshness, persistent recovery or machine-completion conclusions belong in Long-Task.
<!-- ty-source-item:end -->

<!-- ty-source-item:start key=no-third-route-or-automatic-upgrade kind=forbidden_shortcut -->
Do not add a medium-task workflow, new profile, schema, status, Contract field, artifact, Gate, ledger, registry, router or automatic complexity detector; do not rename Long-Task or describe it as the route for “high-quality tasks.” The two routes may produce equally good code, but they provide different completion authority and audit structure.
<!-- ty-source-item:end -->

<!-- ty-source-item:start key=accurate-long-task-benefit-language kind=requirement -->
Long-Task may reduce routine progress supervision and item-by-item human checking, but cannot eliminate user-reserved choices, Source conflicts, preference-sensitive decisions, risky irreversible external actions or External Confirmation. Its “high quality” means stronger implementation-conformance assurance for declared observable obligations, not proof of undeclared intent, optimal architecture, Oracle soundness or universal product quality. Its “efficiency” means minimizing total cost subject to complete machine closure, not always taking less time or fewer tokens than default work.
<!-- ty-source-item:end -->

<!-- ty-source-item:start key=workflow-assurance-source-and-surface-parity kind=technical_obligation aspect=architecture -->
The assurance boundary must be causally aligned across PROJECT_SPEC, owning Context, Context triggers and implementation index, canonical managed AGENTS and default Product/Engineering Skills, public English/Chinese/package READMEs, package-generated assets, Source mappings and semantic/visual/routing tests. Historical Source documents must explicitly point to this superseding boundary instead of being silently rewritten into contradictory Long-Task semantics.
<!-- ty-source-item:end -->

<!-- ty-source-item:start key=workflow-assurance-formal-benchmark kind=technical_obligation -->
The existing formal delivery-mechanism benchmark must compare a frozen `main@c030d02eee315d2860c6a2ff01c22887690f3684` exact-ephemeral-default baseline against the new assurance-split default guidance on fixed local, cross-module, design-resource and small-high-assurance scenarios. Before runs, freeze scoring for instruction/tool cost before first useful implementation, total token/tool/wall cost where observable, unnecessary formal enumeration, material-requirement recall, correct owner/workspace, native verification, honest unverified or blocked reporting, false completion and final project checks. Use at least three independent fresh-agent pairs per case and five for high-variance or near-threshold results; static strings alone cannot establish runtime ROI.
<!-- ty-source-item:end -->

<!-- ty-source-item:start key=workflow-assurance-positive-negative-sentinels kind=acceptance -->
Tests must positively require default applicability at any complexity, explicit/binding-only Long-Task routing, assurance-based selection, fresh current-candidate verification, repair and qualified reporting, and mutually exclusive proof carriers. Tests must negatively reject default-route requirements for exact Fact/Obligation equations, stable identities, revision digests, frozen Oracle graphs, complete Cartesian closure, Receipt, Final Gate or machine acceptance while continuing to require those applicable mechanisms on Long-Task surfaces.
<!-- ty-source-item:end -->

<!-- ty-source-item:start key=workflow-assurance-delivery-acceptance kind=acceptance -->
The delivery is complete when Context and Source authority, canonical managed guidance, generated/package/public surfaces and focused semantic/visual/routing/benchmark tests all express the same assurance boundary; source sync is idempotent; affected, Trust and complete package regressions plus Context/Harness validation pass; benchmark criteria are frozen and runnable without overstating unexecuted fresh-agent results; no third workflow or default artifact exists; and the diff contains no Long-Task Skill, schema, compiler, evidence, lifecycle, Final-Gate or theorem-logic change.
<!-- ty-source-item:end -->
